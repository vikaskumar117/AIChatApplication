APPLY THE IDEA

Worked example

Checkout asks Pricing for a current quote, then publishes OrderPlaced so fulfillment can proceed without Checkout knowing its implementation.

  1. Name the business intent and owning service.
  2. Specify the response, error, and versioning semantics.
  3. Choose direct transport or broker based on timing and coupling.
  4. Instrument the full cross-service path.

TRADE-OFFS

Benefits and limitations

Benefits

  • Explicit contracts allow independent implementation and deployment.
  • Different interaction styles can match synchronous decisions and deferred work.

Limitations

  • Every network hop adds latency and a partial-failure boundary.
  • Poorly owned contracts couple services just as tightly as shared code or schemas.

DECISION GUIDE

When to use it

Use: Use a narrow service API or event contract owned by the producing domain.

Avoid: Avoid chatty calls, shared database access, and contracts that expose internal persistence models.

COMMON MISTAKES

Watch out

  • Avoid chatty calls, shared database access, and contracts that expose internal persistence models.
  • Assuming service communication guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Assign one authoritative owner to each piece of data.
  • Set compatibility rules and trace context at the contract boundary.

SENIOR-LEVEL SCENARIO

Production thinking

A team splits an application and discovers the new services still share tables. Establish data ownership and migrate callers to explicit contracts before claiming independent deployment.

SUMMARY

In one minute

A service boundary is a contract plus ownership and operational behavior, not merely a process or URL.
