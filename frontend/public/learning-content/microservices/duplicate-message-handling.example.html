APPLY THE IDEA

Worked example

A payment consumer stores the event ID and payment result in the same database transaction; redelivery returns the saved result instead of charging again.

  1. Keep the same idempotency identity across retries and replay.
  2. Commit processed identity with the local effect.
  3. Set retention longer than the maximum redelivery/replay horizon.

CODE OR QUERY

Try it

await using var tx = await db.Database.BeginTransactionAsync(ct);
if (await db.ProcessedMessages.AnyAsync(x => x.Id == message.Id, ct)) return;
await payments.ApplyAsync(message.Payment, ct);
db.ProcessedMessages.Add(new ProcessedMessage(message.Id));
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

TRADE-OFFS

Benefits and limitations

Benefits

  • Deduplication protects business effects against redelivery and uncertain acknowledgements.
  • Stable operation identities support replay and reconciliation.

Limitations

  • Deduplication storage needs retention, transaction design, and capacity.
  • External side effects may not share the consumer’s transaction and need provider idempotency or reconciliation.

DECISION GUIDE

When to use it

Use: Assume broker messages can repeat and make effects idempotent or deduplicated.

Avoid: Avoid claiming exactly-once business processing from a broker feature alone.

COMMON MISTAKES

Watch out

  • Avoid claiming exactly-once business processing from a broker feature alone.
  • Assuming duplicate message handling and idempotency guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Design idempotency into consumer contracts.
  • Test crash points before effect, after effect, and before acknowledgement.

INTERVIEW PRACTICE

Common questions

  1. Why can a message be redelivered after a successful effect?
  2. Where should a deduplication record be committed?
  3. How do you handle a provider side effect outside the local transaction?

SENIOR-LEVEL SCENARIO

Production thinking

The consumer commits an invoice, then crashes before ACK. Redelivery finds the event ID transactionally and skips the duplicate; downstream email uses its own idempotency key.

SUMMARY

In one minute

Duplicate handling is a consumer correctness property built from stable identity, atomic local effects, and explicit handling for external side effects.
