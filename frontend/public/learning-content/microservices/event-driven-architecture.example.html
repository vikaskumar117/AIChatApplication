APPLY THE IDEA

Worked example

The Order service emits OrderConfirmed; invoice, fulfillment, and analytics consumers independently react at their own pace.

  1. Publish domain facts, not private table-change dumps.
  2. Track consumer lag and schema compatibility.
  3. Make projections replayable and consumer effects idempotent.

CODE OR QUERY

Try it

public sealed record OrderConfirmed(Guid EventId, Guid OrderId, DateTimeOffset OccurredAt);
// Publish after the order state and outbox row commit together.

TRADE-OFFS

Benefits and limitations

Benefits

  • One event can serve several independent consumers.
  • Producer does not need to know consumer deployment or availability.

Limitations

  • Consumers see stale or reordered views and can fail independently.
  • Event schema and semantics become long-lived public contracts.

DECISION GUIDE

When to use it

Use: Use events for facts and independent reactions that may be eventual.

Avoid: Avoid eventing synchronous decisions that must be atomically answered to the caller.

COMMON MISTAKES

Watch out

  • Avoid eventing synchronous decisions that must be atomically answered to the caller.
  • Assuming event-driven architecture guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Define event ownership and compatibility policy.
  • Expose freshness or pending status when consumers affect user expectations.

INTERVIEW PRACTICE

Common questions

  1. How does an event differ from a command?
  2. Why can an event consumer see stale state?
  3. What does eventual consistency mean to a client?

SENIOR-LEVEL SCENARIO

Production thinking

Analytics falls behind while checkout remains available. Track consumer lag and communicate the freshness of analytics rather than treating event acceptance as projection completion.

SUMMARY

In one minute

Events decouple reactions in time, not meaning; eventual consistency and consumer recovery are part of the contract.
