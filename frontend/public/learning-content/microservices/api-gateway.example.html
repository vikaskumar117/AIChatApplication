APPLY THE IDEA

Worked example

A mobile BFF turns several internal reads into one mobile response, while Order service still validates ownership and order state.

  1. Define allowed edge concerns and delegate domain rules to services.
  2. Use idempotency for any retried mutation.
  3. Version public contracts independently from internal addresses.

TRADE-OFFS

Benefits and limitations

Benefits

  • Reduces client knowledge of service topology.
  • Provides a practical place for edge policies and client-specific composition.

Limitations

  • Can become a bottleneck, shared failure domain, or deployment coupling point.
  • Retries or transformations at the edge can obscure behavior and duplicate side effects.

DECISION GUIDE

When to use it

Use: Use a gateway for external routing and client-specific needs with clear ownership.

Avoid: Avoid placing domain workflows or the only authorization checks in proxy configuration.

COMMON MISTAKES

Watch out

  • Avoid placing domain workflows or the only authorization checks in proxy configuration.
  • Assuming api gateway guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Keep routing configuration reviewable and observable.
  • Design gateway availability, capacity, and rollback as production dependencies.

INTERVIEW PRACTICE

Common questions

  1. What responsibilities belong at the gateway?

  3. Why must services still enforce authorization?

SENIOR-LEVEL SCENARIO

Production thinking

The gateway retries a timed-out order POST and creates duplicate orders. Remove unsafe automatic retries or require an idempotency key enforced by the owning service.

SUMMARY

In one minute

A gateway simplifies clients but becomes critical infrastructure and must preserve service authority.
