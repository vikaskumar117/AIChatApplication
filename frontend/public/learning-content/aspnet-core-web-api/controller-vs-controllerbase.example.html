APPLY THE IDEA

Worked example

An admin website action that returns a Razor view can use Controller; its JSON-backed inventory endpoints should use ControllerBase.

  1. Choose response style
  2. Select matching MVC base class
  3. Keep controller responsibilities explicit

CODE OR QUERY

Try it

public sealed class InventoryApiController : ControllerBase { /* HTTP API actions */ }
public sealed class DashboardController : Controller { /* server-rendered views */ }

TRADE-OFFS

Benefits and limitations

Benefits

  • Choosing the narrow base communicates intent
  • ControllerBase avoids unused view facilities in APIs

Limitations

  • The two types share names and common members, which can confuse newcomers
  • Changing base classes does not itself alter endpoint security or behavior

DECISION GUIDE

When to use it

Use: Use ControllerBase for APIs and Controller only where server-side view rendering is part of the application.

Avoid: Avoid choosing Controller because it appears more powerful when no view behavior is needed.

COMMON MISTAKES

Watch out

  • Claiming ControllerBase cannot return a file or non-JSON result.
  • Assuming Controller automatically provides API validation semantics.

BEST PRACTICES

In practice

  • Keep MVC view actions and API actions recognizable in names and routing.
  • Keep domain logic outside either controller base class.

INTERVIEW PRACTICE

Common questions

  1. What does Controller add beyond ControllerBase?
  2. Does ControllerBase prevent returning HTML?
  3. Does the base class determine whether a route is an API?

SENIOR-LEVEL SCENARIO

Production thinking

A mixed MVC application is being split into API and page controllers; classify actions by response responsibility and retain shared business logic in services rather than controller inheritance.

SUMMARY

In one minute

Controller extends ControllerBase with view and page-oriented capabilities; ControllerBase is the smaller choice for HTTP APIs.
