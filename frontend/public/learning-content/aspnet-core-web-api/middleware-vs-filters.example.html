APPLY THE IDEA

Worked example

Use middleware for request-wide correlation; use an action filter for a legacy MVC-only action convention that requires action arguments.

  1. Middleware receives HTTP request
  2. MVC selects filter pipeline
  3. Action and result execute within middleware

CODE OR QUERY

Try it

app.UseMiddleware<RequestCorrelationMiddleware>();
services.AddControllers(options =>
    options.Filters.Add<AuditActionFilter>());

TRADE-OFFS

Benefits and limitations

Benefits

  • Middleware covers broader endpoint types
  • Filters provide MVC-specific lifecycle context

Limitations

  • Filters do not cover Minimal APIs or unrelated middleware endpoints
  • Middleware lacks action-specific metadata before routing/endpoint selection

DECISION GUIDE

When to use it

Use: Use middleware for application-wide HTTP concerns and filters for MVC controller/action execution concerns.

Avoid: Avoid using an MVC filter to enforce a security boundary across non-MVC endpoints.

COMMON MISTAKES

Watch out

  • Assuming an action filter runs before every application middleware.
  • Using a controller-only filter as the only API-wide authorization defense.

BEST PRACTICES

In practice

  • Place each concern at the narrowest layer that reliably covers it.
  • Test actual endpoint coverage when MVC and Minimal APIs coexist.

INTERVIEW PRACTICE

Common questions

  1. Which layer can see MVC action arguments?
  2. Does a filter run for a Minimal API endpoint?
  3. When is middleware preferable?

SENIOR-LEVEL SCENARIO

Production thinking

An audit rule must cover MVC actions but not health checks; implement and test an MVC filter while keeping authentication and global exception handling in their appropriate layers.

SUMMARY

In one minute

Middleware wraps the application request pipeline; MVC filters run inside MVC execution and have action or result context.
