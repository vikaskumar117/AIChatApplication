APPLY THE IDEA

Worked example

An expired bearer credential yields 401; an authenticated user lacking the required permission gets 403; a stale version update gets 409.

  1. Classify outcome
  2. Select status and safe body
  3. Client follows status-specific recovery

CODE OR QUERY

Try it

return product is null

// A stale write may return Conflict(problemDetails); an unexpected exception is 500.

TRADE-OFFS

Benefits and limitations

Benefits

  • Predictable machine-readable client behavior
  • Clear distinction between authentication, permission, and state conflicts

Limitations

  • A status can leak resource existence if policy requires concealment
  • Poorly defined client retries can amplify transient failures

DECISION GUIDE

When to use it

Use: Use the most specific status consistent with the HTTP contract and security disclosure policy.

Avoid: Avoid returning 200 for failures or using 401 and 403 interchangeably without a deliberate concealment policy.

COMMON MISTAKES

Watch out

  • Using 401 when the caller is authenticated but lacks permission.
  • Returning stack traces or sensitive resource details in error bodies.

BEST PRACTICES

In practice

  • Define status, headers, and error body for every endpoint outcome.
  • Test client retry behavior separately from status classification.

INTERVIEW PRACTICE

Common questions

  1. How do 401 and 403 differ?
  2. When is 409 appropriate?
  3. Should validation errors return 500?

SENIOR-LEVEL SCENARIO

Production thinking

A client retries all non-200 responses and creates load; publish a status contract distinguishing correctable 400, authentication 401, forbidden 403, conflict 409, and retryable server failures.

SUMMARY

In one minute

Status codes classify success, client-side request problems, and server failures; 400, 401, 403, 404, 409, and 500 have distinct meanings.
