APPLY THE IDEA

Worked example

A request-scoped order service may use a request-scoped DbContext, while a singleton clock must be thread-safe and state-independent.

  1. Application requests a service
  2. Container resolves within a scope
  3. Container disposes owned instances at lifetime end

CODE OR QUERY

Try it

services.AddScoped<IOrderService, OrderService>();
services.AddScoped<AppDbContext>();
services.AddSingleton<IClock, SystemClock>();
services.AddTransient<IEmailFormatter, EmailFormatter>();

TRADE-OFFS

Benefits and limitations

Benefits

  • Centralized composition and deterministic disposal
  • Scopes can align stateful work with request boundaries

Limitations

  • Captive dependencies can outlive their required scope
  • Singleton mutable state introduces concurrency risks

DECISION GUIDE

When to use it

Use: Use scoped for request-oriented services, singleton for safe shared services, and transient for lightweight independent objects.

Avoid: Avoid injecting a scoped DbContext into a singleton or registering mutable request state as a singleton.

COMMON MISTAKES

Watch out

  • Assuming AddScoped means one instance per HTTP request in every host.
  • Sharing a DbContext concurrently because it is registered scoped.

BEST PRACTICES

In practice

  • Enable scope validation in development and tests.
  • Keep singleton dependencies thread-safe and immutable where practical.

Production thinking

A hosted worker needs EF Core; inject IServiceScopeFactory, create and dispose an async scope per operation, and use cancellation during the work.
