APPLY THE IDEA

Worked example

A quantity must be a positive integer at request validation, while available inventory must be checked against current persisted stock during the operation.

  1. Deserialize and bind request
  2. Evaluate input constraints
  3. Reject or pass valid request to application

CODE OR QUERY

Try it

public sealed record CreateOrderRequest
{
    [Required, MaxLength(80)] public required string Reference { get; init; }
    [Range(1, 100)] public int Quantity { get; init; }
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Fast, consistent feedback for structural errors
  • Keeps HTTP input rules explicit and testable

Limitations

  • Annotations do not express every business invariant
  • Automatic errors can be breaking if response shape changes

DECISION GUIDE

When to use it

Use: Validate shape and simple request constraints at the API boundary, then validate business rules at the appropriate application boundary.

Avoid: Avoid trusting client validation or checking mutable business facts only before a long-running transaction.

COMMON MISTAKES

Watch out

  • Relying only on browser-side validation.
  • Placing all validation in data annotations, including database-dependent rules.

BEST PRACTICES

In practice

  • Use stable request DTOs and structured validation-problem responses.
  • Test malformed bodies, annotation failures, and business-rule races separately.

INTERVIEW PRACTICE

Common questions

SENIOR-LEVEL SCENARIO

Production thinking

Two valid order requests compete for the last item; boundary validation accepts both shapes, but atomic application logic ensures only one can reserve inventory.

SUMMARY

In one minute

Model validation checks bound input against structural constraints, while application logic separately enforces business invariants.
