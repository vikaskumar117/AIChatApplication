APPLY THE IDEA

Worked example

Keep /api/v1/orders stable while /api/v2/orders introduces a breaking representation change and a published migration window.

  1. Client selects contract version
  2. Routing resolves compatible endpoint
  3. Versioned response follows documented schema

CODE OR QUERY

Try it

[ApiController]
[Route("api/v2/orders")]
public sealed class OrdersV2Controller : ControllerBase { /* v2 DTO contract */ }

TRADE-OFFS

Benefits and limitations

Benefits

  • Supports gradual consumer migration
  • Makes breaking changes explicit and testable

Limitations

  • Every supported version increases test and support burden
  • Versioning cannot rescue poor compatibility discipline

DECISION GUIDE

When to use it

Use: Version when the public contract must break and retain only versions with an owned support and sunset policy.

Avoid: Avoid creating a new version for compatible optional additions or leaving versions supported indefinitely without policy.

COMMON MISTAKES

Watch out

  • Treating a new route alone as a complete versioning strategy.
  • Removing an old version based only on the latest client release date.

BEST PRACTICES

In practice

  • Maintain contract tests for every supported version.
  • Track per-version usage and publish a realistic deprecation schedule.

INTERVIEW PRACTICE

Common questions

  1. What is a breaking API change?
  2. Compare URL and header version selection.
  3. How should a version be retired?

SENIOR-LEVEL SCENARIO

Production thinking

A mobile client remains deployed for months; introduce a new version, measure adoption, publish migration examples, and remove the old contract only after the communicated support period.

SUMMARY

In one minute

API versioning manages incompatible contract evolution while clients migrate at different speeds.
