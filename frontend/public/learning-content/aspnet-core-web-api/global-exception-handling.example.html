APPLY THE IDEA

Worked example

A concurrency exception maps to 409 only when it represents a known client-resolvable conflict; an unexpected database outage remains 500.

  1. Exception escapes endpoint
  2. Boundary logs and maps known failure
  3. Client receives safe error response

CODE OR QUERY

Try it

builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<ApiExceptionHandler>();
app.UseExceptionHandler();

TRADE-OFFS

Benefits and limitations

Benefits

  • Consistent error contract and telemetry
  • Avoids duplicated try/catch and unsafe error construction

Limitations

  • Incorrect exception mapping can misstate system health
  • A handler may suppress framework diagnostics if logging is incomplete

DECISION GUIDE

When to use it

Use: Use centralized handling for unexpected exceptions and explicitly recognized domain failures.

Avoid: Avoid translating every exception to 400 or including stack traces, SQL, tokens, or exception messages in public details.

COMMON MISTAKES

Watch out

  • Returning exception.Message or stack traces to callers.
  • Catching exceptions and returning success-shaped fallbacks.

BEST PRACTICES

In practice

  • Use Problem Details and a trace ID for supportable errors.
  • Test status, content type, disclosure, and logging behavior for every mapping.

INTERVIEW PRACTICE

Common questions

  1. Where must exception middleware be placed?
  2. Which failures should map to 409?
  3. What belongs in the client response versus logs?

SENIOR-LEVEL SCENARIO

Production thinking

Production clients receive inconsistent errors and logs lack correlation; add centralized Problem Details with a trace identifier, preserve safe 500 output, and test known and unknown exceptions.

SUMMARY

In one minute

A global exception boundary logs unexpected failures and returns a stable, safe error contract rather than leaking implementation details.
