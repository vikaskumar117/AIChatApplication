APPLY THE IDEA

Worked example

Use GET /orders/7 to retrieve, POST /orders to create, PUT /orders/7 for full replacement, and PATCH /orders/7 for a defined partial change.

  1. Client selects method and resource
  2. API applies method contract
  3. Response reflects operation outcome

CODE OR QUERY

Try it

[HttpGet("{id:int}")] public Task<ActionResult<OrderDto>> Get(int id) => ...;
[HttpPost] public Task<ActionResult<OrderDto>> Create(CreateOrderDto input) => ...;
[HttpPut("{id:int}")] public Task<IActionResult> Replace(int id, ReplaceOrderDto input) => ...;

TRADE-OFFS

Benefits and limitations

Benefits

  • Standard semantics aid retries, caches, and client libraries
  • Resource-oriented verbs make contracts easier to reason about

Limitations

  • PATCH formats require clear semantics and validation
  • A badly implemented endpoint can violate its declared method semantics

DECISION GUIDE

When to use it

Use: Choose a method based on its HTTP semantics and the resource contract, and document conditional behavior.

Avoid: Avoid state changes on GET or using POST as a catch-all solely for convenience.

COMMON MISTAKES

Watch out

  • Treating every repeated request as harmless regardless of side effects.
  • Using GET for actions that mutate persistent state.

BEST PRACTICES

In practice

  • Document full replacement versus partial update.
  • Use idempotency keys where retryable POST operations must prevent duplicate business effects.

INTERVIEW PRACTICE

Common questions

  1. What is the difference between safe and idempotent?
  2. Is DELETE idempotent if a repeated call returns 404?
  3. When should a resource use PATCH rather than PUT?

SENIOR-LEVEL SCENARIO

Production thinking

A client retries a timed-out update; align method semantics and conditional request behavior so repeating the same operation does not create an additional business effect.

SUMMARY

In one minute

HTTP methods communicate the intended operation and whether it is safe or idempotent, independent of how an endpoint is named.
