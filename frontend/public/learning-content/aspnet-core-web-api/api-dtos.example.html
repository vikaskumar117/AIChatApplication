APPLY THE IDEA

Worked example

A create request accepts ProductName and Price, while the response adds server-assigned Id and CreatedAt without exposing EF navigation properties.

  1. Deserialize request DTO
  2. Map and enforce application rules
  3. Project authorized response DTO

CODE OR QUERY

Try it

public sealed record CreateProductRequest(string Name, decimal Price);
public sealed record ProductResponse(int Id, string Name, decimal Price);

var response = new ProductResponse(entity.Id, entity.Name, entity.Price);

TRADE-OFFS

Benefits and limitations

Benefits

  • Stable, explicit, reviewable API contracts
  • Reduces over-posting and sensitive field leakage

Limitations

  • Requires mapping and contract maintenance
  • Duplicated shapes can drift if boundaries are poorly designed

DECISION GUIDE

When to use it

Use: Use distinct DTOs for externally visible request and response contracts, particularly when data is privileged or versioned.

Avoid: Avoid serializing tracked ORM entities directly or accepting server-managed fields from clients.

COMMON MISTAKES

Watch out

  • Binding a persistence entity directly from an untrusted request.
  • Returning every entity property by default.

BEST PRACTICES

In practice

  • Version and document DTOs as public contracts.
  • Keep mapping explicit for sensitive or permission-dependent fields.

INTERVIEW PRACTICE

Common questions

  1. How do DTOs prevent over-posting?

SENIOR-LEVEL SCENARIO

Production thinking

A new database column stores a fraud-review flag; DTO projection ensures it remains private while the API evolves its public response deliberately.

SUMMARY

In one minute

DTOs define intentional API input and output contracts, decoupled from persistence entities and internal domain models.
