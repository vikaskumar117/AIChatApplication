APPLY THE IDEA

Worked example

An invalid model gets 400, an expired access token gets 401, an authenticated forbidden operation gets 403, a stale edit gets 409 or 412 according to its contract, and an outage gets 500.

  1. Classify failure layer
  2. Choose semantically correct status
  3. Return stable safe error contract

CODE OR QUERY

Try it

return failure switch
{
    InvalidInput => BadRequest(problem),
    MissingResource => NotFound(),
    StaleVersion => Conflict(problem),
    _ => StatusCode(StatusCodes.Status500InternalServerError, safeProblem)
};

TRADE-OFFS

Benefits and limitations

Benefits

  • Enables reliable client recovery and telemetry grouping
  • Prevents normal business outcomes from masquerading as server faults

Limitations

  • Status semantics can leak resource existence
  • Inconsistent mapping creates fragile clients

DECISION GUIDE

When to use it

Use: Define each failure mapping with client recovery, security disclosure, and retry semantics in mind.

Avoid: Avoid returning 500 for normal invalid input or 200 with an error-shaped body.

COMMON MISTAKES

Watch out

  • Returning 401 for every authorization denial.
  • Using 500 for validation or concurrency conflicts.

BEST PRACTICES

In practice

  • Document status codes, challenge headers, and retry guidance per endpoint.
  • Ensure unexpected errors do not expose internal details.

INTERVIEW PRACTICE

Common questions

  1. How do 401 and 403 differ?
  2. When is 412 more precise than 409?
  3. Which failures should clients retry?

SENIOR-LEVEL SCENARIO

Production thinking

A mobile client retries a stale edit and overloads an API; return a distinct conflict code and problem type so it can refresh rather than retrying unchanged input.

SUMMARY

In one minute

Status codes distinguish invalid input, missing authentication, denied access, stale state, and unexpected server failure.
