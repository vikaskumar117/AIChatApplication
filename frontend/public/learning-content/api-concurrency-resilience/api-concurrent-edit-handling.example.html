APPLY THE IDEA

Worked example

A stale If-Match header produces 412 Precondition Failed; an application-level version conflict without HTTP preconditions may use 409 Conflict.

  1. Client submits representation and version
  2. Server checks version in atomic write
  3. Return update or actionable conflict

CODE OR QUERY

Try it

if (!Request.Headers.IfMatch.Contains(currentEtag))
    return StatusCode(StatusCodes.Status412PreconditionFailed);
// Prefer enforcing If-Match atomically through the persistence version check.

TRADE-OFFS

Benefits and limitations

Benefits

  • Clients receive an explicit and actionable result
  • Separates stale updates from infrastructure failures

Limitations

  • Response semantics and retry UX must be designed
  • The server must avoid a time-of-check/time-of-use gap

DECISION GUIDE

When to use it

Use: Choose 412 when a conditional request precondition failed and 409 for a domain-state conflict without that HTTP precondition.

Avoid: Avoid sending a stale full-document retry as an automatic response to conflict.

COMMON MISTAKES

Watch out

  • Checking ETag before starting the transaction and assuming it remains current.
  • Returning 500 for a normal stale edit.

BEST PRACTICES

In practice

  • Use stable problem types and include safe recovery information.
  • Record conflict metrics and test stale If-Match and body-version cases.

INTERVIEW PRACTICE

Common questions

  1. When should an API use 409 versus 412?
  2. What makes a version check race-safe?
  3. Which client recovery choices are appropriate?

SENIOR-LEVEL SCENARIO

Production thinking

A mobile client retries an old update after receiving 409; return a stable Problem Details type and safe current version, then let the client reload or present a merge rather than replaying stale data.

SUMMARY

In one minute

An API should define how a detected stale update is communicated and how a client can recover without overwriting newer state.
