APPLY THE IDEA

Worked example

A checkout POST times out after the order is committed; retry with the same idempotency key returns the already-created order.

  1. Client sends stable operation key
  2. Server claims key and performs operation once
  3. Replay returns recorded outcome

TRADE-OFFS

Benefits and limitations

Benefits

  • Makes retries safe when outcome is uncertain
  • Prevents duplicate creates or charges under concurrent requests

Limitations

  • Requires retention, key scope, and concurrent claim semantics
  • External side effects may need an outbox or provider idempotency support

DECISION GUIDE

When to use it

Use: Use idempotency keys for retryable create or payment operations whose duplicate execution has meaningful cost.

Avoid: Avoid using an idempotency key as authorization or storing keys without expiry, scope, and mismatch policy.

COMMON MISTAKES

Watch out

  • Creating the side effect before claiming the key atomically.
  • Returning a prior result for a different request payload with the same key.

BEST PRACTICES

In practice

  • Use unique constraints, durable outcomes, bounded key retention, and replay metrics.
  • Coordinate external side effects with outbox/inbox patterns and downstream idempotency.

INTERVIEW PRACTICE

Common questions

  1. Why is a timeout an uncertain outcome?
  2. What should happen if the same key has a different request body?
  3. How do concurrent first requests avoid double execution?

SENIOR-LEVEL SCENARIO

Production thinking

Two identical payment requests arrive concurrently with one key; a unique constraint or atomic key claim allows one operation and the other waits for or replays its recorded outcome.

SUMMARY

In one minute

An idempotent operation has the same intended effect when the same request is repeated, which makes uncertain network retries safer.
