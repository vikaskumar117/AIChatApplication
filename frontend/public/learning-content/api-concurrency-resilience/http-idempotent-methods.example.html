APPLY THE IDEA

Worked example

Deleting an already-deleted resource can return 404 on a later call yet remain idempotent because the resource stays absent.

  1. Issue request once
  2. Repeat same request
  3. Intended final state remains equivalent

CODE OR QUERY

Try it

PUT /api/profiles/42
{ "displayName": "Mina", "locale": "en-GB" }

DELETE /api/profiles/42
// Repeating either request does not create an additional intended state change.

TRADE-OFFS

Benefits and limitations

Benefits

  • Supports safer retries for defined operations
  • Aligns endpoint behavior with standard HTTP semantics

Limitations

  • Ancillary side effects can accidentally make repeated calls harmful
  • Idempotence is often misread as identical responses or writes

DECISION GUIDE

When to use it

Use: Use safe/idempotent method semantics to guide client retries and design repeatable resource state transitions.

Avoid: Avoid mutating data on GET or assuming POST is retry-safe without a deduplication contract.

COMMON MISTAKES

Watch out

  • Putting analytics-triggering or payment side effects in GET.
  • Assuming returning the same status code is required for idempotence.

BEST PRACTICES

In practice

  • Document retry semantics and side effects per operation.
  • Test repeated requests, including timeouts and concurrent delivery.

INTERVIEW PRACTICE

Common questions

  1. Which standard methods are idempotent?
  2. Can an idempotent request return different status codes on retry?
  3. Is zero database writes required by idempotence?

SENIOR-LEVEL SCENARIO

Production thinking

A gateway retries DELETE after a timeout; ensure repeat deletion does not trigger a second refund or notification, even if the response to a later call differs.

SUMMARY

In one minute

HTTP defines PUT and DELETE as idempotent in intended effect, and GET, HEAD, OPTIONS, and TRACE as safe and therefore idempotent.
