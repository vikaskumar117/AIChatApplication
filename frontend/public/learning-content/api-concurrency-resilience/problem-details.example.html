APPLY THE IDEA

Worked example

A stale update returns 409 with a stable conflict type and safe guidance, while an unexpected server exception returns a generic 500 problem with a trace identifier.

  1. Application identifies error outcome
  2. Framework serializes problem document
  3. Client interprets status and stable type

CODE OR QUERY

Try it

builder.Services.AddProblemDetails();

return Conflict(new ProblemDetails
{
    Type = "https://api.example/problems/version-conflict",
    Title = "The resource has changed",
    Status = StatusCodes.Status409Conflict,
    Detail = "Reload the resource before applying this update."
});

TRADE-OFFS

Benefits and limitations

Benefits

  • Standardized error structure and framework support
  • Extensible for validation and trace correlation

Limitations

  • Misleading detail or mismatched status can break clients
  • Problem documents do not decide which errors are safe to reveal

DECISION GUIDE

When to use it

Use: Use ProblemDetails for API errors and maintain stable problem types for supported client behavior.

Avoid: Avoid putting secrets, internal exception diagnostics, or sensitive resource snapshots in extensions.

COMMON MISTAKES

Watch out

  • Assuming AddProblemDetails alone globally catches exceptions.
  • Exposing internal detail because the standard has a detail field.

BEST PRACTICES

In practice

  • Use RFC 9457-compatible response bodies and validation contracts.
  • Integration-test status, content type, extensions, and sensitive-data redaction.

INTERVIEW PRACTICE

Common questions

  1. What is the purpose of the type member?

SENIOR-LEVEL SCENARIO

Production thinking

A team enables AddProblemDetails but still sees inconsistent failures; configure exception and status-code handling explicitly, then test content type and body for all failure layers.

SUMMARY

In one minute

ProblemDetails is ASP.NET Core’s model for producing interoperable error documents based on the Problem Details standard.
