APPLY THE IDEA

Worked example

PUT sends the full editable profile; PATCH may update only preferred language without resetting omitted notification settings.

  1. Client selects replacement or patch document
  2. API validates representation and version
  3. Apply full replacement or partial operation

CODE OR QUERY

Try it

[HttpPut("{id:int}")]
public Task<IActionResult> Replace(int id, ReplaceProfileRequest body) => ...;

[HttpPatch("{id:int}")]
public Task<IActionResult> Patch(int id, JsonPatchDocument<ProfileDto> patch) => ...;

TRADE-OFFS

Benefits and limitations

Benefits

  • PUT gives a clear full-replacement contract
  • PATCH can reduce payloads for focused partial changes

Limitations

  • PUT payloads can be larger and completeness rules need care
  • PATCH formats introduce path, authorization, and validation complexity

DECISION GUIDE

When to use it

Use: Use PUT when the client supplies the intended full editable representation and PATCH for deliberately specified partial changes.

Avoid: Avoid applying arbitrary patch paths to persistence entities or silently treating partial input as replacement.

COMMON MISTAKES

Watch out

  • Using a patch document directly against a database entity.
  • Assuming PUT’s omitted fields are preserved without documenting that behavior.

BEST PRACTICES

In practice

  • Advertise supported patch media types and allowed operations.
  • Test repeated PATCH, invalid paths, property authorization, and stale versions.

INTERVIEW PRACTICE

Common questions

  1. Is PATCH necessarily idempotent?
  2. What happens to an omitted field in PUT?
  3. How do you prevent a patch from changing a forbidden property?

SENIOR-LEVEL SCENARIO

Production thinking

A client PATCHes a profile role property by guessing a JSON path; constrain permitted operations, authorize each mutable property, validate the resulting resource, and enforce If-Match.

SUMMARY

In one minute

PUT conventionally replaces a resource representation; PATCH applies a defined partial modification.
