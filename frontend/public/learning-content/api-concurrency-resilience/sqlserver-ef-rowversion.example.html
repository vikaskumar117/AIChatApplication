APPLY THE IDEA

Worked example

An EF Core update uses the original rowversion; if another transaction changed the row first, the API returns a stale-write conflict rather than overwriting.

  1. Read entity and rowversion
  2. EF writes with original version condition
  3. Zero affected rows throws concurrency exception

CODE OR QUERY

Try it

public sealed class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public byte[] RowVersion { get; set; } = [];
}
modelBuilder.Entity<Product>().Property(p => p.RowVersion).IsRowVersion();

TRADE-OFFS

Benefits and limitations

Benefits

  • Database-generated token simplifies row-level optimistic checks
  • EF Core provides a dedicated concurrency exception

Limitations

  • Rowversion is SQL Server-specific and changes on any row update
  • It detects a conflict but does not merge or resolve business intent

DECISION GUIDE

When to use it

Use: Use rowversion for SQL Server row-level optimistic concurrency where any row update should invalidate prior representations.

Avoid: Avoid interpreting rowversion as wall-clock time or exposing it as a mutable, user-selected value.

COMMON MISTAKES

Watch out

  • Calling it a timestamp and assuming it expresses chronological time.
  • Catching the exception and saving stale values over the newer row.

BEST PRACTICES

In practice

  • Treat rowversion as opaque and encode it safely for API use.
  • Handle deleted, changed, and authorized-reload paths explicitly.

INTERVIEW PRACTICE

SENIOR-LEVEL SCENARIO

Production thinking

An EF Core SaveChangesAsync throws DbUpdateConcurrencyException; reload current values only when authorized, distinguish deleted versus modified rows, and return a conflict without leaking protected values.

SUMMARY

In one minute

SQL Server rowversion is an automatically changing binary version stamp that EF Core can use to detect a stale update.
