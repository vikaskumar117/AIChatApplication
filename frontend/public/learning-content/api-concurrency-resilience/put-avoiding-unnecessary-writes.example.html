APPLY THE IDEA

Worked example

A client repeats PUT for an unchanged profile; the API preserves the same representation and avoids creating a duplicate “profile changed” event.

  1. Receive full replacement representation
  2. Compare with current resource under concurrency rules
  3. Persist only meaningful changes or confirm unchanged state

CODE OR QUERY

Try it

if (!Equivalent(current, request))
{
    ApplyReplacement(current, request);
    await db.SaveChangesAsync(ct);
}
// Still enforce the expected row version / If-Match condition.

TRADE-OFFS

Benefits and limitations

Benefits

  • Can reduce database churn, trigger work, and noisy audit events
  • Keeps change events aligned with actual domain changes

Limitations

  • Equality comparison adds complexity and can miss semantic differences
  • Skipping persistence can conflict with audit or freshness policies

DECISION GUIDE

When to use it

Use: Avoid writes only when equality semantics and side effects are defined and measured.

Avoid: Avoid conflating a no-op optimization with request idempotency or skipping stale-version checks.

COMMON MISTAKES

Watch out

  • Claiming idempotence requires that the server perform no second database write.
  • Skipping an If-Match or version check because the values appear equal.

BEST PRACTICES

In practice

  • Define canonical equality and whether audit updates count as meaningful changes.
  • Measure write amplification and test event/outbox behavior on unchanged PUTs.

INTERVIEW PRACTICE

Common questions

  1. Can a repeated PUT be idempotent while issuing SQL UPDATE twice?
  2. Why might an unchanged write still have side effects?
  3. Should equality comparison bypass concurrency validation?

SENIOR-LEVEL SCENARIO

Production thinking

Repeated client synchronization causes update triggers and cache invalidations for unchanged records; compare canonical values, suppress change events for true no-ops, and preserve ETag checks.

SUMMARY

In one minute

A PUT request can be idempotent even if the server writes each time; avoiding needless writes is a separate optimization and side-effect concern.
