APPLY THE IDEA

Worked example

A payment provider charges successfully but the response is lost; retry with the provider’s stable idempotency key and reconcile the same payment rather than creating a second charge.

  1. Receive operation key and command
  2. Atomically create durable operation/order
  3. Coordinate provider effect and replay final result

TRADE-OFFS

Benefits and limitations

Benefits

  • Protects customers against duplicate orders and charges
  • Durable records support retries, audit, and reconciliation

Limitations

  • Distributed workflows require state machines and operational monitoring
  • Provider idempotency windows and local retention policies must align

DECISION GUIDE

When to use it

Use: Use end-to-end deduplication for payment, order, booking, and other non-repeatable business effects.

Avoid: Avoid assuming an HTTP retry policy, a database transaction, or a frontend disabled button guarantees exactly-once payment.

COMMON MISTAKES

Watch out

  • Generating a new provider key on every retry.
  • Marking an order paid before a durable, reconciled payment result exists.

BEST PRACTICES

In practice

  • Use outbox/inbox, unique constraints, state transitions, and reconciliation dashboards.
  • Design customer-visible states for pending, succeeded, failed, and needs-review operations.

INTERVIEW PRACTICE

Common questions

  1. Why cannot one local transaction guarantee exactly one external charge?
  2. How do an outbox and provider idempotency key work together?
  3. How should an ambiguous provider timeout be reconciled?

SENIOR-LEVEL SCENARIO

Production thinking

A payment call times out after the provider may have charged; persist the operation as pending, query or replay using the same provider key, reconcile provider state, and do not tell the customer to start a new charge blindly.

SUMMARY

In one minute

Duplicate-sensitive business operations need durable deduplication across retries, concurrent requests, and downstream failures.
