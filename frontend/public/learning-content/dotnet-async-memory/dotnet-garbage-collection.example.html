APPLY THE IDEA

Worked example

A temporary request buffer becomes eligible for collection after references disappear, but an object still stored in a static cache remains reachable.

  1. Record allocation around a representative operation.
  2. Compare roots and surviving objects in a heap snapshot.
  3. Fix retention/allocation causes and remeasure.

CODE OR QUERY

Try it

long allocatedBefore = GC.GetTotalAllocatedBytes();
ProcessBatch();
long allocated = GC.GetTotalAllocatedBytes() - allocatedBefore;
Console.WriteLine($"Allocated: {allocated} bytes");

TRADE-OFFS

Benefits and limitations

Benefits

  • Automatic reclamation reduces manual memory errors
  • Generations optimize common object lifetimes

Limitations

  • Collections can pause or consume CPU
  • Finalizers and pins complicate lifetime and compaction

DECISION GUIDE

When to use it

Use: Use GC metrics and heap tools to find the cause before optimizing.

Avoid: Avoid routine GC.Collect calls, finalizer-based ownership, and unjustified pooling.

COMMON MISTAKES

Watch out

  • Expecting GC to reclaim referenced cache entries.
  • Using GC.Collect as routine memory management.
  • Pooling allocations without measuring retention and contention costs.

BEST PRACTICES

In practice

  • Use counters and traces under representative load.
  • Release references and disposable resources appropriately.
  • Avoid unnecessary pinning and finalizers.

SENIOR-LEVEL SCENARIO

Production thinking

Memory climbs after every batch. Compare allocation rate and heap snapshots, identify retained roots or large objects, then fix ownership rather than forcing collections.

SUMMARY

In one minute

The GC traces roots to reclaim unreachable managed objects; diagnose allocation and retention with runtime evidence.
