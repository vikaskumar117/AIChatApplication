APPLY THE IDEA

Worked example

Calling Result on an HTTP Task blocks a worker while the asynchronous request needs a continuation to complete, reducing capacity for other work.

  1. Observe queue length and completed work during the incident.
  2. Capture stacks to identify blocking waits.
  3. Replace sync-over-async and remeasure throughput.

CODE OR QUERY

Try it

// Avoid: blocks a pool worker
var data = client.GetStringAsync(url).Result;

// Prefer: yields while I/O is pending
var asyncData = await client.GetStringAsync(url, cancellationToken);

TRADE-OFFS

Benefits and limitations

Benefits

  • Diagnosable using runtime counters and traces
  • Async I/O returns workers to useful work

Limitations

  • Symptoms can resemble slow dependencies
  • Adding workers may increase contention without removing cause

DECISION GUIDE

When to use it

Use: Use async end-to-end, bound CPU concurrency, and inspect blocking traces.

Avoid: Avoid increasing minimum threads as a substitute for fixing sync-over-async.

COMMON MISTAKES

Watch out

  • Blindly raising minimum worker threads.
  • Confusing downstream slowness with proof of starvation.
  • Wrapping blocking I/O in more Task.Run work.

BEST PRACTICES

In practice

  • Make I/O asynchronous end-to-end.
  • Bound long-running CPU/background work.
  • Correlate counters, traces, and dependency latency.

INTERVIEW PRACTICE

Common questions

  1. What metrics suggest starvation?
  2. Why can .Result harm throughput?
  3. How can starvation occur with low CPU?

SENIOR-LEVEL SCENARIO

Production thinking

Latency rises while CPU stays low. Correlate queue length, thread count, completed work, dependency time, and stack traces; remove sync-over-async before tuning pool settings.

SUMMARY

In one minute

Starvation is delayed queued work caused by unavailable workers; diagnose blocking and queue behavior before tuning.
