APPLY THE IDEA

Worked example

A method that awaits a remote refresh must not hold lock; a SemaphoreSlim with try/finally protects the async critical section.

  1. Wait asynchronously for the semaphore permit.
  2. Run the protected asynchronous refresh.
  3. Release in finally after successful acquisition.

CODE OR QUERY

Try it

private readonly SemaphoreSlim gate = new(1, 1);

async Task RefreshAsync(CancellationToken token)
{
    await gate.WaitAsync(token);
    try { await LoadAndUpdateAsync(token); }
    finally { gate.Release(); }
}

TRADE-OFFS

Benefits and limitations

Benefits

  • lock has clear synchronous ownership
  • SemaphoreSlim supports async gating and bounded concurrency

Limitations

  • Semaphore misuse can deadlock or over-release
  • Long critical sections serialize throughput

DECISION GUIDE

When to use it

Use: Use lock only around brief synchronous code with no await.

Avoid: Use SemaphoreSlim for asynchronous exclusion or concurrency limits and release in finally.

COMMON MISTAKES

Watch out

  • Awaiting inside lock.
  • Calling Release when WaitAsync never acquired a permit.
  • Forgetting finally and permanently reducing capacity.

BEST PRACTICES

In practice

  • Keep critical regions small.
  • Use cancellation-aware WaitAsync.
  • Document gate ownership and disposal lifetime.

INTERVIEW PRACTICE

Common questions

  1. Why can a lock not be held across await?
  2. What does SemaphoreSlim count represent?
  3. Why is Release placed in finally?

SENIOR-LEVEL SCENARIO

Production thinking

A token refresh must permit only one asynchronous refresh at a time. Use SemaphoreSlim, add cancellation and timeout policy, and ensure every acquired permit is released.

SUMMARY

In one minute

Use lock for short synchronous mutual exclusion; use SemaphoreSlim when callers must await admission or limit concurrency.
