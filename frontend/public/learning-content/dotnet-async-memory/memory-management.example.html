APPLY THE IDEA

Worked example

A long-lived cache root keeps old response objects reachable, so GC cannot reclaim them even though application code no longer needs them.

  1. Create and store an object in a cache.
  2. Observe that a cache root keeps it reachable.
  3. Remove the reference and separately dispose any external resource it owned.

CODE OR QUERY

Try it

var cache = new Dictionary<string, object>();
cache["latest"] = LoadSnapshot(); // static/cache ownership may retain graph

// Remove values when no longer needed:
cache.Remove("latest");

TRADE-OFFS

Benefits and limitations

Benefits

  • Runtime reclaims unreachable managed objects
  • Ownership scopes make native resource lifetimes explicit

Limitations

  • Reachable leaks remain live
  • Managed heap metrics do not show every native resource

DECISION GUIDE

When to use it

Use: Track roots and ownership; profile both managed heap and native handles.

Avoid: Avoid assuming garbage collection replaces disposal or cache eviction.

COMMON MISTAKES

Watch out

  • Calling GC.Collect to fix a rooted object leak.
  • Assuming a small managed heap means no handle leak.
  • Keeping unbounded caches.

BEST PRACTICES

In practice

  • Bound caches and clear references deliberately.
  • Dispose owned resources deterministically.
  • Profile heap, allocation, and native handles separately.

INTERVIEW PRACTICE

Common questions

  1. What makes an object reachable?
  2. Can a managed memory leak exist?
  3. Why measure handles separately from heap size?

SENIOR-LEVEL SCENARIO

Production thinking

A worker’s memory grows between jobs. Compare heap snapshots for retained roots, inspect native handles, and set bounded cache policies before tuning GC.

SUMMARY

In one minute

The GC reclaims unreachable managed objects; application code must manage reachability and deterministic cleanup of external resources.
