APPLY THE IDEA

Worked example

Do not start order persistence and return success before it completes; await it or enqueue durable work with an acknowledged status.

  1. Compare a naked SaveOrderAsync call with awaiting it.
  2. Observe that await propagates completion and failure.
  3. Move truly durable background work to an owned queue.

CODE OR QUERY

Try it

// Dangerous: task and exception are discarded
SaveOrderAsync(order, token);

// Request-owned work:
await SaveOrderAsync(order, token);

// Deliberate background ownership requires a queue/worker, not a naked call.

TRADE-OFFS

Benefits and limitations

Benefits

  • Awaiting propagates errors and sequencing
  • Durable queues provide explicit background ownership

Limitations

  • Discarded tasks can fail silently
  • Request-scoped dependencies may be disposed too early

DECISION GUIDE

When to use it

Use: Await or return Task from all request-owned work.

Avoid: Avoid naked fire-and-forget tasks and async void outside event handlers.

COMMON MISTAKES

Watch out

  • Launching background work from a request with scoped dependencies.
  • Using async void to hide missing Task ownership.
  • Assuming process shutdown waits for outstanding work.

BEST PRACTICES

In practice

  • Await request-owned work.
  • Capture background work in a durable queue when required.
  • Log, retry, cancel, and drain work deliberately.

INTERVIEW PRACTICE

Common questions

  1. Does an unawaited Task stop running?
  2. When might its exception become visible?
  3. How should durable background work be started?

SENIOR-LEVEL SCENARIO

Production thinking

A request must send an email after accepting an order. Persist an outbox message transactionally and let a monitored worker deliver it rather than discarding SendAsync.

SUMMARY

In one minute

Unawaited asynchronous work continues independently but loses reliable completion and failure handling; establish explicit ownership.
