APPLY THE IDEA

Worked example

ReadAsync should be awaited directly; a substantial CPU-only image transform may be scheduled with Task.Run from a UI event handler.

  1. Await native asynchronous file reading directly.
  2. Schedule only the CPU-intensive digest when offloading is appropriate.
  3. Await both tasks and propagate cancellation.

CODE OR QUERY

Try it

var contents = await File.ReadAllTextAsync(path, token); // direct async I/O
var digest = await Task.Run(() => ComputeDigest(contents), token); // CPU-bound delegate

TRADE-OFFS

Benefits and limitations

Benefits

  • Task composes any supported completion
  • Task.Run protects a responsive caller from CPU work

Limitations

  • Unnecessary scheduling overhead
  • Blocking on pool workers can cause starvation

DECISION GUIDE

When to use it

Use: Use Task.Run selectively for CPU-bound work that benefits from offloading.

Avoid: Avoid wrapping native async I/O or every service method in Task.Run.

COMMON MISTAKES

Watch out

  • Wrapping an already-asynchronous HTTP/database call in Task.Run.
  • Using Task.Run to hide blocking work on a saturated server.

BEST PRACTICES

In practice

  • Classify work as I/O-bound or CPU-bound first.
  • Bound expensive parallel CPU tasks.
  • Measure end-to-end latency and pool queueing.

INTERVIEW PRACTICE

Common questions

  1. What does Task.Run schedule?
  2. Why not wrap HTTP calls in Task.Run?
  3. When could Task.Run help a UI?

SENIOR-LEVEL SCENARIO

Production thinking

A Web API wraps database queries in Task.Run. Remove the wrapper, use the provider’s asynchronous I/O, and separately cap expensive CPU transformations.

SUMMARY

In one minute

Task.Run schedules synchronous delegate work on the pool; it is not a general-purpose async wrapper.
