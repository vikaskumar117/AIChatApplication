APPLY THE IDEA

Worked example

Two shoppers request the last unit. The inventory update must atomically succeed for at most one request; a later payment failure releases the reservation through an idempotent state transition rather than incrementing stock blindly.

  1. Two transactions request the final unit.
  2. The database serializes conditional updates; only one affects a row.
  3. The winner creates a reservation with a stable ID and expiry.
  4. Payment success confirms it; failure releases it only if the expected state/version still matches.

CODE OR QUERY

Try it

UPDATE Inventory
SET Available = Available - @quantity
WHERE Sku = @sku
  AND Available >= @quantity;

-- Require exactly one affected row; zero means unavailable.
-- Persist a unique ReservationId and state transition in the same transaction.

TRADE-OFFS

Benefits and limitations

Benefits

  • Explicit invariants and transitions make behavior testable
  • Atomic conditional writes protect against concurrent oversell

Limitations

  • Concurrency and retry behavior add implementation complexity
  • Incorrect compensations can corrupt stock or release another reservation

DECISION GUIDE

When to use it

Use: Use explicit domain operations and atomic persistence when concurrent requests can compete for scarce inventory.

Avoid: Avoid read-then-write checks without a transaction/condition or a compensating update with no reservation identity.

COMMON MISTAKES

Watch out

  • Reading stock and later decrementing without a conditional update.
  • Incrementing inventory on every retry of a release event.
  • Holding a database transaction open while calling a payment provider.

BEST PRACTICES

In practice

  • Use unique constraints and conditional state/version updates.
  • Test concurrent last-item reservations and duplicate confirm/release commands.
  • Track reservation age and reconcile stuck or ambiguous states.

INTERVIEW PRACTICE

Common questions

  1. Why is checking Available before updating unsafe?
  2. How does a unique reservation ID help with retries?
  3. Which states and transitions should a reservation have?
  4. How do you release stock after payment failure without double-incrementing?

SENIOR-LEVEL SCENARIO

Production thinking

A worker retries a reservation-expiry event after a timeout, while a payment event arrives concurrently. Use conditional, versioned state transitions keyed by reservation ID, serialize or detect conflicting updates, and reconcile ambiguous payment outcomes before releasing stock.

SUMMARY

In one minute

LLD makes invariants executable: conditional updates, state transitions, idempotency, and reconciliation protect inventory under concurrency.
