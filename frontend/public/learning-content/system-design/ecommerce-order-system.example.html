APPLY THE IDEA

Worked example

A customer retries checkout after a gateway timeout. The API returns the already-created order for the same key; if a payment provider later reports success after a timeout, the workflow queries or retries with the provider’s stable key before deciding whether to refund or continue.

  1. Client retries POST with the same idempotency key.
  2. API returns the existing Pending order rather than creating a second one.
  3. Outbox publisher may deliver twice; consumer deduplication prevents repeated reservation.
  4. Payment timeout triggers provider-key retry or status lookup before a refund decision.

CODE OR QUERY

Try it

POST /orders (Idempotency-Key: client-generated stable key)
  -> transaction: create Pending order + Outbox event
  -> publisher: deliver event at least once
  -> workflow: reserve inventory -> authorize payment
  -> transition to Confirmed, or compensate and record failure

TRADE-OFFS

Benefits and limitations

Benefits

  • Queue-backed stages can scale and recover independently
  • Durable state makes retries and operator repair possible

Limitations

  • The workflow is eventually consistent, not one global transaction
  • Outbox, deduplication, compensation, and queue operations require ownership

DECISION GUIDE

When to use it

Use: Use explicit state transitions, a transactional outbox, idempotency at each side-effect boundary, bounded queues, and reconciliation.

Avoid: Avoid claiming “exactly once” across independent services or using distributed locks instead of database constraints and ownership.

COMMON MISTAKES

Watch out

  • Publishing directly after database commit can lose the event if the process crashes between the two operations.
  • Calling a message queue “exactly once” does not remove duplicate side effects in the consumer.
  • Retrying a payment with a new provider key can create a second charge.

BEST PRACTICES

In practice

  • Document state transitions, invariants, idempotency scope, and retention for each key.
  • Set bounded retries, dead-letter handling, queue-age alerts, and a reconciliation process.
  • Use database uniqueness or conditional updates for inventory ownership; load-test overload and recovery behavior.

INTERVIEW PRACTICE

Common questions

  1. Why is an outbox needed if the order is already in a database?
  2. How do you prevent a retried checkout from creating a second charge?
  3. How would you prevent inventory oversell under concurrent orders?
  4. What happens if payment succeeds but the consumer crashes before recording success?

SENIOR-LEVEL SCENARIO

Production thinking

A seasonal sale creates a traffic spike while the payment processor slows down. Keep acceptance within database and queue capacity, return only after durable persistence, slow or reject excess work deliberately, bound retries, and expose stuck-order age so operations can recover or compensate safely.

SUMMARY

In one minute

Durable local acceptance, at-least-once messaging, idempotent effects, and explicit compensation make checkout recoverable under partial failure.
