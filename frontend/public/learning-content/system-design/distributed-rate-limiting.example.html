APPLY THE IDEA

Worked example

Give each authenticated tenant a token bucket with a short burst allowance and a sustained refill limit, while enforcing a stricter global budget on a costly report-generation backend.

  1. Authenticate tenant and map request route to a policy.
  2. Atomically refill and consume one token in the shared limiter.
  3. Continue when a token is available; otherwise respond 429.
  4. Track allowed, rejected, and limiter-unavailable rates separately.

TRADE-OFFS

Benefits and limitations

Benefits

  • Controls bursts and protects shared resources
  • Tenant policies can improve fairness across replicas

Limitations

  • Shared checks add latency and another failure mode
  • Bad identity keys or policy boundaries can unfairly block callers

DECISION GUIDE

When to use it

Use: Use at an ingress or shared enforcement point with authenticated keys, atomic accounting, explicit burst policy, and a documented limiter-outage mode.

Avoid: Avoid trusting arbitrary client-supplied identity headers or relying only on per-instance counters when quotas are meant to be global.

COMMON MISTAKES

Watch out

  • Using an untrusted header as the quota key lets callers evade or share limits.
  • Applying only local limits gives each replica its own full quota.
  • Failing open during limiter outage can overload the very service the limiter protects.

BEST PRACTICES

In practice

  • Separate per-tenant fairness limits from global resource safety limits.
  • Set atomicity, timeout, fail-open/fail-closed behavior, and retry guidance deliberately.
  • Test multi-replica bursts, identity spoofing, and shared-store outage behavior.

INTERVIEW PRACTICE

Common questions

  1. How does token bucket differ from fixed window?
  2. Why can per-process limits exceed the intended quota?
  3. Where should a global backend limit be enforced?
  4. How should clients and the service behave when quota is exhausted or the shared limiter is down?

SENIOR-LEVEL SCENARIO

Production thinking

A tenant spreads a traffic burst across several application replicas and overloads an expensive search endpoint. Enforce a tenant quota at ingress and a global backend budget near search, return 429 consistently, and verify that limiter-store failure cannot silently make every replica unlimited.

SUMMARY

In one minute

A shared, atomic limiter enforces a deliberate burst and sustained-rate policy, with trusted identities and explicit behavior under failure.
