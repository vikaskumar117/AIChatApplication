APPLY THE IDEA

Worked example

A catalog service caches a public product listing for a short TTL. After a successful catalog update it invalidates affected keys; simultaneous misses for a popular listing are coalesced so one database read refreshes the value for waiting requests.

  1. Read a tenant-scoped listing key from Redis.
  2. On miss, join an in-flight refresh or acquire the refresh slot.
  3. Load the authoritative listing and cache it with a measured TTL.
  4. Invalidate the affected key after a catalog update and monitor fallback volume.

CODE OR QUERY

Try it

var value = await cache.GetStringAsync(key, cancellationToken);
if (value is null)
{
    value = await LoadFromDatabaseAsync(cancellationToken);
    await cache.SetStringAsync(
        key,
        value,
        new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
        },
        cancellationToken);
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Shared values reduce duplicate work across instances
  • TTL and eviction can bound stale-data exposure and storage

Limitations

  • A cache hit can still be stale or incorrect if keys are poorly scoped
  • Cache outage can transfer load to the source and trigger a cascading failure

DECISION GUIDE

When to use it

Use: Use for rebuildable or explicitly stale-tolerant data with a clear key, TTL, invalidation, timeout, and fallback budget.

Avoid: Avoid caching authorization-sensitive responses without complete identity-aware keys, or using cache as the only durable copy of critical data.

COMMON MISTAKES

Watch out

  • Using a key without tenant or authorization scope can leak data across users.
  • Letting every concurrent miss hit the database causes a cache stampede.
  • Treating an unbounded database fallback as a safe response to cache failure.

BEST PRACTICES

In practice

  • Set explicit timeouts, TTLs, payload limits, and source fallback concurrency.
  • Use jitter or request coalescing for hot keys and track staleness and hit ratio.
  • Cache only data whose freshness and invalidation contract is understood.

INTERVIEW PRACTICE

Common questions

  1. Explain the cache-aside read and write path.
  2. How do cache penetration, breakdown, and stampede differ?
  3. What should happen to source traffic when Redis is unavailable?
  4. How would you prevent one tenant’s cached data from being served to another?

SENIOR-LEVEL SCENARIO

Production thinking

Redis latency increases during a catalog promotion. Bound cache timeouts, coalesce refreshes for hot keys, and apply a concurrency limit to database fallbacks; if the source budget is exhausted, serve an allowed stale value or fail deliberately rather than overload the database.

SUMMARY

In one minute

Cache-aside trades source work for a bounded, potentially stale copy; key design and failure budgets determine whether it is safe.
