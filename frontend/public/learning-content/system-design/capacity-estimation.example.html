APPLY THE IDEA

Worked example

Illustration: 1 million daily users making 20 actions/day yields 20 million actions/day, about 231 average actions/second. A 5x peak factor gives roughly 1,155 peak actions/second before retries, fan-out, or background work.

  1. Convert 20 million daily actions to about 231 average requests/second.
  2. Apply a stated 5x peak to estimate about 1,155 requests/second.
  3. Include retries, fan-out, and uneven tenant/key distribution.
  4. Load-test the limiting database and external dependency, then set bounded autoscaling.

CODE OR QUERY

Try it

// Illustrative sizing
actionsPerDay = 1_000_000 users * 20 actions = 20,000,000
averageRps = actionsPerDay / 86,400 ≈ 231
peakRps = averageRps * 5 ≈ 1,155

// If each durable event is 2 KB and retained for 30 days:
rawStorage ≈ actionsPerDay * 2 KB * 30
           ≈ 1.2 TB decimal, before indexes, replicas, and compression.

TRADE-OFFS

Benefits and limitations

Benefits

  • Makes hidden load and retention assumptions visible
  • Helps compare architectural options before implementation

Limitations

  • Averages hide bursts, skew, retries, and hot keys
  • Storage and throughput estimates omit overhead unless explicitly modeled

DECISION GUIDE

When to use it

Use: Use as a first-pass sizing and interview reasoning tool; validate with benchmark and telemetry.

Avoid: Avoid using rough calculations as a production quota or omitting replication, indexes, backups, retries, and growth.

COMMON MISTAKES

Watch out

  • Using a daily total as if requests arrive evenly.
  • Ignoring retries and fan-out.
  • Treating raw payload storage as total provisioned storage.

BEST PRACTICES

In practice

  • Estimate orders of magnitude before choosing components.
  • Use realistic peak, skew, retention, and growth assumptions.
  • Validate estimates with load tests and actual production metrics.

INTERVIEW PRACTICE

Common questions

  1. Why calculate both average and peak throughput?
  2. How do fan-out and retries change request volume?
  3. What storage overhead is missing from raw payload estimates?
  4. How would you validate an estimate?

SENIOR-LEVEL SCENARIO

Production thinking

A queue-backed workflow appears to support 1,000 requests/second on average, but a flash sale creates a 10x burst and a downstream vendor accepts only 100/second. Bound ingress, queue safely, pace consumers, define overload responses, and alert on oldest-message age rather than scaling the API without limit.

SUMMARY

In one minute

Capacity math is a hypothesis generator: quantify assumptions, identify bottlenecks, then validate with representative tests.
