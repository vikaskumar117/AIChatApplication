APPLY THE IDEA

Worked example

Use PersonClass for an identity-bearing person, PersonStruct for a small value snapshot, and PersonRecord for concise value equality. The same Person data reveals different assignment behavior.

  1. Construct classA and alias it as classB; mutate through classB.
  2. Copy structA into structB; mutate only the copy.
  3. Compare two records with the same Name and Age, then create a modified with-copy.

CODE OR QUERY

Try it

using System;

public sealed class PersonClass
{
    public string Name { get; set; }
    public int Age { get; set; }
    public PersonClass(string name, int age) { Name = name; Age = age; }
}

public struct PersonStruct
{
    public string Name { get; set; }
    public int Age { get; set; }
    public PersonStruct(string name, int age) { Name = name; Age = age; }
}

public sealed record PersonRecord(string Name, int Age);

public static class Program
{
    public static void Main()
    {
        var classA = new PersonClass("Mira", 30);
        var classB = classA;
        classB.Age = 31;
        Console.WriteLine(classA.Age); // 31: both references point to one object

        var structA = new PersonStruct("Mira", 30);
        var structB = structA;
        structB.Age = 31;
        Console.WriteLine(structA.Age); // 30: assignment copied the fields

        var recordA = new PersonRecord("Mira", 30);
        var recordB = recordA with { Age = 31 };
        Console.WriteLine(recordA == new PersonRecord("Mira", 30)); // True
        Console.WriteLine(recordB.Age); // 31; recordA is unchanged
    }
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Explicit identity and object sharing
  • Value equality for record data

Limitations

  • Aliasing can make mutation surprising
  • Large or mutable structs can copy expensively and behave unexpectedly

DECISION GUIDE

When to use it

Use: Choose class for identity/lifecycle, record for value-shaped data, and struct for a small value with clear copy semantics.

Avoid: Do not choose struct to force stack allocation or assume record immutability is deep.

COMMON MISTAKES

Watch out

  • Assuming every struct is stack allocated.
  • Treating record with as a deep clone.
  • Using records for entities whose identity is independent of their fields.

BEST PRACTICES

In practice

  • Document equality and identity expectations in domain types.
  • Keep structs small, preferably immutable, and benchmark performance claims.
  • Use class for shared mutable entity identity.

INTERVIEW PRACTICE

Common questions

  1. What is copied when assigning a class variable?
  2. Are structs always stored on the stack?
  3. Is a record with-copy deep or shallow?

SENIOR-LEVEL SCENARIO

Production thinking

A service sees allocation pressure in order processing. Keep Order as an identity-bearing class; profile first, then benchmark a small immutable Money struct if value semantics fit.

SUMMARY

In one minute

Class variables share object identity; struct assignment copies a value; records compare data and support shallow non-destructive copies.
