APPLY THE IDEA

Worked example

OrderService depends on IOrderStore, not SqlOrderStore; the application composition root provides the SQL adapter.

  1. Declare the capability the policy needs.
  2. Implement it with an infrastructure adapter.
  3. Wire the adapter at the application boundary.

CODE OR QUERY

Try it

public interface IOrderStore
{
    Task SaveAsync(Order order, CancellationToken token);
}
public sealed class OrderService
{
    private readonly IOrderStore store;
    public OrderService(IOrderStore store) => this.store = store;
    public Task PlaceAsync(Order order, CancellationToken token)
        => store.SaveAsync(order, token);
}
// Startup composition: services.AddScoped<IOrderStore, SqlOrderStore>();

TRADE-OFFS

Benefits and limitations

Benefits

  • Policy isolated from infrastructure changes
  • Simpler focused tests

Limitations

  • Abstractions add indirection
  • Poorly owned generic abstractions become leaky

DECISION GUIDE

When to use it

Use: Invert dependencies across boundaries where infrastructure churn or test isolation matters.

Avoid: Avoid abstractions that expose provider-specific concepts or exist only to mock trivial code.

COMMON MISTAKES

Watch out

  • Let business logic depend directly on provider-specific APIs.
  • Calling every interface DIP even if it is merely a mock seam.

BEST PRACTICES

In practice

  • Keep persistence and transport details at system edges.
  • Test policy with focused fakes and adapters with integration tests.
  • Use constructor injection for required dependencies.

SENIOR-LEVEL SCENARIO

Production thinking

A domain service must switch database providers and remain testable. Keep its dependency on a domain-facing store contract and bind the chosen adapter at application startup.

SUMMARY

In one minute

DIP keeps policy independent of infrastructure contracts; dependency injection composes concrete implementations at runtime.
