APPLY THE IDEA

Worked example

A read-only storage implementation should not implement a writable repository interface and then throw on Save; separate read and write capabilities.

  1. Write down operations a client is promised.
  2. Give read-only implementation only the read capability.
  3. Run shared contract tests against every implementation.

CODE OR QUERY

Try it

public interface IReadStore<T>
{
    Task<T?> FindAsync(Guid id, CancellationToken token);
}
public interface IWriteStore<T>
{
    Task SaveAsync(T value, CancellationToken token);
}
public sealed class ReadOnlyStore<T> : IReadStore<T>
{
    public Task<T?> FindAsync(Guid id, CancellationToken token)
        => Task.FromResult<T?>(default);
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Reliable polymorphic behavior
  • Contracts remain honest

Limitations

  • Bad inheritance can violate assumptions
  • Overly strict contracts make legitimate subtypes impossible

DECISION GUIDE

When to use it

Use: Specify observable behavior, errors, and invariants in contracts.

Avoid: Avoid subtypes that reject operations promised by their base abstraction.

COMMON MISTAKES

Watch out

  • Throwing for a normal base operation in a subtype.
  • Assuming identical method signatures guarantee substitutability.

BEST PRACTICES

In practice

  • Test contracts against all implementations.
  • Separate optional capabilities.
  • Prefer composition or explicit variants for incompatible behaviors.

INTERVIEW PRACTICE

Common questions

SENIOR-LEVEL SCENARIO

Production thinking

A storage abstraction has remote, cached, and read-only implementations. Split capabilities and test each implementation against the same behavioral contract.

SUMMARY

In one minute

A valid subtype preserves the base contract’s behavior; split incompatible capabilities rather than relying on signature compatibility.
