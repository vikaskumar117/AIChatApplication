APPLY THE IDEA

Worked example

A customer has stable identity and lifecycle, so use a class; an address/value snapshot can be a record; a tiny immutable coordinate can be a struct.

  1. Check whether the domain distinguishes two instances with equal fields.
  2. Specify whether mutation should be shared or isolated.
  3. Select class, record, or struct, then profile realistic workloads.

CODE OR QUERY

Try it

public sealed class Customer
{
    public Guid Id { get; }
    public string Name { get; private set; }
    public Customer(Guid id, string name) { Id = id; Name = name; }
    public void Rename(string name) => Name = name;
}

public sealed record Address(string City, string PostalCode);
public readonly record struct Point(int X, int Y);

TRADE-OFFS

Benefits and limitations

Benefits

  • Types communicate domain semantics
  • Small immutable values can be efficient

Limitations

  • Copying and equality rules affect API behavior
  • Micro-optimizing without profiling can add complexity

DECISION GUIDE

When to use it

Use: Use classes for entities with identity and lifecycle, records for value-shaped data, and small immutable structs for lightweight values.

Avoid: Avoid mutable structs and changing domain types solely from stack/heap myths.

COMMON MISTAKES

Watch out

  • Making all DTOs structs to avoid heap allocations.
  • Assuming every data record should be a C# record.
  • Ignoring equality implications in dictionaries and sets.

BEST PRACTICES

In practice

  • Write equality tests for value objects.
  • Keep entity identity explicit and stable.
  • Profile allocations and copies under production-like load.

SENIOR-LEVEL SCENARIO

Production thinking

In an order platform, keep Customer and Order as entities, represent Money with a carefully validated value type, and treat addresses as values only if field equality reflects business rules.

SUMMARY

In one minute

Model entities as identity, value objects as content, and use structs only when their small-value copy semantics are a good fit.
