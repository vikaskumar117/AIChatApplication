APPLY THE IDEA

Worked example

A checkout depends on IPaymentGateway so card and bank-transfer adapters can be substituted; a shared base class is appropriate only if they truly share stateful invariants.

  1. Declare only the payment capability callers need.
  2. Implement it in a provider adapter.
  3. Pass the adapter to business logic through the interface.

CODE OR QUERY

Try it

public interface IPaymentGateway
{
    Task PayAsync(decimal amount, CancellationToken cancellationToken);
}

public sealed class CardGateway : IPaymentGateway
{
    public Task PayAsync(decimal amount, CancellationToken cancellationToken)
        => Task.CompletedTask;
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Multiple contracts and unrelated implementations
  • Abstract base can centralize invariant behavior

Limitations

  • Interface proliferation adds indirection
  • Base-class changes can break all derived classes

DECISION GUIDE

When to use it

Use: Use interfaces at replacement/testing boundaries and abstract classes for coherent shared state or invariants.

Avoid: Avoid deep inheritance and interfaces that simply mirror every class without a real boundary.

COMMON MISTAKES

Watch out

  • Creating interfaces with no independent client or replacement need.
  • Using a base class only to share a few unrelated helper methods.

BEST PRACTICES

In practice

  • Keep contracts small and stable.
  • Put provider-specific behavior behind adapters.
  • Test business rules against the contract and adapter integration separately.

INTERVIEW PRACTICE

SENIOR-LEVEL SCENARIO

Production thinking

Support two payment providers without leaking provider details into checkout. Define a narrow interface, inject an adapter, and preserve provider-specific idempotency and retry policies inside each implementation.

SUMMARY

In one minute

Interfaces enable independent substitution; abstract classes share state and implementation when a true inheritance relationship exists.
