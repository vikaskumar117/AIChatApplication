APPLY THE IDEA

Worked example

Invoice calculation and email delivery change for different reasons, so keep calculation in InvoiceService and notification in an injected notifier.

  1. Identify calculation and delivery as separate change axes.
  2. Place calculation in its cohesive owner.
  3. Expose notification through a narrow collaborator contract.

CODE OR QUERY

Try it

public sealed record Invoice(decimal Subtotal, decimal Tax);
public sealed class InvoiceCalculator
{
    public decimal Total(Invoice invoice) => invoice.Subtotal + invoice.Tax;
}
public interface IInvoiceNotifier
{
    Task SendAsync(decimal total, CancellationToken token);
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Localized changes and tests
  • Clear ownership of behavior

Limitations

  • Too many tiny classes obscure flow
  • Artificial boundaries add indirection

DECISION GUIDE

When to use it

Use: Separate policies with genuinely independent change reasons.

Avoid: Avoid equating SRP with one method per class or extracting trivial wrappers.

COMMON MISTAKES

Watch out

  • A “God class” that calculates, stores, renders, and sends.
  • Splitting each trivial operation into a separate class by rote.

BEST PRACTICES

In practice

  • Use change history and stakeholder ownership to find boundaries.
  • Keep classes cohesive and testable.
  • Refactor when separation reduces actual change coupling.

INTERVIEW PRACTICE

Common questions

  1. What is a “reason to change”?
  2. How can SRP improve tests?
  3. Why does SRP not mean one method per class?

SENIOR-LEVEL SCENARIO

Production thinking

Tax policy changes frequently while notification channels are stable. Keep calculation and delivery separate and let an application service coordinate them.

SUMMARY

In one minute

SRP reduces unrelated change coupling by grouping behavior around one coherent responsibility.
