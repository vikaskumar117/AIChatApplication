APPLY THE IDEA

Worked example

A reporting job needs read access, not repository writes. Depend on IReadStore rather than implementing a broad store interface with dummy methods.

  1. List the operations a report job actually calls.
  2. Inject IReader rather than the full read/write contract.
  3. Combine IReader and IWriter only in a client needing both.

CODE OR QUERY

Try it

public interface IReader<T>
{
    Task<T?> FindAsync(Guid id, CancellationToken token);
}
public interface IWriter<T>
{
    Task SaveAsync(T value, CancellationToken token);
}
public sealed class ReportJob
{
    private readonly IReader<Report> reader;
    public ReportJob(IReader<Report> reader) => this.reader = reader;
    public Task<Report?> LoadAsync(Guid id, CancellationToken token)
        => reader.FindAsync(id, token);
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Clients depend on fewer unrelated operations
  • Implementations avoid dummy members

Limitations

  • Too many interfaces fragment the model
  • Composition can obscure genuinely cohesive APIs

DECISION GUIDE

When to use it

Use: Split contracts when clients or implementations have distinct capability needs.

Avoid: Avoid tiny interfaces that only mirror implementation methods with no independent client value.

COMMON MISTAKES

Watch out

  • Making all consumers implement unsupported methods.
  • Creating dozens of one-method interfaces without useful separation.

BEST PRACTICES

In practice

  • Derive interfaces from client usage.
  • Name contracts by capability.
  • Compose capabilities at application boundaries.

SENIOR-LEVEL SCENARIO

Production thinking

An export worker only reads reports, while administration also writes. Give each service the minimal contract it needs and compose capabilities for administration.

SUMMARY

In one minute

Focused capability interfaces prevent clients from depending on operations they do not use.
