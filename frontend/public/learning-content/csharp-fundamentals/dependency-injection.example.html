APPLY THE IDEA

Worked example

OrderService receives IOrderStore through its constructor so tests can supply a fake and production can supply a database-backed store.

  1. Declare required collaborators in the constructor.
  2. Register implementations and lifetimes in startup.
  3. Use a fake in a test and the SQL adapter in production.

CODE OR QUERY

Try it

      public sealed class OrderService
{
          private readonly IOrderStore store;
          public OrderService(IOrderStore store) => this.store = store;
          public Task PlaceAsync(Order order, CancellationToken token)
        => store.SaveAsync(order, token);
}

// ASP.NET Core composition:
services.AddScoped<IOrderStore, SqlOrderStore>();
services.AddScoped<OrderService>();

TRADE-OFFS

Benefits and limitations

Benefits

  • Dependencies are explicit and replaceable
  • Composition policy stays at startup

Limitations

  • Lifetime mistakes can retain state or dispose too early
  • Container overuse can hide dependency graphs

DECISION GUIDE

When to use it

Use: Inject required services through constructors and align lifetime with ownership.

Avoid: Avoid service locator patterns, captive scoped dependencies, and needless interfaces.

COMMON MISTAKES

Watch out

  • Resolving arbitrary services from IServiceProvider inside business logic.
  • Capturing scoped services in singletons.
  • Registering every class behind an interface without reason.

BEST PRACTICES

In practice

  • Keep composition at the application boundary.
  • Prefer immutable singleton services and scoped request data as appropriate.
  • Validate service registration and disposal behavior.

SENIOR-LEVEL SCENARIO

Production thinking

A request service uses a scoped database context. Register both with compatible scoped lifetimes and do not capture the context inside a singleton background service.

SUMMARY

In one minute

Dependency injection externalizes construction so collaborators and lifetimes can be composed and substituted explicitly.
