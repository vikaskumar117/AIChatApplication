APPLY THE IDEA

Worked example

An order feed raises an event after publication; consumers subscribe for in-process notification and unsubscribe when their lifetime ends.

  1. Create a callback matching Action<int>.
  2. Subscribe before publishing an order ID.
  3. Unsubscribe when the consumer no longer needs notifications.

CODE OR QUERY

Try it

public sealed class OrderFeed
{
    public event Action<int>? Changed;
    public void Publish(int id) => Changed?.Invoke(id);
}

var feed = new OrderFeed();
Action<int> log = id => Console.WriteLine($"Order {id}");
feed.Changed += log;
feed.Publish(17);
feed.Changed -= log; // release subscription

TRADE-OFFS

Benefits and limitations

Benefits

  • Flexible callbacks and fan-out
  • Events prevent arbitrary external invocation

Limitations

  • Synchronous handlers can delay publisher
  • Forgotten subscriptions retain subscribers

DECISION GUIDE

When to use it

Use: Use Func/Action for simple callback shapes and named delegates for domain-specific contracts.

Avoid: Avoid events for durable distributed messaging or subscriptions with unclear ownership.

COMMON MISTAKES

Watch out

  • Assuming event delivery is asynchronous or durable.
  • Leaving a short-lived subscriber attached to a long-lived publisher.
  • Letting one handler’s exception unintentionally break critical publication.

BEST PRACTICES

In practice

  • Make ownership and unsubscribe behavior explicit.
  • Keep event handlers fast or queue work deliberately.
  • Use a broker for cross-process guarantees.

SENIOR-LEVEL SCENARIO

Production thinking

A singleton order feed notifies transient UI or request consumers. Give subscription lifetime explicit disposal or use a scoped messaging mechanism to prevent retention.

SUMMARY

In one minute

Delegates represent callable behavior; events provide controlled in-process notification and require deliberate subscriber lifetimes.
