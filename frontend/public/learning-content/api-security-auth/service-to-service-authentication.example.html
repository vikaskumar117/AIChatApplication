APPLY THE IDEA

Worked example

A background inventory worker uses its managed identity to obtain an Orders API token with only the required application permission.

  1. Workload proves application identity
  2. Issuer returns audience-scoped credential
  3. Target validates identity and application permission

CODE OR QUERY

Try it

// Conceptual managed identity token acquisition:
var token = await credential.GetTokenAsync(
    new TokenRequestContext(["api://orders/.default"]),
    cancellationToken);

TRADE-OFFS

Benefits and limitations

Benefits

  • Avoids embedding long-lived shared secrets
  • Provides distinct audit identity and narrow application permission

Limitations

  • Identity federation and permission configuration span services
  • Certificate, token, or mesh operations need lifecycle ownership

DECISION GUIDE

When to use it

Use: Use managed workload identity or federation and narrowly scoped application permissions for machine callers.

Avoid: Avoid committing client secrets, sharing one identity across unrelated workloads, or treating a service mesh as application authorization.

COMMON MISTAKES

Watch out

  • Using a developer’s personal token in a scheduled job.
  • Assuming a private subnet or service-mesh identity alone authorizes every operation.

BEST PRACTICES

In practice

  • Assign a distinct workload identity per trust boundary.
  • Rotate/revoke credentials and continuously review granted app roles and scopes.

INTERVIEW PRACTICE

Common questions

  1. When is Client Credentials appropriate?

SENIOR-LEVEL SCENARIO

Production thinking

A client secret leaked from deployment settings; revoke and rotate it, migrate to workload identity, audit downstream permissions, and inspect logs for its prior use.

SUMMARY

In one minute

Workload identity authenticates an application or service without pretending it is an end user.
