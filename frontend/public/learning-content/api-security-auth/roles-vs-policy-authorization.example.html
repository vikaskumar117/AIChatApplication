APPLY THE IDEA

Worked example

An administrator role may access a general diagnostics endpoint, while a policy for editing an invoice also requires matching tenant ownership.

  1. Principal carries validated claims
  2. Policy evaluates requirements
  3. Handler grants or denies operation

CODE OR QUERY

Try it

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("Invoices.Read",
        p => p.RequireClaim("permission", "invoice.read"));
});
[Authorize(Policy = "Invoices.Read")]

TRADE-OFFS

Benefits and limitations

Benefits

  • Named policies centralize and test rules
  • Custom requirements scale beyond role-only checks

Limitations

  • Overly broad role claims can grant excess access
  • Custom handlers need clear failure behavior and observability

DECISION GUIDE

When to use it

Use: Use policies for application capabilities and resource handlers for ownership, tenant, or workflow state.

Avoid: Avoid trusting client-supplied roles or scattering magic-string role checks through business logic.

COMMON MISTAKES

Watch out

  • Using broad administrator roles for ordinary user capabilities.
  • Assuming a policy that checks a role also checks record ownership.

BEST PRACTICES

In practice

  • Centralize capability names and policy registration.
  • Unit-test handlers and integration-test endpoint policy behavior.

INTERVIEW PRACTICE

Common questions

  1. How does a role differ from a policy?
  2. When does a requirement need a resource handler?
  3. Do policy requirements combine with AND or OR semantics by default?

SENIOR-LEVEL SCENARIO

Production thinking

A permission model evolves from admin/user roles to tenant-scoped features; introduce named policies and resource handlers with migration tests before removing legacy role checks.

SUMMARY

In one minute

Roles provide coarse identity groupings; policies express named requirements and can combine claims, roles, and custom handlers.
