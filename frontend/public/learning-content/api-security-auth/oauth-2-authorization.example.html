APPLY THE IDEA

Worked example

A reporting client requests orders.read, receives a token through Authorization Code with PKCE, and cannot use that token for the Billing API.

  1. Client requests narrow authorization
  2. Authorization server authenticates and issues token
  3. Resource API validates access and permission

CODE OR QUERY

Try it

GET /authorize?response_type=code&client_id=reporting
  &redirect_uri=https%3A%2F%2Fapp.example%2Fcallback
  &scope=orders.read&state=<unpredictable-value>
  &code_challenge=<S256-PKCE-challenge>
POST /token  // redeem one-time code with code_verifier

TRADE-OFFS

Benefits and limitations

Benefits

  • Delegates limited access without password sharing
  • Scopes, audiences, and consent provide policy boundaries

Limitations

  • Redirect and token flows have security-sensitive parameters
  • Stolen bearer tokens can be replayed until expiry or revocation

DECISION GUIDE

When to use it

Use: Use Authorization Code with PKCE for interactive public clients and supported workload grants for services.

Avoid: Avoid Resource Owner Password Credentials, custom token protocols, broad scopes, and treating OAuth alone as user identity.

COMMON MISTAKES

Watch out

  • Embedding a confidential client secret in a public SPA or mobile app.
  • Assuming a requested scope guarantees authorization to every record.

BEST PRACTICES

In practice

  • Use established identity platform libraries and exact redirect URI registration.
  • Request only necessary scopes and validate audience at each API.

INTERVIEW PRACTICE

Common questions

SENIOR-LEVEL SCENARIO

Production thinking

A native app can no longer protect a client secret; register it as a public client and use Authorization Code with PKCE, exact redirect URIs, minimal scopes, and API audience checks.

SUMMARY

In one minute

OAuth 2.0 lets a client obtain limited access to a protected resource without sharing the resource owner’s password with that client.
