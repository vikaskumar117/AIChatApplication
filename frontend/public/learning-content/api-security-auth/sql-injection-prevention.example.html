APPLY THE IDEA

Worked example

Search for a username using a parameterized equality predicate rather than concatenating it into a WHERE clause.

  1. Untrusted input enters data query
  2. Parameterized query preserves SQL structure
  3. Database executes bounded command under least privilege

CODE OR QUERY

Try it

var user = await db.Users
    .SingleOrDefaultAsync(u => u.Name == requestedName, cancellationToken);

// Raw SQL: pass values as parameters; allow-list dynamic column identifiers.

TRADE-OFFS

Benefits and limitations

Benefits

  • Parameterization blocks value-based SQL syntax injection
  • Least privilege constrains impact of other defects

Limitations

  • Dynamic identifiers and query composition require careful allow-list design
  • Safe SQL does not prove row-level authorization is correct

DECISION GUIDE

When to use it

Use: Use ORM expression trees or explicit parameters and pair them with least privilege and resource authorization.

Avoid: Avoid constructing SQL values through string concatenation or accepting arbitrary ORDER BY/table names.

COMMON MISTAKES

Watch out

  • Using string interpolation in raw SQL for values.
  • Assuming parameterized SQL prevents broken tenant isolation.

BEST PRACTICES

In practice

  • Review raw SQL and use parameter APIs consistently.
  • Test malicious inputs and cross-tenant access with least-privilege database identities.

INTERVIEW PRACTICE

Common questions

  1. Why do query parameters prevent SQL injection?
  2. Can a parameter safely represent a column name?
  3. Does parameterization replace authorization?

SENIOR-LEVEL SCENARIO

Production thinking

A report endpoint builds a sort expression from client input; replace arbitrary SQL fragments with an allow-listed mapping and verify tenant filters are still applied.

SUMMARY

In one minute

SQL injection occurs when untrusted input changes query structure; parameterization keeps values data rather than executable SQL.
