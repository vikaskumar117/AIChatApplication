APPLY THE IDEA

Worked example

A partner webhook uses a rotated, partner-specific key for initial client identification, while signed payload verification and resource authorization protect business operations.

  1. Client retrieves protected key
  2. Request presents key over TLS
  3. Gateway/API checks key and applies limits

CODE OR QUERY

Try it

// Prefer an authorization header, not a URL query parameter.
request.Headers.Authorization = new AuthenticationHeaderValue("ApiKey", apiKey);
// Server stores a verifier/hash where feasible; redact the credential from logs.

TRADE-OFFS

Benefits and limitations

Benefits

  • Simple integration and client metering
  • Supports independent revocation for partner credentials

Limitations

  • Bearer secret theft enables replay
  • Weak identity and authorization semantics if used alone

DECISION GUIDE

When to use it

Use: Use API keys for bounded client identification or low-risk integration access with rotation and abuse controls.

Avoid: Avoid using a single static API key as sole authorization for sensitive user data or embedding a secret in public browser/mobile code.

COMMON MISTAKES

Watch out

  • Logging or committing API keys.
  • Assuming API-key authentication grants per-user permission.

BEST PRACTICES

In practice

  • Issue per-client keys with revocation, expiration, and least privilege.
  • Use a secrets manager, TLS, redaction, monitoring, and planned rotation.

INTERVIEW PRACTICE

Common questions

  1. What does an API key establish?
  2. Why should a key not be placed in a URL?

SENIOR-LEVEL SCENARIO

Production thinking

A public JavaScript bundle exposes a key; revoke it, review usage, assume it was public, move privileged access behind a trusted backend, and issue independently revocable partner credentials.

SUMMARY

In one minute

An API key identifies or gates a client integration but is a bearer secret and usually does not provide end-user identity or fine-grained authorization.
