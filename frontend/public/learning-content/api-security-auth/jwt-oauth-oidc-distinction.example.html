APPLY THE IDEA

Worked example

A SPA signs in with OIDC, obtains an OAuth access token for Orders, and sends that access token—not the ID token—to the Orders API.

  1. OIDC client signs user in
  2. OAuth authorization obtains API access
  3. API validates its intended access token

CODE OR QUERY

Try it

// Conceptual roles; token formats are independent:
OIDC: client validates ID token where aud == client_id
OAuth: client obtains access token for api://orders
API: validates that access token where aud == api://orders

TRADE-OFFS

Benefits and limitations

Benefits

  • Clear role separation improves protocol choices
  • Works with either JWT or opaque access tokens

Limitations

  • Terminology and similarly named tokens confuse implementers
  • Incorrect audience or token-type handling can expose APIs

DECISION GUIDE

When to use it

Use: Use OIDC for user sign-in, OAuth access tokens for delegated or application API access, and treat JWT only as one possible token format.

Avoid: Avoid treating OAuth alone as an identity protocol or assuming every access token is a JWT.

COMMON MISTAKES

Watch out

  • Calling every JWT an access token.
  • Using an ID token as authorization to an API because it is signed.

BEST PRACTICES

In practice

  • Use protocol libraries and issuer metadata rather than parsing tokens to infer purpose.
  • Validate token audience and expected token type at each boundary.

INTERVIEW PRACTICE

Common questions

  1. Which item is a format rather than a protocol?
  2. What is the purpose and audience of an ID token?
  3. Can an OAuth access token be opaque?

SENIOR-LEVEL SCENARIO

Production thinking

A client sends its ID token to a microservice because both are JWTs; reject the wrong token type and audience, configure an API access-token acquisition flow, and verify resource server validation.

SUMMARY

In one minute

JWT is a token format, OAuth 2.0 is an authorization framework, and OpenID Connect is an authentication layer built on OAuth 2.0.
