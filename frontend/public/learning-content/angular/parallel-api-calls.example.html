APPLY THE IDEA

Worked example

A profile page loads identity, preferences, and feature flags independently and displays them together after the responses arrive.

  1. Use object form to retain meaningful property names and inferred types.
  2. Put catchError inside each input when failures should become per-field result states.
  3. Limit concurrency for large collections rather than creating an unbounded request fan-out.

CODE OR QUERY

Try it

readonly pageData$ = forkJoin({
  user: this.http.get<User>('/api/me'),
  preferences: this.http.get<Preferences>('/api/preferences'),
  flags: this.http.get<Flags>('/api/flags')
});

TRADE-OFFS

Benefits and limitations

Benefits

  • Concurrent latency for independent reads
  • Typed aggregate is easy to bind

Limitations

  • One failure fails forkJoin by default
  • Launching too many calls can overload dependencies

DECISION GUIDE

When to use it

Use: Use forkJoin for a finite set of independent requests whose results are needed together.

Avoid: Avoid it for never-completing streams or dependencies where a later request needs an earlier result.

COMMON MISTAKES

Watch out

  • Passing an interval or other non-completing source to forkJoin and waiting forever.
  • Catching only outside forkJoin when partial results are required.
  • Running all API calls concurrently when one requires another response.

BEST PRACTICES

In practice

  • Use switchMap/concatMap to express dependencies and ordering.
  • Represent loading, success, and partial error explicitly.
  • Keep cancellation and owner lifetime in the subscription chain.

SENIOR-LEVEL SCENARIO

Production thinking

A dashboard loads three independent widgets. Start them concurrently, catch expected per-widget failures inside each source if partial rendering is required, and avoid blocking on an unrelated long-lived stream.

SUMMARY

In one minute

Independent HttpClient requests can be created together and subscribed as a group. forkJoin is the common choice for finite HTTP calls when the screen needs one aggregate after every request has emitted and completed. Concurrency reduces wall-clock latency from roughly the sum of request durations toward the slowest request, but increases simultaneous load and can hit rate limits. Dependencies should remain sequential.
