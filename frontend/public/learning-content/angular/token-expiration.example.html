APPLY THE IDEA

Worked example

Five API calls expire together; a single-flight refresh prevents five competing token rotations and each original call is retried at most once.

  1. Use short-lived access credentials and server-side refresh rotation/revocation.
  2. Mark requests already refreshed to prevent loops and cap replay at one.
  3. Treat replay safety separately for mutations; use server idempotency where needed.

CODE OR QUERY

Try it

const refresh$ = this.refreshInFlight ??= this.auth.refresh().pipe(
  tap(token => this.auth.storeAccessToken(token)),
  finalize(() => this.refreshInFlight = undefined),
  shareReplay({ bufferSize: 1, refCount: false })
);

TRADE-OFFS

Benefits and limitations

Benefits

  • Seamless renewal can reduce avoidable sign-ins
  • Single-flight refresh handles concurrent failures

Limitations

  • Refresh races can invalidate rotated credentials
  • Replay may duplicate a mutation or loop on persistent 401

DECISION GUIDE

When to use it

Use: Coordinate one refresh, replay an eligible request once, and fail closed when refresh fails.

Avoid: Avoid infinite 401 retries or trusting client-side exp checks as security enforcement.

COMMON MISTAKES

Watch out

  • Launching one refresh per failed request.
  • Refreshing on every 401, including invalid permissions and the refresh endpoint.
  • Assuming a client-side expiry timer prevents server rejection or clock skew.

BEST PRACTICES

In practice

  • Define an explicit refresh state machine and test concurrent failures.
  • Clear session data on refresh failure and do not leave a half-authenticated UI.
  • Exclude credentials from logs and telemetry.

INTERVIEW PRACTICE

Common questions

  1. Why should simultaneous 401 responses share refresh work?
  2. How do you prevent a refresh loop?
  3. What should happen when refresh fails?

SENIOR-LEVEL SCENARIO

Production thinking

A token rotation endpoint revokes the previous refresh token. Under concurrent 401s, serialize or share refresh, preserve request context, and verify that failed refresh clears session state without exposing tokens in logs.

SUMMARY

In one minute

An access token’s exp claim indicates the time after which a conforming server should reject it, but the client clock can be skewed and a decoded token is not proof of validity. The server remains authoritative. Refresh may occur proactively near expiry or reactively after an eligible 401. Concurrent failures should share a single refresh operation; retry each original request at most once and exclude refresh endpoints to prevent recursion.
