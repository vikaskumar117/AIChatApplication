APPLY THE IDEA

Worked example

A multi-step onboarding flow uses route-scoped state for its draft, server data cache for reference data, and local signals for a dialog’s open state.

  1. Keep server-owned data distinct from client-owned UI state.
  2. Model loading/error/empty states instead of parallel booleans.
  3. Use selectors/computed derivations and explicit mutations; test transitions and invalidation.

CODE OR QUERY

Try it

interface OrderState {
  status: 'idle' | 'loading' | 'ready' | 'error';
  order: Order | null;
}

readonly state = signal<OrderState>({ status: 'idle', order: null });
readonly canSubmit = computed(() =>
  this.state().status === 'ready' && this.state().order !== null
);

TRADE-OFFS

Benefits and limitations

Benefits

  • Explicit ownership prevents conflicting copies
  • Scoped state limits lifetime and unintended coupling

Limitations

  • A global store adds ceremony and migration cost
  • Cache invalidation and stale duplicated state remain hard

DECISION GUIDE

When to use it

Use: Use the smallest state container that meets sharing, observability, and team needs.

Avoid: Avoid putting transient UI state or credentials in a global persistent store by default.

COMMON MISTAKES

Watch out

  • Promoting every local boolean into global state.
  • Keeping multiple independently mutable copies of the same entity.
  • Persisting secrets or user-specific cached data without a threat and invalidation model.

BEST PRACTICES

In practice

  • Start local and elevate only when sharing or coordination is real.
  • Align provider/store lifetime with feature and user-session boundaries.
  • Define logout clearing, cache invalidation, and concurrent update behavior.

SENIOR-LEVEL SCENARIO

Production thinking

A growing commerce app has stale cart badges and duplicated account state. Define a canonical owner, expose derived selectors, invalidate server-backed caches after mutations, and scope checkout draft state to the workflow.

SUMMARY

In one minute

Separate ephemeral view state, route/workflow state, server/cache state, and durable cross-feature client state. Each category has different lifetime, freshness, concurrency, and persistence requirements. Start with component signals or local observables, elevate state to a route-scoped service when siblings share it, and adopt a store when explicit transitions, selectors, effects, tooling, or team coordination justify its cost.
