APPLY THE IDEA

Worked example

A dashboard can show one failed widget beside successful widgets, while a failed authorization request should not be converted into an empty successful result.

  1. Keep loading, success, empty, and error states distinct.
  2. Use exponential backoff with jitter and Retry-After awareness where appropriate.
  3. Attach request/correlation IDs to diagnostics without logging secrets.

CODE OR QUERY

Try it

readonly report$ = this.http.get<Report>('/api/report').pipe(
  retry({ count: 2, delay: (_, attempt) => timer(attempt * 500) }),
  catchError((error: HttpErrorResponse) => {
    this.logger.warn('Report load failed', { status: error.status });
    return throwError(() => error);
  })
);

TRADE-OFFS

Benefits and limitations

Benefits

  • Central policies improve consistency
  • Explicit error states make recovery possible

Limitations

  • Retries can duplicate non-idempotent writes
  • Overly broad catches hide defects and mislead users

DECISION GUIDE

When to use it

Use: Use catchError to model a deliberate fallback or rethrow; retry only known transient, safe operations with bounds.

Avoid: Avoid exposing raw server messages, credentials, or stack details to users.

COMMON MISTAKES

Watch out

  • Returning of([]) for every failure and making outages look like empty data.
  • Retrying every status or blindly retrying POST requests.
  • Displaying raw backend error payloads to end users.

BEST PRACTICES

In practice

  • Handle expected errors at the narrowest boundary that can recover meaningfully.
  • Keep unexpected errors observable for centralized diagnostics.
  • Make retry limits and user recovery paths explicit.

INTERVIEW PRACTICE

Common questions

SENIOR-LEVEL SCENARIO

Production thinking

An analytics screen has independent panels. Each panel maps its own failure to retryable local state so one outage does not erase successful results; logs include status and correlation data but not tokens or private payloads.

SUMMARY

In one minute

HttpClient reports transport, timeout, and non-success responses through HttpErrorResponse on the Observable error channel. A status of 0 commonly represents network-level failure; status codes and server payloads require contextual interpretation. catchError can transform, recover, or rethrow an error. Catch at the boundary that knows whether to provide a fallback, retry a transient failure, or surface an error state; avoid swallowing failures into apparently valid empty data.
