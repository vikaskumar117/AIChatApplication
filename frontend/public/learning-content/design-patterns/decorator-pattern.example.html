APPLY THE IDEA

Worked example

A logging decorator records a payment call while forwarding the same request and cancellation token to the provider implementation.

  1. Pass cancellation and preserve result/error behavior.
  2. Add one focused concern per decorator.
  3. Test wrapper behavior and the composed order.

CODE OR QUERY

Try it

public sealed class LoggingPayment(IPaymentMethod inner, ILogger<LoggingPayment> log)
    : IPaymentMethod
{
    public async Task<PaymentResult> PayAsync(PaymentRequest request, CancellationToken ct)
    {
        log.LogInformation("Starting payment {Id}", request.Id);
        return await inner.PayAsync(request, ct);
    }
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Composes optional concerns around stable contracts.
  • Avoids subclass explosion and keeps core implementation focused.

Limitations

  • Wrapper ordering can change semantics and become hard to trace.
  • A decorator that changes errors or ignores cancellation violates substitutability.

DECISION GUIDE

When to use it

Use: Use for cross-cutting behavior that can be expressed while preserving the contract.

Avoid: Avoid wrapping every service in generic layers that obscure call flow.

COMMON MISTAKES

Watch out

  • Avoid wrapping every service in generic layers that obscure call flow.
  • Assuming decorator pattern guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Name wrappers by the behavior they add.
  • Keep ordering visible in composition and diagnostics.

SENIOR-LEVEL SCENARIO

Production thinking

A caching decorator returns stale payment status. Restrict caching to suitable read contracts and define invalidation and freshness explicitly.
