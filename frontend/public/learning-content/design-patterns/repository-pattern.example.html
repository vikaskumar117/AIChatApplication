APPLY THE IDEA

Worked example

An OrderRepository exposes GetForConfirmationAsync with required lines and status rather than leaking a generic IQueryable to every caller.

  1. Keep aggregate invariants with the aggregate and its application use case.
  2. Make transaction/commit ownership explicit.
  3. Use direct projections for read models when they are clearer.

CODE OR QUERY

Try it

public interface IOrderRepository
{
    Task<Order?> GetForConfirmationAsync(Guid id, CancellationToken ct);
    void Add(Order order);
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Domain-specific operations communicate intent and can protect aggregate boundaries.
  • Can isolate persistence technology when that is a real architectural seam.

Limitations

  • Generic repositories duplicate ORM APIs and restrict query composition.
  • Extra abstractions complicate transactions, projections, and testing if they add no behavior.

DECISION GUIDE

When to use it

Use: Use a repository for aggregate-oriented operations or a meaningful persistence boundary.

Avoid: Avoid wrapping every DbSet method or returning IQueryable across an abstraction boundary without an explicit design.

COMMON MISTAKES

Watch out

  • Avoid wrapping every DbSet method or returning IQueryable across an abstraction boundary without an explicit design.
  • Assuming repository pattern guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Use domain-focused method names and cancellation.
  • Keep query tracking and consistency expectations visible.

INTERVIEW PRACTICE

SENIOR-LEVEL SCENARIO

Production thinking

A report query needs grouping and projection. Keep it as an explicit query optimized for reporting instead of forcing it through a CRUD repository designed for aggregate writes.

SUMMARY

In one minute

A repository is useful when it protects a meaningful domain or persistence boundary, not as a mandatory wrapper around an ORM.
