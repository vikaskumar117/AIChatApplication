APPLY THE IDEA

Worked example

When an order changes in memory, UI observers refresh; for durable invoice generation across processes, publish a persisted domain event instead.

  1. Define whether notification is synchronous or queued.
  2. Unsubscribe or scope event handlers to component lifetime.
  3. Persist an outbox event for durable integration.

CODE OR QUERY

Try it

public event EventHandler<OrderChangedEventArgs>? Changed;
protected void OnChanged(Order order) =>
    Changed?.Invoke(this, new OrderChangedEventArgs(order.Id));

TRADE-OFFS

Benefits and limitations

Benefits

  • Publisher need not call each subscriber by concrete type.
  • Can support extensible local notifications and reactive views.

Limitations

  • Synchronous observers can slow or fail the publisher.
  • Unmanaged subscriptions cause leaks; in-memory events are lost on process crash.

DECISION GUIDE

When to use it

Use: Use for local notifications with clear lifetime and failure semantics.

Avoid: Avoid in-process Observer when durable cross-service delivery or independent recovery is required.

COMMON MISTAKES

Watch out

  • Avoid in-process Observer when durable cross-service delivery or independent recovery is required.
  • Assuming observer pattern guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Keep event payloads small and meaningful.
  • Test subscription cleanup and observer failure behavior.

INTERVIEW PRACTICE

Common questions

  1. How does Observer reduce coupling?
  2. What happens if a synchronous observer throws?
  3. Why is an in-memory event not a durable integration event?

SENIOR-LEVEL SCENARIO

Production thinking

A UI subscriber remains attached after a view closes and leaks memory. Unsubscribe with the view lifetime; persist cross-service events through an outbox.

SUMMARY

In one minute

Observer decouples notification relationships but requires explicit delivery, lifetime, and error semantics.
