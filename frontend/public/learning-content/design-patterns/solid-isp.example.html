APPLY THE IDEA

Worked example

A receipt printer implements IPrintReceipt, while a multifunction device implements both print and scan capabilities.

  1. Group operations by real client use and change together.
  2. Make unsupported capability impossible to request through the contract.
  3. Use contract tests for each capability.

CODE OR QUERY

Try it

public interface IPrintReceipt { Task PrintAsync(Receipt receipt, CancellationToken ct); }
public interface IScanDocument { Task<Scan> ScanAsync(CancellationToken ct); }
public sealed class ReceiptPrinter : IPrintReceipt { /* print only */ }

TRADE-OFFS

Benefits and limitations

Benefits

  • Changes to unused methods no longer affect every client.
  • Implementations and test doubles need only fulfill relevant capabilities.

Limitations

  • Too many micro-interfaces can obscure cohesive concepts.
  • Splitting interfaces does not automatically make domain boundaries correct.

DECISION GUIDE

When to use it

Use: Separate methods when distinct clients need independent capabilities.

Avoid: Avoid interfaces so small they carry no meaningful cohesion or substitution role.

COMMON MISTAKES

Watch out

  • Avoid interfaces so small they carry no meaningful cohesion or substitution role.
  • Assuming solid: interface segregation principle guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Follow actual client dependency boundaries.
  • Keep composition manageable as interfaces are split.

SENIOR-LEVEL SCENARIO

Production thinking

A shipping client changes because an unrelated invoice method was added to a large gateway interface. Split interfaces along stable client capabilities.

SUMMARY

In one minute

ISP keeps clients coupled only to cohesive capabilities they consume.
