APPLY THE IDEA

Worked example

A read-only storage implementation should not implement an interface promising deletion; split read and write capabilities rather than throwing NotSupportedException.

  1. Document semantics and error behavior in contracts.
  2. Test implementations against shared contract tests.
  3. Use composition or narrower capabilities for divergent behavior.

TRADE-OFFS

Benefits and limitations

Benefits

  • Reliable substitution reduces type-specific branches in callers.
  • Clear contracts encourage correct abstraction and composition.

Limitations

  • Broad base types can be hard to design without accidental promises.
  • Replacing inheritance with excessive tiny interfaces can also fragment the design.

DECISION GUIDE

When to use it

Use: Use inheritance when derived types honor the same observable contract.

Avoid: Avoid subclasses that reject valid base operations or change their meaning unexpectedly.

COMMON MISTAKES

Watch out

  • Avoid subclasses that reject valid base operations or change their meaning unexpectedly.
  • Assuming solid: liskov substitution principle guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Prefer small truthful abstractions over broad speculative base classes.
  • Test all implementations against the same behavioral expectations.

Production thinking
