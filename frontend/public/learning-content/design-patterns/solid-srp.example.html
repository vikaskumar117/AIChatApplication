APPLY THE IDEA

Worked example

A tax-rule change should not require editing a class whose other reason to change is SMTP formatting or database schema.

  1. Identify actors or policies that drive changes.
  2. Keep related decisions together and unrelated decisions separate.
  3. Test pure domain rules independently.

CODE OR QUERY

Try it

public sealed class InvoiceCalculator
{
    public decimal Total(Invoice invoice) =>
        invoice.Lines.Sum(x => x.Quantity * x.UnitPrice) + invoice.Tax;
}
// Persistence and notification belong to separate collaborators.

TRADE-OFFS

Benefits and limitations

Benefits

  • Independent changes affect smaller, more cohesive units.
  • Domain behavior can be tested without database or email infrastructure.

Limitations

  • Over-splitting produces tiny types and navigation overhead.
  • Responsibility boundaries depend on the domain and change ownership.

DECISION GUIDE

When to use it

Use: Separate code with independent policy owners or change cadence.

Avoid: Avoid treating every operation or field as a separate responsibility.

COMMON MISTAKES

Watch out

  • Avoid treating every operation or field as a separate responsibility.
  • Assuming solid: single responsibility principle guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Use change history and ownership to find useful boundaries.
  • Refactor when changes repeatedly collide, not based on line count alone.

INTERVIEW PRACTICE

Common questions

  1. What does “one reason to change” mean in practice?
  2. Why is a one-method-per-class rule not SRP?
  3. How would you split a class that calculates, saves, and emails an invoice?

SENIOR-LEVEL SCENARIO

Production thinking

A tax update repeatedly breaks email notifications because both behaviors share one class. Separate the policies and test calculation independently.

SUMMARY

In one minute

SRP improves cohesion by aligning a module with one coherent change responsibility.
