APPLY THE IDEA

Worked example

Order policy depends on IPaymentAuthorizer; the infrastructure adapter depends on the provider SDK and implements that port.

  1. Keep ports in the layer whose policy needs the capability.
  2. Translate vendor models at the infrastructure boundary.
  3. Test business policy against the abstraction and adapter separately.

CODE OR QUERY

Try it

public interface IPaymentAuthorizer
{
    Task<Authorization> AuthorizeAsync(Payment payment, CancellationToken ct);
}
public sealed class OrderCheckout(IPaymentAuthorizer payments) { /* high-level policy */ }

TRADE-OFFS

Benefits and limitations

Benefits

  • High-level domain policy can be tested without external systems.
  • Infrastructure replacement does not require rewriting business rules.

Limitations

  • Abstractions can become needless indirection if no meaningful boundary exists.
  • A poorly owned abstraction can leak vendor details or be shaped by low-level constraints.

DECISION GUIDE

When to use it

Use: Use at volatile or external boundaries where policy must remain independent.

Avoid: Avoid introducing abstractions for stable internal details that have no substitutability need.

COMMON MISTAKES

Watch out

  • Avoid introducing abstractions for stable internal details that have no substitutability need.
  • Assuming solid: dependency inversion principle guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Keep contracts small and domain-relevant.
  • Use explicit composition rather than service location.

SENIOR-LEVEL SCENARIO

Production thinking

A vendor SDK type has spread through domain services. Introduce an application-owned port and adapter, then map provider errors into meaningful application outcomes.

SUMMARY

In one minute

DIP protects higher-level policy from low-level detail through a meaningful abstraction owned by the policy.
