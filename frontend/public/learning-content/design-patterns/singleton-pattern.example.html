APPLY THE IDEA

Worked example

A stateless serializer is singleton-safe; a request-specific shopping cart is not and should be scoped to its user/session context.

  1. Review every dependency lifetime and mutable field.
  2. Prefer immutable data or explicit synchronization for shared state.
  3. Use DI registration rather than hidden static access.

CODE OR QUERY

Try it

services.AddSingleton<IClock, SystemClock>();
services.AddScoped<IOrderService, OrderService>();
// Do not inject a scoped DbContext into a singleton.

TRADE-OFFS

Benefits and limitations

Benefits

  • Shares expensive, safe-to-share infrastructure for the process lifetime.
  • DI makes lifecycle explicit and substitutes implementations in tests.

Limitations

  • Mutable shared state creates races and cross-request leakage.
  • A singleton can retain resources or accidentally depend on request-scoped state.

DECISION GUIDE

When to use it

Use: Use singleton for stateless or deliberately thread-safe shared services.

Avoid: Avoid storing user/request data or injecting scoped dependencies into a singleton.

COMMON MISTAKES

Watch out

  • Avoid storing user/request data or injecting scoped dependencies into a singleton.
  • Assuming singleton pattern and di lifetime guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Keep singleton state minimal and bounded.
  • Use distributed storage when state must be shared across processes.

INTERVIEW PRACTICE

Common questions

SENIOR-LEVEL SCENARIO

Production thinking

A singleton cache stores the current user ID and leaks one customer’s state into another request. Move request data to scoped state and use a properly designed shared cache if needed.

SUMMARY

In one minute

Singleton is a lifetime choice with concurrency and dependency consequences, not a universal object-management shortcut.
