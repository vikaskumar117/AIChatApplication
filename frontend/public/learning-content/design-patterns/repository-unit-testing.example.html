APPLY THE IDEA

Worked example

Test that a confirmation handler rejects cancelled orders with a fake repository; separately test its EF query and transaction against a relational test database.

  1. Test observable behavior rather than private method calls.
  2. Use a relational provider for SQL-dependent query semantics.
  3. Keep fake repository behavior faithful to its contract.

CODE OR QUERY

Try it

var repository = new FakeOrderRepository(Order.Cancelled(orderId));
var handler = new ConfirmOrderHandler(repository);
var result = await handler.Handle(new ConfirmOrder(orderId), ct);
Assert.Equal(ConfirmResult.AlreadyCancelled, result);

TRADE-OFFS

Benefits and limitations

Benefits

  • Focused tests give fast feedback on business outcomes.
  • Provider integration tests catch SQL, mapping, and transaction errors that mocks cannot.

Limitations

  • Mocks can become coupled to implementation details.
  • In-memory providers may differ from production relational behavior.

DECISION GUIDE

When to use it

Use: Use unit tests for deterministic policy and interaction boundaries; integration tests for persistence semantics.

Avoid: Avoid mocking every DbSet and treating those tests as proof of database correctness.

COMMON MISTAKES

Watch out

  • Avoid mocking every DbSet and treating those tests as proof of database correctness.
  • Assuming repository pattern and unit testing guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Keep unit and integration test goals distinct.
  • Run important repository tests against the same provider family as production.

INTERVIEW PRACTICE

Common questions

  1. What should a repository unit test prove?
  2. When is an integration test necessary?
  3. Why can mocking EF Core hide defects?

SENIOR-LEVEL SCENARIO

Production thinking

A repository test passes with an in-memory fake but production SQL fails on a translation. Add provider-backed coverage for the query and retain unit tests for domain rules.

SUMMARY

In one minute

Repository boundaries can support focused tests, but persistence correctness requires provider-backed integration coverage.
