APPLY THE IDEA

Worked example

ConfirmOrder validates and changes the aggregate; GetOrderSummary projects a lightweight DTO for the customer dashboard.

  1. Make command handling authoritative for invariants.
  2. Return query DTOs rather than exposing persistence entities.
  3. Specify projection freshness when read models lag.

CODE OR QUERY

Try it

public sealed record ConfirmOrder(Guid OrderId);
public sealed record GetOrderSummary(Guid OrderId);
// Command handler enforces the invariant; query handler projects read data.

TRADE-OFFS

Benefits and limitations

Benefits

  • Separates write invariants from read-oriented projection needs.
  • Enables independent optimization when workloads materially diverge.

Limitations

  • Additional message types and handlers add indirection.
  • Separate read stores introduce replication lag, rebuild, and reconciliation concerns.

DECISION GUIDE

When to use it

Use: Use when read and write models or scaling constraints differ materially.

Avoid: Avoid a separate database, event sourcing, or MediatR solely because the term CQRS is fashionable.

COMMON MISTAKES

Watch out

  • Avoid a separate database, event sourcing, or MediatR solely because the term CQRS is fashionable.
  • Assuming cqrs guarantees outcomes beyond its stated scope.

BEST PRACTICES

In practice

  • Start with logical separation in one database.
  • Measure read/write pressure before adding another store.

INTERVIEW PRACTICE

Common questions

  1. Does CQRS require two databases?
  2. How does a command differ from a query?
  3. What new consistency problem comes with a separate read model?

SENIOR-LEVEL SCENARIO

Production thinking

A dashboard requires denormalized search while writes remain authoritative. Update the projection reliably, state its freshness, and retain a rebuild path.

SUMMARY

In one minute

CQRS separates intent and models; physical separation and event sourcing are independent choices.
