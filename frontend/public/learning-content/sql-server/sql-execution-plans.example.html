APPLY THE IDEA

Worked example

A key lookup repeated hundreds of thousands of times may indicate an index coverage trade-off; verify rows, reads, and write costs before changing it.

  1. Capture an actual plan using representative parameters in a safe environment.
  2. Read data flow from leaves toward root and inspect predicates, joins, and row counts.
  3. Compare estimated and actual rows; investigate spills, memory grants, and repeated lookups.
  4. Correlate with logical reads, CPU, waits, and application latency before changing anything.

CODE OR QUERY

Try it

SET STATISTICS IO, TIME ON;
-- In SSMS, enable Include Actual Execution Plan, then run a representative query.
SELECT EmployeeId, Name
FROM dbo.Employee
WHERE DepartmentId = @departmentId
ORDER BY Salary DESC;
SET STATISTICS IO, TIME OFF;

TRADE-OFFS

Benefits and limitations

Benefits

  • Shows operator choices and estimate/runtime evidence.
  • Helps explain scans, lookups, joins, sorts, spills, and memory grants.

Limitations

  • Actual plan capture adds overhead and may expose sensitive literals or schema details.
  • Estimated operator percentages are relative estimates, not direct elapsed-time attribution.

DECISION GUIDE

When to use it

Use: Use actual plans with representative parameter values alongside Query Store, reads, CPU, waits, and latency.

Avoid: Avoid assuming the largest estimated-cost operator is the actual bottleneck or that an estimated plan proves runtime behavior.

COMMON MISTAKES

Watch out

  • Reading plan flow as if it guaranteed the written SQL clause order.
  • Treating estimated cost percentages as actual elapsed-time percentages.
  • Capturing an actual plan with unrepresentative parameters and extrapolating.

BEST PRACTICES

In practice

  • Use Query Store to examine plan history and regressions.
  • Use representative parameters/data and protect captured plan artifacts.
  • Confirm a plan hypothesis with IO, TIME, waits, and end-to-end measurements.

INTERVIEW PRACTICE

Common questions

  1. What extra information does an actual plan provide?
  2. How do you interpret estimated-versus-actual row discrepancy?
  3. Why is a key lookup not automatically bad?

SENIOR-LEVEL SCENARIO

Production thinking

A query suddenly spills to tempdb. Capture an actual plan on representative data, inspect sort/hash warnings, memory grant and estimate errors, validate statistics and parameter behavior, then test a measured fix.

SUMMARY

In one minute

An execution plan is the optimizer’s chosen physical strategy: operators and data flow used to execute a query. An estimated plan contains estimates; an actual plan adds runtime observations such as actual rows and executions. Plans reveal access methods, join algorithms, sorts, aggregates, lookups, spills, and estimate errors. They explain implementation, not the logical SQL binding order or every external bottleneck.
