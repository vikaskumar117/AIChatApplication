APPLY THE IDEA

Worked example

Support department salary ordering and return employee name without making Name part of the index search key.

  1. List filters, joins, order columns, selected fields, and write rates.
  2. Review existing indexes and actual execution plans.
  3. Design key columns in useful leading order; add minimal included payload.
  4. Measure logical reads, duration, and write overhead under representative load.

CODE OR QUERY

Try it

-- Example only: verify existing indexes, workload, and write cost first.
CREATE NONCLUSTERED INDEX IX_Employee_Department_Salary
ON dbo.Employee (DepartmentId, Salary DESC)
INCLUDE (EmployeeId, Name);

TRADE-OFFS

Benefits and limitations

Benefits

  • Can reduce logical reads, support ordered access, and cover a query.
  • Unique indexes enforce data invariants as well as aiding access.

Limitations

  • Every insert/update/delete may maintain affected indexes.
  • Indexes consume storage, can cause page splits, and may be unused or duplicated.

DECISION GUIDE

When to use it

Use: Use a focused index when measured predicates, joins, ordering, or constraints justify its read benefit.

Avoid: Avoid indexing every column or using wide, volatile clustered keys without considering write amplification and row-locator size.

COMMON MISTAKES

Watch out

  • Creating overlapping indexes without comparing their key and include columns.
  • Putting every selected column into the key instead of using INCLUDE.
  • Treating an index seek as proof of a fast query regardless of rows read or lookups.

BEST PRACTICES

In practice

  • Use plans and workload measurements to justify index changes.
  • Keep keys narrow and stable; include only columns that avoid material cost.
  • Monitor usage, write impact, statistics, and duplicate/overlapping indexes.

INTERVIEW PRACTICE

Common questions

  1. What is stored at the leaf level of a clustered index?
  2. Why does a nonclustered index need a row locator?
  3. When does INCLUDE help versus adding a key column?

SENIOR-LEVEL SCENARIO

Production thinking

A salary report scans a large employee table. Confirm query shape and selectivity, compare existing indexes and actual plan, evaluate a department/salary key with includes, then measure read improvement against insert/update cost.

SUMMARY

In one minute

A clustered index is the table’s rowstore B-tree whose leaf level contains the data rows; a table has at most one. A nonclustered index is a separate B-tree with key columns and a row locator (clustered key or RID), and a table may have many. Indexes provide ordered access paths, support constraints, and can avoid scans or lookups. Each index also adds storage, write work, and maintenance.
