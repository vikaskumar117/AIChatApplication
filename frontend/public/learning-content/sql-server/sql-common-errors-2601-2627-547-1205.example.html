APPLY THE IDEA

Worked example

A repeated import gets 2601/2627 on an idempotency key: treat the unique constraint as authoritative and return the already-created result where appropriate.

  1. Log the SQL exception number, constraint/index, statement context, and correlation ID without secrets.
  2. For 2601/2627, determine whether the write is a legitimate idempotent replay or a true conflict.
  3. For 547, inspect violated FK/CHECK invariant and transaction operation order.
  4. For 1205, inspect deadlock graph and retry only a safe whole transaction with bounded policy.

CODE OR QUERY

Try it

try
{
    await repository.InsertAsync(entity, ct);
}
catch (SqlException ex) when (ex.Number is 2601 or 2627)
{
    // Only treat as idempotent success after verifying the conflicting key
    // represents this same request; otherwise propagate the conflict.
    var existing = await repository.FindByRequestKeyAsync(requestKey, ct);
    if (existing is null || existing.PayloadHash != payloadHash) throw;
}
// A 547 needs relationship/business correction; a 1205 needs graph diagnosis
// and at most a bounded retry of a safe database transaction.

TRADE-OFFS

Benefits and limitations

Benefits

  • Cause-focused handling preserves database constraints and business semantics.
  • Structured errors improve diagnosis and safe recovery.

Limitations

  • Exception classification must account for provider and constraint context.
  • Overly broad catches can hide data corruption or programming errors.

DECISION GUIDE

When to use it

Use: Use targeted handling for known constraint conflicts and transient deadlock victims with verified idempotency.

Avoid: Avoid retrying every SqlException, suppressing a foreign-key conflict, or using error number as the only diagnostic evidence.

COMMON MISTAKES

Watch out

  • Retrying unique-key violations as though they were transient outages.
  • Disabling constraints to bypass a 547 without repairing data integrity.
  • Treating every database exception as retryable or logging sensitive parameters.

BEST PRACTICES

In practice

  • Handle uniqueness conflicts according to idempotency and business semantics.
  • Keep FK/check/unique constraints as authoritative safeguards.
  • Use bounded retry only for classified transient failures.
  • Log safe structured diagnostics and preserve the original exception.

INTERVIEW PRACTICE

Common questions

  1. What do 2601/2627, 547, and 1205 broadly indicate?
  2. Why can 2601/2627 require different caller behavior?
  3. What should be captured with an error number?

SENIOR-LEVEL SCENARIO

Production thinking

An import service floods retries after duplicate-key errors. Keep the unique key as the concurrency authority, look up and validate the existing request for idempotent replay, surface mismatches as conflicts, and diagnose 547/1205 independently.

SUMMARY

In one minute

SQL Server error numbers identify a failure category, but the constraint, statement, transaction state, and surrounding context explain the root cause. 2601 and 2627 indicate unique-key violations; 547 indicates a CHECK or FOREIGN KEY constraint conflict; 1205 means the transaction was selected as a deadlock victim. Fixing the invariant or concurrency behavior is more reliable than memorizing numbers or retrying every database exception.
