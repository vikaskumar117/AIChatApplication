THE IDEA

What is it?

An execution plan is the optimizer’s chosen physical strategy: operators and data flow used to execute a query. An estimated plan contains estimates; an actual plan adds runtime observations such as actual rows and executions.

WHY IT MATTERS

What problem does it solve?

Plans reveal access methods, join algorithms, sorts, aggregates, lookups, spills, and estimate errors. They explain implementation, not the logical SQL binding order or every external bottleneck.

UNDER THE HOOD

How does it work?

Read from data-producing inputs toward parent operators; compare estimated and actual rows, check warnings and memory grants, inspect predicates and rows read, and correlate with runtime metrics and waits. A graphical icon or cost percentage is not a complete diagnosis.

KEY TAKEAWAYS

Remember

  • A plan describes physical implementation, not logical clause-binding order.
  • Actual plans provide runtime evidence unavailable from estimated plans.
  • Estimate errors can propagate into join, memory, and access-path choices.
  • Plan cost percentages and seek/scan labels are clues, not conclusions.
