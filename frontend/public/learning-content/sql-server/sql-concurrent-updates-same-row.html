Concurrent Updates to the Same Row in SQL Server

Learn how SQL Server manages simultaneous updates, prevents conflicting writes, and protects data from lost updates. Explore locking, blocking, isolation levels, rowversion, optimistic concurrency, and production-ready T-SQL patterns.

1. Learning Objectives

  • Understand concurrent database updates.
  • Understand lost updates and stale data.
  • Learn how SQL Server locks rows and pages.
  • Understand blocking and lock compatibility.
  • Compare pessimistic and optimistic concurrency.
  • Use atomic UPDATE statements to avoid race conditions.
  • Implement optimistic concurrency with rowversion.
  • Understand isolation levels and their effect on updates.
  • Diagnose blocking and deadlocks.
  • Design safe concurrent update patterns for production.

2. What Is a Concurrent Update?

A concurrent update occurs when two or more sessions attempt to modify the same database record at approximately the same time.

Consider a bank account with a balance of 10,000. Two users simultaneously attempt withdrawals:

  • User A withdraws 2,000.
  • User B withdraws 3,000.

The correct final balance should be 5,000 if both withdrawals are valid.

Sample table

DROP TABLE IF EXISTS dbo.ConcurrentAccount;

CREATE TABLE dbo.ConcurrentAccount
(
    AccountId INT PRIMARY KEY,
    AccountName VARCHAR(50) NOT NULL,
    Balance DECIMAL(12,2) NOT NULL
);

INSERT INTO dbo.ConcurrentAccount
VALUES
    (1, 'Alice', 10000.00),
    (2, 'Bob', 5000.00);

SELECT *
FROM dbo.ConcurrentAccount;
AccountId AccountName Balance
1Alice10000.00
2Bob5000.00

3. The Lost Update Problem

A lost update occurs when two sessions read the same original value, independently calculate a new value, and one update overwrites the other's result.

Example scenario

Initial account balance: 10,000.

Time Session A Session B
1 Reads 10,000
2 Reads 10,000
3 Calculates 10,000 - 2,000 = 8,000
4 Calculates 10,000 - 3,000 = 7,000
5 Writes 8,000
6 Writes 7,000

The final balance becomes 7,000. Session A's withdrawal has effectively been overwritten.

This example represents an application-level read-calculate-write race. Ordinary SQL Server UPDATE statements acquire write locks and do not simply allow two conflicting writes to overwrite each other simultaneously. The risk commonly appears when applications read a value, calculate a replacement outside the database, and later write that stale replacement.

Reproduce the lost update pattern

Run the following workflow using two separate query windows.

Session A — Read the current balance

DECLARE @Balance DECIMAL(12,2);

SELECT @Balance = Balance
FROM dbo.ConcurrentAccount
WHERE AccountId = 1;

SELECT @Balance AS BalanceReadBySessionA;

WAITFOR DELAY '00:00:10';

UPDATE dbo.ConcurrentAccount
SET Balance = @Balance - 2000
WHERE AccountId = 1;

SELECT Balance AS FinalBalance
FROM dbo.ConcurrentAccount
WHERE AccountId = 1;

Session B — Run during Session A's delay

DECLARE @Balance DECIMAL(12,2);

SELECT @Balance = Balance
FROM dbo.ConcurrentAccount
WHERE AccountId = 1;

SELECT @Balance AS BalanceReadBySessionB;

UPDATE dbo.ConcurrentAccount
SET Balance = @Balance - 3000
WHERE AccountId = 1;

SELECT Balance AS FinalBalance
FROM dbo.ConcurrentAccount
WHERE AccountId = 1;

Both sessions can read 10,000 before either performs its update. Session B may write 7,000, followed by Session A writing its stale calculation of 8,000.

Reset the test data before running it again: 

UPDATE dbo.ConcurrentAccount
SET Balance = 10000
WHERE AccountId = 1;

4. Solution 1 — Use Atomic UPDATE Statements

One of the simplest ways to prevent lost updates is to perform the calculation directly inside the UPDATE statement.

Instead of reading and writing a calculated value

-- Avoid this application pattern:
-- 1. SELECT Balance.
-- 2. Calculate a new balance in application code.
-- 3. UPDATE Balance using the old calculation.

Use an atomic update

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - 2000
WHERE AccountId = 1;

The calculation uses the current row value when SQL Server executes the update. Conflicting writers are coordinated by SQL Server's locking mechanisms.

Safe withdrawal with a balance check

DECLARE @WithdrawalAmount DECIMAL(12,2) = 2000;

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - @WithdrawalAmount
WHERE AccountId = 1
  AND Balance >= @WithdrawalAmount;

IF @@ROWCOUNT = 0
BEGIN
    THROW 50001,
        'Account not found or insufficient funds.',
        1;
END;

The balance check and debit are part of the same SQL statement. If two withdrawals compete, SQL Server coordinates the updates. The second statement evaluates the predicate against the applicable current row state after obtaining the required lock.

Why this works

Session A starts update

Requests the necessary write locks.

Session B requests update

Waits if it conflicts with Session A's locks.

Session A completes

Its changes are committed and locks are released.

Session B proceeds

Evaluates and applies its update using the applicable current row value.

5. How SQL Server Locks Rows During Updates

SQL Server uses locks to coordinate concurrent operations. An UPDATE typically acquires an update lock during qualification and converts it to an exclusive lock when modifying the row.

Important lock modes

Lock Purpose
Shared (S) Protects data being read under locking isolation.
Update (U) Used when a row is read with the intention of updating it.
Exclusive (X) Protects data being modified.
Intent Shared (IS) Indicates shared locks exist at a lower level.
Intent Exclusive (IX) Indicates exclusive locks exist at a lower level.
Shared with Intent Exclusive (SIX) Combines shared protection with exclusive intent at a lower level.

Basic lock compatibility

Requested lock Existing S Existing U Existing X
SCompatibleCompatibleBlocked
UCompatibleBlockedBlocked
XBlockedBlockedBlocked

This is a simplified compatibility view. Actual locking behavior also depends on lock granularity, intent locks, isolation level, lock hints, and the query execution plan.

Lock granularity

  • Key or RID lock: Protects an individual index key or heap row.
  • Page lock: Protects an 8 KB data or index page.
  • Table lock: Protects a table or its associated lock resource.
  • Database lock: Protects database-level resources for particular operations.

SQL Server can choose different lock granularities based on workload and execution behavior. It may also escalate many fine-grained locks to a table-level lock.

6. Blocking Between Concurrent Updates

Blocking occurs when one session cannot continue because another session holds an incompatible lock on a resource it needs.

Session A

BEGIN TRANSACTION;

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - 100
WHERE AccountId = 1;

WAITFOR DELAY '00:00:20';

COMMIT TRANSACTION;

Session B

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - 200
WHERE AccountId = 1;

Run Session A first, then run Session B while Session A is waiting. Session B will generally wait for Session A to release its conflicting lock.

Blocking flow

Session A updates row

Obtains an exclusive lock.

Session B requests same row

Requests a conflicting lock.

Session B waits

SQL Server records a blocking relationship.

Session A commits

Its locks are released.

Session B continues

Its update can now proceed.

Find blocked requests

SELECT
    session_id,
    blocking_session_id,
    status,
    wait_type,
    wait_time,
    wait_resource,
    command
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;

Inspect current locks

SELECT
    request_session_id,
    resource_type,
    request_mode,
    request_status,
    resource_description
FROM sys.dm_tran_locks
WHERE resource_database_id = DB_ID()
ORDER BY request_session_id;

These queries provide a snapshot of current activity. A blocking relationship may disappear before the query runs, so capture repeated samples or use monitoring tools when investigating intermittent problems.

7. Pessimistic Concurrency Control

Pessimistic concurrency assumes conflicts are possible and protects data using locks before allowing the relevant modification to proceed.

Use UPDLOCK

UPDLOCK requests update locks for rows read by the query and holds them until the transaction completes. 

BEGIN TRANSACTION;

DECLARE @CurrentBalance DECIMAL(12,2);

SELECT @CurrentBalance = Balance
FROM dbo.ConcurrentAccount WITH (UPDLOCK)
WHERE AccountId = 1;

IF @CurrentBalance >= 1000
BEGIN
    UPDATE dbo.ConcurrentAccount
    SET Balance = @CurrentBalance - 1000
    WHERE AccountId = 1;
END
ELSE
BEGIN
    THROW 50002, 'Insufficient funds.', 1;
END;

COMMIT TRANSACTION;

The update lock helps prevent another session from independently reading the same row with the intention of updating it under conflicting locking behavior.

Use UPDLOCK with HOLDLOCK

BEGIN TRANSACTION;

SELECT Balance
FROM dbo.ConcurrentAccount
    WITH (UPDLOCK, HOLDLOCK)
WHERE AccountId = 1;

-- Perform business validation and update.

COMMIT TRANSACTION;

HOLDLOCK applies SERIALIZABLE semantics to the referenced table for that statement. With UPDLOCK, the update lock is retained through the transaction. Depending on the access path, SQL Server may use key-range locks to protect relevant ranges.

Lock hints are powerful but can reduce concurrency. Prefer a simple atomic UPDATE when it satisfies the business requirement. Add hints only when you understand the required protection and have tested the resulting execution plan and lock behavior.

8. Optimistic Concurrency Control

Optimistic concurrency assumes that conflicts are relatively uncommon. Instead of locking a row for the entire time an application user is editing it, the application checks whether the row has changed before saving.

A typical workflow is:

  1. Read the record and its version value.
  2. Allow the application to edit the data.
  3. Submit the update with the original version.
  4. SQL Server updates only if the version is unchanged.
  5. If no row is updated, report a concurrency conflict.

Example: Create a table with rowversion

DROP TABLE IF EXISTS dbo.ProductInventory;

CREATE TABLE dbo.ProductInventory
(
    ProductId INT PRIMARY KEY,
    ProductName VARCHAR(100) NOT NULL,
    Quantity INT NOT NULL,

    VersionNumber ROWVERSION
);

INSERT INTO dbo.ProductInventory
(
    ProductId,
    ProductName,
    Quantity
)
VALUES
    (1, 'Laptop', 20),
    (2, 'Keyboard', 50);

SELECT *
FROM dbo.ProductInventory;

ROWVERSION is an automatically generated 8-byte binary value. SQL Server changes it whenever a row containing a rowversion column is inserted or updated.

ROWVERSION is not a date or time. It is a database-wide version counter value represented as binary data. It does not tell you when the row was changed.

9. Implement Optimistic Concurrency Using ROWVERSION

Step 1 — Read the row

SELECT
    ProductId,
    ProductName,
    Quantity,
    VersionNumber
FROM dbo.ProductInventory
WHERE ProductId = 1;

Suppose the application receives a quantity of 20 and a version value such as 0x00000000000007D1. The application stores that original version while the user edits the record.

Step 2 — Update using the original version

DECLARE @OriginalVersion BINARY(8) = 0x00000000000007D1;

UPDATE dbo.ProductInventory
SET Quantity = 18
WHERE ProductId = 1
  AND VersionNumber = @OriginalVersion;

IF @@ROWCOUNT = 0
BEGIN
    THROW 50003,
        'Concurrency conflict. The product was modified by another user.',
        1;
END;

The binary value above is illustrative. In a real application, use the exact version value returned by the initial SELECT.

Step 3 — Return the new version

DECLARE @OriginalVersion BINARY(8) = 0x00000000000007D1;

UPDATE dbo.ProductInventory
SET Quantity = 18
OUTPUT
    inserted.ProductId,
    inserted.Quantity,
    inserted.VersionNumber
WHERE ProductId = 1
  AND VersionNumber = @OriginalVersion;

IF @@ROWCOUNT = 0
BEGIN
    THROW 50004,
        'Concurrency conflict. Reload the record before saving.',
        1;
END;

The OUTPUT clause returns the new version generated by SQL Server. The application should retain it for the next update.

10. Demonstrate a ROWVERSION Conflict

This scenario simulates two application users editing the same product.

Initial read by both users

Both users read ProductId 1, Quantity 20, and the same original VersionNumber.

User A saves first

DECLARE @VersionA BINARY(8);

SELECT @VersionA = VersionNumber
FROM dbo.ProductInventory
WHERE ProductId = 1;

UPDATE dbo.ProductInventory
SET Quantity = 18
WHERE ProductId = 1
  AND VersionNumber = @VersionA;

SELECT @@ROWCOUNT AS RowsUpdatedByUserA;

User B saves using the old version

To simulate User B, use the version value captured before User A's update. The following example retrieves a stale version before performing User A's update. 

DECLARE @StaleVersion BINARY(8);

-- Capture the version before another user's update.
SELECT @StaleVersion = VersionNumber
FROM dbo.ProductInventory
WHERE ProductId = 1;

-- Simulate another user changing the row.
UPDATE dbo.ProductInventory
SET Quantity = 17
WHERE ProductId = 1;

-- Attempt to save with the stale version.
UPDATE dbo.ProductInventory
SET Quantity = 15
WHERE ProductId = 1
  AND VersionNumber = @StaleVersion;

SELECT @@ROWCOUNT AS RowsUpdatedByUserB;

Expected result for the second update: 0 rows affected. The row has changed since the stale version was captured.

Why optimistic concurrency is useful

  • Prevents silent overwriting of another user's changes.
  • Allows users to edit data without holding database locks for the entire editing session.
  • Works well for web applications and business forms.
  • Provides an explicit conflict signal for application handling.

11. Pessimistic vs Optimistic Concurrency

Aspect Pessimistic Optimistic
Approach Locks data to prevent conflicting work. Checks whether data changed before saving.
Typical mechanism UPDATE locks, exclusive locks, UPDLOCK. ROWVERSION or original-value comparison.
Conflict handling Other sessions may wait. Conflicting update is rejected.
Good fit High-conflict critical updates. Low-conflict interactive applications.

12. Isolation Levels and Concurrent Updates

Isolation levels influence how transactions read data and how locks or row versions are used. They do not eliminate the need for correct update logic.

Isolation level Read behavior Update considerations
READ UNCOMMITTED Can read uncommitted changes. Does not provide safe application-level read-calculate-write behavior.
READ COMMITTED Prevents dirty reads. Write locks coordinate conflicting updates.
REPEATABLE READ Retains shared locks on read rows until transaction end. Can increase blocking.
SERIALIZABLE Protects qualifying key ranges against phantom changes. Provides stronger protection but may reduce concurrency.
SNAPSHOT Reads a transactionally consistent row-versioned snapshot. Can raise an update conflict if the row changed after the snapshot began.

Important SNAPSHOT behavior

Under SNAPSHOT isolation, if a transaction tries to update a row that has been modified by another transaction since its snapshot was established, SQL Server can terminate the transaction with an update conflict. 

-- Enable SNAPSHOT isolation at database level.
ALTER DATABASE YourDatabaseName
SET ALLOW_SNAPSHOT_ISOLATION ON;
GO

-- Run in a session after enabling the option.
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

BEGIN TRANSACTION;

SELECT *
FROM dbo.ConcurrentAccount
WHERE AccountId = 1;

-- Perform additional work here.

COMMIT TRANSACTION;

A SNAPSHOT transaction that encounters an update conflict must be rolled back. The application can then reload the current values and retry the complete business operation if appropriate.

13. Use SERIALIZABLE to Protect a Business Rule

Consider a reservation system where only one reservation is allowed for a particular seat and show. 

DROP TABLE IF EXISTS dbo.SeatReservation;

CREATE TABLE dbo.SeatReservation
(
    ReservationId INT IDENTITY PRIMARY KEY,
    ShowId INT NOT NULL,
    SeatNumber VARCHAR(10) NOT NULL,
    CustomerName VARCHAR(100) NOT NULL,

    CONSTRAINT UQ_Show_Seat
        UNIQUE (ShowId, SeatNumber)
);

The unique constraint is the strongest direct protection against duplicate reservations for the same show and seat. The application should still handle duplicate-key errors cleanly.

Attempt to reserve a seat

DECLARE @ShowId INT = 100;
DECLARE @SeatNumber VARCHAR(10) = 'A10';

BEGIN TRY

    INSERT INTO dbo.SeatReservation
    (
        ShowId,
        SeatNumber,
        CustomerName
    )
    VALUES
    (
        @ShowId,
        @SeatNumber,
        'Alice'
    );

    SELECT 'Reservation successful' AS Result;

END TRY
BEGIN CATCH

    IF ERROR_NUMBER() IN (2601, 2627)
        SELECT 'Seat already reserved' AS Result;
    ELSE
        THROW;

END CATCH;

A unique index protects the rule even when two sessions attempt to insert the same reservation simultaneously. Only one can successfully create the duplicate key.

14. Avoid Race Conditions with Conditional Updates

A race condition occurs when the result of an operation depends on the timing or ordering of concurrent operations.

Unsafe inventory pattern

-- Application reads quantity first.
SELECT Quantity
FROM dbo.ProductInventory
WHERE ProductId = 1;

-- Application later decides whether enough stock exists.
-- Another transaction could change the quantity in between.

Safer inventory update

DECLARE @RequestedQuantity INT = 2;

UPDATE dbo.ProductInventory
SET Quantity = Quantity - @RequestedQuantity
WHERE ProductId = 1
  AND Quantity >= @RequestedQuantity;

IF @@ROWCOUNT = 0
BEGIN
    THROW 50005,
        'Product not found or insufficient stock.',
        1;
END;

The availability check and quantity reduction occur in the same statement. This is usually simpler and safer than separately reading, checking, and updating the quantity.

15. Deadlocks During Concurrent Updates

A deadlock occurs when two or more sessions each hold resources needed by the others, forming a cycle of dependencies. SQL Server detects the cycle and selects a transaction as the deadlock victim.

Example

Session A:

BEGIN TRANSACTION;

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - 100
WHERE AccountId = 1;

WAITFOR DELAY '00:00:05';

UPDATE dbo.ConcurrentAccount
SET Balance = Balance + 100
WHERE AccountId = 2;

COMMIT TRANSACTION;

Session B:

BEGIN TRANSACTION;

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - 100
WHERE AccountId = 2;

WAITFOR DELAY '00:00:05';

UPDATE dbo.ConcurrentAccount
SET Balance = Balance + 100
WHERE AccountId = 1;

COMMIT TRANSACTION;

If both sessions acquire their first lock before requesting the other account, each may wait for the other. SQL Server can detect the deadlock and roll back one transaction.

Prevent this pattern by using a consistent order

Both transactions should access accounts in the same order. For example, always update the lower AccountId first. 

BEGIN TRY

    BEGIN TRANSACTION;

    -- First update AccountId 1.
    UPDATE dbo.ConcurrentAccount
    SET Balance = Balance - 100
    WHERE AccountId = 1;

    -- Then update AccountId 2.
    UPDATE dbo.ConcurrentAccount
    SET Balance = Balance + 100
    WHERE AccountId = 2;

    COMMIT TRANSACTION;

END TRY
BEGIN CATCH

    IF XACT_STATE() <> 0
        ROLLBACK TRANSACTION;

    THROW;

END CATCH;

Consistent access order reduces one common source of deadlocks. It does not eliminate every possible deadlock, so applications should still handle deadlock error 1205.

16. Handle Deadlock Errors with Safe Retries

SQL Server reports error 1205 to the deadlock victim. An application can retry the complete transaction after a short delay, provided the business operation is safe to retry.

Example T-SQL retry pattern

DECLARE @Attempt INT = 1;
DECLARE @MaxAttempts INT = 3;
DECLARE @Completed BIT = 0;

WHILE @Attempt <= @MaxAttempts
  AND @Completed = 0
BEGIN
    BEGIN TRY

        BEGIN TRANSACTION;

        UPDATE dbo.ConcurrentAccount
        SET Balance = Balance - 100
        WHERE AccountId = 1;

        UPDATE dbo.ConcurrentAccount
        SET Balance = Balance + 100
        WHERE AccountId = 2;

        COMMIT TRANSACTION;

        SET @Completed = 1;

    END TRY
    BEGIN CATCH

        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;

        IF ERROR_NUMBER() = 1205
           AND @Attempt < @MaxAttempts
        BEGIN
            SET @Attempt += 1;

            WAITFOR DELAY '00:00:01';
        END
        ELSE
        BEGIN
            THROW;
        END;

    END CATCH;
END;

This is an illustrative retry pattern. Production applications should use bounded exponential backoff with jitter where appropriate, log retry attempts, and ensure the complete business operation is safe to execute again.

Do not blindly retry every database error. A timeout or connection failure can leave the application uncertain about whether a commit succeeded. Use idempotency keys or another reliable request-tracking strategy when duplicate execution would cause incorrect business results.

17. Inspect Transaction and Session Information

Find sessions with open transactions

SELECT
    s.session_id,
    s.login_name,
    s.host_name,
    s.program_name,
    s.status,
    s.open_transaction_count
FROM sys.dm_exec_sessions AS s
WHERE s.is_user_process = 1
  AND s.open_transaction_count > 0
ORDER BY s.open_transaction_count DESC;

Find active transactions

SELECT
    st.session_id,
    at.transaction_id,
    at.name AS TransactionName,
    at.transaction_begin_time,
    at.transaction_state
FROM sys.dm_tran_session_transactions AS st
JOIN sys.dm_tran_active_transactions AS at
    ON st.transaction_id = at.transaction_id
ORDER BY at.transaction_begin_time;

Find blocking chains

SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_time,
    wait_resource,
    status,
    command
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0
   OR session_id IN
      (
          SELECT blocking_session_id
          FROM sys.dm_exec_requests
          WHERE blocking_session_id <> 0
      );

These diagnostic queries may require appropriate server permissions. Depending on SQL Server version, viewing server state may require VIEW SERVER STATE or VIEW SERVER PERFORMANCE STATE.

18. SQL Server Internals: What Happens During an UPDATE?

A typical UPDATE involves several internal components:

Query compilation

SQL Server creates or reuses an execution plan.

Access data

The execution plan locates the target row through an index or scan.

Acquire locks

SQL Server requests the locks required by the operation.

Modify buffer pages

The affected data page is modified in memory.

Generate log records

Changes are recorded in the transaction log.

Commit

Required log records are hardened for a fully durable commit.

Important execution plan operators

  • Index Seek: Locates rows using an index key.
  • Index Scan: Reads an index range or the entire index.
  • Clustered Index Update: Modifies rows in a clustered index.
  • Table Update: Modifies rows in a heap.
  • Index Update: Maintains affected nonclustered indexes.
  • Sort: May be used to prepare rows for an operation or optimize access order.

The actual plan depends on indexes, predicates, statistics, cardinality estimates, SQL Server version, and optimizer choices.

19. Performance Optimization for Concurrent Updates

1. Create useful indexes

An index on the columns used to locate a row can reduce the number of rows SQL Server must examine and can reduce unnecessary lock acquisition. 

CREATE INDEX IX_ConcurrentAccount_AccountId
ON dbo.ConcurrentAccount(AccountId);

In this example, AccountId is already the primary key and therefore has a supporting index. The additional index is unnecessary and is shown only to illustrate the syntax.

2. Keep transactions short

Do not perform unrelated application operations, file uploads, user interactions, or long-running calculations while holding database locks.

3. Update only required columns

UPDATE dbo.ConcurrentAccount
SET Balance = Balance - 100
WHERE AccountId = 1;

4. Avoid unnecessary scans

Ensure that update predicates are supported by appropriate indexes. A poorly selective update can touch many rows and increase lock duration and transaction-log activity.

5. Monitor waits and blocking

SELECT
    wait_type,
    waiting_tasks_count,
    wait_time_ms,
    max_wait_time_ms
FROM sys.dm_os_wait_stats
WHERE wait_type LIKE 'LCK%'
ORDER BY wait_time_ms DESC;

Wait statistics are cumulative since the last reset or server start. They should be interpreted alongside workload timing and other diagnostic evidence.

20. Production Design Patterns

Pattern A — Atomic counter increment

UPDATE dbo.ProductInventory
SET Quantity = Quantity + 1
WHERE ProductId = 1;

Use a database-side expression rather than reading the existing value into application code and writing a calculated replacement later.

Pattern B — Conditional stock reservation

DECLARE @RequestedQuantity INT = 3;

UPDATE dbo.ProductInventory
SET Quantity = Quantity - @RequestedQuantity
WHERE ProductId = 1
  AND Quantity >= @RequestedQuantity;

IF @@ROWCOUNT = 0
BEGIN
    THROW 50006, 'Insufficient inventory.', 1;
END;

Pattern C — Optimistic update with ROWVERSION

UPDATE dbo.ProductInventory
SET Quantity = 15
WHERE ProductId = 1
  AND VersionNumber = @OriginalVersion;

IF @@ROWCOUNT = 0
BEGIN
    THROW 50007, 'Record changed. Reload and try again.', 1;
END;

Pattern D — Prevent duplicate operations

For operations such as payment processing or order submission, a unique request identifier can help prevent duplicate processing when clients retry requests. 

CREATE TABLE dbo.ProcessedRequest
(
    RequestId UNIQUEIDENTIFIER NOT NULL
        CONSTRAINT PK_ProcessedRequest PRIMARY KEY,

    ProcessedAt DATETIME2 NOT NULL
        CONSTRAINT DF_ProcessedRequest_ProcessedAt
        DEFAULT SYSUTCDATETIME()
);

Insert the request identifier and perform the associated database changes in the same transaction. A duplicate key indicates that the request identifier has already been used. The application must also define how to return the result of an earlier successful request.

21. Common Mistakes

  • Reading a value, calculating a replacement in application code, and writing stale data later.
  • Assuming READ COMMITTED prevents every application-level lost update.
  • Holding transactions open while waiting for user input.
  • Using UPDLOCK or HOLDLOCK everywhere without understanding the impact.
  • Assuming ROWVERSION represents a date or timestamp.
  • Ignoring the possibility of deadlocks.
  • Retrying transactions without ensuring that the operation is safe to repeat.
  • Using a SELECT followed by an UPDATE when a single conditional UPDATE would work.
  • Failing to check @@ROWCOUNT after a conditional update.
  • Assuming an application timeout proves that a transaction did not commit.

23. Knowledge Check

Question 1

What is a lost update?

  • A. A database backup failure.
  • B. One update overwrites another user's intended change.
  • C. An index becomes fragmented.
  • D. A transaction is automatically committed.

Answer: B — A stale calculated value can overwrite a newer value.

Question 2

Which technique is often simplest for a counter increment?

  • A. Read, calculate, and write in separate application operations.
  • B. Use an atomic UPDATE expression.
  • C. Disable locking.
  • D. Use READ UNCOMMITTED.

Answer: B — SQL Server applies the calculation as part of the update statement.

Question 3

What does ROWVERSION provide?

  • A. A human-readable date.
  • B. A row change version value.
  • C. A transaction isolation level.
  • D. A backup identifier.

Answer: B — ROWVERSION changes when a row containing that column is updated.

Question 4

What does UPDLOCK request?

  • A. An update lock on rows read by the query.
  • B. A database backup.
  • C. A table deletion.
  • D. A shared snapshot.

Answer: A — UPDLOCK requests update locks and holds them until the transaction completes.

Question 5

What is blocking?

  • A. A query waiting for an incompatible lock.
  • B. A query running without indexes.
  • C. A transaction-log backup.
  • D. A failed database connection.

Answer: A — One session waits for another session to release a conflicting resource.

Question 6

Which SQL Server error is commonly associated with a deadlock victim?

  • A. 2627
  • B. 1205
  • C. 208
  • D. 245

Answer: B — Error 1205 indicates that the transaction was chosen as a deadlock victim.

Question 7

Why use a conditional inventory UPDATE?

  • A. To disable concurrent transactions.
  • B. To check stock and reduce it within one statement.
  • C. To remove all indexes.
  • D. To avoid transaction logging.

Answer: B — The condition and update are evaluated as one database operation.

24. Key Takeaways

  • Concurrent updates occur when multiple sessions modify shared data.
  • Lost updates often result from application-level read-calculate-write patterns.
  • Atomic UPDATE statements are a strong default for counters, balances, and inventory changes.
  • SQL Server uses locks to coordinate conflicting writes.
  • Blocking occurs when a session waits for an incompatible lock.
  • Pessimistic concurrency uses locks to protect data.
  • Optimistic concurrency detects changes using ROWVERSION or original values.
  • Isolation levels affect read consistency and concurrency behavior.
  • Consistent resource access order helps reduce deadlocks.
  • Production applications should handle conflicts, deadlocks, retries, and uncertain request outcomes carefully.

Reliable concurrent update design is essential for banking, inventory, order processing, booking, and other multi-user systems. The best solution usually combines atomic SQL operations, appropriate constraints, short transactions, and a concurrency strategy suited to the workload.
