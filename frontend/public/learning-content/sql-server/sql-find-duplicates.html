Find Duplicate Rows by Business Key in SQL Server

Learn how to identify duplicate records using business keys, GROUP BY, HAVING, composite keys, and practical SQL Server queries. Understand how duplicate data affects real-world applications and how to prevent it.

1. What Are Duplicate Rows?

Duplicate rows are records that represent the same business entity or business information more than once.

In real-world applications, duplicate records can occur because of:

  • A user submitting the same form multiple times.
  • An application retrying a failed database request.
  • Importing the same file more than once.
  • Missing validation in an application.
  • Incorrect data migration.
  • Multiple systems creating the same business record.

Real-world example

A company maintains customer records. The customer registration system accidentally inserts the same customer twice with the same email address. The records have different CustomerId values, but both represent the same customer.

Our task is to identify such duplicate records.

2. What Is a Business Key?

A business key is an attribute, or a combination of attributes, that identifies a business entity according to business rules.

Example: Customer table

CustomerId CustomerName Email
101 John Smith john@example.com
102 John Smith john@example.com
103 Mary Johnson mary@example.com

CustomerId is the primary key. It uniquely identifies each database row.

Email is the business key in this example, assuming the business rule says that each customer must have a unique email address.

Important distinction: Different primary keys do not necessarily mean that the records represent different business entities.

Primary key vs business key

Primary Key Business Key
Identifies a database row. Identifies a business entity.
Often an identity or generated value. Comes from business rules.
Example: CustomerId. Example: Email or CustomerCode.
Usually unique by database constraint. Should be unique according to business rules.

4. Find Duplicate Rows Using GROUP BY

GROUP BY groups records that have the same values in the selected columns.

When we group by a business key, all records with the same business key are placed in the same group.

Basic query


SELECT
    CustomerCode,
    COUNT(*) AS DuplicateCount
FROM Customers
GROUP BY CustomerCode;

Result

CustomerCode DuplicateCount
C0012
C0021
C0032
C0041
C0052

This query displays the number of records in each CustomerCode group. It does not yet filter out groups that occur only once.

How GROUP BY works

Input rows

8 customer records

GROUP BY

Group by CustomerCode

COUNT

Count records per group

Result

5 groups

5. Use HAVING to Find Only Duplicate Groups

HAVING filters groups created by GROUP BY.

A group is considered duplicated when its record count is greater than one.

Query


SELECT
    CustomerCode,
    COUNT(*) AS DuplicateCount
FROM Customers
GROUP BY CustomerCode
HAVING COUNT(*) > 1;

Result

CustomerCode DuplicateCount
C0012
C0032
C0052
Key concept: GROUP BY creates groups. HAVING filters those groups. COUNT(*) counts the rows in each group.

6. Retrieve the Complete Rows That Are Duplicated

The previous query returns only CustomerCode and its count. In a real application, we often need the complete customer records.

One approach is to identify duplicate business keys first and then join them back to the original table.

Query using a CTE


WITH DuplicateCustomers AS
(
    SELECT
        CustomerCode
    FROM Customers
    GROUP BY CustomerCode
    HAVING COUNT(*) > 1
)
SELECT
    c.CustomerId,
    c.CustomerCode,
    c.CustomerName,
    c.Email,
    c.City
FROM Customers AS c
INNER JOIN DuplicateCustomers AS d
    ON c.CustomerCode = d.CustomerCode
ORDER BY c.CustomerCode, c.CustomerId;

Result

CustomerId CustomerCode CustomerName Email City
1C001John Smithjohn@example.comPune
2C001John Smithjohn@example.comPune
4C003David Browndavid@example.comDelhi
5C003David Browndavid@example.comDelhi
7C005Robert Millerrobert@example.comChennai
8C005Robert Millerrobert@example.comChennai

The CTE identifies duplicated CustomerCode values. The JOIN retrieves every original row belonging to those duplicate groups.

7. Find Duplicates Using a Composite Business Key

A business key does not always consist of a single column. Sometimes multiple columns together identify a business record.

Real-world example

An employee's attendance record may be uniquely identified by:

  • EmployeeId
  • AttendanceDate

The business rule is that an employee should have only one attendance record per day.

Create a sample attendance table


CREATE TABLE EmployeeAttendance
(
    AttendanceId INT IDENTITY(1,1) PRIMARY KEY,
    EmployeeId INT NOT NULL,
    AttendanceDate DATE NOT NULL,
    Status VARCHAR(20)
);

INSERT INTO EmployeeAttendance
    (EmployeeId, AttendanceDate, Status)
VALUES
    (101, '2026-11-01', 'Present'),
    (101, '2026-11-01', 'Present'),
    (101, '2026-11-02', 'Present'),
    (102, '2026-11-01', 'Absent'),
    (102, '2026-11-01', 'Absent'),
    (103, '2026-11-01', 'Present');

Find duplicate attendance records


SELECT
    EmployeeId,
    AttendanceDate,
    COUNT(*) AS DuplicateCount
FROM EmployeeAttendance
GROUP BY
    EmployeeId,
    AttendanceDate
HAVING COUNT(*) > 1;

Result

EmployeeId AttendanceDate DuplicateCount
1012026-11-012
1022026-11-012
Important: When checking a composite business key, include every column that participates in the business uniqueness rule. Grouping by only EmployeeId would incorrectly treat different attendance dates as duplicates.

8. Business Duplicates vs Exact Duplicate Rows

These two concepts are related, but they are not necessarily the same.

Business duplicates

Two records have the same business key even if some other attributes are different.

CustomerId Email City
101john@example.comPune
102john@example.comMumbai

If Email is the business key, these records are business duplicates even though City is different.

Exact duplicate business data

Two records contain the same values across all selected business columns.

For example, the same CustomerCode, CustomerName, Email and City appear more than once. 


SELECT
    CustomerCode,
    CustomerName,
    Email,
    City,
    COUNT(*) AS DuplicateCount
FROM Customers
GROUP BY
    CustomerCode,
    CustomerName,
    Email,
    City
HAVING COUNT(*) > 1;

This query checks duplication across all four selected columns, rather than CustomerCode alone.

9. How NULL Values Affect Duplicate Detection

SQL Server GROUP BY places NULL values into the same group for a grouped column.

Therefore, multiple rows with a NULL CustomerCode will appear as one group when grouped by CustomerCode.

Example


SELECT
    CustomerCode,
    COUNT(*) AS RecordCount
FROM Customers
GROUP BY CustomerCode
HAVING COUNT(*) > 1;

If multiple CustomerCode values are NULL, the NULL group will also satisfy COUNT(*) greater than one.

Business consideration: Decide whether missing business keys should be treated as duplicate groups, ignored, or handled as data-quality errors. The correct choice depends on the business rule.

Exclude NULL business keys


SELECT
    CustomerCode,
    COUNT(*) AS DuplicateCount
FROM Customers
WHERE CustomerCode IS NOT NULL
GROUP BY CustomerCode
HAVING COUNT(*) > 1;

WHERE filters individual rows before grouping. This query excludes rows whose CustomerCode is NULL.

10. Case Sensitivity and Whitespace

Text comparisons and grouping depend on the collation of the relevant SQL Server expression or column.

Under a case-insensitive collation, values such as john@example.com and JOHN@example.com may be treated as equal.

Under a case-sensitive collation, they can be treated as different values.

Inspect the column collation


SELECT
    COLUMN_NAME,
    COLLATION_NAME
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Customers'
  AND COLUMN_NAME = 'Email';

Check values after trimming surrounding spaces


SELECT
    LTRIM(RTRIM(Email)) AS NormalizedEmail,
    COUNT(*) AS DuplicateCount
FROM Customers
WHERE Email IS NOT NULL
GROUP BY LTRIM(RTRIM(Email))
HAVING COUNT(*) > 1;

LTRIM and RTRIM remove leading and trailing ordinary space characters. They do not provide complete normalization for every possible whitespace or Unicode character.

Do not normalize business keys blindly. For example, case sensitivity may be meaningful in some systems. Follow the business definition of equality.

11. Performance Considerations

Finding duplicates using GROUP BY can require SQL Server to process a large number of rows.

Depending on available indexes, statistics, data distribution and memory, SQL Server may use operators such as:

  • Index Scan
  • Table Scan
  • Sort
  • Stream Aggregate
  • Hash Match Aggregate

Index on the business key


CREATE NONCLUSTERED INDEX IX_Customers_CustomerCode
ON Customers(CustomerCode);

An index can provide an ordered access path for grouping by CustomerCode and may help some queries. It does not guarantee that SQL Server will use the index or that the query will always be faster.

Check logical reads and execution time


SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    CustomerCode,
    COUNT(*) AS DuplicateCount
FROM Customers
GROUP BY CustomerCode
HAVING COUNT(*) > 1;

SET STATISTICS TIME OFF;
SET STATISTICS IO OFF;

In SQL Server Management Studio, enable the Actual Execution Plan and inspect the actual plan, logical reads, row counts and execution operators.

12. How to Prevent Duplicate Business Keys

Identifying duplicates is useful, but preventing unwanted duplicates is even more important.

If CustomerCode must be unique and existing data satisfies that rule, create a unique index: 


CREATE UNIQUE NONCLUSTERED INDEX
    UX_Customers_CustomerCode
ON Customers(CustomerCode);
Important: This statement will fail if duplicate non-NULL CustomerCode values already exist. SQL Server unique indexes also enforce uniqueness for NULL keys according to SQL Server's unique-index rules. Clean and validate the data before creating the index.

For a composite business key, use a unique index containing all key columns. 


CREATE UNIQUE NONCLUSTERED INDEX
    UX_EmployeeAttendance_Employee_Date
ON EmployeeAttendance(EmployeeId, AttendanceDate);

This prevents multiple attendance records for the same employee on the same date.

13. Production-Level Considerations

1. Identify the correct business key

Do not assume that every repeated column value represents a duplicate. Confirm the business rules with the application or data owner.

2. Check historical and valid records

Some systems intentionally allow multiple records for the same customer, such as multiple addresses, subscriptions or historical versions.

3. Consider soft-deleted records

If the application has an IsDeleted or IsActive column, determine whether deleted or inactive records should participate in duplicate detection.

4. Consider concurrent inserts

An application-side check followed by an INSERT is not sufficient to guarantee uniqueness when multiple requests arrive simultaneously.

A database unique constraint or unique index provides the final enforcement. The application should handle duplicate-key errors appropriately.

5. Do not delete records immediately

First identify duplicate groups, inspect the records, understand which one is authoritative and check dependencies such as orders, invoices and audit history.

Deleting duplicate records is a separate operation that requires a carefully defined retention rule.

14. Common Mistakes

  • Grouping by the primary key instead of the business key.
  • Forgetting to use HAVING COUNT(*) greater than one.
  • Checking only one column when the business key consists of multiple columns.
  • Treating every repeated name as a duplicate customer.
  • Ignoring NULL, case-sensitivity and whitespace rules.
  • Assuming an index automatically makes duplicate detection fast.
  • Running a duplicate cleanup without checking foreign-key dependencies and business history.
