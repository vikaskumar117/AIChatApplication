Slow Query Optimization Method in SQL Server

Learn a systematic, production-oriented approach to diagnosing slow SQL queries, identifying bottlenecks, analyzing execution plans, improving indexes, reducing logical reads, and validating performance improvements.

1. Learning Objectives

  • Identify why a SQL Server query is slow.
  • Distinguish CPU, I/O, memory, blocking, and network problems.
  • Measure query performance before making changes.
  • Analyze execution plans and expensive operators.
  • Identify table scans, key lookups, sorts, and spills.
  • Optimize queries using appropriate indexes.
  • Rewrite non-SARGable predicates.
  • Understand parameter sniffing and cardinality estimation.
  • Use Query Store and DMVs for investigation.
  • Validate improvements safely in production.

2. What Is Query Optimization?

Query optimization is the process of improving a SQL query so that SQL Server can retrieve or modify the required data using fewer resources.

A query may be slow because it:

  • Reads too many data pages.
  • Performs expensive joins.
  • Uses inefficient indexes.
  • Processes more rows than necessary.
  • Performs unnecessary sorting or aggregation.
  • Waits for locks held by another transaction.
  • Experiences memory pressure or tempdb spills.
  • Receives an inefficient execution plan.
  • Transfers too much data to the application.
A slow query is not always a query-writing problem. The cause may be an index, blocking session, resource bottleneck, inaccurate statistics, parameter-sensitive plan, or application behavior.

3. Understand the Query Optimization Process

Use a consistent process instead of randomly changing SQL statements or creating indexes.

Step 1: Identify the slow query

Find the exact query, execution frequency, and affected users.

Step 2: Establish a baseline

Measure elapsed time, CPU time, logical reads, and row counts.

Step 3: Identify the bottleneck

Determine whether the query is CPU-bound, I/O-bound, blocked, or waiting for resources.

Step 4: Inspect the execution plan

Find expensive operators, cardinality problems, and missing access paths.

Step 5: Optimize

Improve predicates, indexes, joins, filtering, or query structure.

Step 6: Validate

Compare the new execution plan and measured resource usage.

Step 7: Monitor

Confirm that the improvement is stable under real workload conditions.

5. Step One — Identify the Slow Query

Before optimizing anything, identify which query is actually slow.

Common sources include:

  • Application monitoring and database logs.
  • SQL Server Query Store.
  • Dynamic Management Views.
  • Extended Events.
  • SQL Server monitoring tools.

Find currently executing requests

SELECT
    R.session_id,
    R.status,
    R.command,
    R.cpu_time,
    R.total_elapsed_time,
    R.logical_reads,
    R.reads,
    R.writes,
    R.wait_type,
    R.blocking_session_id,
    DB_NAME(R.database_id) AS DatabaseName,
    SUBSTRING
    (
        T.text,
        (R.statement_start_offset / 2) + 1,
        (
            (
                CASE R.statement_end_offset
                    WHEN -1 THEN DATALENGTH(T.text)
                    ELSE R.statement_end_offset
                END
                - R.statement_start_offset
            ) / 2
        ) + 1
    ) AS RunningStatement
FROM sys.dm_exec_requests AS R
CROSS APPLY sys.dm_exec_sql_text(R.sql_handle) AS T
WHERE R.session_id <> @@SPID
ORDER BY R.total_elapsed_time DESC;

Important columns

Column Meaning
cpu_timeCPU time consumed by the request, in milliseconds.
total_elapsed_timeTotal elapsed time, in milliseconds.
logical_readsNumber of logical page reads.
readsPhysical reads reported for the request.
writesWrites performed by the request.
wait_typeCurrent or most recent wait type for the request.
blocking_session_idSession currently blocking this request, if any.
These values are useful diagnostic signals, not a complete diagnosis by themselves. For example, physical reads can be affected by caching, and a query with low CPU time may still spend a long time waiting for another transaction.

6. Step Two — Establish a Performance Baseline

Always measure the original query before modifying it. Otherwise, you cannot reliably determine whether your optimization improved performance.

Enable performance statistics

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    OrderId,
    CustomerId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = 500;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

In SQL Server Management Studio, the messages tab displays logical reads, physical reads, CPU time, and elapsed time.

Understand STATISTICS IO

Example illustrative output:

Table 'Orders'.
Scan count 1,
logical reads 850,
physical reads 0,
read-ahead reads 0.
Metric Meaning
Logical readsPages accessed from the SQL Server buffer pool.
Physical readsPages read from storage into memory.
Read-ahead readsPages read ahead of demand by the storage engine.
Scan countNumber of scan or seek operations reported for the table access.

Understand STATISTICS TIME

Example illustrative output:

SQL Server Execution Times:
CPU time = 120 ms,
elapsed time = 180 ms.
  • CPU time measures processing time on the CPU.
  • Elapsed time measures total wall-clock execution time.

Elapsed time can be greater than CPU time because a query may spend time waiting for I/O, locks, memory grants, or other resources.

Do not rely on a single execution. Cache state, concurrency, compilation, parallelism, and storage activity can change measurements. Compare repeated executions under reasonably consistent conditions.

7. Step Three — Understand the Type of Bottleneck

Different bottlenecks require different solutions. Adding an index will not fix every performance problem.

7.1 CPU-bound queries

A CPU-bound query spends a large amount of time performing calculations, joins, sorting, aggregation, or processing many rows.

Potential causes:

  • Large scans and expensive joins.
  • Complex scalar expressions.
  • Repeated computations.
  • Excessive row processing.

Potential solutions:

  • Reduce the number of rows processed.
  • Improve filtering and join conditions.
  • Remove unnecessary calculations.
  • Review expensive operators in the execution plan.

7.2 I/O-bound queries

An I/O-bound query spends substantial time accessing data pages from storage or waiting for data access.

Potential causes:

  • Large table scans.
  • Missing or unsuitable indexes.
  • Retrieving unnecessary columns.
  • Reading a large number of rows.

Potential solutions:

  • Build appropriate indexes.
  • Return only required columns.
  • Improve selective predicates.
  • Reduce unnecessary data access.

7.3 Blocking and locking

A query may be slow because another transaction holds incompatible locks. 

SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_time,
    wait_resource
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;

Common blocking-related waits include LCK_M_* wait types.

Potential solutions:

  • Find the blocking transaction.
  • Keep transactions short.
  • Review transaction isolation requirements.
  • Ensure indexes support frequently executed statements.
  • Consider row versioning where appropriate.

Do not automatically kill a blocking session. First inspect the transaction, its business purpose, and rollback impact.

7.4 Memory and tempdb pressure

Sort and hash operations may need memory grants. If memory is insufficient, SQL Server may spill intermediate data to tempdb.

Potential indicators:

  • Sort warnings.
  • Hash warnings.
  • Spill information in execution plans.
  • Long-running sorts and hash joins.

Investigate row estimates, memory grants, indexes that provide useful ordering, and the amount of data processed.

7.5 Network and application delays

SQL Server may complete a query quickly while the application remains slow because it transfers too many rows or performs expensive client-side processing.

Potential solutions:

  • Return only required columns.
  • Apply filtering in SQL Server.
  • Implement pagination where appropriate.
  • Review application data-reading behavior.

8. Step Four — Identify Table Scans and Index Scans

SQL Server uses scans and seeks to access data. A scan is not automatically bad, and a seek is not automatically good. The important question is how much work the operation performs relative to the rows returned.

Table Scan

A table scan reads the data pages of a heap to locate qualifying rows. 

SELECT *
FROM dbo.Orders
WHERE CustomerId = 500;

If no useful index exists, SQL Server may scan the table.

Clustered Index Scan

If a table has a clustered index, SQL Server may scan the clustered index to evaluate the predicate.

Index Seek

An index seek navigates the index structure to locate a range or key value.

Index Scan

An index scan reads index entries. It may be efficient when the index is smaller than the base table or when a large proportion of rows is needed.

Operator Typical behavior What to investigate
Table ScanReads heap data pages.Could a selective index help?
Clustered Index ScanReads clustered index rows.Are too many rows being processed?
Index ScanReads index entries.Is the scan appropriate for the result size?
Index SeekNavigates index keys.Are residual predicates or lookups expensive?

9. Step Five — Optimize Using an Index

Let's optimize the original query that retrieves orders for a specific customer.

Original query

SELECT
    OrderId,
    CustomerId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = 500;

Without a suitable index, SQL Server may need to scan many rows.

Create a nonclustered index

CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON dbo.Orders(CustomerId);

Execute the query again

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    OrderId,
    CustomerId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = 500;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

SQL Server can now use the index to locate matching customer records. However, the index does not contain OrderDate or TotalAmount.

Depending on the selected plan, SQL Server may perform Key Lookup operations to retrieve those columns from the clustered index.

Understand Key Lookup

Index Seek

Find the matching CustomerId entries.

Read row locators

Obtain the clustered key for each matching entry.

Key Lookup

Retrieve additional requested columns from the clustered index.

Return results

Produce the final rows.

Create a covering index

CREATE NONCLUSTERED INDEX IX_Orders_CustomerId_Covering
ON dbo.Orders(CustomerId)
INCLUDE
(
    OrderDate,
    TotalAmount
);

The clustered key OrderId is automatically available in a nonclustered index on a clustered table as its row locator. Therefore, the query's requested columns can be satisfied from this index without a separate Key Lookup.

Covering indexes can reduce lookup operations, but they increase storage and write-maintenance costs. Do not add every output column to every index.

10. Step Six — Optimize Composite Indexes

A composite index contains multiple key columns. Column order matters because SQL Server organizes the index by the key sequence.

Example query

SELECT
    OrderId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = 500
  AND OrderStatus = 'Completed';

Create a composite index

CREATE NONCLUSTERED INDEX IX_Orders_Customer_Status
ON dbo.Orders
(
    CustomerId,
    OrderStatus
)
INCLUDE
(
    OrderDate,
    TotalAmount
);

The index first orders entries by CustomerId, then OrderStatus within each CustomerId value.

Why column order matters

Index definition Example access pattern
(CustomerId, OrderStatus) Useful for CustomerId alone and for CustomerId plus OrderStatus.
(OrderStatus, CustomerId) Useful for OrderStatus alone and for both columns.

An index may still be useful in other access patterns, depending on predicates and plan choices, but its leading key strongly influences efficient navigation.

Choose key order based on actual query patterns, selectivity, range predicates, joins, and ordering requirements rather than applying a universal rule.

11. Step Seven — Make Predicates SARGable

SARGable means a predicate can be used effectively as a search argument for an index access method.

Applying functions or conversions to indexed columns can prevent an efficient seek or make it less likely.

Example A — Function on an indexed column

Potentially inefficient predicate:

SELECT *
FROM dbo.Orders
WHERE YEAR(OrderDate) = 2026;

SQL Server may need to evaluate YEAR() for many rows rather than directly navigating an index range on OrderDate.

Rewrite using a date range

SELECT *
FROM dbo.Orders
WHERE OrderDate >= '20260101'
  AND OrderDate <  '20270101';

The range predicate can use an index on OrderDate more effectively.

Example B — Function on a text column

Potentially inefficient:

SELECT *
FROM dbo.Orders
WHERE UPPER(Region) = 'NORTH';

Possible rewrite:

SELECT *
FROM dbo.Orders
WHERE Region = 'North';

This rewrite assumes the database collation and business rules make the comparison equivalent. Case sensitivity, accent sensitivity, and other collation rules matter.

Example C — Leading wildcard

Often difficult to seek efficiently with a normal B-tree index:

SELECT *
FROM dbo.Orders
WHERE Region LIKE '%orth';

A leading wildcard prevents ordinary left-to-right B-tree navigation from identifying a narrow starting range. Consider a different search design if this is a frequent requirement.

Example D — Implicit conversion

Suppose CustomerId is INT. Avoid passing a string parameter that causes SQL Server to convert the indexed column.

Preferred:

DECLARE @CustomerId INT = 500;

SELECT *
FROM dbo.Orders
WHERE CustomerId = @CustomerId;

Match parameter data types to column data types to avoid unnecessary conversions and plan complications.

12. Step Eight — Avoid SELECT *

SELECT * retrieves every column even when the application needs only a few.

Less desirable

SELECT *
FROM dbo.Orders
WHERE CustomerId = 500;

Better

SELECT
    OrderId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = 500;

Benefits include:

  • Less data transferred to the application.
  • Potentially fewer page accesses.
  • Smaller covering indexes may be sufficient.
  • Less memory required for some downstream operations.
  • Reduced coupling to table schema changes.

13. Step Nine — Review JOIN Performance

Joins can become expensive when they process large inputs, use unsuitable predicates, or multiply rows unexpectedly.

Example

SELECT
    O.OrderId,
    O.CustomerId,
    C.CustomerName,
    O.TotalAmount
FROM dbo.Orders AS O
INNER JOIN dbo.Customers AS C
    ON O.CustomerId = C.CustomerId
WHERE O.OrderStatus = 'Completed';

A good optimization investigation includes:

  • Are the join columns compatible in data type?
  • Does the join use an appropriate predicate?
  • Are indexes available on frequently searched join keys?
  • Are statistics representative of current data?
  • Are estimated and actual row counts significantly different?
  • Does the join produce more rows than the business requirement expects?

Example index for filtering and joining

CREATE NONCLUSTERED INDEX IX_Orders_Status_Customer
ON dbo.Orders
(
    OrderStatus,
    CustomerId
)
INCLUDE
(
    OrderId,
    TotalAmount
);

This is an example candidate, not a universal recommendation. Evaluate it against the actual workload and existing indexes.

14. Step Ten — Investigate Expensive Operators

An execution plan describes how SQL Server intends to execute a query. An actual execution plan also contains runtime information for the execution.

Operators worth investigating

Operator What it does What to investigate
Table Scan Reads heap data. Whether a useful index could reduce reads.
Clustered Index Scan Reads clustered index rows. Whether the query needs that many rows.
Key Lookup Fetches additional columns from clustered index. Whether a covering index is justified.
Sort Orders rows. Whether an index can provide the required order.
Hash Match Performs hash join or aggregation operations. Memory grants, spills, and input row counts.
Nested Loops Repeatedly searches an inner input. Whether repeated lookups are expensive.
Parallelism Distributes work across worker threads. Whether parallel execution is appropriate.
The percentage displayed on a graphical execution plan operator is an estimated relative cost within that plan. It is not a direct measurement of elapsed time or proof that the operator is the root cause.

15. Step Eleven — Check Statistics

SQL Server uses statistics to estimate how many rows will qualify for predicates and joins.

Poor or outdated statistics can lead to inaccurate cardinality estimates and an unsuitable execution plan.

Inspect statistics

SELECT
    name,
    stats_id,
    auto_created,
    user_created,
    no_recompute
FROM sys.stats
WHERE object_id = OBJECT_ID('dbo.Orders');

Inspect statistics details

DBCC SHOW_STATISTICS
(
    'dbo.Orders',
    'IX_Orders_CustomerId'
);

DBCC SHOW_STATISTICS displays the statistics header, density information, and histogram.

Update statistics when appropriate

UPDATE STATISTICS dbo.Orders
WITH FULLSCAN;

FULLSCAN reads all rows when creating the statistics information. It can be expensive on large tables, so use it deliberately.

SQL Server also supports automatic statistics updates. Do not blindly update every statistic after every slow query. First investigate whether statistics are actually contributing to the problem.

16. Step Twelve — Understand Parameter Sniffing

SQL Server can compile a parameterized query using parameter values available during compilation. The resulting execution plan may be reused for later parameter values.

This behavior is commonly called parameter sniffing. It is often beneficial, but a single cached plan may perform poorly when parameter values have very different data distributions.

Example stored procedure

CREATE OR ALTER PROCEDURE dbo.GetOrdersByCustomer
    @CustomerId INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        OrderId,
        OrderDate,
        TotalAmount
    FROM dbo.Orders
    WHERE CustomerId = @CustomerId;
END;

Imagine one customer has 5 orders and another has 20,000 orders.

A plan suitable for a customer with very few orders may not be suitable for a customer with many orders.

Investigate the issue

EXEC dbo.GetOrdersByCustomer
    @CustomerId = 500;

EXEC dbo.GetOrdersByCustomer
    @CustomerId = 1000;

Compare actual row counts, execution plans, and runtime resource usage for representative parameter values.

Possible techniques

Recompile for a statement:

SELECT
    OrderId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = @CustomerId
OPTION (RECOMPILE);

OPTION (RECOMPILE) can compile using current parameter values, but adds compilation overhead.

Use a parameterized query with a query-specific hint:

SELECT
    OrderId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = @CustomerId
OPTION (OPTIMIZE FOR (@CustomerId = 500));

OPTIMIZE FOR uses a specified representative value for optimization. The chosen value must be appropriate for the workload.

Other approaches include Query Store plan forcing, carefully designed dynamic SQL, and SQL Server's Parameter Sensitive Plan optimization where supported and applicable.

Do not automatically add OPTION (RECOMPILE) to every slow query. It can solve a parameter-sensitive plan problem but may increase CPU usage through repeated compilation.

17. Step Thirteen — Use Query Store

Query Store captures query, plan, and runtime-statistics history. It helps identify queries whose performance has changed over time.

Enable Query Store

ALTER DATABASE YourDatabase
SET QUERY_STORE = ON;

Replace YourDatabase with the actual database name. Check database compatibility and Query Store configuration for your SQL Server version.

Inspect Query Store configuration

SELECT
    actual_state_desc,
    desired_state_desc,
    current_storage_size_mb,
    max_storage_size_mb,
    query_capture_mode_desc
FROM sys.database_query_store_options;

Find queries with high average duration

SELECT TOP (20)
    Q.query_id,
    P.plan_id,
    RS.count_executions,
    RS.avg_duration / 1000.0 AS AvgDurationMs,
    RS.max_duration / 1000.0 AS MaxDurationMs,
    RS.avg_cpu_time / 1000.0 AS AvgCpuMs,
    RS.avg_logical_io_reads AS AvgLogicalReads,
    QT.query_sql_text
FROM sys.query_store_query AS Q
INNER JOIN sys.query_store_query_text AS QT
    ON Q.query_text_id = QT.query_text_id
INNER JOIN sys.query_store_plan AS P
    ON Q.query_id = P.query_id
INNER JOIN sys.query_store_runtime_stats AS RS
    ON P.plan_id = RS.plan_id
ORDER BY RS.avg_duration DESC;

Query Store runtime statistics are stored across intervals. The query above is a useful starting point, but a detailed investigation should account for runtime-statistics intervals and execution counts.

Why Query Store is useful

  • Identify frequently executed expensive queries.
  • Compare plans over time.
  • Investigate performance regressions.
  • Identify changes in CPU, duration, and logical reads.
  • Use plan forcing as a controlled mitigation when justified.

18. Step Fourteen — Review Missing Index Suggestions Carefully

SQL Server may display missing-index recommendations in execution plans or expose them through DMVs.

Find missing-index recommendations

SELECT TOP (20)
    DB_NAME(D.database_id) AS DatabaseName,
    OBJECT_NAME(D.object_id, D.database_id) AS TableName,
    GS.user_seeks,
    GS.user_scans,
    GS.avg_total_user_cost,
    GS.avg_user_impact,
    D.equality_columns,
    D.inequality_columns,
    D.included_columns
FROM sys.dm_db_missing_index_group_stats AS GS
INNER JOIN sys.dm_db_missing_index_groups AS G
    ON GS.group_handle = G.index_group_handle
INNER JOIN sys.dm_db_missing_index_details AS D
    ON G.index_handle = D.index_handle
WHERE D.database_id = DB_ID()
ORDER BY
    GS.avg_user_impact DESC,
    GS.user_seeks DESC;

Missing-index information is a recommendation, not an instruction to create every suggested index.

Before creating an index:

  • Check whether a similar index already exists.
  • Review key-column order.
  • Consider included columns.
  • Evaluate write overhead.
  • Consider index storage requirements.
  • Test against the complete workload.
Missing-index DMV information is transient and has limitations. It does not fully model the impact of competing indexes, write costs, or all workload patterns.

19. Step Fifteen — Avoid Excessive Indexing

Indexes improve some read operations but introduce additional work when rows are inserted, updated, or deleted.

Index maintenance costs

  • Additional storage consumption.
  • More transaction log activity for modifications.
  • Extra work during INSERT operations.
  • Extra work when indexed columns are updated.
  • Index fragmentation and maintenance overhead.
  • More complex choices for the query optimizer.

Inspect index usage

SELECT
    OBJECT_SCHEMA_NAME(I.object_id) AS SchemaName,
    OBJECT_NAME(I.object_id) AS TableName,
    I.name AS IndexName,
    I.type_desc,
    COALESCE(U.user_seeks, 0) AS UserSeeks,
    COALESCE(U.user_scans, 0) AS UserScans,
    COALESCE(U.user_lookups, 0) AS UserLookups,
    COALESCE(U.user_updates, 0) AS UserUpdates
FROM sys.indexes AS I
LEFT JOIN sys.dm_db_index_usage_stats AS U
    ON I.object_id = U.object_id
   AND I.index_id = U.index_id
   AND U.database_id = DB_ID()
WHERE I.object_id = OBJECT_ID('dbo.Orders')
ORDER BY I.index_id;

Usage statistics reset after certain SQL Server events, including service restarts. Low usage alone does not prove that an index is unnecessary. It may support an important infrequent report or constraint.

20. Step Sixteen — Compare Before and After

A successful optimization should be demonstrated through measurements rather than assumptions.

Example comparison

The following figures are illustrative only. Actual results depend on data distribution, hardware, indexes, cache state, SQL Server version, and execution plans.

Metric Before After
Logical reads85012
CPU time120 ms8 ms
Elapsed time180 ms15 ms
Access methodClustered Index ScanIndex Seek
Key LookupNot applicableNone in covering plan

Calculate improvement percentage

For a metric where lower is better: 

Improvement Percentage =
(
    (BeforeValue - AfterValue)
    / BeforeValue
) * 100

For example, logical reads reduced from 850 to 12:

((850 - 12) / 850) * 100
= 98.59%

Always compare equivalent executions that return the same result set and satisfy the same business requirement.

21. Common Query Optimization Mistakes

Mistake Why it is a problem Better approach
Adding indexes without investigation Creates unnecessary storage and write overhead. Inspect actual plans and workload.
Using SELECT * Retrieves unnecessary columns. Select only required columns.
Ignoring logical reads Elapsed time alone can be misleading. Measure I/O and CPU.
Using functions on indexed columns Can prevent efficient index navigation. Use SARGable predicates.
Ignoring parameter sensitivity A cached plan may be unsuitable for some values. Test representative parameter values.
Trusting estimated cost percentages blindly Estimated relative costs are not actual elapsed time. Inspect actual runtime metrics.
Using NOLOCK everywhere Can return dirty, missing, or duplicated data. Choose isolation based on consistency requirements.
Changing several things at once Makes it difficult to identify the actual improvement. Change and measure incrementally.

22. Production Optimization Checklist

  • Identify the exact slow query and affected workload.
  • Record the original execution plan.
  • Measure CPU time, elapsed time, and logical reads.
  • Check whether the query is blocked.
  • Identify the dominant wait types.
  • Compare estimated and actual row counts.
  • Review scans, seeks, lookups, sorts, and hash operations.
  • Check index definitions and existing index usage.
  • Check statistics and data distribution.
  • Investigate parameter-sensitive plans.
  • Test with representative parameters and data volumes.
  • Validate correctness and result consistency.
  • Measure improvements under realistic concurrency.
  • Monitor for regressions after deployment.

23. Real-World Scenario — Slow Customer Order Search

Business requirement

An e-commerce application allows users to search for orders by CustomerId and OrderStatus. The search page takes several seconds to load.

Initial query

SELECT *
FROM dbo.Orders
WHERE CustomerId = 500
  AND OrderStatus = 'Completed'
ORDER BY OrderDate DESC;

Investigation

  1. Capture the actual execution plan.
  2. Enable STATISTICS IO and STATISTICS TIME.
  3. Check whether SQL Server scans the table.
  4. Check whether a Sort operator is required.
  5. Check whether the query retrieves unnecessary columns.

Potential optimized query

SELECT
    OrderId,
    OrderDate,
    TotalAmount
FROM dbo.Orders
WHERE CustomerId = 500
  AND OrderStatus = 'Completed'
ORDER BY OrderDate DESC;

Potential index

CREATE NONCLUSTERED INDEX IX_Orders_Customer_Status_Date
ON dbo.Orders
(
    CustomerId,
    OrderStatus,
    OrderDate DESC
)
INCLUDE
(
    TotalAmount
);

This index may support the equality predicates and the requested ordering. OrderId is available through the clustered key because the sample table has a clustered primary key.

The actual plan must still be checked. If a customer has many matching orders, SQL Server may reasonably choose a different access strategy.

25. Knowledge Check

Question 1

Which metric indicates the number of buffer pages accessed?

  • A. CPU time
  • B. Logical reads
  • C. Elapsed time
  • D. Row count

Answer: B — Logical reads.

Question 2

What does a Key Lookup generally retrieve?

Question 5

Does an Index Seek always mean a query is efficient?

  • A. Yes
  • B. No

Answer: B — A seek can still read many rows, perform expensive lookups, or feed costly downstream operators.

26. Key Takeaways

  • Always identify the actual bottleneck before changing a query.
  • Establish a baseline using CPU time, elapsed time, and logical reads.
  • Use actual execution plans to understand runtime behavior.
  • Use indexes to reduce unnecessary data access, not indiscriminately.
  • Write SARGable predicates wherever possible.
  • Design composite and covering indexes around real workload patterns.
  • Investigate blocking, memory pressure, statistics, and parameter sensitivity.
  • Use Query Store to identify performance regressions over time.
  • Validate improvements with equivalent results and realistic workload conditions.

The most important optimization principle is: measure first, identify the root cause, make a focused change, and measure again.
