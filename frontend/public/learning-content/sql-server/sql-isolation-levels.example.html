APPLY THE IDEA

Worked example

For a transfer, protect the debit/credit invariant with an atomic transaction and appropriate concurrency control; do not use READ UNCOMMITTED for balances.

  1. Describe the correctness invariant and possible anomalies.
  2. Choose isolation and transaction boundaries that protect it.
  3. Check database options for RCSI/SNAPSHOT and understand statement versus transaction snapshots.
  4. Load-test blocking, update conflicts, and version-store capacity.

CODE OR QUERY

Try it

SET TRANSACTION ISOLATION LEVEL SNAPSHOT;
BEGIN TRANSACTION;
  SELECT AccountId, Balance
  FROM dbo.Account
  WHERE AccountId IN (@fromId, @toId);
  -- Validate and update both accounts atomically; handle snapshot update conflicts.
COMMIT TRANSACTION;
-- SNAPSHOT must be enabled for the database; verify operations policy first.

TRADE-OFFS

Benefits and limitations

Benefits

  • Versioned reads can reduce reader/writer blocking.
  • Higher isolation can protect multi-statement invariants from anomalies.

Limitations

  • Serializable range locks may reduce concurrency.
  • Snapshot/RCSI consume version-store resources; snapshot transactions can encounter update conflicts.

DECISION GUIDE

When to use it

Use: Use the lowest isolation that preserves the actual invariant; consider versioned reads for workloads where blocking is costly and capacity is monitored.

Avoid: Avoid READ UNCOMMITTED for correctness-sensitive data and avoid changing database-wide RCSI or transaction isolation without workload testing.

COMMON MISTAKES

Watch out

  • Assuming READ COMMITTED means one consistent snapshot across a multi-statement transaction.
  • Enabling row versioning without monitoring version-store capacity.
  • Using NOLOCK to “fix” blocking while accepting inconsistent results unknowingly.

BEST PRACTICES

In practice

  • Choose isolation from explicit business correctness requirements.
  • Keep transaction scopes short and use constraints/conditional updates.
  • Monitor lock waits, deadlocks, snapshot conflicts, and version-store growth.

INTERVIEW PRACTICE

Common questions

  1. Which level can allow dirty reads?
  2. How do SNAPSHOT and RCSI differ?
  3. What anomaly does SERIALIZABLE prevent that REPEATABLE READ may allow?

SENIOR-LEVEL SCENARIO

Production thinking

A balance report blocks writers while occasional reports need a consistent view. Evaluate RCSI for statement-level consistency or SNAPSHOT for transaction-level view, check tempdb/version-store headroom, and preserve atomic conditional updates for invariant enforcement.

SUMMARY

In one minute

Isolation defines what changes a transaction can observe and which concurrent anomalies are prevented. SQL Server offers READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE, and SNAPSHOT; READ COMMITTED SNAPSHOT (RCSI) is a database option that provides statement-level versioned reads. Isolation is a correctness and concurrency decision: stronger guarantees can increase locking, blocking, or row-version storage. Snapshot and RCSI use row versions rather than making readers wait for many writers.
