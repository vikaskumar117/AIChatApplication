APPLY THE IDEA

Worked example

An equality filter on DepartmentId followed by salary ordering can use an index beginning with DepartmentId then Salary.

  1. Capture the actual plan and SET STATISTICS IO, TIME output in a safe representative environment.
  2. Check predicate sargability, estimated/actual cardinality, and index leading keys.
  3. Look beyond “seek” for rows read, lookups, joins, sorts, and spills.
  4. Compare before/after read, CPU, latency, and write overhead.

CODE OR QUERY

Try it

-- Sargable predicate can use a key on HireDate.
SELECT EmployeeId, HireDate
FROM dbo.Employee
WHERE HireDate >= @startDate
  AND HireDate < @endDate;
-- Avoid wrapping the indexed column in CONVERT(YEAR, HireDate) = @year.

TRADE-OFFS

Benefits and limitations

Benefits

  • Reduces pages read for selective access and may satisfy ordering.
  • Covering indexes can eliminate key lookups for a specific query.

Limitations

  • Low-selectivity scans may be cheaper than many random lookups.
  • Indexes cannot compensate for bad estimates, excessive rows, or costly downstream operators.

DECISION GUIDE

When to use it

Use: Use an index when plan and I/O evidence shows it supports a meaningful predicate, join, ordering, or coverage need.

Avoid: Do not add an index solely because a query is slow; first inspect waits, row estimates, sargability, and bottleneck location.

COMMON MISTAKES

Watch out

  • Assuming every scan is bad or every seek is good.
  • Applying functions to indexed columns unnecessarily in predicates.
  • Adding indexes without accounting for write amplification.

BEST PRACTICES

In practice

  • Measure logical reads, actual rows, CPU, waits, and end-to-end latency.
  • Keep predicates type-compatible and sargable where semantics allow.
  • Validate index changes with read-heavy and write-heavy workload tests.

SENIOR-LEVEL SCENARIO

Production thinking

An indexed endpoint gets slower as data grows. Compare actual and estimated rows, check whether a seek reads most of the table or causes lookups, review statistics and parameter sensitivity, and test a narrow index against logical reads and write workload.

SUMMARY

In one minute

A B-tree index narrows the rows that must be visited for selective predicates and can provide ordered rows or cover all columns needed by a query. Reading fewer pages can reduce I/O and CPU, but an index seek can still return many rows, perform many lookups, or feed an expensive join or sort.
