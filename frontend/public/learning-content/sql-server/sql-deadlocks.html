Deadlocks and Safe Recovery in SQL Server

Understand SQL Server locking, blocking, deadlock cycles, deadlock detection, victim selection, Extended Events, and practical techniques for preventing and recovering from deadlocks.

1. Learning Objectives

  • Understand locks, blocking, and deadlocks.
  • Recognize the four conditions required for a deadlock.
  • Reproduce a deadlock using two SQL Server sessions.
  • Understand how SQL Server selects a deadlock victim.
  • Capture and interpret deadlock graphs.
  • Write transactions that handle deadlock errors safely.
  • Reduce deadlock risk through indexing and consistent access order.
  • Distinguish deadlocks from ordinary blocking and long-running transactions.

2. What Is a Deadlock?

A deadlock occurs when two or more sessions are waiting for resources held by each other, creating a circular wait that prevents any participating session from continuing.

Consider two bank accounts:

AccountId AccountName Balance
1Account A1000
2Account B2000

Two sessions attempt to update the accounts in opposite orders:

  • Session 1 locks Account A and then requests Account B.
  • Session 2 locks Account B and then requests Account A.
Session 1

Owns lock on Account A

Waits for Account B

Session 2

Owns lock on Account B

Waits for Account A

Circular wait

Neither session can proceed

Deadlock detected

SQL Server terminates one victim

A deadlock is different from blocking. Blocking is a normal consequence of incompatible locks. A deadlock is a cycle of dependencies that cannot resolve without intervention.

3. Understand SQL Server Locks

SQL Server uses locks to protect data while transactions read or modify it. Locks help preserve consistency and isolation.

Lock type Purpose
Shared (S) Used for reading under locking-based isolation.
Exclusive (X) Used to protect modified data.
Update (U) Helps coordinate operations that may update data.
Intent (IS, IX, SIX) Indicates that lower-level locks exist or may be acquired.
Schema (Sch-S, Sch-M) Protects schema stability and schema modifications.

Common lock resources

  • RID: A row identifier in a heap.
  • KEY: An index key.
  • PAGE: An 8 KB data or index page.
  • OBJECT: A table or other object.
  • HoBT: A heap or B-tree structure.
  • METADATA: Metadata resources.

Locks can be acquired at different granularities. SQL Server may also escalate locks when appropriate. The actual lock strategy depends on the statement, isolation level, indexes, and workload.

4. Blocking Versus Deadlock

Blocking example

Session 1 updates an employee and holds an exclusive lock. Session 2 tries to update the same employee and must wait.

Session Action Status
Session 1Updates Employee 10Running or holding transaction open
Session 2Updates Employee 10Waiting for Session 1

When Session 1 commits or rolls back, Session 2 can continue. There is no circular dependency, so this is blocking rather than a deadlock.

Deadlock example

Session Owns Waits for
Session 1Resource AResource B
Session 2Resource BResource A

Each session is waiting for a resource held by the other. SQL Server must break the cycle by terminating one transaction.

5. The Four Necessary Conditions for a Deadlock

The classical deadlock model describes four conditions that must exist simultaneously for a deadlock to occur.

  1. Mutual exclusion: A resource cannot be simultaneously held in incompatible modes.
  2. Hold and wait: A session holds one resource while requesting another.
  3. No preemption: A resource cannot simply be taken away from a session; it must be released by the owner.
  4. Circular wait: Sessions form a cycle of resource dependencies.

A prevention strategy attempts to eliminate one or more of these conditions in the application or database design.

7. Reproduce a Deadlock Using Two SQL Server Sessions

Open two separate query windows connected to the same SQL Server database. These examples are for a test environment only.

Session 1

BEGIN TRANSACTION;

UPDATE dbo.BankAccount
SET Balance = Balance - 100
WHERE AccountId = 1;

WAITFOR DELAY '00:00:10';

UPDATE dbo.BankAccount
SET Balance = Balance + 100
WHERE AccountId = 2;

COMMIT TRANSACTION;

Session 2

BEGIN TRANSACTION;

UPDATE dbo.BankAccount
SET Balance = Balance - 200
WHERE AccountId = 2;

WAITFOR DELAY '00:00:10';

UPDATE dbo.BankAccount
SET Balance = Balance + 200
WHERE AccountId = 1;

COMMIT TRANSACTION;

Execution instructions

  1. Start Session 1.
  2. Within approximately five seconds, start Session 2.
  3. Both sessions acquire exclusive locks on different accounts.
  4. Each session then requests the account locked by the other.
  5. SQL Server detects the cycle and chooses a deadlock victim.

One session should receive error 1205. The exact timing can vary, so this demonstration may need to be repeated. 

Msg 1205, Level 13, State 51
Transaction (Process ID ...) was deadlocked on lock resources
with another process and has been chosen as the deadlock victim.
Rerun the transaction.
Do not run this demonstration against production data. If you interrupt a session manually or an unexpected error occurs, inspect the transaction state and clean up the test session before repeating it.

8. How SQL Server Detects and Resolves Deadlocks

SQL Server has a deadlock monitor that periodically checks for deadlock cycles. When a cycle is detected, the Database Engine selects a victim and terminates its transaction to break the cycle.

Sessions acquire locks

Each session owns one or more resources.

Sessions request additional locks

Requests become blocked by other sessions.

Deadlock monitor detects cycle

SQL Server examines the wait-for relationships.

Victim selected

SQL Server chooses one transaction to terminate.

Victim transaction rolled back

Locks are released and the other transaction can proceed.

How is the victim selected?

SQL Server considers deadlock priority and estimated rollback cost. The transaction with the lower DEADLOCK_PRIORITY is generally selected. If priorities are equal, SQL Server considers rollback cost. A tie can be resolved by other internal selection criteria.

Set deadlock priority

SET DEADLOCK_PRIORITY LOW;

-- This session is more willing to become
-- the victim when competing with a NORMAL priority session.

BEGIN TRANSACTION;

UPDATE dbo.BankAccount
SET Balance = Balance + 10
WHERE AccountId = 1;

COMMIT TRANSACTION;

Supported values include LOW, NORMAL, HIGH, or a numeric value from -10 through 10.

DEADLOCK_PRIORITY does not prevent deadlocks. It only influences victim selection. It should not be used as a substitute for correcting transaction design.

9. Error 1205: Handling a Deadlock Victim

SQL Server reports error number 1205 to the session selected as the victim. The victim transaction is rolled back by SQL Server. The application should treat the operation as failed and decide whether it is safe to retry.

Basic TRY/CATCH handling

BEGIN TRY

    BEGIN TRANSACTION;

    UPDATE dbo.BankAccount
    SET Balance = Balance - 100
    WHERE AccountId = 1;

    UPDATE dbo.BankAccount
    SET Balance = Balance + 100
    WHERE AccountId = 2;

    COMMIT TRANSACTION;

END TRY
BEGIN CATCH

    IF XACT_STATE() <> 0
        ROLLBACK TRANSACTION;

    SELECT
        ERROR_NUMBER() AS ErrorNumber,
        ERROR_MESSAGE() AS ErrorMessage,
        ERROR_LINE() AS ErrorLine;

    THROW;

END CATCH;

This pattern ensures that an open or uncommittable transaction is rolled back before the error is rethrown.

Understanding XACT_STATE()

Value Meaning Action
1 Transaction is active and committable. Commit or roll back as appropriate.
0 No active user transaction. No rollback is required.
-1 Transaction is active but uncommittable. Must roll back the transaction.

10. Implement a Retry Strategy

Deadlocks are sometimes unavoidable in concurrent systems. A common recovery approach is to retry the entire transaction after a short delay.

Example stored procedure with retry logic

CREATE OR ALTER PROCEDURE dbo.TransferMoney
    @FromAccountId INT,
    @ToAccountId INT,
    @Amount DECIMAL(12,2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    DECLARE @Attempt INT = 1;
    DECLARE @MaxAttempts INT = 3;

    WHILE @Attempt <= @MaxAttempts
    BEGIN
        BEGIN TRY

            BEGIN TRANSACTION;

            IF @Amount <= 0
                THROW 50001, 'Amount must be greater than zero.', 1;

            IF @FromAccountId = @ToAccountId
                THROW 50002, 'Source and destination must differ.', 1;

            -- Validate sufficient balance.
            IF NOT EXISTS
            (
                SELECT 1
                FROM dbo.BankAccount
                WHERE AccountId = @FromAccountId
                  AND Balance >= @Amount
            )
                THROW 50003, 'Insufficient balance or account missing.', 1;

            -- Debit source account.
            UPDATE dbo.BankAccount
            SET Balance = Balance - @Amount
            WHERE AccountId = @FromAccountId;

            IF @@ROWCOUNT <> 1
                THROW 50004, 'Source account update failed.', 1;

            -- Credit destination account.
            UPDATE dbo.BankAccount
            SET Balance = Balance + @Amount
            WHERE AccountId = @ToAccountId;

            IF @@ROWCOUNT <> 1
                THROW 50005, 'Destination account update failed.', 1;

            COMMIT TRANSACTION;
            RETURN;

        END TRY
        BEGIN CATCH

            DECLARE @ErrorNumber INT = ERROR_NUMBER();

            IF XACT_STATE() <> 0
                ROLLBACK TRANSACTION;

            IF @ErrorNumber = 1205
               AND @Attempt < @MaxAttempts
            BEGIN
                SET @Attempt += 1;

                -- Simple example delay. Production applications
                -- should use bounded backoff with jitter.
                WAITFOR DELAY '00:00:01';

                CONTINUE;
            END;

            THROW;

        END CATCH;
    END;
END;

Example execution:

EXEC dbo.TransferMoney
    @FromAccountId = 1,
    @ToAccountId = 2,
    @Amount = 100.00;

SELECT *
FROM dbo.BankAccount;
Retry the complete transaction, not just the statement that encountered error 1205. The transaction may have been rolled back, so earlier work must be repeated as part of the same logical operation.

Production retry considerations

  • Retry only errors known to be transient and safe to retry.
  • Use a limited retry count.
  • Use exponential backoff with random jitter for high-concurrency applications.
  • Log retry attempts and deadlock frequency.
  • Make externally visible operations idempotent where possible.
  • Do not send emails, issue payments, or call external systems again blindly after a retry.

11. Prevent Deadlocks by Accessing Resources in a Consistent Order

One of the most effective prevention techniques is to make all transactions acquire resources in the same order.

Problem: opposite account order

-- Transaction A
UPDATE dbo.BankAccount
SET Balance = Balance - 100
WHERE AccountId = 1;

UPDATE dbo.BankAccount
SET Balance = Balance + 100
WHERE AccountId = 2;

-- Transaction B
UPDATE dbo.BankAccount
SET Balance = Balance - 200
WHERE AccountId = 2;

UPDATE dbo.BankAccount
SET Balance = Balance + 200
WHERE AccountId = 1;

Improvement: consistent account order

Both transactions should access AccountId 1 before AccountId 2, regardless of which account is the source or destination. 

-- Illustrative pattern:
-- Determine the lower and higher account IDs first.
-- Acquire/update the lower ID before the higher ID.

DECLARE @FirstAccountId INT =
    CASE
        WHEN @FromAccountId < @ToAccountId
            THEN @FromAccountId
        ELSE @ToAccountId
    END;

DECLARE @SecondAccountId INT =
    CASE
        WHEN @FromAccountId < @ToAccountId
            THEN @ToAccountId
        ELSE @FromAccountId
    END;

-- Perform operations in this consistent order,
-- while applying the correct debit/credit to each account.

Consistent ordering reduces circular wait for those resources. It does not guarantee that every possible deadlock in the system disappears, because other tables, indexes, triggers, and application operations may introduce additional dependencies.

12. Prevent Deadlocks Through Better Indexing

Poor access paths can cause SQL Server to examine and lock more rows or index keys than necessary. Appropriate indexes can reduce the amount of work and the time locks are held.

Example table

CREATE TABLE dbo.Orders
(
    OrderId INT NOT NULL
        CONSTRAINT PK_Orders PRIMARY KEY,
    CustomerId INT NOT NULL,
    OrderStatus VARCHAR(20) NOT NULL,
    OrderDate DATETIME2 NOT NULL
);

Example query:

UPDATE dbo.Orders
SET OrderStatus = 'Processed'
WHERE CustomerId = 100
  AND OrderStatus = 'Pending';

Potential supporting index:

CREATE NONCLUSTERED INDEX IX_Orders_Customer_Status
ON dbo.Orders
(
    CustomerId,
    OrderStatus
);

The index may allow SQL Server to locate the matching rows more efficiently. However, indexes also introduce additional structures that must be maintained and can themselves participate in lock dependencies.

13. Keep Transactions Short

Long-running transactions hold locks for longer periods and increase the opportunity for blocking and deadlocks.

Risky pattern

BEGIN TRANSACTION;

UPDATE dbo.BankAccount
SET Balance = Balance - 100
WHERE AccountId = 1;

-- Avoid user interaction, external API calls,
-- lengthy calculations, or unnecessary waits here.

WAITFOR DELAY '00:00:30';

UPDATE dbo.BankAccount
SET Balance = Balance + 100
WHERE AccountId = 2;

COMMIT TRANSACTION;

Better approach

  • Perform lengthy calculations before opening the transaction when safe.
  • Do not wait for user input while holding database locks.
  • Do not call external services inside a database transaction unless the architecture explicitly requires it.
  • Update only the necessary rows.
  • Commit or roll back promptly.

14. Capture Deadlocks Using Extended Events

SQL Server provides the Extended Events infrastructure for capturing diagnostic events. The system_health session commonly captures the xml_deadlock_report event by default.

Read deadlock reports from system_health

SELECT
    XEvent.value(
        '(event/@timestamp)[1]',
        'datetime2'
    ) AS DeadlockTime,

    XEvent.query(
        '(event/data/value/deadlock)[1]'
    ) AS DeadlockGraph

FROM
(
    SELECT
        CAST(st.target_data AS XML) AS TargetData
    FROM sys.dm_xe_session_targets AS st
    INNER JOIN sys.dm_xe_sessions AS s
        ON s.address = st.event_session_address
    WHERE s.name = 'system_health'
      AND st.target_name = 'ring_buffer'
) AS Data
CROSS APPLY TargetData.nodes(
    'RingBufferTarget/event[@name="xml_deadlock_report"]'
) AS XEventData(XEvent);

This query reads the ring-buffer target, which is limited in size and can lose older events. The system_health session may also use an event-file target depending on SQL Server version and configuration.

Inspect the session targets

SELECT
    s.name AS SessionName,
    t.target_name,
    CAST(t.target_data AS XML) AS TargetData
FROM sys.dm_xe_sessions AS s
JOIN sys.dm_xe_session_targets AS t
    ON s.address = t.event_session_address
WHERE s.name = 'system_health';

Create a dedicated deadlock capture session

CREATE EVENT SESSION CaptureDeadlocks
ON SERVER
ADD EVENT sqlserver.xml_deadlock_report
ADD TARGET package0.event_file
(
    SET filename = 'C:\SQLXEvents\CaptureDeadlocks.xel',
        max_file_size = 20,
        max_rollover_files = 5
)
WITH
(
    STARTUP_STATE = ON
);

ALTER EVENT SESSION CaptureDeadlocks
ON SERVER
STATE = START;

The SQL Server service account must have permission to write to the specified directory. Create the directory before starting the session.

Read the event file

SELECT
    object_name,
    CAST(event_data AS XML) AS EventData
FROM sys.fn_xe_file_target_read_file
(
    'C:\SQLXEvents\CaptureDeadlocks*.xel',
    NULL,
    NULL,
    NULL
);
Creating server-level Extended Events sessions and reading diagnostic data requires appropriate permissions. Confirm supported permissions and target paths for your SQL Server version and environment.

15. How to Read a Deadlock Graph

A deadlock graph contains information about participating processes, resources, ownership, and waiting relationships.

Important XML elements

Element What it tells you
victim-listIdentifies the selected deadlock victim.
process-listDescribes sessions involved in the deadlock.
resource-listDescribes locked resources and their owners and waiters.
process idInternal process identifier in the deadlock graph.
spidSQL Server session identifier.
waitresourceResource the process is waiting for.
lockModeLock mode requested or held.
inputbufSubmitted SQL batch or statement context.
executionStackExecution context and statement information.

Analysis procedure

  1. Identify the victim process.
  2. Find the other participating processes.
  3. Inspect the resource list for each lock resource.
  4. Determine which process owns each resource.
  5. Determine which process is waiting for each resource.
  6. Inspect the SQL statements and execution context.
  7. Check indexes, transaction boundaries, and access order.
  8. Change the design and verify that the deadlock is reduced or eliminated.

16. Monitor Current Blocking and Waiting Sessions

The following query helps identify sessions currently blocked by another session. 

SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_time,
    wait_resource,
    status,
    command
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;

To inspect the SQL text associated with active requests: 

SELECT
    r.session_id,
    r.blocking_session_id,
    r.wait_type,
    r.wait_time,
    r.wait_resource,
    t.text AS SqlText
FROM sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.blocking_session_id <> 0;

These queries show current requests, not a complete historical record of deadlocks. Use Extended Events or other monitoring infrastructure to capture events over time.

17. Other Deadlock Causes

17.1 Different table access order

One transaction updates Orders and then Customers, while another updates Customers and then Orders.

17.2 Missing or unsuitable indexes

A statement may scan a larger range or acquire more locks than a more selective access path would require.

17.3 Foreign key relationships

Updates and deletes can require checks against related tables. Different access patterns involving parent and child tables can contribute to deadlocks.

17.4 Triggers

A trigger can access additional tables during a modification. The application may appear to update one table while the complete transaction actually touches several tables.

17.5 Lock escalation

SQL Server can escalate many fine-grained locks to a table-level lock when appropriate. This changes the resources that concurrent sessions need and can affect blocking and deadlock behavior.

17.6 Parallel query execution

Some deadlocks involve exchange or worker-thread resources in parallel plans rather than only ordinary data locks. These require inspection of the deadlock graph and execution plan.

18. Should You Use NOLOCK to Prevent Deadlocks?

NOLOCK is often suggested as a quick way to avoid blocking. It is not a general deadlock prevention solution. 

SELECT *
FROM dbo.BankAccount WITH (NOLOCK);

NOLOCK is equivalent to READ UNCOMMITTED for the table reference. It can allow dirty reads and other inconsistent results, including missing or duplicated rows under some concurrent data movement conditions.

It also does not eliminate every lock interaction. Queries still acquire schema-stability locks, and schema-modification operations can still conflict with them.

Consider row-versioning isolation, such as READ COMMITTED SNAPSHOT, when reducing reader-writer blocking is an appropriate architectural goal. Row versioning has its own storage and operational considerations and does not eliminate all deadlocks.

19. Production Deadlock Prevention Checklist

  • Access shared tables and rows in a consistent order.
  • Keep transactions as short as possible.
  • Create indexes that support frequent transactional predicates.
  • Update only the rows that need modification.
  • Avoid unnecessary user interaction inside transactions.
  • Review triggers and foreign key access patterns.
  • Capture deadlock graphs using Extended Events.
  • Use bounded retry logic for error 1205.
  • Log deadlock frequency, statements, and retry outcomes.
  • Test changes under realistic concurrency.
  • Evaluate row-versioning isolation where appropriate.
  • Do not use NOLOCK as a universal concurrency fix.

22. Key Takeaways

  • A deadlock is a circular wait between two or more sessions.
  • Blocking alone is not a deadlock.
  • SQL Server detects deadlocks and selects a victim to break the cycle.
  • Error 1205 indicates that a transaction was chosen as the victim.
  • TRY/CATCH and XACT_STATE() help manage transaction cleanup.
  • Retry the entire logical transaction, not just one statement.
  • Consistent resource access order is an important prevention technique.
  • Short transactions and appropriate indexes can reduce deadlock risk.
  • Extended Events provides valuable deadlock diagnostic information.
  • NOLOCK is not a universal solution to concurrency problems.

The goal is not merely to recover from deadlocks. It is to understand their resource dependencies, correct the underlying design where possible, and make the application resilient when a deadlock still occurs.
