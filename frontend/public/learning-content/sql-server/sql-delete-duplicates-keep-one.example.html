APPLY THE IDEA

Worked example

Keep the earliest customer record per normalized email; use CustomerId to break timestamp ties.

  1. Preview the ranked result and verify each rn = 1 keeper.
  2. Check every duplicate candidate for foreign-key references and domain history.
  3. Back up, test rollback, estimate log impact, and get approval.
  4. Delete in controlled batches or a reviewed transaction, verify row counts, then enforce uniqueness.

CODE OR QUERY

Try it

-- PREVIEW ONLY: review the candidate IDs and dependent references first.
WITH ranked AS (
  SELECT CustomerId, NormalizedEmail, CreatedAt,
         ROW_NUMBER() OVER (
           PARTITION BY NormalizedEmail
           ORDER BY CreatedAt, CustomerId
         ) AS rn
  FROM dbo.Customer
  WHERE NormalizedEmail IS NOT NULL
)
SELECT CustomerId, NormalizedEmail, CreatedAt
FROM ranked
WHERE rn > 1
ORDER BY NormalizedEmail, CreatedAt, CustomerId;

TRADE-OFFS

Benefits and limitations

Benefits

  • A unique ordering makes survivor selection repeatable.
  • A preview allows reconciliation and rollback planning before data changes.

Limitations

  • Large deletes can block, fill the transaction log, and cascade or orphan business data.
  • Batching introduces operational complexity and needs a stable candidate strategy.

DECISION GUIDE

When to use it

Use: Use only after defining the true business key and approved retention/merge behavior.

Avoid: Do not execute the delete on production as an unreviewed script or rely on a non-unique ordering.

COMMON MISTAKES

Watch out

  • Running a DELETE before reviewing candidate IDs and foreign-key relationships.
  • Using CreatedAt alone when timestamps can tie.
  • Putting an enormous delete in one transaction without checking log and blocking capacity.

BEST PRACTICES

In practice

  • Run the preview and deletion against the same controlled candidate definition.
  • Use a tested restore/rollback procedure and capture affected IDs.
  • Consider batches, lock timeout, monitoring, and resumability for large tables.
  • Create the unique constraint or unique filtered index only after validating its semantics.

INTERVIEW PRACTICE

Common questions

  1. Why must the ROW_NUMBER ordering end with a unique key?
  2. What must be checked before deleting a duplicate with foreign-key references?
  3. How do batching and transactions trade off atomicity and operational impact?

SENIOR-LEVEL SCENARIO

Production thinking

An online customer table contains millions of duplicate imports. Export and review candidate IDs, resolve foreign-key references to the keeper, rehearse a logged batch process on a restored copy, monitor log and blocking, then add a unique constraint after cleanup.

SUMMARY

In one minute

A deterministic keeper rule selects exactly one surviving row per duplicate business key; other rows become deletion candidates. A cleanup query without an explicit retention policy can delete the valuable or referenced record. Large unbounded deletes also create locks, log growth, and replication or availability impact.
