Prevent SQL Injection in SQL Server

Learn how SQL injection vulnerabilities occur and how to prevent them using parameterized queries, safe dynamic SQL, stored procedures, input validation, and database security controls. Explore practical attack demonstrations, execution behavior, application examples, and production security practices.

1. Learning Objectives

  • Understand SQL injection and how attackers exploit it.
  • Recognize unsafe dynamic SQL construction.
  • Understand how injected SQL changes query behavior.
  • Use parameterized queries to protect application inputs.
  • Use sp_executesql safely.
  • Write secure stored procedures.
  • Understand why stored procedures alone do not prevent SQL injection.
  • Validate input and safely handle dynamic identifiers.
  • Apply least-privilege database permissions.
  • Recognize second-order SQL injection.
  • Test and audit SQL Server applications for injection risks.

2. What Is SQL Injection?

SQL injection is a security vulnerability in which untrusted application input is interpreted as part of an SQL command instead of being treated only as data.

It commonly happens when an application builds SQL statements by concatenating user-supplied text into a query string.

Example application scenario

Imagine a login form that accepts:

  • Username
  • Password

The application sends those values to SQL Server to verify whether the account exists.

If the application directly inserts the values into SQL command text, a malicious user may change the meaning of the query.

Normal input

Username: alice
Password: MyPassword123

Potential malicious input

Username: ' OR 1=1 --
Password: anything

The exact impact depends on how the application constructs the SQL statement and what permissions its database account has.

4. How SQL Injection Happens

Consider an application that creates a query using string concatenation.

Unsafe SQL construction

DECLARE @Username VARCHAR(100);

SET @Username = 'alice';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    'SELECT UserId, Username
     FROM dbo.AppUsers
     WHERE Username = '''
     + @Username
     + '''';

PRINT @SQL;

EXEC(@SQL);

For ordinary input, the generated SQL is: 

SELECT UserId, Username
FROM dbo.AppUsers
WHERE Username = 'alice';

The query appears to work correctly. The problem is that @Username is being treated as part of the SQL command text.

Illustrative injection demonstration

In this isolated demonstration, a crafted input changes the WHERE condition so that it becomes true for every row. 

DECLARE @Username VARCHAR(100);

SET @Username = ''' OR 1=1 --';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    'SELECT UserId, Username
     FROM dbo.AppUsers
     WHERE Username = '''
     + @Username
     + '''';

PRINT @SQL;

EXEC(@SQL);

The resulting command is equivalent to:

SELECT UserId, Username
FROM dbo.AppUsers
WHERE Username = '' OR 1=1 --';

The expression 1=1 is always true. The double hyphen starts a SQL Server single-line comment, so the remaining text on that line is ignored.

The query can therefore return every user in the table, rather than only the requested user.

Why this is dangerous

  • Authentication checks may be bypassed.
  • Private records may be exposed.
  • Data may be modified or deleted.
  • Application privileges may be abused.
  • Database objects may be exposed or damaged.
Run demonstrations only against a local test database that you control. Never test injection payloads against systems without explicit authorization.

5. SQL Injection Processing Flow

User submits input

An application receives a username or search value.

Application constructs SQL

Unsafe code concatenates the input into SQL text.

SQL Server parses the command

The supplied text becomes part of the SQL syntax.

Query executes

The database may execute a modified condition or command.

Unauthorized result or change

Data can be exposed or modified beyond the intended operation.

Secure processing flow

User submits input

The application receives untrusted values.

Parameterized command

SQL text and parameter values are supplied separately.

SQL Server binds parameters

Values are interpreted as data, not SQL syntax.

Query executes

The intended SQL structure is preserved.

Controlled result

The query processes the supplied value as data.

6. Solution 1 — Parameterized Queries

Parameterized queries are one of the most important defenses against SQL injection.

Instead of inserting a value into SQL command text, define a parameter placeholder and pass the value separately.

Unsafe approach

DECLARE @Username VARCHAR(100) =
    'alice';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    'SELECT UserId, Username
     FROM dbo.AppUsers
     WHERE Username = '''
     + @Username
     + '''';

EXEC(@SQL);

Safe approach with sp_executesql

DECLARE @Username NVARCHAR(50) =
    N'alice';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    N'SELECT UserId, Username
      FROM dbo.AppUsers
      WHERE Username = @Username';

EXEC sys.sp_executesql
    @SQL,
    N'@Username NVARCHAR(50)',
    @Username = @Username;

SQL command text and the parameter value are passed separately. SQL Server does not reinterpret the parameter value as additional SQL syntax.

What happens with malicious input?

DECLARE @Username NVARCHAR(50) =
    N''' OR 1=1 --';

DECLARE @SQL NVARCHAR(MAX) =
    N'SELECT UserId, Username
      FROM dbo.AppUsers
      WHERE Username = @Username';

EXEC sys.sp_executesql
    @SQL,
    N'@Username NVARCHAR(50)',
    @Username = @Username;

The entire input is treated as one username value. SQL Server searches for a username containing that text instead of executing the input as a condition.

7. Solution 2 — Use Stored Procedures Safely

Stored procedures can provide a controlled database interface, but they do not automatically prevent SQL injection.

A procedure that concatenates untrusted input into dynamic SQL can still be vulnerable.

Unsafe stored procedure

CREATE OR ALTER PROCEDURE dbo.SearchUserUnsafe
    @Username NVARCHAR(100)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SQL NVARCHAR(MAX);

    SET @SQL =
        N'SELECT UserId, Username
          FROM dbo.AppUsers
          WHERE Username = '''
        + @Username
        + N'''';

    EXEC(@SQL);
END;
GO

The stored procedure is vulnerable because the input is concatenated into SQL command text.

Safe stored procedure

CREATE OR ALTER PROCEDURE dbo.SearchUserSafe
    @Username NVARCHAR(50)
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        UserId,
        Username,
        IsActive
    FROM dbo.AppUsers
    WHERE Username = @Username;
END;
GO

Execute the procedure

EXEC dbo.SearchUserSafe
    @Username = N'alice';

SQL Server receives a fixed SQL statement and a separate parameter value. The input cannot change the structure of the SELECT statement.

8. Solution 3 — Use sp_executesql Correctly

sp_executesql executes a Unicode SQL statement and supports explicitly declared parameters.

Syntax

EXEC sys.sp_executesql
    @stmt,
    @params,
    @parameter_name = @parameter_value;

Example with multiple parameters

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    N'SELECT
          UserId,
          Username,
          IsActive
      FROM dbo.AppUsers
      WHERE Username = @Username
        AND IsActive = @IsActive';

EXEC sys.sp_executesql
    @SQL,
    N'@Username NVARCHAR(50),
      @IsActive BIT',
    @Username = N'alice',
    @IsActive = 1;

Example with a numeric parameter

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    N'SELECT *
      FROM dbo.Employee
      WHERE Salary >= @MinimumSalary';

EXEC sys.sp_executesql
    @SQL,
    N'@MinimumSalary DECIMAL(12,2)',
    @MinimumSalary = 50000.00;

Benefits

  • Separates SQL command structure from input values.
  • Supports strongly typed parameters.
  • Can support execution-plan reuse when statement text remains stable.
  • Supports dynamic queries without unsafe value concatenation.
sp_executesql is not automatically safe if untrusted input is concatenated into the SQL statement itself. Parameterize every data value that can be supplied as a parameter.

9. SQL Injection in Dynamic SQL

Dynamic SQL is useful when the application must construct a query based on optional filters, selected columns, or sorting. However, it must be designed carefully.

Unsafe dynamic SQL with a search filter

DECLARE @SearchText NVARCHAR(100) =
    N'alice';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    N'SELECT UserId, Username
      FROM dbo.AppUsers
      WHERE Username LIKE N''%'
      + @SearchText
      + N'%''';

EXEC(@SQL);

The search value is embedded in the SQL text. This creates an injection risk.

Safe dynamic SQL with a parameter

DECLARE @SearchText NVARCHAR(100) =
    N'alice';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    N'SELECT UserId, Username
      FROM dbo.AppUsers
      WHERE Username LIKE @SearchPattern';

EXEC sys.sp_executesql
    @SQL,
    N'@SearchPattern NVARCHAR(202)',
    @SearchPattern = N'%' + @SearchText + N'%';

The search value is passed separately. A value containing SQL-looking text remains data.

Search wildcard behavior

Parameterization prevents SQL injection, but it does not automatically make wildcard characters literal.

In a LIKE expression, the percent sign and underscore have pattern meanings. If the application intends to search for those characters literally, escape them and specify an ESCAPE character. 

DECLARE @SearchText NVARCHAR(100) =
    N'50%';

SET @SearchText = REPLACE(@SearchText, N'~', N'~~');
SET @SearchText = REPLACE(@SearchText, N'%', N'~%');
SET @SearchText = REPLACE(@SearchText, N'_', N'~_');
SET @SearchText = REPLACE(@SearchText, N'[', N'~[');

SELECT UserId, Username
FROM dbo.AppUsers
WHERE Username LIKE N'%' + @SearchText + N'%'
ESCAPE N'~';

10. Dynamic Table Names and Column Names

SQL parameters can represent values, but they cannot directly represent SQL identifiers such as table names, column names, or sort directions.

For dynamic identifiers, use an allowlist and QUOTENAME.

Unsafe example

DECLARE @ColumnName NVARCHAR(100) =
    N'Username';

DECLARE @SQL NVARCHAR(MAX);

SET @SQL =
    N'SELECT ' + @ColumnName +
    N' FROM dbo.AppUsers';

EXEC(@SQL);

An attacker-controlled identifier could change the SQL statement structure.

Safe example with an allowlist

DECLARE @ColumnName SYSNAME =
    N'Username';

DECLARE @SQL NVARCHAR(MAX);

IF @ColumnName NOT IN
(
    N'UserId',
    N'Username',
    N'IsActive'
)
BEGIN
    THROW 50010, 'Invalid column selection.', 1;
END;

SET @SQL =
    N'SELECT ' + QUOTENAME(@ColumnName) +
    N' FROM dbo.AppUsers';

EXEC sys.sp_executesql @SQL;

QUOTENAME safely delimits a SQL Server identifier. It does not determine whether the requested identifier is permitted. The allowlist provides that authorization decision.

Safe dynamic sorting

DECLARE @SortColumn SYSNAME = N'Username';
DECLARE @SortDirection NVARCHAR(4) = N'ASC';

DECLARE @SQL NVARCHAR(MAX);

IF @SortColumn NOT IN
(
    N'UserId',
    N'Username',
    N'IsActive'
)
BEGIN
    THROW 50011, 'Invalid sort column.', 1;
END;

IF @SortDirection NOT IN (N'ASC', N'DESC')
BEGIN
    THROW 50012, 'Invalid sort direction.', 1;
END;

SET @SQL =
    N'SELECT UserId, Username, IsActive
      FROM dbo.AppUsers
      ORDER BY '
    + QUOTENAME(@SortColumn)
    + N' '
    + @SortDirection;

EXEC sys.sp_executesql @SQL;

The sort column and direction are validated against fixed choices before they are added to the SQL statement.

11. Input Validation and Parameter Types

Parameterization is the primary defense against SQL injection for data values. Input validation provides additional protection by enforcing application rules.

Example: Validate an account identifier

DECLARE @AccountId INT = 100;

IF @AccountId <= 0
BEGIN
    THROW 50020, 'Invalid account identifier.', 1;
END;

SELECT *
FROM dbo.BankAccount
WHERE AccountId = @AccountId;

Example: Validate a username length

DECLARE @Username NVARCHAR(50) =
    N'alice';

IF NULLIF(LTRIM(RTRIM(@Username)), N'') IS NULL
BEGIN
    THROW 50021, 'Username is required.', 1;
END;

IF LEN(@Username) > 50
BEGIN
    THROW 50022, 'Username is too long.', 1;
END;

SELECT UserId, Username
FROM dbo.AppUsers
WHERE Username = @Username;

Why parameter data types matter

  • Use INT for integer identifiers.
  • Use DECIMAL for exact monetary values.
  • Use DATE or DATETIME2 for date values.
  • Use NVARCHAR for Unicode text.
  • Match parameter lengths and types to the target columns where practical.

Correct parameter types also help avoid unnecessary implicit conversions and can improve query-plan quality.

12. SQL Injection Through Application Code

Many SQL injection vulnerabilities originate in application code rather than in the SQL Server database itself.

Unsafe C# example

string username = txtUsername.Text;

string sql =
    "SELECT UserId, Username " +
    "FROM dbo.AppUsers " +
    "WHERE Username = '" + username + "'";

using (SqlCommand command = new SqlCommand(sql, connection))
{
    using (SqlDataReader reader = command.ExecuteReader())
    {
        while (reader.Read())
        {
            // Process results.
        }
    }
}

The SQL statement is built using direct string concatenation. User input can alter its structure.

Safe C# example with SqlParameter

string username = txtUsername.Text;

string sql =
    "SELECT UserId, Username " +
    "FROM dbo.AppUsers " +
    "WHERE Username = @Username";

using (SqlCommand command = new SqlCommand(sql, connection))
{
    command.Parameters.Add(
        "@Username",
        SqlDbType.NVarChar,
        50
    ).Value = username;

    using (SqlDataReader reader = command.ExecuteReader())
    {
        while (reader.Read())
        {
            // Process results.
        }
    }
}

The parameter is sent separately from the command text. The SQL structure remains fixed even when the user supplies unusual characters.

Safe parameterized INSERT

string sql =
    "INSERT INTO dbo.AppUsers " +
    "(Username, PasswordHash, IsActive) " +
    "VALUES (@Username, @PasswordHash, @IsActive)";

using (SqlCommand command = new SqlCommand(sql, connection))
{
    command.Parameters.Add(
        "@Username",
        SqlDbType.NVarChar,
        50
    ).Value = username;

    command.Parameters.Add(
        "@PasswordHash",
        SqlDbType.NVarChar,
        255
    ).Value = passwordHash;

    command.Parameters.Add(
        "@IsActive",
        SqlDbType.Bit
    ).Value = true;

    command.ExecuteNonQuery();
}
Parameterize every user-controlled data value. Do not construct SQL command text by concatenating form fields, URL parameters, request headers, cookies, or other untrusted input.

13. Second-Order SQL Injection

Second-order SQL injection occurs when malicious-looking input is safely stored as data, but a later operation retrieves that stored value and inserts it into dynamically constructed SQL without parameterization.

Example scenario

  1. An application accepts a search configuration or label.
  2. The value is stored in a database using a parameterized INSERT.
  3. A reporting procedure later reads the stored value.
  4. The reporting procedure concatenates it into dynamic SQL.
  5. The stored value is now interpreted as SQL syntax.

Important lesson

Data does not become trustworthy simply because it came from your own database. Stored values may originally have come from untrusted users.

Apply the same parameterization and identifier-validation rules every time data is used to construct a SQL command.

14. Least-Privilege Database Permissions

Parameterization prevents input from changing SQL command structure. Least privilege limits what an application can do if a vulnerability exists elsewhere.

An application account should receive only the permissions needed for its business operations.

Create a restricted application role

CREATE ROLE AppUserRole;

GRANT EXECUTE
ON OBJECT::dbo.SearchUserSafe
TO AppUserRole;

A database user can be added to the role through the appropriate database provisioning process. 

-- Example for an existing database user:
ALTER ROLE AppUserRole
ADD MEMBER AppServiceUser;

This example assumes AppServiceUser already exists in the database. Do not grant application accounts broad permissions such as db_owner simply for convenience.

Review effective permissions

SELECT
    pr.name AS PrincipalName,
    pe.permission_name,
    pe.state_desc,
    OBJECT_SCHEMA_NAME(pe.major_id) AS SchemaName,
    OBJECT_NAME(pe.major_id) AS ObjectName
FROM sys.database_permissions AS pe
JOIN sys.database_principals AS pr
    ON pe.grantee_principal_id = pr.principal_id
ORDER BY
    pr.name,
    pe.permission_name;

Security principles

  • Use a dedicated database identity for the application.
  • Avoid sysadmin and db_owner privileges for ordinary application connections.
  • Grant EXECUTE only on required stored procedures where appropriate.
  • Separate application roles from administrative accounts.
  • Protect credentials and connection strings.
  • Review permissions periodically.

Be aware that dynamic SQL inside a stored procedure can have different permission behavior from ordinary static SQL. Test execution permissions and use an appropriate ownership or signing strategy when required.

15. Why Escaping Quotes Is Not Enough

A common but unreliable approach is to manually replace quotation marks before concatenating user input into SQL.

Example of manual escaping

DECLARE @Username NVARCHAR(100) =
    N'alice';

SET @Username = REPLACE(
    @Username,
    N'''',
    N''''''
);

-- Escaping alone is not the preferred defense.
-- Use a parameterized query instead.

Manual escaping is easy to implement incorrectly. Different SQL contexts have different syntax rules, and escaping quotation marks does not safely handle arbitrary identifiers, operators, sort directions, or complete SQL fragments.

Prefer parameterized queries for values and allowlists for identifiers and other SQL syntax choices.

16. Common SQL Injection Patterns

Pattern Risk Recommended protection
String concatenation User input changes SQL syntax. Parameterized queries.
Unsafe dynamic SQL Untrusted input is embedded in command text. sp_executesql with parameters.
Dynamic table or column name Untrusted identifier changes the statement. Allowlist and QUOTENAME.
Unsafe stored procedure Procedure concatenates input into SQL. Static SQL or parameterized dynamic SQL.
Second-order injection Stored untrusted values are later used unsafely. Parameterize every later query as well.
Excessive permissions Vulnerability has a larger impact. Least-privilege database accounts.

17. SQL Server Execution and Plan Reuse

SQL Server processes SQL commands through parsing, binding, optimization, and execution. Parameterized queries help keep SQL structure separate from data values.

Parameterized query example

DECLARE @SQL NVARCHAR(MAX) =
    N'SELECT UserId, Username
      FROM dbo.AppUsers
      WHERE Username = @Username';

EXEC sys.sp_executesql
    @SQL,
    N'@Username NVARCHAR(50)',
    @Username = N'alice';

Execution flow

SQL statement

The fixed statement text is supplied.

Parameter declaration

SQL Server receives the parameter name and type.

Optimization

The optimizer creates or reuses a suitable execution plan.

Parameter binding

The value is supplied as data.

Execution

The statement executes without treating the parameter as SQL syntax.

Parameterization can improve plan reuse when the statement text and parameter definitions remain stable. It does not guarantee a single ideal execution plan for every value. Parameter sniffing and data distribution can still affect plan quality.

18. How to Detect and Investigate SQL Injection Risks

Security reviews should focus on application code, database permissions, dynamic SQL construction, and query execution patterns.

Review dynamic SQL modules

SELECT
    OBJECT_SCHEMA_NAME(object_id) AS SchemaName,
    OBJECT_NAME(object_id) AS ObjectName,
    definition
FROM sys.sql_modules
WHERE definition LIKE '%EXEC(%'
   OR definition LIKE '%EXECUTE(%'
   OR definition LIKE '%sp_executesql%';

This query can help identify modules containing dynamic SQL patterns. It is not a vulnerability scanner. Safe and unsafe code can both match these patterns, and encrypted or externally generated SQL may not be visible.

Review permissions

SELECT
    name,
    type_desc,
    is_disabled
FROM sys.server_principals
ORDER BY name;

Review application identities, their database roles, server-level privileges, and any unnecessary elevated access.

Use application security testing

  • Perform static analysis of application code.
  • Review every dynamic SQL construction point.
  • Test parameterized query behavior in an authorized test environment.
  • Use approved dynamic application security testing tools.
  • Review database audit events and application logs.
  • Investigate unusual query patterns and permission failures.
Do not rely on a single keyword search or a list of suspicious strings to prove that an application is secure. SQL injection review requires understanding how data flows from the user into the SQL command.

19. Secure Coding Checklist

  • Use parameterized queries for all user-controlled values.
  • Use sp_executesql when dynamic SQL is necessary.
  • Never concatenate untrusted input directly into SQL command text.
  • Use allowlists for dynamic identifiers and sort directions.
  • Use QUOTENAME for validated SQL identifiers.
  • Use correct parameter data types and lengths.
  • Validate inputs against business rules.
  • Use least-privilege database accounts.
  • Review stored procedures for unsafe dynamic SQL.
  • Do not assume stored procedures are automatically secure.
  • Handle database errors without exposing sensitive internals to users.
  • Review second-order SQL injection risks.
  • Use code review and security testing before production release.
  • Protect credentials, connection strings, and secrets.

20. Real-World Applications

Banking Applications

Account lookups, transaction history, beneficiary searches, and transfer procedures should use parameterized SQL. Application database accounts should have only the permissions needed for those operations.

E-commerce Applications

Product search, order lookup, customer details, and inventory queries frequently accept user-controlled values. These operations should use typed parameters.

Reporting Systems

Reporting interfaces often allow users to select columns, filters, and sort orders. Data filters should be parameters, while dynamic identifiers should be validated against explicit allowlists.

Administrative Dashboards

Administrative interfaces may have access to sensitive data. Use separate database roles and tightly controlled stored procedures to reduce the impact of application vulnerabilities.

22. Knowledge Check

Question 1

What is SQL injection?

  • A. A database backup technique.
  • B. An attack that changes SQL command behavior through untrusted input.
  • C. An indexing strategy.
  • D. A transaction isolation level.

Answer: B — SQL injection occurs when untrusted input changes the meaning of SQL command text.

Question 2

What is the preferred defense for user-supplied SQL values?

  • A. String concatenation.
  • B. Removing every space.
  • C. Parameterized queries.
  • D. Using SELECT *.

Answer: C — Parameterized queries separate data values from SQL syntax.

Question 3

Does using a stored procedure automatically prevent SQL injection?

  • A. Yes, always.
  • B. No, unsafe dynamic SQL inside a procedure can still be vulnerable.

Answer: B — Stored procedures must also use safe SQL construction.

Question 4

What is sp_executesql commonly used for?

  • A. Parameterized dynamic SQL.
  • B. Creating backups.
  • C. Deleting database files.
  • D. Changing server configuration.

Answer: A — It executes dynamic SQL with separately declared parameters.

Question 5

Can SQL parameters directly replace table names or column names?

  • A. Yes.
  • B. No.

Answer: B — Identifiers require controlled SQL construction, allowlists, and appropriate quoting.

Question 6

What does QUOTENAME do?

  • A. Hashes a password.
  • B. Delimits a SQL Server identifier.
  • C. Encrypts a database.
  • D. Creates a parameterized query automatically.

Answer: B — QUOTENAME safely delimits an identifier but does not authorize it.

Question 7

What is least privilege?

  • A. Giving every user administrator access.
  • B. Giving an account only the permissions it needs.
  • C. Disabling database permissions.
  • D. Using only read-only tables.

Answer: B — Least privilege limits the impact of security failures.

Question 8

What is second-order SQL injection?

  • A. An attack using two database servers.
  • B. Stored untrusted data being used unsafely in a later SQL command.
  • C. A second transaction in a session.
  • D. A query with two parameters.

Answer: B — Previously stored input can become dangerous if later concatenated into dynamic SQL.

23. Key Takeaways

  • SQL injection happens when untrusted input changes SQL command structure.
  • String concatenation is a common cause of injection vulnerabilities.
  • Parameterized queries are the primary defense for data values.
  • sp_executesql supports safely parameterized dynamic SQL.
  • Stored procedures can still be vulnerable if they construct unsafe dynamic SQL.
  • Dynamic identifiers must be validated against allowlists and safely delimited.
  • QUOTENAME is useful for identifiers but is not a substitute for validation.
  • Input validation supplements parameterization; it does not replace it.
  • Least-privilege permissions limit the potential impact of a vulnerability.
  • Second-order injection requires reviewing how stored data is used later.
  • Application code, database code, and permissions must all be reviewed together.

Preventing SQL injection requires treating every external value as untrusted, keeping SQL syntax separate from data, restricting database permissions, and testing the complete application data flow. Parameterization should be the default approach whenever application values are supplied to SQL Server.
