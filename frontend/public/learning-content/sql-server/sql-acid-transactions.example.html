APPLY THE IDEA

Worked example

A funds transfer debits and credits two accounts in one transaction and uses a conditional debit to prevent overdraft.

  1. Identify the state invariant and all rows that participate.
  2. Use constraints and a transaction to apply the database unit.
  3. Rollback and propagate failures; do not report success before commit.
  4. Use durable messaging patterns for external effects.

CODE OR QUERY

Try it

SET XACT_ABORT ON;
BEGIN TRY
  BEGIN TRANSACTION;
  UPDATE dbo.Account
    SET Balance = Balance - @amount
    WHERE AccountId = @fromId AND Balance >= @amount;
  IF @@ROWCOUNT <> 1 THROW 50001, 'Insufficient funds or account missing.', 1;
  UPDATE dbo.Account SET Balance = Balance + @amount WHERE AccountId = @toId;
  IF @@ROWCOUNT <> 1 THROW 50002, 'Destination account missing.', 1;
  COMMIT TRANSACTION;
END TRY
BEGIN CATCH
  IF XACT_STATE() <> 0 ROLLBACK TRANSACTION;
  THROW;
END CATCH;

TRADE-OFFS

Benefits and limitations

Benefits

  • Atomic commits prevent partially applied database units.
  • Constraints and transactions protect consistency during concurrency.

Limitations

  • Long transactions hold locks or versions and can increase contention.
  • A local transaction does not atomically commit email, payment gateway, or message broker effects.

DECISION GUIDE

When to use it

Use: Use transactions for a bounded set of database changes that must succeed or fail together.

Avoid: Avoid holding a DB transaction open across slow external calls; use an outbox/saga and idempotency for cross-system workflows.

COMMON MISTAKES

Watch out

  • Assuming a successful application method means the transaction committed.
  • Holding a transaction open while calling remote services.
  • Relying only on application validation instead of database constraints for shared invariants.

BEST PRACTICES

In practice

  • Keep transactions short and scoped to related database writes.
  • Use constraints and conditional writes for invariants.
  • Use outbox, idempotency, and compensating actions across service boundaries.
  • Handle rollback and uncertain commit outcomes explicitly.

SENIOR-LEVEL SCENARIO

Production thinking

An order is saved but inventory is not decremented. Put database invariant changes in one transaction and use an outbox for subsequent events; make consumers idempotent to handle delivery retries.

SUMMARY

In one minute

ACID describes Atomicity (all-or-nothing), Consistency (valid states/invariants), Isolation (concurrent work behaves according to isolation rules), and Durability (committed work survives failures according to configured guarantees). ACID guides schema constraints, transaction boundaries, error handling, and recovery design. It does not mean every business workflow automatically has correct invariants or that all isolation levels provide serial behavior.
