SQL Query Processing

Have you ever wondered what happens after you execute a SQL query? How does a database understand your query, find the required records, optimize the execution, and return the result?

1. What is SQL Query Processing?

SQL (Structured Query Language) is used to communicate with relational databases.
We use SQL to retrieve, insert, update, and delete data.

SQL Query Processing is the mechanism through which a database understands a SQL statement, determines how to execute it, retrieves the required data, and returns the result.

Let's understand with a simple example

Imagine you are working in an organization with 10,000 employees. You want to retrieve employees whose salary is greater than 50,000. 

SELECT *
FROM employees
WHERE salary > 50000;

You submit this query to PostgreSQL. But how does PostgreSQL know where the employees table is located? How does it check the salary condition? Does it read every record? Can it use an index?

All these activities are part of SQL Query Processing.

Remember: A database does not simply read your SQL statement and execute it line by line. It analyzes the query and creates an execution strategy before retrieving the result.

3. SQL Logical Query Processing Order

Why do we need to understand this?

When writing SQL, we generally start with SELECT, followed by FROM and WHERE. However, SQL clauses have a logical processing order that is different from their written order.

Understanding this order helps us understand how filtering, grouping, aggregation, and sorting work together.

Example query

SELECT
    department_id,
    COUNT(*) AS total_employees
FROM employees
WHERE salary > 50000
GROUP BY department_id
HAVING COUNT(*) > 5
ORDER BY total_employees DESC
LIMIT 10;

Logical processing sequence

1. FROM
2. WHERE
3. GROUP BY
4. HAVING
5. SELECT
6. ORDER BY
7. LIMIT

JOIN and ON are part of the FROM/join processing stage. DISTINCT is applied after SELECT and before ORDER BY.

3.1 FROM – Identify the source table

FROM employees

FROM tells PostgreSQL which table should provide the data. In our example, the source table is employees, containing 14 records.

3.6 ORDER BY – Sort the result

ORDER BY sorts the result according to the specified column or expression. DESC means descending order, while ASC means ascending order.

Our two departments have equal counts, so their relative ordering is not guaranteed. To guarantee deterministic ordering, we could add department_id as a second sort key. 

ORDER BY total_employees DESC,
         department_id ASC

LIMIT returns at most 10 rows from the sorted result. Since our example produces only two rows, both are returned.

Important distinction: Logical processing order describes the meaning of a SQL query. It does not mean PostgreSQL physically creates a separate table after every clause.

4. SQL Parsing and Validation

What is SQL parsing?

Parsing is the process of analyzing the structure of a SQL statement to understand whether it follows the SQL grammar. PostgreSQL converts the statement into a structured representation called a parse tree.

Example

SELECT employee_name
FROM employees
WHERE salary > 50000;

PostgreSQL identifies different elements of this statement:

What happens if the SQL syntax is incorrect?

Consider this invalid query:

SELEC employee_name
FROM employees;

SELECT has been misspelled as SELEC. PostgreSQL cannot recognize the statement according to its SQL grammar and reports a syntax error.

What is semantic validation?

A query can have valid syntax but still refer to a table or column that does not exist. 

SELECT employee_address
FROM employees;

If employee_address does not exist in the employees table, PostgreSQL reports a missing-column error during analysis.

ValidationExamplePurpose
Syntax SELEC instead of SELECT Check SQL grammar
Table resolution Unknown table Find the referenced table
Column resolution Unknown column Find the referenced column
Type checking Incompatible expression types Check expression compatibility
PostgreSQL separates parsing from parse analysis. Table and column resolution, type checking, and other semantic checks happen during analysis, not merely during syntax parsing.

5. Query Optimization

What is query optimization?

A database may have multiple ways to retrieve the same data. Query optimization is the process of choosing an efficient execution strategy based on available information such as table statistics, indexes, and estimated costs.

Example: Find an employee by ID

SELECT *
FROM employees
WHERE employee_id = 100;

Assume employees contains 1 million records and employee_id has a primary key index.

The database could consider two approaches:

Approach 1: Sequential Scan

Read table rows sequentially and check whether employee_id equals 100.

Read table rows
Check employee_id
Find matching row

Approach 2: Index Scan

Use the index on employee_id to locate the matching row, then retrieve the corresponding table record.

Search index
Locate row reference
Retrieve table row
ApproachHow it worksTypical use
Sequential Scan Reads table pages sequentially Large portion of table needed
Index Scan Uses an index to locate matching rows Selective lookup

Does the database always use an index?

No. An index does not guarantee a faster query. If a query needs a large percentage of the table, a sequential scan may be more efficient.

Understand query plans using PostgreSQL

EXPLAIN
SELECT *
FROM employees
WHERE employee_id = 100;

EXPLAIN displays the execution plan chosen by PostgreSQL. It helps us understand which operations the database intends to perform.

6. Physical Query Execution

What is physical query execution?

After the optimizer chooses an execution plan, PostgreSQL executes that plan using physical execution operators. These operators perform actual data retrieval, filtering, joining, sorting, and aggregation.

Example: Retrieve high-salary employees

SELECT *
FROM employees
WHERE salary > 50000;

One possible execution plan is a sequential scan with a filter condition.

Sequential Scan
Filter salary > 50000
Return matching rows

Common physical operators

6.1 Sequential Scan

Reads the table's pages sequentially and checks rows against the query condition.

6.2 Index Scan

Uses an index to locate matching entries and fetches the corresponding table rows. 

CREATE INDEX idx_employee_salary

6.3 Nested Loop Join

For each row from one input, PostgreSQL searches for matching rows in the other input. 

SELECT e.employee_name, d.department_name
FROM employees e
JOIN departments d
ON e.department_id = d.department_id;

PostgreSQL builds a hash table from one input and probes it using rows from the other input to find matching keys.

6.5 Sort

Sorts rows based on the requested ordering criteria. Depending on the operation, sorting may use memory and can spill to temporary disk files.

FROM employees
ORDER BY salary DESC;

6.6 Aggregate

Calculates values such as COUNT, SUM, AVG, MIN, and MAX. PostgreSQL can use different aggregation strategies, including HashAggregate and GroupAggregate. 

SELECT department_id, AVG(salary)
FROM employees
GROUP BY department_id;

7. Database Engine Internals

Why do we need to understand database internals?

Knowing SQL syntax is not enough when building high-performance applications. We also need to understand how databases store, retrieve, and manage data internally.

7.1 What happens when data is requested?

Imagine a query requests an employee record. PostgreSQL needs to access the relevant table data. The required data page may already be available in memory or may need to be read from storage.

7.2 What are database pages?

PostgreSQL stores table and index data in fixed-size pages. The default page size in a standard PostgreSQL build is commonly 8 KB.

A table is stored across multiple pages. Each page contains a page header and row-related information.

7.3 What is Shared Buffers?

Shared Buffers is PostgreSQL's main shared memory area used to cache table and index pages. It helps avoid repeatedly reading the same pages from disk.

SituationWhat happens
Page already in memory PostgreSQL can access the cached page.
Page not in memory PostgreSQL reads it from storage into shared buffers.

7.4 What is MVCC?

MVCC stands for Multi-Version Concurrency Control. PostgreSQL uses MVCC to allow transactions to work with consistent snapshots of data while other transactions may be modifying records.

Example:

  • Transaction A starts reading employee records.
  • Transaction B updates an employee salary.
  • Transaction A continues using its transaction snapshot.
  • Transaction A sees data according to its isolation level and snapshot.

8. Query Performance and Optimization

Why are some SQL queries slow?

A query may be slow because it reads too much data, uses inefficient joins, lacks appropriate indexes, performs expensive sorting, or waits on resources.

Example: Analyze query performance

EXPLAIN ANALYZE
SELECT *
FROM employees
WHERE salary > 50000;

EXPLAIN ANALYZE executes the query and reports the actual execution plan and runtime statistics.

Important execution plan metrics

MetricMeaning
Seq Scan Table rows are scanned sequentially.
Index Scan Rows are accessed through an index.
Estimated Rows Rows the optimizer expects an operation to produce.
Actual Rows Rows actually produced during execution.
Planning Time Time spent planning the query.
Execution Time Reported execution time.

How can we improve performance?

-- Create an index
CREATE INDEX idx_employees_salary
ON employees(salary);

-- Analyze table statistics
ANALYZE employees;

-- Inspect the execution plan
EXPLAIN ANALYZE
SELECT *
FROM employees
WHERE salary > 50000;
An index is not always the answer. Always examine the execution plan and understand the workload before adding indexes.

9. Database Architecture and Production Scenarios

How does SQL Query Processing fit into an application?

In a real application, users do not normally connect to database storage directly. Requests travel through application services and database connections before reaching the database engine.

Example: Employee management application

User
Frontend
Backend API
Connection Pool
PostgreSQL

When a user opens the employee list:

  1. The frontend sends a request to the backend.
  2. The backend obtains a database connection.
  3. The backend submits a SQL query.
  4. PostgreSQL parses, plans, and executes the query.
  5. The database returns rows.
  6. The backend sends the response to the frontend.
