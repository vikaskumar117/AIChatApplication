APPLY THE IDEA

Worked example

A date-range query scans because a conversion wraps the indexed column; rewrite to a half-open date range, then validate correctness and reads.

  1. Identify the exact query and capture representative parameters.
  2. Record baseline duration, CPU, logical reads, row counts, waits, and plan.
  3. Determine whether database execution, blocking, network transfer, or client work dominates.
  4. Test one change and compare correctness, p95/p99, reads, CPU, and write impact.

CODE OR QUERY

Try it

-- Prefer a half-open range over applying YEAR() to the column.
SELECT OrderId, CreatedAt, Total
FROM dbo.[Order]
WHERE CreatedAt >= @dayStart
  AND CreatedAt < DATEADD(day, 1, @dayStart);

TRADE-OFFS

Benefits and limitations

Benefits

  • Evidence-driven changes target the measured bottleneck.
  • A baseline and controlled comparison reduce regression risk.

Limitations

  • Plan/runtime collection and representative load testing require time and access.
  • Parameter sensitivity and changing data distributions can make one plan or benchmark misleading.

DECISION GUIDE

When to use it

Use: Use this workflow for regressions and expensive queries before changing schema or query shape.

Avoid: Avoid optimizing from elapsed time alone or treating a single plan screenshot as a representative workload.

COMMON MISTAKES

Watch out

  • Adding an index before checking whether the query is blocked or returning too many rows.
  • Using only average duration and missing tail latency or parameter variation.
  • Applying a rewrite without comparing semantics and result cardinality.

BEST PRACTICES

In practice

  • Correlate API traces with database query identity and Query Store.
  • Record parameter ranges, plan, actual rows, reads, CPU, waits, and result size.
  • Roll out risky changes gradually with monitoring and a rollback path.

INTERVIEW PRACTICE

Common questions

  1. Which metrics distinguish CPU-bound from I/O-bound work?
  2. What does a large estimated-versus-actual row difference suggest?
  3. How do parameter-sensitive plans affect query tuning?

SENIOR-LEVEL SCENARIO

Production thinking

An API’s p95 latency doubled after data growth. Correlate request traces with Query Store, compare plan IDs and logical reads, inspect waits and row estimates, test a sargable predicate/index change on representative parameters, then monitor p95 and write costs after rollout.

SUMMARY

In one minute

Query optimization is a measured process of identifying the dominant cost (I/O, CPU, waits, blocking, network, or client processing) and changing the query, index, statistics, or workload safely. A slow endpoint is not always a slow SQL statement. Guessing or rewriting before collecting a baseline can optimize the wrong layer and cause regressions.
