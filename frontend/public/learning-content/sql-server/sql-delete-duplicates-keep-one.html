Delete Duplicate Rows While Keeping One in SQL Server

Learn how to identify duplicate records, decide which record to retain, safely delete the remaining duplicates, validate the results, and prevent duplicates from returning.

1. Understanding the Problem

Duplicate records occur when multiple rows represent the same business entity or event. For example, a customer may have been imported twice because of a failed integration or missing validation.

Consider these customer records:

CustomerId CustomerCode CustomerName Email CreatedDate
1C001Alicealice@example.com2025-01-01
2C002Bobbob@example.com2025-01-02
3C001Alicealice@example.com2025-01-05
4C003Carolcarol@example.com2025-01-06
5C002Bobbob@example.com2025-01-08
6C001Alicealice@example.com2025-01-10

CustomerCode is the business key in this example. C001 appears three times and C002 appears twice.

Important: A duplicate is defined by the business rule, not necessarily by identical values in every column. Two records can have different CustomerIds and CreatedDates but still represent the same customer.

2. Create the Sample Table

CREATE TABLE Customers
(
    CustomerId INT IDENTITY(1,1) PRIMARY KEY,
    CustomerCode VARCHAR(20),
    CustomerName VARCHAR(100),
    Email VARCHAR(150),
    CreatedDate DATE
);

INSERT INTO Customers
    (CustomerCode, CustomerName, Email, CreatedDate)
VALUES
    ('C001', 'Alice', 'alice@example.com', '2025-01-01'),
    ('C002', 'Bob', 'bob@example.com', '2025-01-02'),
    ('C001', 'Alice', 'alice@example.com', '2025-01-05'),
    ('C003', 'Carol', 'carol@example.com', '2025-01-06'),
    ('C002', 'Bob', 'bob@example.com', '2025-01-08'),
    ('C001', 'Alice', 'alice@example.com', '2025-01-10');

View the records:

SELECT *
FROM Customers
ORDER BY CustomerId;

We will keep the oldest record for each CustomerCode and delete the newer records.

3. Step 1 — Identify Duplicate Business Keys

Before deleting anything, identify which business keys occur more than once. 

SELECT
    CustomerCode,
    COUNT(*) AS DuplicateCount
FROM Customers
GROUP BY CustomerCode
HAVING COUNT(*) > 1;

Output

CustomerCode DuplicateCount
C0013
C0022

There are two duplicate business keys.

Retrieve all rows belonging to duplicate keys

SELECT C.*
FROM Customers C
INNER JOIN
(
    SELECT CustomerCode
    FROM Customers
    GROUP BY CustomerCode
    HAVING COUNT(*) > 1
) D
    ON C.CustomerCode = D.CustomerCode
ORDER BY C.CustomerCode, C.CustomerId;

This query returns all rows belonging to duplicated CustomerCodes. It does not delete anything.

4. Step 2 — Assign a Row Number to Each Duplicate Group

The most common SQL Server solution is ROW_NUMBER(). 

SELECT
    CustomerId,
    CustomerCode,
    CustomerName,
    Email,
    CreatedDate,
    ROW_NUMBER() OVER
    (
        PARTITION BY CustomerCode
        ORDER BY CreatedDate ASC, CustomerId ASC
    ) AS RowNum
FROM Customers;

Understand the window function

  • PARTITION BY CustomerCode creates a separate group for each customer code.
  • ORDER BY CreatedDate ASC places the oldest record first.
  • CustomerId ASC breaks ties when CreatedDate is identical.
  • ROW_NUMBER() assigns a sequential number within each group.

Output

CustomerId CustomerCode CreatedDate RowNum Action
1C0012025-01-011Keep
3C0012025-01-052Delete
6C0012025-01-103Delete
2C0022025-01-021Keep
5C0022025-01-082Delete
4C0032025-01-061Keep
Partition

Separate rows by CustomerCode.

Sort

Place the oldest record first within each group.

Number

Assign row numbers starting at 1.

Classify

Keep row 1 and mark rows greater than 1 for deletion.

The key rule is: retain RowNum = 1 and remove RowNum greater than 1.

5. Step 3 — Delete Duplicates Using a CTE

SQL Server supports deleting rows directly from an updatable CTE. This makes the duplicate deletion query concise. 

WITH DuplicateRecords AS
(
    SELECT
        CustomerId,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerCode
            ORDER BY CreatedDate ASC, CustomerId ASC
        ) AS RowNum
    FROM Customers
)
DELETE FROM DuplicateRecords
WHERE RowNum > 1;

What happens?

  1. The CTE reads the Customers records.
  2. ROW_NUMBER() numbers rows within each CustomerCode group.
  3. Rows with RowNum = 1 are retained.
  4. Rows with RowNum greater than 1 are deleted from the underlying Customers table.

Expected remaining data

CustomerId CustomerCode CustomerName CreatedDate
1C001Alice2025-01-01
2C002Bob2025-01-02
4C003Carol2025-01-06
Why is this safe only after validation? The query permanently deletes rows when committed. First verify the business key, the retention rule, and the rows marked for deletion.

6. Step 4 — Preview Rows Before Deleting

In production, never begin with the DELETE statement. First run a SELECT using the same ranking logic. 

WITH DuplicateRecords AS
(
    SELECT
        CustomerId,
        CustomerCode,
        CustomerName,
        CreatedDate,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerCode
            ORDER BY CreatedDate ASC, CustomerId ASC
        ) AS RowNum
    FROM Customers
)
SELECT *
FROM DuplicateRecords
WHERE RowNum > 1
ORDER BY CustomerCode, RowNum;

Review the output carefully. It should contain only the records that the business has approved for removal.

Preview the records to keep

WITH RankedCustomers AS
(
    SELECT
        *,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerCode
            ORDER BY CreatedDate ASC, CustomerId ASC
        ) AS RowNum
    FROM Customers
)
SELECT *
FROM RankedCustomers
WHERE RowNum = 1;

7. Step 5 — Delete Duplicates Inside a Transaction

A transaction allows you to inspect the deletion before deciding whether to commit or roll back. 

SET XACT_ABORT ON;

BEGIN TRY
    BEGIN TRANSACTION;

    WITH DuplicateRecords AS
    (
        SELECT
            CustomerId,
            ROW_NUMBER() OVER
            (
                PARTITION BY CustomerCode
                ORDER BY CreatedDate ASC, CustomerId ASC
            ) AS RowNum
        FROM Customers
    )
    DELETE FROM DuplicateRecords
    WHERE RowNum > 1;

    -- Inspect the remaining records before committing.
    SELECT *
    FROM Customers
    ORDER BY CustomerCode, CustomerId;

    -- Choose ONE of the following:
    -- COMMIT TRANSACTION;
    -- ROLLBACK TRANSACTION;

END TRY
BEGIN CATCH

    IF XACT_STATE() <> 0
        ROLLBACK TRANSACTION;

    THROW;

END CATCH;

How to use this example

  1. Execute the script with the COMMIT and ROLLBACK lines still commented.
  2. Inspect the result while the transaction remains open in the same session.
  3. Uncomment COMMIT to permanently save the deletion, or ROLLBACK to restore the deleted rows.
  4. Do not execute both statements.
Production warning: A long-running transaction can hold locks and consume transaction log space. Use a controlled maintenance window, monitor blocking, and consider batching for large tables.

8. Alternative — Delete Using a Temporary Table

If you want to inspect and store the exact IDs to delete before performing the deletion, use a temporary table. 

SELECT CustomerId
INTO #DuplicateCustomerIds
FROM
(
    SELECT
        CustomerId,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerCode
            ORDER BY CreatedDate ASC, CustomerId ASC
        ) AS RowNum
    FROM Customers
) R
WHERE RowNum > 1;

-- Preview IDs selected for deletion.
SELECT *
FROM #DuplicateCustomerIds;

-- Delete the selected records.
DELETE C
FROM Customers C
INNER JOIN #DuplicateCustomerIds D
    ON C.CustomerId = D.CustomerId;

DROP TABLE #DuplicateCustomerIds;

This separates identification from deletion. However, the temporary list can become stale if another session modifies the table between the two operations. For production use, coordinate concurrent writes or perform selection and deletion under an appropriate transaction and isolation strategy.

9. What If We Want to Keep the Latest Record?

Sometimes the newest record is the correct one to retain. In that case, reverse the date ordering. 

WITH DuplicateRecords AS
(
    SELECT
        CustomerId,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerCode
            ORDER BY CreatedDate DESC, CustomerId DESC
        ) AS RowNum
    FROM Customers
)
DELETE FROM DuplicateRecords
WHERE RowNum > 1;

The newest CreatedDate receives RowNum = 1. CustomerId DESC provides a deterministic tie-breaker when dates are equal.

The correct record to retain is a business decision. It could be the oldest, newest, most recently verified, or the record with the most complete information.

10. What If the Business Key Contains Multiple Columns?

A duplicate may be identified by a combination of columns, rather than one column alone.

For example, attendance records may be unique by EmployeeId and AttendanceDate.

WITH DuplicateAttendance AS
(
    SELECT
        AttendanceId,
        EmployeeId,
        AttendanceDate,
        ROW_NUMBER() OVER
        (
            PARTITION BY EmployeeId, AttendanceDate
            ORDER BY CreatedDate ASC, AttendanceId ASC
        ) AS RowNum
    FROM EmployeeAttendance
)
DELETE FROM DuplicateAttendance
WHERE RowNum > 1;

Here, two rows are considered duplicates only when both EmployeeId and AttendanceDate match.

The same pattern works for composite business keys such as:

  • OrderId + ProductId
  • AccountId + TransactionReference
  • EmployeeId + AttendanceDate
  • ProductCode + WarehouseId

11. Handling NULL Values in Business Keys

SQL Server groups NULL values together in GROUP BY and PARTITION BY operations. 

SELECT
    CustomerCode,
    COUNT(*) AS TotalRows
FROM Customers
GROUP BY CustomerCode;

If CustomerCode is NULL for multiple records, they form one group. A ROW_NUMBER() partitioned by CustomerCode will also number those rows together.

Decide whether NULL means an unknown business key, an invalid record, or a shared category. Do not automatically delete all but one NULL-key record unless that matches the business rule.

If records with NULL business keys should not participate in duplicate removal, filter them out: 

WITH DuplicateRecords AS
(
    SELECT
        CustomerId,
        ROW_NUMBER() OVER
        (
            PARTITION BY CustomerCode
            ORDER BY CreatedDate ASC, CustomerId ASC
        ) AS RowNum
    FROM Customers
    WHERE CustomerCode IS NOT NULL
)
DELETE FROM DuplicateRecords
WHERE RowNum > 1;

12. Exact Duplicates vs Business-Key Duplicates

These two situations are different and require different definitions of a duplicate.

Type Definition Example
Exact duplicate All relevant data columns have identical values. Same name, email, city and date.
Business-key duplicate The business identifier matches, even if other values differ. Same CustomerCode but different CreatedDate.

For exact duplicate detection, partition by the relevant data columns rather than only CustomerCode. 

WITH ExactDuplicates AS
(
    SELECT
        CustomerId,
        ROW_NUMBER() OVER
        (
            PARTITION BY
                CustomerCode,
                CustomerName,
                Email,
                CreatedDate
            ORDER BY CustomerId
        ) AS RowNum
    FROM Customers
)
SELECT *
FROM ExactDuplicates
WHERE RowNum > 1;

This example identifies duplicate combinations of those four columns. It does not mean that every column in the table is identical.

13. Prevent Duplicates from Returning

Removing existing duplicates is only part of the solution. The application or database should prevent new duplicates from being inserted.

Step 1: Validate that the data is clean

SELECT
    CustomerCode,
    COUNT(*) AS TotalRows
FROM Customers
GROUP BY CustomerCode
HAVING COUNT(*) > 1;

Resolve all duplicate keys before creating a unique index.

Step 2: Create a unique index

CREATE UNIQUE INDEX UX_Customers_CustomerCode
ON Customers(CustomerCode);

SQL Server will reject an insert or update that creates another row with an existing non-NULL CustomerCode.

A SQL Server unique index allows only one NULL key value for a single-column unique index. If the business key is optional and multiple NULL values are valid, consider a filtered unique index: 
CREATE UNIQUE INDEX UX_Customers_CustomerCode_NotNull
ON Customers(CustomerCode)
WHERE CustomerCode IS NOT NULL;

For a composite key, create the unique index over all columns that together define uniqueness.

14. SQL Server Internals and Performance

How SQL Server processes ROW_NUMBER()

1. Access the table

SQL Server reads rows from a heap, clustered index or nonclustered index.

2. Partition and order rows

Rows are organized by business key and the chosen retention order.

3. Calculate row numbers

Windowing operators assign row numbers within each partition.

4. Filter duplicate rows

Rows with RowNum greater than 1 are selected for deletion.

5. Delete from the base table

SQL Server removes the selected rows and maintains affected indexes.

Possible execution plan operators

Operator Purpose
Index ScanReads rows from an index.
Table ScanReads rows from a heap.
SortOrders rows by partition and ordering columns when needed.
SegmentIdentifies boundaries between partitions in applicable plans.
Sequence ProjectCan calculate row-number values in applicable plans.
FilterRetains rows satisfying RowNum greater than 1.
DeleteDeletes selected records from the base table.

The actual plan can vary with SQL Server version, indexes, cardinality estimates and data distribution.

Index to support duplicate detection

CREATE NONCLUSTERED INDEX IX_Customers_DuplicateCheck
ON Customers
(
    CustomerCode,
    CreatedDate,
    CustomerId
);

This index may help SQL Server read rows in an order useful for partitioning and ranking. Whether it eliminates a sort or improves the overall delete depends on the chosen plan.

Measure performance

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Run the duplicate identification SELECT first.

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

Check logical reads, CPU time, elapsed time, sort costs, memory grants and possible spills. For DELETE operations, also account for transaction log activity and index maintenance.

15. Production Considerations

1. Foreign key dependencies

Other tables may reference the duplicate CustomerId. Deleting a customer can fail because of foreign key constraints or cause dependent records to be removed if cascading deletes are configured.

Before deletion, identify child records and decide whether they should be reassigned to the retained CustomerId.

2. Concurrent inserts

Another application session could insert a duplicate while cleanup is running. A transaction alone does not automatically prevent every possible concurrent duplicate insertion.

Coordinate the cleanup with application writes, use suitable isolation and locking where required, and enforce uniqueness with a unique index after cleanup.

3. Large tables

Deleting millions of rows in one transaction can generate substantial transaction log activity, cause blocking, and increase recovery time. Consider batching, monitoring log growth and testing the operation on representative data.

4. Audit and recovery

For important business tables, retain an audit record of deleted IDs and relevant column values. Confirm that a tested backup and recovery strategy exists before cleanup.

16. Common Mistakes

  1. Deleting before identifying the business key. Two rows that look similar may represent different business entities.
  2. Using ROW_NUMBER() without a deterministic order. The retained row may not be predictable when the ordering columns tie.
  3. Deleting every row in a duplicate group. The correct filter is usually RowNum greater than 1, not RowNum greater than 0.
  4. Ignoring foreign keys. Related records may prevent deletion or become orphaned if constraints are absent.
  5. Ignoring NULL business keys. NULL rows can be grouped together by PARTITION BY.
  6. Assuming a transaction is a backup. A transaction helps control the current operation; it does not replace a recovery strategy.
  7. Failing to prevent new duplicates. Clean data can become duplicated again unless uniqueness is enforced appropriately.

18. Knowledge Check

Question 1

Which function is commonly used to number duplicate rows?

  • A. MAX()
  • B. ROW_NUMBER()
  • C. COUNT()
  • D. SUM()

Answer: B. ROW_NUMBER()

Question 2

Which condition removes all but the first row in each group?

  • A. RowNum = 1
  • B. RowNum = 0
  • C. RowNum greater than 1
  • D. RowNum greater than 0

Answer: C. RowNum greater than 1.

Question 3

Why should a unique tie-breaker be included in the ORDER BY clause?

  • A. To increase the number of duplicates
  • B. To make the retained row deterministic
  • C. To remove the primary key
  • D. To avoid using a CTE

Answer: B. To make the retained row deterministic.

Question 4

What is the best way to prevent the same business key from being inserted again?

  • A. Run DELETE every day
  • B. Use DISTINCT in every SELECT
  • C. Enforce uniqueness with an appropriate unique index or constraint
  • D. Hide duplicate rows in the application

Answer: C. Enforce uniqueness with an appropriate unique index or constraint.

19. What You Should Be Able to Do

  • Identify duplicates using GROUP BY and HAVING.
  • Distinguish business-key duplicates from exact duplicates.
  • Use ROW_NUMBER() to select which record to retain.
  • Delete duplicates using a CTE.
  • Preview deletion candidates before removing records.
  • Use transactions to control and validate cleanup operations.
  • Handle composite keys and NULL business keys.
  • Understand foreign key, concurrency and transaction log considerations.
  • Use unique indexes to prevent future duplicates.

The most important production principle is to define the business key and retention rule first, preview the deletion candidates, and only then execute the cleanup.
