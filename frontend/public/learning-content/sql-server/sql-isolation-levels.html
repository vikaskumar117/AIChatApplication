Transaction Isolation Levels in SQL Server

Understand how SQL Server manages concurrent transactions, prevents inconsistent reads, and balances data consistency against concurrency and performance.

1. Learning Objectives

  • Understand transaction isolation and concurrency control.
  • Learn all five SQL Server transaction isolation levels.
  • Reproduce dirty reads, non-repeatable reads, and phantom reads.
  • Understand shared, update, and exclusive locks.
  • Understand row versioning and the version store.
  • Compare READ COMMITTED SNAPSHOT and SNAPSHOT isolation.
  • Choose an appropriate isolation level for different workloads.
  • Understand the performance and blocking trade-offs.

2. What Is Transaction Isolation?

In a database, multiple users and applications can execute transactions simultaneously. Isolation determines how one transaction is allowed to observe changes made by another transaction.

Consider two users accessing the same bank account:

AccountId AccountName Balance
1John5000.00
  • Transaction A updates the balance to 4000.
  • Transaction B reads the balance before Transaction A commits.
  • Transaction A might subsequently roll back.

Should Transaction B be allowed to read the uncommitted value? The answer depends on the isolation level.

Transaction A

Updates database data

Transaction B

Reads or modifies related data

Isolation control

Locks or row versions control visibility

Consistent result

Database follows the configured isolation rules

4. The Five SQL Server Isolation Levels

Isolation level Dirty reads Non-repeatable reads Phantom reads
READ UNCOMMITTED Possible Possible Possible
READ COMMITTED Prevented Possible Possible
REPEATABLE READ Prevented Prevented Possible
SERIALIZABLE Prevented Prevented Prevented
SNAPSHOT Prevented Prevented within the transaction's snapshot Prevented within the transaction's snapshot

SQL Server also supports READ COMMITTED SNAPSHOT (RCSI), a database-level option that uses row versioning to provide statement-level read consistency under READ COMMITTED. It is not a sixth session isolation level.

5. READ UNCOMMITTED

READ UNCOMMITTED is the lowest isolation level. It permits a transaction to read changes that another transaction has not committed.

This behavior is called a dirty read.

Set the isolation level

SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

BEGIN TRANSACTION;

SELECT *
FROM dbo.Account
WHERE AccountId = 1;

COMMIT TRANSACTION;

Demonstrate a dirty read

Open two query windows connected to the same database.

Session 1 — Update without committing

BEGIN TRANSACTION;

UPDATE dbo.Account
SET Balance = 1000
WHERE AccountId = 1;

-- Keep the transaction open.
WAITFOR DELAY '00:00:20';

ROLLBACK TRANSACTION;

Session 2 — Read uncommitted data

Execute this while Session 1 is waiting:

SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

SELECT
    AccountId,
    AccountName,
    Balance
FROM dbo.Account
WHERE AccountId = 1;

Session 2 may return:

AccountId AccountName Balance
1John1000.00

After Session 1 rolls back, the actual balance returns to 5000. Session 2 has read a value that was never committed.

READ UNCOMMITTED can also produce inconsistent results while rows are being modified or moved. It should not be used simply to make a slow query appear faster.

Equivalent table hint

SELECT *
FROM dbo.Account WITH (NOLOCK);

NOLOCK is equivalent to READ UNCOMMITTED for that table reference. It does not eliminate every lock interaction, including schema stability locks.

6. READ COMMITTED

READ COMMITTED is SQL Server's default isolation level for a newly opened session unless it has been changed.

It prevents dirty reads. A transaction can only read committed data, but it may see different committed values if it reads the same row multiple times. 

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN TRANSACTION;

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

COMMIT TRANSACTION;

Demonstrate non-repeatable reads

Session 1 — Read the account twice

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

BEGIN TRANSACTION;

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

WAITFOR DELAY '00:00:10';

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

COMMIT TRANSACTION;

Session 2 — Update between the reads

Execute during Session 1's delay:

UPDATE dbo.Account
SET Balance = Balance + 500
WHERE AccountId = 1;

Possible Session 1 output:

Read Balance
First read5000.00
Second read5500.00

The same transaction reads the same row twice but receives different committed values. This is a non-repeatable read.

Locking behavior

With locking-based READ COMMITTED, shared locks are generally released after the statement finishes. Exclusive locks protecting modifications are held until transaction completion.

If READ_COMMITTED_SNAPSHOT is enabled, READ COMMITTED uses statement-level row versions instead of shared data locks for ordinary reads.

7. REPEATABLE READ

REPEATABLE READ prevents another transaction from modifying rows already read by the current transaction until it completes.

Shared locks on qualifying rows are held until transaction completion. However, new rows matching the search condition may still be inserted by other transactions. 

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

BEGIN TRANSACTION;

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

WAITFOR DELAY '00:00:10';

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

COMMIT TRANSACTION;

Session 2 — Try to update the same row

UPDATE dbo.Account
SET Balance = Balance + 500
WHERE AccountId = 1;

Session 2 must wait while Session 1 holds its shared lock. Session 1 should see the same committed row value both times.

REPEATABLE READ protects rows that have been read, but it does not protect the entire range of values matching a predicate. That distinction is important when preventing phantom reads.

8. SERIALIZABLE

SERIALIZABLE is the strongest locking-based isolation level. It prevents dirty reads, non-repeatable reads, and phantom reads.

SQL Server uses key-range locks where necessary to prevent another transaction from inserting rows into a range read by the current transaction.

Demonstrate phantom protection

First, create a test table:

DROP TABLE IF EXISTS dbo.EmployeeSalary;

CREATE TABLE dbo.EmployeeSalary
(
    EmployeeId INT NOT NULL
        CONSTRAINT PK_EmployeeSalary PRIMARY KEY,
    EmployeeName VARCHAR(50) NOT NULL,
    Salary DECIMAL(12,2) NOT NULL
);

INSERT INTO dbo.EmployeeSalary
(
    EmployeeId,
    EmployeeName,
    Salary
)
VALUES
    (1, 'Alice', 50000),
    (2, 'Bob', 65000),
    (3, 'Carol', 75000);

Session 1 — Read a salary range

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

BEGIN TRANSACTION;

SELECT *
FROM dbo.EmployeeSalary
WHERE Salary BETWEEN 50000 AND 70000;

WAITFOR DELAY '00:00:20';

SELECT *
FROM dbo.EmployeeSalary
WHERE Salary BETWEEN 50000 AND 70000;

COMMIT TRANSACTION;

Session 2 — Insert into the range

Execute while Session 1 is waiting:

INSERT INTO dbo.EmployeeSalary
(
    EmployeeId,
    EmployeeName,
    Salary
)
VALUES
(
    4,
    'David',
    60000
);

Session 2 should wait until Session 1 finishes because the serializable transaction protects the relevant key range.

Session 1 therefore does not see a newly inserted row in its second query.

Why indexes matter

Create an index on Salary to provide an ordered key structure for range access: 

CREATE NONCLUSTERED INDEX IX_EmployeeSalary_Salary
ON dbo.EmployeeSalary (Salary);

SQL Server can use this index for range access and key-range locking. Without a suitable index, it may need broader locking strategies to enforce serializable behavior.

9. SNAPSHOT Isolation

SNAPSHOT isolation uses row versioning to provide a transaction with a consistent view of committed data as of the start of that transaction.

Unlike locking-based REPEATABLE READ, a reader generally does not need to hold shared data locks that block writers.

Enable SNAPSHOT isolation

This is a database-level configuration change. Run it in a suitable maintenance window after evaluating the application and version-store implications. 

ALTER DATABASE YourDatabaseName
SET ALLOW_SNAPSHOT_ISOLATION ON;

Set transaction isolation

SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

BEGIN TRANSACTION;

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

WAITFOR DELAY '00:00:10';

SELECT Balance
FROM dbo.Account
WHERE AccountId = 1;

COMMIT TRANSACTION;

Concurrent update demonstration

Start the previous SNAPSHOT transaction in Session 1. While it is waiting, update the same account from Session 2 and commit. 

UPDATE dbo.Account
SET Balance = Balance + 500
WHERE AccountId = 1;

Session 1 continues to see the committed version that existed when its transaction began. It does not see Session 2's later committed update.

Important: Snapshot update conflicts

SNAPSHOT isolation is not simply a way to allow every transaction to update concurrently. If two snapshot transactions attempt to modify the same row after one has committed a change since the other transaction's snapshot began, SQL Server can terminate one transaction with an update conflict.

The application must handle the conflict and decide whether retrying the entire transaction is safe.

10. READ COMMITTED SNAPSHOT (RCSI)

READ COMMITTED SNAPSHOT is a database-level option that changes how READ COMMITTED reads are implemented.

With RCSI enabled, each statement sees a consistent snapshot of committed data as of the beginning of that statement.

Enable RCSI

ALTER DATABASE YourDatabaseName
SET READ_COMMITTED_SNAPSHOT ON;

The database may need exclusive access while this setting is changed. Plan the change carefully and verify the database state.

RCSI versus SNAPSHOT

Feature READ COMMITTED SNAPSHOT SNAPSHOT
Configuration Database option Database option plus session isolation level
Consistency point Beginning of each statement Beginning of the transaction
Ordinary read/write blocking Usually reduced Usually reduced
Repeat reads May see different committed versions in separate statements See the same transaction snapshot
Update conflicts Uses locking for writes; normal write conflicts can still occur Can produce snapshot update conflict errors
RCSI and SNAPSHOT are different consistency models. RCSI provides statement-level consistency; SNAPSHOT provides transaction-level consistency.

11. Understand Row Versioning Internals

SQL Server can preserve earlier committed versions of modified rows so that readers can access a consistent version without waiting for a writer's exclusive data lock.

Transaction A modifies a row

SQL Server creates or maintains version information.

Earlier row version retained

The previous committed version remains available.

Transaction B reads

The reader accesses the appropriate committed version.

Version cleanup

Old versions are cleaned up when no longer needed.

Where are row versions stored?

Depending on SQL Server version and configuration, row versions can be stored in tempdb or in the Persistent Version Store (PVS) associated with Accelerated Database Recovery (ADR).

  • Traditional row versioning uses the tempdb version store.
  • When ADR is enabled, the PVS in the user database is used for the relevant versioning workloads.
  • Long-running snapshot transactions can delay cleanup of versions they still need.
  • Version storage requires monitoring and capacity planning.

Inspect version-store usage in tempdb

SELECT
    database_id,
    reserved_page_count,
    reserved_space_kb
FROM sys.dm_tran_version_store_space_usage;

This DMV reports version-store space usage in tempdb by database. It does not report the Persistent Version Store inside user databases.

Inspect active snapshot transactions

SELECT
    transaction_id,
    transaction_sequence_num,
    elapsed_time_seconds,
    is_snapshot
FROM sys.dm_tran_active_snapshot_database_transactions;

DMV availability and permissions vary by SQL Server version. Monitor long-running transactions and version-store pressure as part of normal operations.

12. Isolation Level Comparison

Isolation Read behavior Concurrency impact Typical use
READ UNCOMMITTED Can read uncommitted data. Low reader-writer blocking, but inconsistent reads possible. Rare, carefully justified cases where dirty data is acceptable.
READ COMMITTED Reads committed data at statement execution. Locking-based implementation can block writers and readers. General transactional workloads.
REPEATABLE READ Previously read rows cannot be changed by other transactions until completion. More locks held for longer. Transactions requiring stable values for previously read rows.
SERIALIZABLE Protects rows and relevant key ranges. Can produce significant blocking and deadlocks. Operations requiring serializable range behavior.
SNAPSHOT Reads from a transaction-level committed snapshot. Reader-writer blocking reduced; update conflicts possible. Transactions needing consistent multi-statement reads.
RCSI Each statement reads a committed snapshot. Reader-writer blocking usually reduced. Systems with substantial concurrent read activity.

13. How to Change Isolation Levels

Change isolation for the current session

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT *
FROM dbo.Account;

-- Change back when required.
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SET TRANSACTION ISOLATION LEVEL changes the isolation setting for the current connection. Applications using connection pools should ensure that session settings are managed consistently.

Check the current session isolation level

SELECT
    session_id,
    transaction_isolation_level
FROM sys.dm_exec_sessions

14. Isolation Levels and SQL Server Locking

Locking-based isolation levels use locks to coordinate concurrent access. The duration and granularity of locks depend on the isolation level and execution plan.

Isolation Typical read behavior Range protection
READ UNCOMMITTED Does not request shared data locks for ordinary reads. No serializable range protection.
READ COMMITTED Shared locks are generally released after each statement under locking-based READ COMMITTED. No serializable range protection.
REPEATABLE READ Shared locks on qualifying rows held until transaction completion. Does not generally protect gaps against new qualifying rows.
SERIALIZABLE Uses locks and key-range locks as required. Protects qualifying ranges against phantom inserts.
SNAPSHOT Reads committed row versions. Uses a transaction-level snapshot instead of reader range locks.

Actual lock acquisition can vary because of query plans, indexes, lock hints, optimized locking features, and SQL Server version.

15. Choosing the Right Isolation Level

Scenario 1: General web application

READ COMMITTED is a common default. RCSI may be appropriate when read-heavy workloads suffer from reader-writer blocking.

Scenario 2: Financial transaction

A transfer operation must maintain business invariants. Use appropriate transactional updates, constraints, and concurrency controls. Do not assume that choosing SERIALIZABLE alone replaces application-level validation.

Scenario 3: Consistent report with multiple queries

SNAPSHOT may be suitable when several statements in one transaction need to observe the same committed database view.

Scenario 4: Prevent inserts into a searched range

SERIALIZABLE can protect the relevant key range against phantom inserts. Ensure the transaction is short and the access path is suitable.

Scenario 5: Analytics with tolerance for changing results

READ COMMITTED or RCSI may be appropriate depending on whether each statement needs a committed snapshot and how the reporting workload interacts with writers.

16. Common Mistakes

  • Assuming READ COMMITTED guarantees the same value across multiple statements.
  • Confusing READ COMMITTED SNAPSHOT with SNAPSHOT isolation.
  • Using NOLOCK to hide blocking without understanding dirty reads.
  • Choosing SERIALIZABLE for every transaction without measuring concurrency impact.
  • Ignoring long-running transactions that retain locks or row versions.
  • Enabling row versioning without monitoring version-store capacity.
  • Assuming SNAPSHOT prevents all write conflicts.
  • Ignoring transaction scope in application code.
  • Changing database isolation options without testing connection and application behavior.

18. Knowledge Check

Question 1

Which isolation level permits dirty reads?

  • A. READ COMMITTED
  • B. SERIALIZABLE
  • C. READ UNCOMMITTED
  • D. SNAPSHOT

Answer: C — READ UNCOMMITTED permits reading uncommitted changes.

Question 2

Which isolation level prevents non-repeatable reads using locking?

  • A. READ UNCOMMITTED
  • B. READ COMMITTED
  • C. REPEATABLE READ
  • D. All of the above

Answer: C — REPEATABLE READ holds shared locks on previously read qualifying rows until transaction completion.

Question 3

Which isolation level prevents phantom reads through key-range locking?

  • A. READ COMMITTED
  • B. REPEATABLE READ
  • C. READ UNCOMMITTED
  • D. SERIALIZABLE

Answer: D — SERIALIZABLE protects relevant key ranges.

Question 4

What is the consistency scope of SNAPSHOT isolation?

  • A. One statement
  • B. The entire transaction
  • C. One column
  • D. One index

Answer: B — SNAPSHOT provides a transaction-level view of committed data.

Question 5

What is the consistency scope of READ COMMITTED SNAPSHOT?

  • A. One statement
  • B. The entire transaction
  • C. The entire server lifetime
  • D. One database file

Answer: A — RCSI provides statement-level consistency.

Question 6

What is one potential cost of row versioning?

  • A. Version-store storage and cleanup overhead
  • B. Automatic removal of indexes
  • C. Inability to insert rows
  • D. Automatic disabling of constraints

Answer: A — Row versions require storage and cleanup management.

19. Key Takeaways

  • Isolation levels define how concurrent transactions observe data.
  • READ UNCOMMITTED allows dirty reads.
  • READ COMMITTED prevents dirty reads but allows non-repeatable and phantom reads.
  • REPEATABLE READ protects rows already read but does not prevent all phantom inserts.
  • SERIALIZABLE protects relevant key ranges.
  • SNAPSHOT provides transaction-level consistency through row versioning.
  • RCSI provides statement-level consistency through row versioning.
  • Row versioning reduces many reader-writer conflicts but has storage and cleanup costs.
  • Isolation level selection should reflect application consistency requirements and workload behavior.

The best isolation level is not necessarily the strongest one. It is the level that satisfies the application's consistency requirements while maintaining acceptable concurrency and operational performance.
