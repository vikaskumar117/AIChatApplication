APPLY THE IDEA

Worked example

Count active employees per department, retain departments with more than ten, then return the highest counts. The sample input is deliberately small; the result table represents a larger data set.

  1. Join employee to department on the key, establishing row grain.
  2. WHERE removes inactive employee rows before grouping.
  3. GROUP BY forms one group per department; HAVING removes small groups.
  4. SELECT computes count and alias; ORDER BY can bind that alias; OFFSET-FETCH selects a page.

CODE OR QUERY

Try it

SELECT d.Name AS DepartmentName, COUNT(e.EmployeeId) AS ActiveEmployees
FROM dbo.Employee AS e
INNER JOIN dbo.Department AS d ON d.DepartmentId = e.DepartmentId
WHERE e.IsActive = 1
GROUP BY d.Name
HAVING COUNT(e.EmployeeId) > 10
ORDER BY ActiveEmployees DESC, DepartmentName
OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY;

WHAT THE ENGINE MAY DO

Example execution plan

  1. Illustrative: Index Seek / Scan ? Read Employee and Department according to available indexes and estimated selectivity.
  2. Illustrative: Filter ? Apply the active-row predicate; the optimizer may push it toward the access operator.
  3. Illustrative: Nested Loops / Hash Match ? Join on DepartmentId; chosen based on estimates, indexes, and row counts.
  4. Illustrative: Hash or Stream Aggregate ? Group joined active rows by department and compute count.
  5. Illustrative: Filter ? Apply HAVING count > 10 after aggregate semantics.
  6. Illustrative: Sort + Top ? Order by count and apply the requested page. This is not a guaranteed plan.

TRADE-OFFS

Benefits and limitations

Benefits

  • Predictable name and aggregate scope makes queries easier to reason about.
  • Separating logical meaning from physical operators helps diagnose correctness and performance independently.

Limitations

  • Logical ordering does not guarantee a particular operator, access path, or fast runtime.
  • A legal query can still multiply rows or sort a large input expensively.

DECISION GUIDE

When to use it

Use: Use logical binding order to debug aliases, joins, filters, grouping, and paging; use the actual plan and runtime statistics to diagnose cost.

Avoid: Do not assume the engine physically executes each clause in this exact order, or use HAVING for ordinary row predicates. Do not page without a deterministic order.

COMMON MISTAKES

Watch out

  • Treating the logical order as a required physical execution sequence.
  • Using HAVING instead of WHERE for a non-aggregate predicate.
  • Filtering a nullable side of a LEFT JOIN in WHERE when unmatched rows must survive.
  • Using TOP or pagination without a stable ORDER BY and unique tie-breaker.

BEST PRACTICES

In practice

  • State the intended grain and join keys before aggregating.
  • Use WHERE for row predicates and HAVING for aggregate predicates.
  • Use aliases in ORDER BY, not as if SELECT had already run in WHERE.
  • Compare actual versus estimated rows and inspect the actual plan for performance.

INTERVIEW PRACTICE

Common questions

  1. Why is a SELECT alias usually unavailable to WHERE but available to ORDER BY?
  2. How do WHERE and HAVING differ?
  3. Does logical binding order prescribe physical operator order?
  4. How can an outer join change the effect of a predicate in WHERE?

SENIOR-LEVEL SCENARIO

Production thinking

A department report counts too many employees. Verify join cardinality and duplicate keys, place row-level active filtering in WHERE, group at the intended grain, and apply thresholds in HAVING. Compare actual and estimated row counts and inspect the plan; do not infer execution order from the written query.

SUMMARY

In one minute

A SELECT statement has a logical binding order: FROM, ON, JOIN, WHERE, GROUP BY, GROUPING SETS/CUBE/ROLLUP, HAVING, SELECT, DISTINCT, ORDER BY, then TOP/OFFSET-FETCH. FROM establishes input rowsets; ON evaluates the join predicate; JOIN combines matches (and preserves unmatched rows for outer joins); WHERE filters individual rows; GROUP BY forms groups; HAVING filters groups; SELECT computes output expressions and aliases; DISTINCT removes duplicate projected rows; ORDER BY orders output; TOP limits it. Logical binding explains why a SELECT alias is generally unavailable in WHERE but available in ORDER BY, why WHERE and HAVING are not interchangeable, and where join multiplication occurs. It describes meaning and scope, not a mandatory physical sequence of CPU operations.
