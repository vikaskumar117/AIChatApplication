THE IDEA

What is it?

A SELECT statement has a logical binding order: FROM, ON, JOIN, WHERE, GROUP BY, GROUPING SETS/CUBE/ROLLUP, HAVING, SELECT, DISTINCT, ORDER BY, then TOP/OFFSET-FETCH. FROM establishes input rowsets; ON evaluates the join predicate; JOIN combines matches (and preserves unmatched rows for outer joins); WHERE filters individual rows; GROUP BY forms groups; HAVING filters groups; SELECT computes output expressions and aliases; DISTINCT removes duplicate projected rows; ORDER BY orders output; TOP limits it.

WHY IT MATTERS

What problem does it solve?

Logical binding explains why a SELECT alias is generally unavailable in WHERE but available in ORDER BY, why WHERE and HAVING are not interchangeable, and where join multiplication occurs. It describes meaning and scope, not a mandatory physical sequence of CPU operations.

UNDER THE HOOD

How does it work?

The optimizer transforms the relational expression and selects physical operators such as seeks, scans, nested loops, hash joins, aggregates, and sorts. It may push a safe predicate earlier or reorder inner joins while preserving semantics. Outer-join null preservation, nondeterministic expressions, and other semantic boundaries constrain transformations. Inspect the actual execution plan for implementation, not as a restatement of logical clause order.

KEY TAKEAWAYS

Remember

  • WHERE filters rows; HAVING filters aggregate groups.
  • SELECT aliases are bound after WHERE; ORDER BY can generally use output aliases.
  • Joins can multiply rows before grouping; check key cardinality and result grain.
  • The optimizer may reorder or transform work; inspect the actual physical plan separately.
