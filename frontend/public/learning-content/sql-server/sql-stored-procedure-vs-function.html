Stored Procedure vs Function in SQL Server

Understand how stored procedures and user-defined functions work, how they differ, when to use each, and how SQL Server executes and optimizes them.

1. Learning Objectives

  • Understand stored procedures and user-defined functions.
  • Compare syntax, parameters, return values, and execution behavior.
  • Learn scalar, inline table-valued, and multi-statement table-valued functions.
  • Understand function restrictions and transaction behavior.
  • Analyze execution plans and performance differences.
  • Choose the appropriate database object for real-world requirements.

2. What Is a Stored Procedure?

A stored procedure is a named collection of SQL statements stored in a SQL Server database. It can accept input parameters, perform operations, execute multiple statements, manage transactions, return result sets, and return an integer status code.

Basic stored procedure

CREATE OR ALTER PROCEDURE dbo.GetEmployees
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        EmployeeID,
        EmployeeName,
        Salary
    FROM dbo.Employees;
END;

Execute the procedure

EXEC dbo.GetEmployees;

SQL Server executes the statements inside the procedure and sends the SELECT result set to the client.

Stored procedure characteristics

  • Can contain multiple SQL statements.
  • Can perform INSERT, UPDATE, DELETE, and SELECT operations.
  • Can manage transactions.
  • Can use TRY...CATCH error handling.
  • Can return one or more result sets.
  • Can accept input and output parameters.
  • Can return an integer status code.
  • Can execute dynamic SQL.

3. What Is a User-Defined Function?

A user-defined function (UDF) is a database object that accepts parameters, performs calculations or data retrieval, and returns a value or table.

Unlike a stored procedure, a function can be used inside SQL expressions and queries, subject to the function type and SQL Server's function restrictions.

Example: Scalar function

CREATE OR ALTER FUNCTION dbo.CalculateAnnualSalary
(
    @MonthlySalary DECIMAL(12,2)
)
RETURNS DECIMAL(14,2)
AS
BEGIN

    RETURN @MonthlySalary * 12;

END;

Use the function in a SELECT statement

SELECT
    EmployeeID,
    EmployeeName,
    Salary,
    dbo.CalculateAnnualSalary(Salary) AS AnnualSalary
FROM dbo.Employees;

The function calculates an annual salary for each row using the monthly salary passed to it.

Function characteristics

  • Must return a scalar value or a table.
  • Can accept input parameters.
  • Can be used in SELECT statements and other permitted expressions.
  • Cannot directly modify permanent database state through ordinary DML.
  • Cannot independently manage transactions using BEGIN TRANSACTION, COMMIT, or ROLLBACK.
  • Cannot use ordinary TRY...CATCH error handling inside the function body.
  • Cannot execute stored procedures using EXEC.

4. Stored Procedure vs Function: Core Differences

Feature Stored Procedure User-Defined Function
Primary purpose Perform database operations and business workflows. Calculate and return values or tables.
Return requirement Does not require a RETURN value. Must return a scalar value or table.
Execution EXEC or EXECUTE. Used in expressions or FROM clauses, depending on type.
SELECT integration Cannot be called directly as a scalar expression or FROM source. Can be used in supported query contexts.
INSERT, UPDATE, DELETE Can modify database tables. Cannot directly modify permanent database state through ordinary DML.
Transactions Can manage transactions. Cannot independently manage transactions.
TRY...CATCH Supported for catchable execution errors. Not supported inside the function body.
Dynamic SQL Can execute dynamic SQL. Cannot execute dynamic SQL through EXEC or sp_executesql.
Output parameters Supports OUTPUT parameters. Does not support OUTPUT parameters.
Multiple result sets Can return multiple result sets. Returns one scalar value or one table result.

5. Types of SQL Server Functions

SQL Server supports several types of user-defined functions. The most important categories are scalar functions and table-valued functions.

User-Defined Functions

Functions created by database developers.

Scalar Functions

Return one scalar value.

Table-Valued Functions

Return a table that can participate in queries.

Table-Valued Variants

Inline TVF and multi-statement TVF.

5.1 Scalar Function

A scalar function returns a single value such as INT, DECIMAL, VARCHAR, DATE, or another supported scalar data type. 

CREATE OR ALTER FUNCTION dbo.CalculateBonus
(
    @Salary DECIMAL(12,2),
    @BonusPercentage DECIMAL(5,2)
)
RETURNS DECIMAL(12,2)
AS
BEGIN

    RETURN @Salary * @BonusPercentage / 100;

END;

Usage:

SELECT
    EmployeeID,
    EmployeeName,
    Salary,
    dbo.CalculateBonus(Salary, 10) AS Bonus
FROM dbo.Employees;

Sample output:

EmployeeID EmployeeName Salary Bonus
1 Amit 50000.00 5000.00
2 Priya 70000.00 7000.00
3 Rahul 60000.00 6000.00

5.2 Inline Table-Valued Function

An inline table-valued function (iTVF) returns a table defined by a single SELECT statement. It is often a strong choice for reusable relational query logic. 

CREATE OR ALTER FUNCTION dbo.GetEmployeesByDepartment
(
    @DepartmentID INT
)
RETURNS TABLE
AS
RETURN
(
    SELECT
        EmployeeID,
        EmployeeName,
        Salary,
        DepartmentID
    FROM dbo.Employees
    WHERE DepartmentID = @DepartmentID
);

Use the inline function

SELECT *
FROM dbo.GetEmployeesByDepartment(10);

Join an inline function with another table

SELECT
    e.EmployeeName,
    e.Salary,
    d.DepartmentName
FROM dbo.GetEmployeesByDepartment(10) AS e
JOIN dbo.Departments AS d
    ON e.DepartmentID = d.DepartmentID;

SQL Server can generally expand an inline table-valued function into the calling query, allowing the optimizer to consider the combined relational expression.

5.3 Multi-Statement Table-Valued Function

A multi-statement table-valued function (MSTVF) declares a return table variable and populates it through one or more statements. 

CREATE OR ALTER FUNCTION dbo.GetHighSalaryEmployees
(
    @MinimumSalary DECIMAL(12,2)
)
RETURNS @EmployeeList TABLE
(
    EmployeeID INT,
    EmployeeName VARCHAR(100),
    Salary DECIMAL(12,2)
)
AS
BEGIN

    INSERT INTO @EmployeeList
    (
        EmployeeID,
        EmployeeName,
        Salary
    )
    SELECT
        EmployeeID,
        EmployeeName,
        Salary
    FROM dbo.Employees
    WHERE Salary >= @MinimumSalary;

    RETURN;

END;

Use the multi-statement function

SELECT *
FROM dbo.GetHighSalaryEmployees(60000);

MSTVFs are useful when a function needs to construct its result through multiple statements. However, their optimization behavior can be less favorable than inline TVFs for complex workloads.

Function type Return Definition Typical optimization behavior
Scalar UDF Single value Function body with RETURN Can be expensive when invoked repeatedly; eligible functions may be inlined.
Inline TVF Table Single relational SELECT Usually optimized as part of the calling query.
Multi-statement TVF Table Return table variable populated by statements May have weaker cardinality estimates and optimization choices.

6. Stored Procedure Parameters

Stored procedures support input parameters and output parameters. They can also return an integer status code.

Input parameter

CREATE OR ALTER PROCEDURE dbo.GetEmployeeByID
    @EmployeeID INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        EmployeeID,
        EmployeeName,
        Salary
    FROM dbo.Employees
    WHERE EmployeeID = @EmployeeID;
END;

Execute with a named parameter:

EXEC dbo.GetEmployeeByID
    @EmployeeID = 1;

Output parameter

CREATE OR ALTER PROCEDURE dbo.GetEmployeeCount
    @DepartmentID INT,
    @EmployeeCount INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        @EmployeeCount = COUNT(*)
    FROM dbo.Employees
    WHERE DepartmentID = @DepartmentID;
END;

Execute and retrieve output:

DECLARE @TotalEmployees INT;

EXEC dbo.GetEmployeeCount
    @DepartmentID = 10,
    @EmployeeCount = @TotalEmployees OUTPUT;

SELECT @TotalEmployees AS EmployeeCount;

Return status code

CREATE OR ALTER PROCEDURE dbo.CheckEmployee
    @EmployeeID INT
AS
BEGIN
    SET NOCOUNT ON;

    IF EXISTS
    (
        SELECT 1
        FROM dbo.Employees
        WHERE EmployeeID = @EmployeeID
    )
        RETURN 1;

    RETURN 0;
END;

Capture the return code:

DECLARE @Status INT;

EXEC @Status = dbo.CheckEmployee
    @EmployeeID = 1;

SELECT @Status AS StatusCode;
A stored procedure's RETURN value is an integer status code. It is not the same as a SELECT result set or an OUTPUT parameter. Use OUTPUT parameters for additional scalar values and SELECT statements for result sets.

7. Why Functions Cannot Perform Ordinary Data Modification

Functions are designed to return values and participate in expressions. SQL Server restricts side effects so that functions can be used more predictably inside query execution.

Example of a prohibited operation

CREATE FUNCTION dbo.UpdateEmployeeSalary
(
    @EmployeeID INT,
    @NewSalary DECIMAL(12,2)
)
RETURNS INT
AS
BEGIN

    UPDATE dbo.Employees
    SET Salary = @NewSalary
    WHERE EmployeeID = @EmployeeID;

    RETURN 1;

END;

This is not a valid way to update a permanent table from a user-defined function. SQL Server rejects ordinary data modification against permanent tables inside a function.

Correct implementation using a stored procedure

CREATE OR ALTER PROCEDURE dbo.UpdateEmployeeSalary
    @EmployeeID INT,
    @NewSalary DECIMAL(12,2)
AS
BEGIN
    SET NOCOUNT ON;

    UPDATE dbo.Employees
    SET Salary = @NewSalary
    WHERE EmployeeID = @EmployeeID;

    IF @@ROWCOUNT = 0
    BEGIN
        THROW 50010, 'Employee not found.', 1;
    END;
END;

Execute:

EXEC dbo.UpdateEmployeeSalary
    @EmployeeID = 1,
    @NewSalary = 55000;

SQL Server functions can modify local variables and their own return table variable where applicable. They can also read data and use certain permitted built-in functions. The restriction is specifically about prohibited side effects, not every assignment or intermediate operation.

8. Can a Stored Procedure Be Used Inside SELECT?

A stored procedure cannot be called as a scalar expression or directly used as a table source in an ordinary SELECT statement.

Invalid usage

SELECT dbo.GetEmployees();

This is invalid if GetEmployees is a stored procedure.

Valid procedure execution

EXEC dbo.GetEmployees;

Alternative: Use a table-valued function

SELECT *
FROM dbo.GetEmployeesByDepartment(10);

Alternative: Capture a procedure result into a table

When a procedure returns a compatible result set, INSERT...EXEC can capture it into a table or table variable. 

CREATE TABLE #EmployeeResults
(
    EmployeeID INT,
    EmployeeName VARCHAR(100),
    Salary DECIMAL(12,2)
);

INSERT INTO #EmployeeResults
EXEC dbo.GetEmployees;

SELECT *
FROM #EmployeeResults;

DROP TABLE #EmployeeResults;
INSERT...EXEC has important restrictions. It cannot be freely nested, and the destination column structure must match the procedure's returned result set. For reusable relational logic, an inline TVF or a view may be a better design.

9. SQL Server Internals: How Stored Procedures Execute

When a stored procedure is executed, SQL Server processes its statements, compiles or reuses plans as appropriate, and executes the resulting operators.

1. EXEC request

Client submits a procedure call with parameter values.

2. Object resolution

SQL Server resolves the stored procedure and its dependencies.

3. Plan lookup or compilation

SQL Server looks for a reusable plan or compiles statements as needed.

4. Optimization

Statements are optimized using available metadata and statistics.

5. Execution

The execution engine runs the plan and performs requested operations.

6. Results

SQL Server returns result sets, output parameters, and a status code.

Plan caching

SQL Server can cache execution plans for stored procedure statements. When the procedure is executed again, SQL Server may reuse an existing plan instead of compiling a new one.

Inspect cached plans and their associated SQL text:

SELECT
    cp.objtype,
    cp.usecounts,
    cp.size_in_bytes,
    st.text
FROM sys.dm_exec_cached_plans AS cp
CROSS APPLY sys.dm_exec_sql_text(cp.plan_handle) AS st
WHERE cp.objtype = 'Proc'
ORDER BY cp.usecounts DESC;

Plan caching is not a guarantee that every execution will use the same plan. Plans can be evicted, invalidated, recompiled, or reoptimized under different conditions.

10. SQL Server Internals: How Functions Execute

Function execution behavior depends heavily on the function type. An inline TVF, multi-statement TVF, and scalar UDF can produce very different execution plans.

Scalar UDF

Historically, scalar UDFs often caused performance problems because the function could be invoked repeatedly for rows in the outer query. This could lead to iterative execution and hide work from the optimizer.

Scalar UDF inlining

SQL Server 2019 introduced scalar UDF inlining for eligible functions when the database compatibility level is 150 or higher. The optimizer can transform eligible scalar UDF logic into relational expressions in the calling query.

Not every scalar function is eligible. Eligibility depends on the function definition, SQL Server version, compatibility level, configuration, and other restrictions.

Check database compatibility level

SELECT
    name,
    compatibility_level
FROM sys.databases
WHERE name = DB_NAME();

Check scalar UDF inlining configuration

SELECT
    name,
    value,
    value_for_secondary
FROM sys.database_scoped_configurations
WHERE name = 'TSQL_SCALAR_UDF_INLINING';

Inline TVF optimization

An inline TVF is conceptually similar to a parameterized relational query expression. SQL Server can generally incorporate its SELECT definition into the calling query, allowing the optimizer to choose joins, indexes, and access methods across the combined expression.

Multi-statement TVF optimization

A multi-statement TVF populates a return table variable. Historically, cardinality estimates for these functions could be poor, resulting in inefficient joins and memory grants.

Interleaved execution, available in SQL Server 2017 and later for eligible workloads at the appropriate compatibility level, can improve estimates by materializing an MSTVF during optimization and using its observed row count in the outer query plan.

11. Performance Comparison: Procedure vs Function

It is incorrect to assume that stored procedures are always faster than functions. Performance depends on the function type, query design, invocation pattern, optimizer behavior, and workload.

Example: Scalar function over many rows

SELECT
    EmployeeID,
    EmployeeName,
    dbo.CalculateAnnualSalary(Salary) AS AnnualSalary
FROM dbo.Employees;

If a scalar function cannot be inlined, repeated invocation may create overhead for a large result set.

Alternative: Direct expression

SELECT
    EmployeeID,
    EmployeeName,
    Salary * 12 AS AnnualSalary
FROM dbo.Employees;

A direct expression is often simpler for straightforward arithmetic. However, reusable function logic may still be valuable when the function is eligible for inlining and the abstraction improves maintainability.

Compare with an actual execution plan

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    EmployeeID,
    dbo.CalculateAnnualSalary(Salary) AS AnnualSalary
FROM dbo.Employees;

SELECT
    EmployeeID,
    Salary * 12 AS AnnualSalary
FROM dbo.Employees;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

Compare logical reads, CPU time, elapsed time, row counts, and execution plan operators. Run tests more than once and avoid drawing conclusions from a single execution.

Performance characteristics

Object Performance consideration
Stored procedure Can use cached plans and execute complex database workflows.
Scalar UDF May add per-row overhead if not inlined.
Inline TVF Usually provides optimizer-friendly relational composition.
Multi-statement TVF May introduce cardinality estimation and intermediate-result overhead.

12. Parameter Sniffing in Stored Procedures

SQL Server can use parameter values supplied during compilation to estimate row counts and select an execution plan. This behavior is commonly called parameter sniffing.

A plan optimized for one parameter value may perform poorly for another value when the data distribution is uneven.

Example procedure

CREATE OR ALTER PROCEDURE dbo.GetEmployeesByDepartment
    @DepartmentID INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        EmployeeID,
        EmployeeName,
        Salary
    FROM dbo.Employees
    WHERE DepartmentID = @DepartmentID;
END;

Test different parameter values

EXEC dbo.GetEmployeesByDepartment
    @DepartmentID = 10;

EXEC dbo.GetEmployeesByDepartment
    @DepartmentID = 20;

Suppose Department 10 contains 50 employees, while Department 20 contains 100,000 employees. A plan optimized for one department may not be ideal for the other.

Possible mitigation strategies

  • Improve statistics and indexing.
  • Use OPTION (RECOMPILE) for appropriate statements when recompilation cost is acceptable.
  • Use OPTIMIZE FOR when a deliberate representative estimate is appropriate.
  • Consider separate query paths for materially different data distributions.
  • Use Query Store to investigate plan regressions and evaluate supported plan forcing options.
  • Evaluate Parameter Sensitive Plan optimization where supported.
Do not add RECOMPILE to every stored procedure as a default fix. Recompilation has CPU and compilation overhead. Measure the workload and choose a strategy based on actual parameter distribution.

13. Real-World Scenario: Order Processing

Consider an e-commerce application that processes customer orders. The operation requires multiple database actions:

  • Validate customer existence.
  • Validate product availability.
  • Insert the order header.
  • Insert order items.
  • Update inventory.
  • Commit all changes together.

This is a transactional workflow. A stored procedure is an appropriate database object because it can coordinate multiple data modifications inside a transaction.

Sample schema

CREATE TABLE dbo.Products
(
    ProductID INT PRIMARY KEY,
    ProductName VARCHAR(100),
    StockQuantity INT,
    UnitPrice DECIMAL(12,2)
);

CREATE TABLE dbo.Orders
(
    OrderID INT IDENTITY(1,1) PRIMARY KEY,
    CustomerID INT,
    OrderDate DATETIME2 NOT NULL
        DEFAULT SYSUTCDATETIME(),
    TotalAmount DECIMAL(14,2)
);

CREATE TABLE dbo.OrderItems
(
    OrderItemID INT IDENTITY(1,1) PRIMARY KEY,
    OrderID INT NOT NULL,
    ProductID INT NOT NULL,
    Quantity INT NOT NULL,
    UnitPrice DECIMAL(12,2) NOT NULL,

    FOREIGN KEY (OrderID)
        REFERENCES dbo.Orders(OrderID),

    FOREIGN KEY (ProductID)
        REFERENCES dbo.Products(ProductID)
);

Stored procedure for processing an order

CREATE OR ALTER PROCEDURE dbo.ProcessOrder
    @CustomerID INT,
    @ProductID INT,
    @Quantity INT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    DECLARE @OrderID INT;
    DECLARE @UnitPrice DECIMAL(12,2);

    BEGIN TRY

        IF @Quantity <= 0
        BEGIN
            THROW 50020, 'Quantity must be greater than zero.', 1;
        END;

        BEGIN TRANSACTION;

        SELECT
            @UnitPrice = UnitPrice
        FROM dbo.Products WITH (UPDLOCK, HOLDLOCK)
        WHERE ProductID = @ProductID
          AND StockQuantity >= @Quantity;

        IF @UnitPrice IS NULL
        BEGIN
            THROW 50021, 'Product unavailable or insufficient stock.', 1;
        END;

        INSERT INTO dbo.Orders
        (
            CustomerID,
            TotalAmount
        )
        VALUES
        (
            @CustomerID,
            @UnitPrice * @Quantity
        );

        SET @OrderID = SCOPE_IDENTITY();

        INSERT INTO dbo.OrderItems
        (
            OrderID,
            ProductID,
            Quantity,
            UnitPrice
        )
        VALUES
        (
            @OrderID,
            @ProductID,
            @Quantity,
            @UnitPrice
        );

        UPDATE dbo.Products
        SET StockQuantity = StockQuantity - @Quantity
        WHERE ProductID = @ProductID
          AND StockQuantity >= @Quantity;

        IF @@ROWCOUNT = 0
        BEGIN
            THROW 50022, 'Inventory update failed.', 1;
        END;

        COMMIT TRANSACTION;

        SELECT @OrderID AS OrderID;

    END TRY
    BEGIN CATCH

        IF XACT_STATE() <> 0
        BEGIN
            ROLLBACK TRANSACTION;
        END;

        THROW;

    END CATCH;
END;

Execute:

EXEC dbo.ProcessOrder
    @CustomerID = 101,
    @ProductID = 10,
    @Quantity = 2;

The stored procedure is responsible for the workflow and transaction. A function could separately calculate a discount, tax amount, or other derived value, but it should not replace the transaction orchestration.

This example assumes that the referenced customer is validated elsewhere or protected by a foreign key. Production order processing should also consider multiple order lines, idempotency, currency rounding, customer validation, inventory concurrency, and retry behavior.

14. When Should You Use a Stored Procedure?

Choose a stored procedure when you need to:

  • Insert, update, or delete permanent table data.
  • Execute a multi-step business workflow.
  • Manage transactions.
  • Handle errors with TRY...CATCH.
  • Return multiple result sets.
  • Use output parameters.
  • Execute dynamic SQL.
  • Control database access through an application-facing interface.
  • Perform batch processing and scheduled database operations.

Examples

Business requirement Suggested object
Transfer money between accounts Stored procedure
Process an order Stored procedure
Update employee salaries Stored procedure
Import a batch of records Stored procedure
Generate a multi-result-set report Stored procedure
Perform scheduled cleanup Stored procedure

15. When Should You Use a Function?

Choose a function when you need to:

  • Calculate a reusable scalar value.
  • Return a filtered table for use in a query.
  • Encapsulate reusable relational logic.
  • Use derived values inside SELECT statements.
  • Join reusable query logic with other tables.
  • Centralize deterministic business calculations where appropriate.

Examples

Business requirement Suggested object
Calculate annual salary Scalar function or direct expression
Calculate discount percentage Scalar function where appropriate
Return employees for a department Inline table-valued function
Return reusable filtered order rows Inline table-valued function
Build a table result through multiple statements Multi-statement TVF when justified

16. Security and Permissions

Stored procedures and functions can both be used as part of a database security design. Ownership chaining can allow users to execute a module without having direct permissions on every underlying table, depending on ownership and execution context.

Grant procedure execution

GRANT EXECUTE
ON OBJECT::dbo.GetEmployeeByID
TO ApplicationUser;

Grant function permission

GRANT SELECT
ON OBJECT::dbo.GetEmployeesByDepartment
TO ApplicationUser;

The required permission depends on the function type and how it is referenced. Use the narrowest permissions necessary and test with the actual application user.

Inspect object permissions

SELECT
    USER_NAME(dp.grantee_principal_id) AS Grantee,
    dp.permission_name,
    dp.state_desc,
    OBJECT_SCHEMA_NAME(dp.major_id) AS SchemaName,
    OBJECT_NAME(dp.major_id) AS ObjectName
FROM sys.database_permissions AS dp
WHERE dp.major_id > 0
ORDER BY Grantee, ObjectName;
Module signing and EXECUTE AS can provide more controlled execution contexts for complex security requirements. Avoid using broad database or server roles merely to make an application procedure work.

17. Common Mistakes and Misconceptions

  • Assuming every function is slower than every stored procedure.
  • Using scalar functions over large row sets without examining their execution plans.
  • Using multi-statement TVFs when an inline TVF would be sufficient.
  • Trying to update permanent tables inside a user-defined function.
  • Assuming a procedure's RETURN statement returns a result set.
  • Using OUTPUT parameters when a result set would be clearer.
  • Using a stored procedure when reusable relational logic belongs in an inline TVF.
  • Assuming stored procedures automatically prevent SQL injection.
  • Building dynamic SQL by concatenating untrusted input.
  • Ignoring parameter sniffing and plan quality.

Prevent SQL injection in stored procedures

Stored procedures are not automatically immune to SQL injection. Use parameterized statements and validate identifiers when dynamic SQL is necessary. 

CREATE OR ALTER PROCEDURE dbo.SearchEmployee
    @EmployeeName NVARCHAR(100)
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SQL NVARCHAR(MAX);

    SET @SQL =
        N'SELECT EmployeeID, EmployeeName
          FROM dbo.Employees
          WHERE EmployeeName = @Name;';

    EXEC sys.sp_executesql
        @SQL,
        N'@Name NVARCHAR(100)',
        @Name = @EmployeeName;
END;

18. Decision Framework

Question 1: Do you need to modify permanent data?

Yes: Use a stored procedure or another suitable DML statement.

Question 2: Do you need a transaction or multi-step workflow?

Yes: Use a stored procedure.

Question 3: Do you need one reusable calculated value?

Consider a scalar function or direct expression.

Question 4: Do you need reusable rows inside a query?

Consider an inline table-valued function.

Question 5: Do you need to build a table result through multiple statements?

Consider a multi-statement TVF, after evaluating its performance implications.

Quick decision table

Requirement Best starting choice
Business workflow Stored procedure
Transactional data modification Stored procedure
One calculated value Scalar function or expression
Reusable query result Inline TVF
Multiple result sets Stored procedure
Dynamic SQL Stored procedure
Output parameter Stored procedure

20. Knowledge Check

  1. Can a stored procedure return multiple result sets?

    Answer: Yes.

  2. Can a scalar function be used inside a SELECT expression?

    Answer: Yes, when used in a permitted context.

  3. Which function type returns a table using a single SELECT statement?

    Answer: Inline table-valued function.

  4. Can a user-defined function independently begin and commit a transaction?

    Answer: No.

  5. What does a stored procedure's RETURN statement return?

    Answer: An integer status code.

  6. Which function type can be more difficult for the optimizer because it uses a return table variable?

    Answer: Multi-statement table-valued function.

  7. What is scalar UDF inlining?

    Answer: An optimization that transforms eligible scalar UDF logic into relational expressions in the calling query.

  8. Are stored procedures automatically protected from SQL injection?

    Answer: No. Dynamic SQL must still be parameterized and safely constructed.

  9. Which object is generally more suitable for a multi-step order-processing transaction?

    Answer: Stored procedure.

  10. Which object is generally suitable for reusable relational query logic?

    Answer: Inline table-valued function.

21. Final Learning Outcome

You should now understand the differences between stored procedures and functions, how their execution models differ, and how to choose an appropriate object for a database requirement.

Remember these core principles:

  • Use stored procedures for workflows, transactions, and data modifications.
  • Use scalar functions for suitable reusable calculations.
  • Prefer inline TVFs for reusable relational query logic.
  • Use multi-statement TVFs only when their additional flexibility is justified.
  • Measure performance using execution plans and runtime statistics.
  • Design security, parameter handling, and error handling deliberately.

The best database object is not determined by syntax alone. It should fit the required behavior, query composition, performance, security model, and long-term maintainability.
