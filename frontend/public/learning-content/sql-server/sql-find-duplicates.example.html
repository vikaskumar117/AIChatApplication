APPLY THE IDEA

Worked example

Find duplicate normalized emails while retaining full row details for review.

  1. Agree on the normalized business key and NULL treatment.
  2. Use GROUP BY / HAVING to identify repeated key values.
  3. Join the duplicate keys back to the base table and review every candidate.
  4. Record a retention or merge rule before changing data.

CODE OR QUERY

Try it

SELECT NormalizedEmail, COUNT_BIG(*) AS DuplicateCount
FROM dbo.Customer
WHERE NormalizedEmail IS NOT NULL
GROUP BY NormalizedEmail
HAVING COUNT_BIG(*) > 1
ORDER BY DuplicateCount DESC, NormalizedEmail;

-- Review all rows for the duplicate keys before taking any action.
SELECT c.*
FROM dbo.Customer AS c
JOIN (
  SELECT NormalizedEmail
  FROM dbo.Customer
  WHERE NormalizedEmail IS NOT NULL
  GROUP BY NormalizedEmail
  HAVING COUNT_BIG(*) > 1
) AS dup ON dup.NormalizedEmail = c.NormalizedEmail
ORDER BY c.NormalizedEmail, c.CreatedAt, c.CustomerId;

TRADE-OFFS

Benefits and limitations

Benefits

  • Groups expose frequency and duplicate-key distribution.
  • The review query makes candidate records visible before remediation.

Limitations

  • Grouping may scan and aggregate a large table.
  • Incorrect key normalization can merge distinct people or miss equivalent values.

DECISION GUIDE

When to use it

Use: Use for profiling, data-quality monitoring, and reviewed duplicate remediation.

Avoid: Do not define duplicates by a convenient single column if the business key is composite or NULLs have special meaning.

COMMON MISTAKES

Watch out

  • Deleting records based on a non-unique or incomplete key.
  • Ignoring case, whitespace, collation, or NULL semantics.
  • Assuming identical displayed values mean no dependent records need merging.

BEST PRACTICES

In practice

  • Normalize keys consistently at ingestion and comparison boundaries.
  • Capture candidate counts and sample rows for review.
  • Add a unique invariant after all existing conflicting data is resolved.

INTERVIEW PRACTICE

Common questions

  1. Which columns determine logical uniqueness?
  2. How should case and whitespace be normalized?
  3. Why inspect full rows after grouping duplicate keys?

SENIOR-LEVEL SCENARIO

Production thinking

A CRM import reports duplicate customer emails. Confirm canonicalization and NULL rules with product owners, count duplicate groups, review their histories and references, and plan a reversible merge policy.

SUMMARY

In one minute

A duplicate is a repeated business key, not necessarily a byte-for-byte identical database row. The key might be a normalized email, external reference, or composite of several columns. Reliable duplicate detection requires agreeing on equality rules, including case, whitespace, collation, NULL behavior, and which columns define one logical entity.
