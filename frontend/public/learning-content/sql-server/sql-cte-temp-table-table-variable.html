CTE vs Temporary Table vs Table Variable in SQL Server

Understand the differences between Common Table Expressions (CTEs), temporary tables, and table variables. Learn how SQL Server handles them internally and when to choose each approach in real applications.

1. Introduction

SQL Server developers often need to store intermediate query results before using them in another operation. SQL Server provides several approaches, including CTEs, temporary tables, and table variables.

  • CTE: A named query expression available to one following statement.
  • Temporary table: A temporary table created in tempdb, with support for indexes and statistics.
  • Table variable: A table-like variable declared using DECLARE, with scope and lifetime similar to a variable.
These three approaches are not interchangeable in every situation. The best choice depends on row count, query complexity, reuse, indexing requirements, statistics, and SQL Server version.

3. Common Table Expression (CTE)

What is a CTE?

A Common Table Expression is a named query expression defined using the WITH keyword. It can be referenced by the single statement immediately following its definition.

Syntax

WITH CTE_Name AS
(
    SELECT column1, column2
    FROM SomeTable
)
SELECT *
FROM CTE_Name;

Example: Calculate department average salary

WITH DepartmentAverage AS
(
    SELECT
        Department,
        AVG(Salary) AS AverageSalary
    FROM Employees
    GROUP BY Department
)
SELECT
    Department,
    AverageSalary
FROM DepartmentAverage;

Expected output

DepartmentAverageSalary
Finance73,333.33
HR61,666.67
IT75,000.00

CTE to find employees above their department average

WITH DepartmentAverage AS
(
    SELECT
        Department,
        AVG(Salary) AS AverageSalary
    FROM Employees
    GROUP BY Department
)
SELECT
    E.EmployeeName,
    E.Department,
    E.Salary,
    D.AverageSalary
FROM Employees E
INNER JOIN DepartmentAverage D
    ON E.Department = D.Department
WHERE E.Salary > D.AverageSalary
ORDER BY E.Department, E.Salary DESC;

Expected output

Employee Department Salary Department Average
GraceFinance85,00073,333.33
AliceIT90,00075,000.00
BobIT80,00075,000.00

Important CTE characteristics

  • A CTE is scoped to one following statement.
  • A CTE is not automatically stored as a physical temporary table.
  • A CTE can make complex queries easier to read.
  • A CTE can reference another CTE defined earlier in the same WITH clause.
  • A recursive CTE can process hierarchical data.
  • A CTE cannot be indexed directly.
A CTE is generally expanded into the surrounding query during optimization. Do not assume that defining a CTE means SQL Server calculates and stores its results once. The optimizer may transform or reevaluate parts of the query depending on the plan.

4. Temporary Tables (#Temp)

What is a temporary table?

A temporary table is a table created in SQL Server's tempdb database. It can hold intermediate data and can be referenced by multiple statements while it remains in scope.

Create a temporary table

CREATE TABLE #DepartmentAverage
(
    Department VARCHAR(30),
    AverageSalary DECIMAL(12,2)
);

INSERT INTO #DepartmentAverage
(
    Department,
    AverageSalary
)
SELECT
    Department,
    AVG(Salary)
FROM Employees
GROUP BY Department;

SELECT *
FROM #DepartmentAverage;

Expected output

DepartmentAverageSalary
Finance73333.33
HR61666.67
IT75000.00

Reuse the temporary table in multiple statements

-- First use
SELECT *
FROM #DepartmentAverage;

-- Second use
SELECT
    E.EmployeeName,
    E.Department,
    E.Salary,
    D.AverageSalary
FROM Employees E
INNER JOIN #DepartmentAverage D
    ON E.Department = D.Department
WHERE E.Salary > D.AverageSalary;

-- Third use
SELECT
    Department,
    COUNT(*) AS DepartmentCount
FROM #DepartmentAverage
GROUP BY Department;

Create an index on a temporary table

CREATE INDEX IX_DepartmentAverage_Department
ON #DepartmentAverage(Department);

Temporary table scope

  • A local temporary table starts with #.
  • It is generally visible within the creating session and nested execution scopes that can access it.
  • It is normally dropped when its creating session ends, or it can be explicitly dropped.
  • Temporary tables created inside stored procedures are normally dropped when the procedure finishes.
  • Global temporary tables start with ## and have broader visibility, with lifetime governed by their creation and active references.
DROP TABLE IF EXISTS #DepartmentAverage;

5. Table Variables (@Table)

What is a table variable?

A table variable is declared using DECLARE and a table type. It can store rows and be queried like a table within its scope.

Syntax

DECLARE @DepartmentAverage TABLE
(
    Department VARCHAR(30),
    AverageSalary DECIMAL(12,2)
);

Insert data into a table variable

DECLARE @DepartmentAverage TABLE
(
    Department VARCHAR(30),
    AverageSalary DECIMAL(12,2)
);

INSERT INTO @DepartmentAverage
(
    Department,
    AverageSalary
)
SELECT
    Department,
    AVG(Salary)
FROM Employees
GROUP BY Department;

SELECT *
FROM @DepartmentAverage;

Expected output

DepartmentAverageSalary
Finance73333.33
HR61666.67
IT75000.00

Table variable with a primary key

DECLARE @Employees TABLE
(
    EmployeeId INT PRIMARY KEY,
    EmployeeName VARCHAR(50),
    Department VARCHAR(30),
    Salary DECIMAL(10,2)
);

INSERT INTO @Employees
SELECT
    EmployeeId,
    EmployeeName,
    Department,
    Salary
FROM Employees;

SELECT *
FROM @Employees;

Table variable characteristics

  • Declared using DECLARE.
  • Its scope is limited to the batch, procedure, or function in which it is declared.
  • It can have primary keys, unique constraints, and indexes defined through supported table-variable syntax.
  • It does not support the same post-creation index-management flexibility as a temporary table.
  • It can be passed to stored procedures using table-valued parameters when defined with a user-defined table type.
Table variables are not guaranteed to remain entirely in memory. They use tempdb-backed storage as needed, just like other temporary relational structures.

7. SQL Server Internals — How They Work

CTE internal behavior

SQL Server parses the CTE definition
The optimizer incorporates the expression into the statement
The optimizer chooses scans, joins, aggregates, and other operators
The execution engine produces the result

A CTE does not automatically create a separate object in tempdb. SQL Server can choose to introduce a spool operator when useful, but a spool is an execution-plan decision, not a guaranteed property of CTEs.

Temporary table internal behavior

CREATE TABLE creates a temporary object in tempdb
INSERT or SELECT INTO loads rows
SQL Server maintains relevant metadata and statistics
Subsequent statements compile or recompile as needed
The temporary object is dropped explicitly or automatically at scope end

Temporary tables support statistics and flexible indexing. Their creation, population, and maintenance have costs, so materializing intermediate results is useful only when it benefits the overall workload.

Table variable internal behavior

DECLARE defines the table variable structure
INSERT adds rows to its temporary storage
The optimizer compiles queries referencing the variable
SQL Server uses available metadata and cardinality information
The variable is cleaned up when its scope ends

Table variables do not have the same column-statistics behavior as temporary tables. This can affect cardinality estimates and join choices, especially for complex queries.

8. Table Variable Deferred Compilation

SQL Server 2019 introduced table variable deferred compilation as part of the Intelligent Query Processing family, with compatibility level 150 or higher.

Earlier behavior often compiled a statement using a fixed one-row estimate for a table variable. Deferred compilation delays compilation of the referencing statement until its first execution, allowing SQL Server to use the actual row count present at that time. 

SELECT
    name,
    compatibility_level
FROM sys.databases
WHERE name = DB_NAME();

Check the database compatibility level

ALTER DATABASE YourDatabase
SET COMPATIBILITY_LEVEL = 150;
Changing compatibility level can affect many queries in the database. Test the impact in a non-production environment before changing production settings.

Important limitation

Deferred compilation uses the row count observed at initial compilation. It does not give table variables full column statistics. If row counts vary significantly between executions, plan reuse and parameter sensitivity can still matter.

Test using a table variable

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

(

    DepartmentId INT,
    Salary DECIMAL(10,2)
);

    DepartmentId,

Compare logical reads, CPU time, elapsed time, actual row counts, memory grants, and execution plans. Run each test more than once under comparable conditions.

Do not assume the temporary-table query must be faster. The outcome depends on data volume, indexes, compilation, cache state, server workload, and the downstream operations.

10. CTE vs Temporary Table — Reusing Intermediate Results

CTE example

WITH HighSalaryEmployees AS
(
    SELECT
        EmployeeId,
        EmployeeName,
        Department,
        Salary
    FROM Employees
    WHERE Salary > 70000
)
SELECT *
FROM HighSalaryEmployees;

-- A second statement cannot directly reference
-- the CTE defined above.
SELECT *
FROM HighSalaryEmployees;

The second SELECT fails because the CTE is only available to the immediately following statement.

Temporary table example

SELECT
    EmployeeId,
    EmployeeName,
    Department,
    Salary
INTO #HighSalaryEmployees
FROM Employees
WHERE Salary > 70000;

-- First use
SELECT *
FROM #HighSalaryEmployees;

-- Second use
SELECT Department, COUNT(*) AS EmployeeCount
FROM #HighSalaryEmployees
GROUP BY Department;

-- Third use
SELECT *
FROM #HighSalaryEmployees
WHERE Department = 'IT';

DROP TABLE #HighSalaryEmployees;

A temporary table is more appropriate when an intermediate result must be reused by several statements.

11. Recursive CTE Example — Employee Hierarchy

Recursive CTEs are useful for hierarchical data such as organizational structures, category trees, and parent-child relationships. 

CREATE TABLE EmployeeHierarchy
(
    EmployeeId INT PRIMARY KEY,
    EmployeeName VARCHAR(50),
    ManagerId INT NULL
);

INSERT INTO EmployeeHierarchy
VALUES
    (1, 'CEO', NULL),
    (2, 'IT Manager', 1),
    (3, 'HR Manager', 1),
    (4, 'Developer A', 2),
    (5, 'Developer B', 2),
    (6, 'HR Executive', 3);

WITH EmployeeTree AS
(
    -- Anchor member
    SELECT
        EmployeeId,
        EmployeeName,
        ManagerId,
        0 AS HierarchyLevel
    FROM EmployeeHierarchy
    WHERE ManagerId IS NULL

    UNION ALL

    -- Recursive member
    SELECT
        E.EmployeeId,
        E.EmployeeName,
        E.ManagerId,
        T.HierarchyLevel + 1
    FROM EmployeeHierarchy E
    INNER JOIN EmployeeTree T
        ON E.ManagerId = T.EmployeeId
)
SELECT
    EmployeeId,
    EmployeeName,
    ManagerId,
    HierarchyLevel
FROM EmployeeTree
ORDER BY HierarchyLevel, EmployeeId
OPTION (MAXRECURSION 100);

Expected output

EmployeeManagerIdHierarchyLevel
CEONULL0
IT Manager11
HR Manager11
Developer A22
Developer B22
HR Executive32
Recursive CTEs require care with cycles and recursion limits. MAXRECURSION limits recursion depth; it does not automatically detect and correct bad hierarchical data.

13. Common Mistakes

  • Assuming a CTE is materialized: A CTE is not automatically stored as an intermediate table.
  • Using a CTE across multiple statements: Its scope ends after the following statement.
  • Assuming table variables are always in memory: They can use tempdb-backed storage.
  • Assuming temporary tables are always faster: Their setup and maintenance have overhead.
  • Ignoring statistics: Missing or limited statistics can affect cardinality estimates and join choices.
  • Creating unnecessary indexes: Indexes cost storage and increase insert and maintenance work.
  • Ignoring scope: A local temporary table and a table variable have different lifetime rules.
  • Ignoring version differences: SQL Server compatibility level and version can change compilation behavior.

14. Production Considerations

tempdb workload

Temporary tables and table variables can use tempdb. Heavy concurrent use can contribute to tempdb allocation, metadata, and I/O pressure. Monitor tempdb rather than assuming every temporary object is expensive.

Stored procedures

A temporary table created within a stored procedure is normally dropped when that procedure completes. A table variable declared inside a procedure is also scoped to that procedure execution.

Transaction behavior

Temporary objects participate in SQL Server transaction and logging behavior. Do not assume that their data changes are completely outside transaction management.

Plan quality

A temporary table can provide a useful optimization boundary: SQL Server can compile later statements using information about the populated temporary table. However, recompilation and plan quality depend on the actual workload and execution context.
