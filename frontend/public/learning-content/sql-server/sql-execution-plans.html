Read SQL Server Execution Plans

Understand how SQL Server executes queries internally, interpret graphical and XML execution plans, identify expensive operators, investigate cardinality estimation, and use execution plans to optimize real-world queries.

1. Learning Objectives

  • Understand what an execution plan is.
  • Understand how SQL Server compiles and executes queries.
  • Compare estimated, actual, and live execution plans.
  • Read graphical execution plans from right to left.
  • Understand common physical operators.
  • Interpret estimated and actual row counts.
  • Identify scans, seeks, lookups, sorts, and spills.
  • Understand join algorithms and parallel execution.
  • Investigate missing indexes and implicit conversions.
  • Use execution plans to diagnose real production problems.

2. What Is a SQL Server Execution Plan?

An execution plan describes the operations SQL Server chooses to execute a SQL statement.

For example, when you execute: 

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE EmployeeId = 100;

SQL Server must determine how to locate EmployeeId 100, retrieve the required columns, and return the result.

It may use an index seek, an index scan, a table scan, or another access method depending on the table structure, available indexes, statistics, and estimated costs.

Execution plan responsibilities

  • Determine how tables and indexes are accessed.
  • Determine how multiple tables are joined.
  • Determine where filtering and sorting occur.
  • Determine how aggregation is performed.
  • Determine whether parallel execution is beneficial.
  • Estimate CPU, I/O, and other resource costs.

3. SQL Server Query Compilation Process

SQL Server does not simply execute the SQL text exactly as written. It processes the statement and generates an execution plan.

1. Query submission

The application or user sends a SQL statement.

2. Parsing

SQL Server checks syntax and builds an internal representation.

3. Binding and algebrization

Names, objects, columns, and data types are resolved.

4. Query optimization

The optimizer evaluates possible execution strategies.

5. Plan generation

SQL Server selects an execution plan based on estimated costs.

6. Execution

The execution engine runs the selected operators.

7. Result delivery

Rows or statement results are returned to the client.

SQL Server may reuse a cached execution plan for later executions of a statement. Recompilation can occur when required by metadata, settings, statistics, or other compilation conditions.

4. Types of Execution Plans

4.1 Estimated Execution Plan

An estimated execution plan shows the plan SQL Server expects to use without executing the query.

In SQL Server Management Studio:

  • Open a query window.
  • Write the SQL statement.
  • Select Display Estimated Execution Plan.
  • Alternatively, press Ctrl + L.
SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE DepartmentId = 10;

The estimated plan can be useful for reviewing a query without running it. However, it does not contain the actual runtime row counts and execution measurements.

4.2 Actual Execution Plan

An actual execution plan is captured when the query executes. It includes runtime information such as actual rows and execution counts.

In SQL Server Management Studio:

  • Select Include Actual Execution Plan.
  • Alternatively, press Ctrl + M.
  • Execute the query.
  • Open the Execution Plan tab.
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE DepartmentId = 10;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;

4.3 Live Query Statistics

Live Query Statistics provides a view of query execution while the query is running.

It can help investigate long-running statements by showing operator progress and runtime row-flow information.

Plan type Execution required? Runtime information
Estimated No Estimated rows and costs.
Actual Yes Estimated and actual runtime information.
Live Query Statistics Yes Execution progress while running.

6. How to Read a Graphical Execution Plan

In SQL Server Management Studio, a graphical execution plan contains operator icons connected by arrows.

A useful starting rule is to read the data flow from right to left. Operators on the right generally produce input rows consumed by operators farther to the left.

Example query

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE DepartmentId = 2;

Conceptual execution flow

Employee access

SQL Server reads rows from the table or index.

Filter evaluation

DepartmentId = 2 is evaluated.

Column retrieval

Required EmployeeId and EmployeeName values are made available.

Return result

Matching rows are sent to the client.

The exact graphical plan depends on indexes, statistics, data distribution, SQL Server version, and optimizer decisions.

7. Understand the Most Important Operators

7.1 Table Scan

A Table Scan reads rows from a heap table. A heap is a table without a clustered index.

Create a heap for demonstration: 

DROP TABLE IF EXISTS dbo.EmployeeHeap;

CREATE TABLE dbo.EmployeeHeap
(
    EmployeeId INT,
    EmployeeName VARCHAR(100),
    DepartmentId INT
);

INSERT INTO dbo.EmployeeHeap
(
    EmployeeId,
    EmployeeName,
    DepartmentId
)
SELECT
    EmployeeId,
    EmployeeName,
    DepartmentId
FROM dbo.Employee;

SELECT *
FROM dbo.EmployeeHeap
WHERE DepartmentId = 2;

Without a suitable index, SQL Server may scan the heap to find rows matching DepartmentId = 2.

7.2 Clustered Index Scan

A clustered index scan reads rows from the clustered index. It may be appropriate when a large proportion of the table is required. 

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee;

Since the query retrieves most or all employees, scanning the clustered index can be a reasonable plan.

7.3 Index Seek

An Index Seek navigates an index structure to locate matching key values or a range of key values. 

CREATE NONCLUSTERED INDEX IX_Employee_DepartmentId
ON dbo.Employee(DepartmentId);

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE DepartmentId = 2;

SQL Server may use the new index to locate rows belonging to DepartmentId 2.

However, because EmployeeName is not included in the nonclustered index, a Key Lookup may be required.

7.4 Index Scan

An Index Scan reads index entries. It is not necessarily inefficient: scanning a narrow index can be cheaper than scanning a wider clustered index.

7.5 Key Lookup

A Key Lookup retrieves additional columns from the clustered index using the clustered key found in a nonclustered index.

Nonclustered Index Seek

Find qualifying DepartmentId entries.

Read clustered key

Obtain the row locator from the nonclustered index.

Key Lookup

Retrieve EmployeeName from the clustered index.

Return rows

Produce the requested result.

7.6 RID Lookup

A RID Lookup retrieves additional columns from a heap using a Row Identifier. It is the heap equivalent of a Key Lookup.

8. Understand Join Operators

SQL Server supports multiple physical join algorithms. The execution plan shows which algorithm was selected.

8.1 Nested Loops

Nested Loops typically reads rows from one input and searches the other input for matches. 

SELECT
    E.EmployeeName,
    D.DepartmentName
FROM dbo.Employee AS E
INNER JOIN dbo.Department AS D
    ON E.DepartmentId = D.DepartmentId
WHERE E.EmployeeId <= 10;

Nested Loops can be efficient when the outer input is small and the inner input has an efficient access path.

8.2 Hash Match

Hash Match uses a hash table to match rows or perform certain aggregate operations. 

SELECT
    D.DepartmentName,
    COUNT(*) AS EmployeeCount
FROM dbo.Employee AS E
INNER JOIN dbo.Department AS D
    ON E.DepartmentId = D.DepartmentId
GROUP BY D.DepartmentName;

A hash join may be selected when joining larger inputs without useful ordering.

Inspect memory grants and spill warnings when a Hash Match operator performs poorly.

8.3 Merge Join

Merge Join processes two inputs ordered by their join keys. It can be efficient when the required ordering is already available.

Comparison

Operator Typical scenario Potential issue
Nested Loops Small outer input and efficient inner lookup. Too many repeated inner accesses.
Hash Match Large inputs without useful ordering. Memory pressure and spills.
Merge Join Inputs ordered by join key. Sort cost when ordering is unavailable.

9. Understand Sort and Aggregate Operators

9.1 Sort

Sort orders rows according to requested columns. It may be needed for ORDER BY, merge joins, or other operations requiring ordered data. 

SELECT
    EmployeeId,
    EmployeeName,
    Salary
FROM dbo.Employee
ORDER BY Salary DESC;

SQL Server may use a Sort operator if no suitable access path already provides the requested ordering.

9.2 Stream Aggregate

Stream Aggregate groups ordered input rows and calculates aggregates. It benefits from appropriately ordered input. 

SELECT
    DepartmentId,
    COUNT(*) AS EmployeeCount
FROM dbo.Employee
GROUP BY DepartmentId;

9.3 Hash Aggregate

Hash Aggregate uses a hash structure to group rows. It can process unordered input but requires memory.

A hash aggregate may be suitable when the input is not already ordered by the grouping columns.

10. Estimated Rows vs Actual Rows

One of the most important execution plan skills is comparing estimated row counts with actual row counts.

  • Estimated rows: the optimizer's prediction.
  • Actual rows: rows produced during execution.

Illustrative example

Operator Estimated rows Actual rows
Index Seek10015,000
Nested Loops input10015,000
Key Lookup10015,000

A significant difference may indicate that the optimizer underestimated the number of rows.

Why cardinality estimates can be wrong

  • Outdated or insufficient statistics.
  • Correlated columns.
  • Skewed data distribution.
  • Expressions and non-SARGable predicates.
  • Implicit data-type conversions.
  • Parameter-sensitive query behavior.
  • Complex predicates and estimation limitations.

Investigate statistics

SELECT
    name,
    stats_id,
    auto_created,
    user_created
FROM sys.stats
WHERE object_id = OBJECT_ID('dbo.Employee');

DBCC SHOW_STATISTICS
(
    'dbo.Employee',
    'IX_Employee_DepartmentId'
);

Compare estimates with actual values at important operators, especially where a large difference changes the amount of work performed downstream.

11. Understand Execution Plan Cost

The graphical execution plan displays estimated operator costs and relative percentages.

These estimates help the optimizer compare possible plans, but they are not direct measurements of actual execution time.

Important cost concepts

  • Estimated I/O cost.
  • Estimated CPU cost.
  • Estimated subtree cost.
  • Estimated operator cost.
  • Estimated number of rows.
An operator showing 80% of estimated plan cost does not necessarily consume 80% of actual runtime. Always combine plan inspection with actual execution metrics.

12. Understand Predicate Properties

When inspecting an operator, open its Properties window. Review the predicates and understand how the filter is applied.

Seek Predicate

A Seek Predicate defines the key range or value used to navigate an index.

Predicate

A Predicate may be a residual filter evaluated after the access method retrieves candidate rows.

Example

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE DepartmentId = 2
  AND Salary > 80000;

If the index is on DepartmentId only, SQL Server may seek to DepartmentId 2 and evaluate Salary as a residual predicate.

Potential composite index

CREATE NONCLUSTERED INDEX IX_Employee_Department_Salary
ON dbo.Employee
(
    DepartmentId,
    Salary
)
INCLUDE
(
    EmployeeName
);

This index may support both the equality predicate and salary range predicate, while covering the requested EmployeeName.

13. Understand Implicit Conversions

SQL Server may convert one data type to another when comparing values of different types.

Depending on data types and conversion direction, an implicit conversion can reduce index efficiency or affect cardinality estimates.

Example

-- DepartmentId is INT.
DECLARE @DepartmentId VARCHAR(10) = '2';

SELECT *
FROM dbo.Employee
WHERE DepartmentId = @DepartmentId;

SQL Server must reconcile the different data types. INT has higher precedence than VARCHAR, so SQL Server converts the string parameter to INT in this comparison.

Preferred approach

DECLARE @DepartmentId INT = 2;

SELECT *
FROM dbo.Employee
WHERE DepartmentId = @DepartmentId;

Match parameter types to column types and inspect execution plan warnings for implicit conversions.

14. Understand Parallelism

SQL Server can divide query work across multiple worker threads. This is called parallel execution.

Parallelism can improve performance for large operations, but it also introduces coordination and resource costs.

Common parallelism operators

  • Distribute Streams.
  • Repartition Streams.
  • Gather Streams.

Conceptual parallel execution flow

Input data

Rows are prepared for parallel processing.

Distribute Streams

Work is distributed among worker threads.

Parallel operations

Workers perform operations concurrently.

Gather Streams

Results are combined for downstream processing.

Inspect parallelism settings

SELECT
    name,
    value,
    value_in_use
FROM sys.configurations
WHERE name IN
(
    'max degree of parallelism',
    'cost threshold for parallelism'
);

A parallel plan is not automatically better than a serial plan. Review CPU usage, elapsed time, worker distribution, and the workload's concurrency requirements.

15. Understand Memory Grants and Spills

Certain operators require memory to process data. Sort and Hash Match operators are common examples.

SQL Server requests a memory grant based on estimated execution requirements.

Potential problems

  • Insufficient memory grants.
  • Excessively large memory grants.
  • Sort spills to tempdb.
  • Hash spills to tempdb.
  • Memory grant waits.

Inspect memory grant information

SELECT
    session_id,
    request_time,
    grant_time,
    requested_memory_kb,
    granted_memory_kb,
    required_memory_kb,
    used_memory_kb,
    max_used_memory_kb,
    wait_time_ms
FROM sys.dm_exec_query_memory_grants;

Actual execution plans can also expose memory grant information and spill warnings, depending on the SQL Server version and operator.

16. Understand Missing Index Warnings

SQL Server may show a missing-index recommendation in an execution plan.

The recommendation may include:

  • Equality columns.
  • Inequality columns.
  • Included columns.

Example query

SELECT
    EmployeeId,
    EmployeeName,
    Salary
FROM dbo.Employee
WHERE DepartmentId = 2;

A potential index could be: 

CREATE NONCLUSTERED INDEX IX_Employee_DepartmentId_Covering
ON dbo.Employee(DepartmentId)
INCLUDE
(
    EmployeeName,
    Salary
);

This is only a candidate. Check existing indexes, write overhead, storage requirements, and whether the plan actually improves.

17. Read an Execution Plan Using XML

SQL Server execution plans can be represented as XML. The XML contains detailed information about operators, estimates, runtime metrics, predicates, and warnings.

Generate an estimated plan as XML

SET SHOWPLAN_XML ON;
GO

SELECT
    EmployeeId,
    EmployeeName
FROM dbo.Employee
WHERE DepartmentId = 2;
GO

SET SHOWPLAN_XML OFF;
GO

SHOWPLAN_XML returns the estimated plan without executing the query. Statements between SET SHOWPLAN_XML ON and OFF are compiled for plan output rather than executed.

Generate an actual plan as XML

In SQL Server Management Studio, enable the actual execution plan and execute the query. You can save the plan as a .sqlplan file and inspect its XML.

Important XML information

  • PhysicalOp and LogicalOp.
  • EstimatedRows.
  • ActualRows in runtime information.
  • EstimatedTotalSubtreeCost.
  • SeekPredicates and residual predicates.
  • Warnings and spill information.
  • Memory grant details.
  • Object and index names.

18. Find Expensive Queries Using Query Store

Query Store helps identify query performance changes over time and compare different execution plans.

Enable Query Store

ALTER DATABASE YourDatabase
SET QUERY_STORE = ON;

Replace YourDatabase with the actual database name.

Find queries with high average duration

SELECT TOP (20)
    Q.query_id,
    P.plan_id,
    RS.count_executions,
    RS.avg_duration / 1000.0 AS AvgDurationMs,
    RS.avg_cpu_time / 1000.0 AS AvgCpuMs,
    RS.avg_logical_io_reads AS AvgLogicalReads,
    QT.query_sql_text
FROM sys.query_store_query AS Q
INNER JOIN sys.query_store_query_text AS QT
    ON Q.query_text_id = QT.query_text_id
INNER JOIN sys.query_store_plan AS P
    ON Q.query_id = P.query_id
INNER JOIN sys.query_store_runtime_stats AS RS
    ON P.plan_id = RS.plan_id
ORDER BY RS.avg_duration DESC;

This is a starting-point diagnostic query. For detailed reporting, account for runtime-statistics intervals, plan changes, and execution counts.

19. Real-World Scenario — Slow Employee Search

Business requirement

A human resources application needs to retrieve employees from a particular department whose salary exceeds a specified amount.

Initial query

SELECT
    EmployeeId,
    EmployeeName,
    DepartmentId,
    Salary
FROM dbo.Employee
WHERE DepartmentId = 2
  AND Salary > 80000;

Investigation process

  1. Capture the actual execution plan.
  2. Check whether SQL Server scans the clustered index.
  3. Review estimated versus actual rows.
  4. Check whether Salary is a residual predicate.
  5. Review logical reads and CPU time.

Potential index

CREATE NONCLUSTERED INDEX IX_Employee_Department_Salary
ON dbo.Employee
(
    DepartmentId,
    Salary
)
INCLUDE
(
    EmployeeName
);

This index may support the equality and range predicates while covering the requested columns. Validate its effectiveness using the actual plan and measured workload.

20. Common Execution Plan Mistakes

Misunderstanding Correct interpretation
Index Seek is always good. A seek can still read many rows or perform expensive lookups.
Table Scan is always bad. A scan may be efficient when most rows are required.
Highest cost operator is always the bottleneck. Estimated cost is not actual elapsed time.
Missing index warning means create the index. Review workload, existing indexes, and write overhead first.
Actual rows must equal estimated rows. Differences can occur; investigate material estimation errors.
Parallel plans are always faster. Parallelism has coordination and resource costs.
Key Lookup is always bad. A small number of lookups may be perfectly reasonable.

21. Execution Plan Troubleshooting Checklist

  • Capture the actual execution plan.
  • Identify the main access operators.
  • Compare estimated and actual row counts.
  • Inspect predicates and implicit conversions.
  • Review Key Lookup operations.
  • Review join algorithms and their input sizes.
  • Investigate Sort and Hash Match operators.
  • Check memory grants and spill warnings.
  • Review parallelism and worker distribution.
  • Check statistics and index definitions.
  • Compare logical reads and CPU time.
  • Validate the effect of any changes.

23. Knowledge Check

Question 1

Which plan includes actual runtime row information?

  • A. Estimated plan
  • B. Actual plan
  • C. Query text
  • D. Database diagram

Answer: B — Actual plan.

Question 2

Which operator retrieves additional data from a clustered index?

  • A. Sort
  • B. Key Lookup
  • C. Hash Match
  • D. Stream Aggregate

Answer: B — Key Lookup.

Question 3

Which join algorithm uses a hash structure?

  • A. Nested Loops
  • B. Merge Join
  • C. Hash Match
  • D. RID Lookup

Answer: C — Hash Match.

Question 4

What does a large estimated-versus-actual row difference suggest?

  • A. Potential cardinality estimation problem.
  • B. Database backup completed.
  • C. Indexes are automatically correct.
  • D. The query returned no data.

Answer: A.

Question 5

Is a Clustered Index Scan always inefficient?

  • A. Yes
  • B. No

Answer: B — It can be appropriate when many rows are needed.

Question 6

Which operator can indicate sorting work?

  • A. Sort
  • B. Key Lookup
  • C. Index Seek
  • D. Constant Scan

Answer: A — Sort.

24. Key Takeaways

  • An execution plan shows how SQL Server intends to execute a query.
  • Use actual execution plans to investigate runtime behavior.
  • Read graphical plans in the direction of data flow, generally right to left.
  • Understand the difference between scans, seeks, and lookups.
  • Compare estimated and actual row counts.
  • Investigate join algorithms, sorts, aggregates, and parallelism.
  • Review memory grants and spill warnings.
  • Use Query Store to investigate plan changes over time.
  • Never optimize based only on graphical cost percentages.

The key skill is not simply identifying an expensive-looking operator. It is understanding why SQL Server selected that operator, how much work it performed, and whether a better plan can satisfy the same business requirement with fewer resources.
