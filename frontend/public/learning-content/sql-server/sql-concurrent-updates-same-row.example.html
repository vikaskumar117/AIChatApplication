APPLY THE IDEA

Worked example

An inventory decrement must never make stock negative; perform one conditional UPDATE and treat zero affected rows as unavailable or stale.

  1. Identify invariant and concurrent write pattern.
  2. Express simple checks in the UPDATE predicate and update atomically.
  3. Check affected rows or compare concurrency token.
  4. Handle conflict as a domain outcome and keep external effects idempotent.

CODE OR QUERY

Try it

UPDATE dbo.Inventory
SET Quantity = Quantity - @requested
WHERE ProductId = @productId
  AND Quantity >= @requested;

IF @@ROWCOUNT = 0
  THROW 50010, 'Insufficient stock or product not found.', 1;

TRADE-OFFS

Benefits and limitations

Benefits

  • Atomic predicates prevent stale application reads from violating invariants.
  • Optimistic concurrency supports conflict detection without long-held read locks.

Limitations

  • Conflicts require domain-specific retry, merge, or rejection behavior.
  • Pessimistic locking can reduce throughput when contention is high.

DECISION GUIDE

When to use it

Use: Use conditional updates for simple invariants and rowversion/ETag-style optimistic concurrency for user-edited records.

Avoid: Avoid silently overwriting stale state or retrying a business update without revalidating its preconditions.

COMMON MISTAKES

Watch out

  • Overwriting a row with a stale entity without concurrency checking.
  • Retrying stale writes blindly and reintroducing the same conflict.
  • Assuming a transaction alone prevents lost updates at every isolation level.

BEST PRACTICES

In practice

  • Use conditional updates or optimistic concurrency tokens.
  • Keep transactions short and handle conflict exceptions explicitly.
  • Use unique constraints and domain-level idempotency for concurrent requests.

SENIOR-LEVEL SCENARIO

Production thinking

Two shoppers attempt to buy the last item. Use a single conditional inventory decrement, commit order state atomically, treat zero affected rows as a domain conflict, and emit the order event through an outbox.

SUMMARY

In one minute

Concurrent writes to one row contend for locks or encounter optimistic concurrency conflicts. A later write may wait, overwrite earlier values, or fail based on transaction and application design. A read-modify-write sequence can lose updates if application code calculates from stale data. Correctness requires atomic SQL operations, concurrency tokens, or an explicit serialization strategy.
