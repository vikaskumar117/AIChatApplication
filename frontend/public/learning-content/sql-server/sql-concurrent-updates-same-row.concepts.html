THE IDEA

What is it?

Concurrent writes to one row contend for locks or encounter optimistic concurrency conflicts. A later write may wait, overwrite earlier values, or fail based on transaction and application design.

WHY IT MATTERS

What problem does it solve?

A read-modify-write sequence can lose updates if application code calculates from stale data. Correctness requires atomic SQL operations, concurrency tokens, or an explicit serialization strategy.

UNDER THE HOOD

How does it work?

Prefer atomic conditional updates such as Balance = Balance - @amount WHERE Balance >= @amount and check affected rows. In EF use a concurrency token/rowversion and handle DbUpdateConcurrencyException by reloading, merging, or rejecting. Keep transactions short.

KEY TAKEAWAYS

Remember

  • Read-modify-write in application memory can lose updates.
  • Atomic conditional SQL is effective for simple invariants.
  • Rowversion detects stale writes; it does not automatically resolve conflicts.
  • Check affected rows and make retry/merge semantics explicit.
