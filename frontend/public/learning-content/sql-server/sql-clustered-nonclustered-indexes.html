Clustered and Nonclustered Indexes in SQL Server

Understand how SQL Server stores indexes, locates rows, retrieves data, and improves query performance. Learn the internal structure of B-tree indexes and how to design indexes for production workloads.

1. What Is an Index?

An index is a database structure that helps SQL Server locate rows without scanning every row in a table. Indexes are designed to improve data retrieval, although they introduce additional storage and maintenance costs.

Consider a table containing 10 million employees. If an application searches for one employee using EmployeeId, SQL Server may need to inspect a large number of rows if no useful index exists. An appropriate index can make the row easier to locate.

An index does not automatically make every query faster. The optimizer chooses whether to use an index based on estimated cost, selectivity, available statistics, and the query.

2. Types of SQL Server Indexes

Two fundamental index types are:

  • Clustered index: Defines the logical order of rows at the leaf level of the index. The table's data rows are stored in the clustered index.
  • Nonclustered index: A separate index structure containing index keys and row locators that identify the corresponding data rows.
FeatureClustered IndexNonclustered Index
Leaf levelContains the table data rowsContains index keys, row locators, and included columns
Number per tableOneMultiple
Separate from table dataNo; the clustered index is the table's row storage structureYes
Primary purposeOrganizes the table's row storageProvides additional access paths
Can be unique?YesYes

A table without a clustered index is called a heap. A heap stores rows without a clustered index defining their logical order.

4. Clustered Index

What is a clustered index?

A clustered index is a B-tree structure whose leaf level contains the actual data rows of the table. The clustered index key determines the logical ordering of rows at the leaf level.

Create a clustered index

CREATE CLUSTERED INDEX
    IX_Employees_EmployeeId
ON Employees(EmployeeId);

SQL Server creates a clustered index using EmployeeId as its index key. The table is no longer a heap.

Conceptual B-tree structure

Root page

Contains key values and pointers to intermediate pages or leaf pages.

Intermediate pages

Guide SQL Server toward the appropriate leaf page.

Leaf pages

Contain the actual table data rows in clustered key order.

SQL Server follows the B-tree from the root through intermediate levels to the leaf level to locate a key. The number of levels depends on the size and structure of the index.

Query using the clustered key

SELECT
    EmployeeId,
    EmployeeName,
    Department,
    Salary
FROM Employees
WHERE EmployeeId = 3;

SQL Server can use the clustered index to locate the employee. Because the leaf level contains the full table row, no additional lookup to a separate base table is required.

5. Nonclustered Index

What is a nonclustered index?

A nonclustered index is a separate B-tree structure. Its leaf pages contain the index key values, any included columns, and a row locator that identifies the underlying table row.

Create a nonclustered index

CREATE NONCLUSTERED INDEX
    IX_Employees_Department
ON Employees(Department);

Query using the nonclustered index

SELECT
    EmployeeId,
    EmployeeName,
    Department
FROM Employees
WHERE Department = 'IT';

SQL Server can locate matching index entries through the nonclustered index. If the index does not contain all required columns, SQL Server may need to retrieve the remaining columns from the underlying table.

Nonclustered index structure

Root page

Contains index navigation keys and page pointers.

Intermediate pages

Guide the search to the correct leaf page.

Leaf pages

Contain nonclustered index keys, row locators, and included columns.

Underlying row access when needed

SQL Server uses the row locator to retrieve additional columns.

6. How Does SQL Server Locate a Row?

Clustered index lookup

SELECT *
FROM Employees
WHERE EmployeeId = 5;
Read clustered index root page
Follow intermediate page pointers
Locate EmployeeId = 5 at the leaf level
Return the complete data row

Nonclustered index lookup

SELECT
    EmployeeId,
    EmployeeName,
    Department,
    Salary
FROM Employees
WHERE Department = 'IT';
Search the nonclustered index on Department
Find matching leaf entries
Read row locators
Retrieve missing columns from the clustered index when necessary
Return the result

7. Key Lookup

A Key Lookup occurs when SQL Server uses a nonclustered index to find matching rows but must access the clustered index to retrieve additional columns.

Create a narrow index

CREATE NONCLUSTERED INDEX
    IX_Employees_Department
ON Employees(Department);

Run a query requiring additional columns

SELECT
    EmployeeName,
    Salary
FROM Employees
WHERE Department = 'IT';

The nonclustered index contains Department and the clustered index row locator. EmployeeName and Salary are not in the nonclustered index, so SQL Server may use a Key Lookup to retrieve them.

A Key Lookup is not automatically a problem. It may be efficient when only a few rows qualify. When many rows qualify, repeated lookups can become expensive.

8. Covering Index

A covering index contains all columns needed by a particular query. SQL Server can return the required values from the nonclustered index without accessing the clustered index for additional columns.

Create a covering index

CREATE NONCLUSTERED INDEX
    IX_Employees_Department_Covering
ON Employees(Department)
INCLUDE
(
    EmployeeName,
    Salary
);

Run the same query

SELECT
    EmployeeName,
    Salary
FROM Employees
WHERE Department = 'IT';

The index contains the Department search key and the EmployeeName and Salary included columns. This query can potentially be satisfied entirely from the nonclustered index.

INCLUDE columns are stored at the nonclustered index leaf level. They are not part of the index's search key or ordering key. Avoid including large or unnecessary columns because they increase index size and write costs.

10. Clustered Index and Heap Storage

A table without a clustered index is a heap. SQL Server stores heap rows without a clustered B-tree ordering structure.

Create a heap

CREATE TABLE HeapEmployees
(
    EmployeeId INT,
    EmployeeName VARCHAR(100),
    Department VARCHAR(50)
);

Insert rows

INSERT INTO HeapEmployees
VALUES
    (1, 'Alice', 'IT'),
    (2, 'Bob', 'HR'),
    (3, 'Carol', 'Finance');

Inspect table type

SELECT
    t.name AS TableName,
    i.name AS IndexName,
    i.type_desc
FROM sys.tables t
LEFT JOIN sys.indexes i
    ON t.object_id = i.object_id
    AND i.index_id IN (0, 1)
WHERE t.name = 'HeapEmployees';

A heap can still have nonclustered indexes. In a heap, the nonclustered index row locator is a RID (row identifier), which identifies the row's physical location.

11. What Happens When a Clustered Index Is Created?

If a heap already contains rows and a clustered index is created, SQL Server organizes the rows into the clustered index structure. The clustered key becomes the table's row organization key. 

CREATE CLUSTERED INDEX
    IX_HeapEmployees_EmployeeId
ON HeapEmployees(EmployeeId);

Existing nonclustered indexes on a heap use RIDs as row locators. When a clustered index is created, SQL Server must maintain nonclustered row locators using the clustered key instead.

This is one reason clustered index design matters: the clustered key is carried as the row locator in nonclustered indexes. A wide clustered key can make every nonclustered index larger.

12. Clustered Index Key Selection

A good clustered index key often has these properties:

  • Unique or nearly unique, preferably enforced as unique.
  • Narrow, to reduce storage overhead in nonclustered indexes.
  • Stable, so key updates are uncommon.
  • Suitable for the table's common access patterns.
  • Often increasing for insert-heavy workloads, when that fits the application.

Example: Identity key

CREATE TABLE Orders
(
    OrderId BIGINT IDENTITY(1,1) NOT NULL,
    CustomerId INT NOT NULL,
    OrderDate DATETIME2 NOT NULL,
    TotalAmount DECIMAL(12,2) NOT NULL,

    CONSTRAINT PK_Orders
        PRIMARY KEY CLUSTERED (OrderId)
);

An increasing identity key can provide a simple clustered access path. However, it is not automatically the best key for every table. Query patterns, insert concurrency, and range access requirements should guide the design.

13. Composite Indexes

A composite index uses more than one key column. The order of the key columns matters because the B-tree is organized by the complete key sequence.

Create a composite index

CREATE NONCLUSTERED INDEX
    IX_Employees_Department_Salary
ON Employees
(
    Department,
    Salary DESC
);

Query using the leading column

SELECT *
FROM Employees
WHERE Department = 'IT';

Query using both columns

SELECT *
FROM Employees
WHERE Department = 'IT'
  AND Salary > 75000;

The index is ordered first by Department and then by Salary within each department. It is particularly suitable for queries that filter or seek using the leading Department key.

Query using only the second column

SELECT *
FROM Employees
WHERE Salary > 75000;

This query cannot generally seek efficiently using Salary as the leading key because Department comes first. SQL Server may choose an index scan or another access path instead.

14. Index Seek vs Index Scan

Index Seek

An Index Seek navigates an index to locate a qualifying key range or value. It is often efficient for selective predicates. 

SELECT *
FROM Employees
WHERE EmployeeId = 3;

Index Scan

An Index Scan reads index pages across a larger portion or all of the index. A scan can be appropriate when a large proportion of rows is needed. 

SELECT *
FROM Employees;
An Index Scan is not automatically bad, and an Index Seek is not automatically good. The important question is whether the chosen access path is efficient for the number of rows needed and the total query cost.

15. Clustered Index Scan vs Clustered Index Seek

OperatorTypical behaviorExample
Clustered Index SeekNavigates to matching key values or rangesWHERE EmployeeId = 3
Clustered Index ScanReads a larger part or all of the clustered indexSELECT * FROM Employees

SQL Server can choose a scan even when a seek is possible. If many rows qualify, reading the clustered index sequentially can be cheaper than performing many individual lookups.

16. Index Lookup and RID Lookup

Key Lookup

A Key Lookup retrieves missing columns from the clustered index after a nonclustered index has identified matching rows.

RID Lookup

A RID Lookup retrieves missing columns from a heap using the row identifier stored in a nonclustered index.

Lookup typeUnderlying tableRow locator
Key LookupClustered tableClustered index key

17. Unique Index

A unique index enforces uniqueness of its key values. It also provides an access path for queries using those key columns. 

CREATE UNIQUE NONCLUSTERED INDEX
    UX_Employees_EmployeeId
ON Employees(EmployeeId);

This example is illustrative: because EmployeeId is not declared unique in the original table definition, creating this index will succeed only if the existing values are unique.

SQL Server unique indexes enforce uniqueness. For a single nullable key column, a unique index permits only one NULL. A filtered unique index can be used when multiple NULL values should be allowed while non-NULL values remain unique.

18. Filtered Index

A filtered index stores only rows matching a filter predicate. It can reduce index size and maintenance when queries repeatedly access a specific subset of a table.

Example: Index only IT employees

CREATE NONCLUSTERED INDEX
    IX_Employees_IT_Salary
ON Employees(Salary DESC)
INCLUDE(EmployeeName)
WHERE Department = 'IT';

Query matching the filter

SELECT
    EmployeeName,
    Salary
FROM Employees
WHERE Department = 'IT'
  AND Salary > 70000;

The optimizer may use the filtered index because the query predicate is compatible with the index filter.

19. Index Maintenance and Page Splits

What is a page split?

SQL Server stores index pages in fixed-size pages, typically 8 KB. When a page cannot accommodate an insertion or a key update that changes its position, SQL Server may split the page and move some rows to another page.

A new row needs to be inserted into an index page
The target page does not have enough free space
SQL Server allocates another page
Rows are redistributed between the pages
Parent index structures are updated as needed

Page splits can increase write activity and may contribute to fragmentation. Their impact depends on workload, page fill, key patterns, and index design.

Inspect index fragmentation

SELECT
    OBJECT_NAME(ips.object_id) AS TableName,
    i.name AS IndexName,
    ips.avg_fragmentation_in_percent,
    ips.page_count
FROM sys.dm_db_index_physical_stats
(
    DB_ID(),
    OBJECT_ID('dbo.Employees'),
    NULL,
    NULL,
    'LIMITED'
) AS ips
INNER JOIN sys.indexes i
    ON ips.object_id = i.object_id
    AND ips.index_id = i.index_id
ORDER BY ips.avg_fragmentation_in_percent DESC;

Evaluate fragmentation together with page count, workload, and query performance. A high fragmentation percentage on a tiny index may not justify maintenance.

20. Rebuild and Reorganize Indexes

Reorganize

ALTER INDEX IX_Employees_Department
ON Employees
REORGANIZE;

REORGANIZE is an online, incremental leaf-level operation that compacts and orders leaf pages. It does not update index statistics in the same way as a rebuild.

Rebuild

ALTER INDEX IX_Employees_Department
ON Employees
REBUILD;

REBUILD recreates the index and can update its statistics. Availability and locking behavior depend on edition, version, options, and index type.

Do not apply universal fragmentation thresholds without considering index size and workload. Index maintenance should be based on measured benefit, resource usage, and an appropriate maintenance window.

21. Check Existing Indexes

SELECT
    t.name AS TableName,
    i.name AS IndexName,
    i.type_desc,
    i.is_unique,
    i.is_primary_key
FROM sys.tables t
INNER JOIN sys.indexes i
    ON t.object_id = i.object_id
WHERE t.name = 'Employees'
ORDER BY i.index_id;

Inspect index columns

SELECT
    i.name AS IndexName,
    c.name AS ColumnName,
    ic.key_ordinal,
    ic.is_included_column,
    ic.is_descending_key
FROM sys.indexes i
INNER JOIN sys.index_columns ic
    ON i.object_id = ic.object_id
    AND i.index_id = ic.index_id
INNER JOIN sys.columns c
    ON ic.object_id = c.object_id
    AND ic.column_id = c.column_id
WHERE i.object_id = OBJECT_ID('dbo.Employees')
ORDER BY i.index_id, ic.key_ordinal, ic.index_column_id;

Operators to understand

  • Clustered Index Seek: Locates rows through the clustered index.
  • Clustered Index Scan: Reads the clustered index across a larger range or all rows.
  • Index Seek: Locates matching entries in a nonclustered index.
  • Index Scan: Reads index pages across a larger portion of the index.
  • Key Lookup: Retrieves missing columns from the clustered index.
  • RID Lookup: Retrieves missing columns from a heap.
  • Sort: Orders rows when the required ordering is not already available.

Review actual rows, estimated rows, logical reads, execution time, and operator costs. Estimated operator cost is a model, not a direct measurement of elapsed time.

24. Common Indexing Mistakes

  • Too many indexes: Every additional index increases storage and write maintenance.
  • Wide clustered key: The clustered key is carried in nonclustered row locators, increasing index size.
  • Wrong composite key order: A query that filters only on a non-leading key may not benefit from an efficient seek.
  • Ignoring covering indexes: Repeated lookups may be avoidable when a carefully designed index includes required columns.
  • Assuming every scan is bad: Scans can be efficient when a query needs many rows.
  • Ignoring write workload: Indexes speed some reads but can slow inserts, updates, and deletes.
  • Using wide INCLUDE columns unnecessarily: This increases leaf-level storage and maintenance.
  • Rebuilding every index on a schedule: Maintenance should be based on measured need.

25. Real-World Index Design Scenarios

Scenario 1: Search orders by customer

CREATE NONCLUSTERED INDEX
    IX_Orders_CustomerId_OrderDate
ON Orders(CustomerId, OrderDate DESC)
INCLUDE(TotalAmount);

This can support queries that filter by CustomerId and retrieve orders in date order, while covering TotalAmount.

Scenario 2: Find active users

CREATE NONCLUSTERED INDEX
    IX_Users_Active
ON Users(LastLoginDate DESC)
INCLUDE(UserName)
WHERE IsActive = 1;

A filtered index can be useful when active users are a subset of the table and queries repeatedly target that subset.

Scenario 3: Product inventory

CREATE NONCLUSTERED INDEX
    IX_Inventory_Product_Warehouse
ON Inventory(ProductId, WarehouseId)
INCLUDE(Quantity);

This index can support inventory lookups by product and warehouse while making Quantity available at the leaf level.
