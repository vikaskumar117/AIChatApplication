Diagnose SQL Server Errors by Cause

Learn a systematic approach to diagnosing SQL Server errors using error numbers, messages, execution context, system views, transactions, and troubleshooting techniques.

1. Learning Objectives

  • Understand SQL Server error messages and error numbers.
  • Identify syntax, object, conversion, constraint, and permission errors.
  • Diagnose deadlocks, blocking, timeouts, and transaction failures.
  • Use TRY...CATCH, ERROR_MESSAGE(), and THROW correctly.
  • Investigate errors using Extended Events and system views.
  • Build production-ready error handling and logging.

2. How SQL Server Reports an Error

SQL Server detects errors at different stages of query processing. The stage at which an error occurs determines whether it can be handled by a particular TRY...CATCH block and what diagnostic information is available.

1. Parse

Checks SQL syntax and statement structure.

2. Bind and Compile

Resolves object names, columns, data types, and query dependencies.

3. Execute

Runs the query and evaluates expressions.

4. Runtime Validation

Checks constraints, conversions, permissions, and resource conditions.

5. Error Handling

Returns the error to the client or transfers control to CATCH where applicable.

Important distinction

Not every SQL Server error is raised at the same execution level. Some compilation and name-resolution errors occur before a TRY block starts executing. A TRY...CATCH block does not catch every possible error, including certain connection-terminating errors and errors occurring at the same execution level during compilation.

3. Understand SQL Server Error Information

SQL Server error messages commonly include an error number, severity, state, procedure, line number, and message text.

Property Meaning Diagnostic value
Error number Identifies the error type. Helps classify the failure.
Severity Indicates the seriousness of the error. Helps distinguish ordinary errors from serious system problems.
State Identifies a particular occurrence or code path. Can help distinguish where the error originated.
Procedure Identifies the stored procedure, trigger, or function when available. Locates the database module involved.
Line number Indicates the line associated with the error. Helps locate the failing statement.
Message Human-readable description. Provides details about the failure.

Inspect an error using TRY...CATCH

BEGIN TRY

    SELECT 10 / 0 AS Result;

END TRY
BEGIN CATCH

    SELECT
        ERROR_NUMBER() AS ErrorNumber,
        ERROR_SEVERITY() AS ErrorSeverity,
        ERROR_STATE() AS ErrorState,
        ERROR_PROCEDURE() AS ErrorProcedure,
        ERROR_LINE() AS ErrorLine,
        ERROR_MESSAGE() AS ErrorMessage;

END CATCH;

Typical result:

ErrorNumber ErrorSeverity ErrorState ErrorMessage
8134 16 1 Divide by zero error encountered.
Important: Error line numbers are relative to the relevant batch or module. When dynamic SQL is involved, the reported line may be relative to the dynamic SQL batch rather than the outer stored procedure.

5. Diagnose Syntax and Object Errors

Example A: Invalid column name (Error 207)

CREATE TABLE Employees
(
    EmployeeID INT,
    EmployeeName VARCHAR(100),
    Salary DECIMAL(12,2)
);

SELECT EmployeeID, EmployeeName, MonthlySalary
FROM Employees;

The query refers to MonthlySalary, but the table contains Salary. SQL Server cannot bind the unknown column.

Diagnosis:

SELECT
    COLUMN_NAME,
    DATA_TYPE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Employees';

Correction:

SELECT EmployeeID, EmployeeName, Salary
FROM dbo.Employees;

Example B: Invalid object name (Error 208)

SELECT *
FROM Employee;

Possible causes:

  • The actual table is named Employees.
  • The table belongs to a different schema.
  • The query is running in the wrong database.
  • The object does not exist or is not visible to the caller.

Diagnostic commands:

SELECT DB_NAME() AS CurrentDatabase;

SELECT
    SCHEMA_NAME(schema_id) AS SchemaName,
    name AS ObjectName,
    type_desc
FROM sys.objects
WHERE name = 'Employees';

Correct query:

SELECT *
FROM dbo.Employees;
Always use schema-qualified object names in production SQL, such as dbo.Employees, to reduce ambiguity and improve consistency.

6. Diagnose Data Conversion Errors

Conversion errors occur when SQL Server cannot convert a value into the requested data type.

Example: Error 245

CREATE TABLE ImportData
(
    EmployeeID INT,
    SalaryText VARCHAR(30)
);

INSERT INTO ImportData
VALUES
(1, '50000'),
(2, '65000'),
(3, 'UNKNOWN');

SELECT
    EmployeeID,
    CAST(SalaryText AS INT) AS Salary
FROM ImportData;

The third row contains UNKNOWN, which cannot be converted to INT. The conversion fails.

Find invalid values safely

SELECT
    EmployeeID,
    SalaryText
FROM ImportData
WHERE TRY_CONVERT(INT, SalaryText) IS NULL
  AND SalaryText IS NOT NULL;

Expected result:

EmployeeID SalaryText
3 UNKNOWN

Safe conversion

SELECT
    EmployeeID,
    TRY_CONVERT(INT, SalaryText) AS Salary
FROM ImportData;

TRY_CONVERT returns NULL for values that cannot be converted. This prevents an ordinary conversion failure from terminating the statement, but it does not automatically make invalid data valid. Production systems should record or reject invalid source values according to the business rules.

7. Diagnose Constraint Errors

Constraints enforce data integrity. SQL Server raises errors when an INSERT or UPDATE violates these rules.

Example: Foreign key violation (Error 547)

CREATE TABLE Departments
(
    DepartmentID INT PRIMARY KEY,
    DepartmentName VARCHAR(100)
);

CREATE TABLE Employees
(
    EmployeeID INT PRIMARY KEY,
    EmployeeName VARCHAR(100),
    DepartmentID INT,
    CONSTRAINT FK_Employees_Departments
        FOREIGN KEY (DepartmentID)
        REFERENCES Departments(DepartmentID)
);

INSERT INTO Departments
VALUES (10, 'IT');

INSERT INTO Employees
VALUES (1, 'Amit', 99);

Department 99 does not exist. The foreign key prevents an employee from referencing a nonexistent department.

Investigate parent records:

SELECT *
FROM Departments
WHERE DepartmentID = 99;

Correct the data or reject the request:

INSERT INTO Employees
VALUES (1, 'Amit', 10);

Example: Duplicate key (Error 2627 or 2601)

CREATE TABLE Users
(
    UserID INT PRIMARY KEY,
    Email VARCHAR(200) UNIQUE
);

INSERT INTO Users
VALUES (1, 'amit@example.com');

INSERT INTO Users
VALUES (1, 'amit2@example.com');

The second statement violates the primary key. A duplicate email would violate the unique constraint or unique index.

A preliminary SELECT to check whether a key exists is not sufficient to prevent duplicates under concurrency. Two sessions can both pass the check. Keep the unique constraint or index as the final integrity safeguard, and handle duplicate-key errors appropriately.

8. Diagnose String Truncation Errors

A truncation error occurs when the incoming string or binary value is larger than the destination column allows. 

CREATE TABLE Customers
(
    CustomerID INT PRIMARY KEY,
    CustomerName VARCHAR(10)
);

INSERT INTO Customers
VALUES (1, 'International');

International exceeds the ten-character capacity of CustomerName. Depending on SQL Server version and configuration, the error may identify only the general truncation problem or provide the table, column, and truncated value details.

Inspect column capacity

SELECT
    COLUMN_NAME,
    DATA_TYPE,
    CHARACTER_MAXIMUM_LENGTH
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_NAME = 'Customers';

Check incoming values before insertion

DECLARE @CustomerName VARCHAR(100) = 'International';

SELECT
    @CustomerName AS IncomingValue,
    LEN(@CustomerName) AS CharacterCount;

IF LEN(@CustomerName) > 10
BEGIN
    PRINT 'Customer name exceeds the allowed length.';
END;

For Unicode data, use NVARCHAR and consider the distinction between LEN, DATALENGTH, and the storage capacity of the destination column. LEN excludes trailing spaces, while DATALENGTH reports bytes.

9. Diagnose Deadlocks and Blocking

Deadlocks and blocking are related but different concurrency problems.

Condition Meaning Typical symptom
Blocking One session waits for another session's lock. Query waits for a resource.
Deadlock Two or more sessions form a circular dependency. SQL Server selects a victim and raises Error 1205.
Lock timeout A lock request exceeds the configured wait limit. Error 1222 when the lock timeout is reached.

Example: Find currently blocked sessions

SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_time,
    wait_resource,
    status,
    command
FROM sys.dm_exec_requests
WHERE blocking_session_id <> 0;

Find active requests and their SQL text

SELECT
    r.session_id,
    r.blocking_session_id,
    r.status,
    r.wait_type,
    r.wait_time,
    r.cpu_time,
    r.total_elapsed_time,
    DB_NAME(r.database_id) AS DatabaseName,
    SUBSTRING
    (
        st.text,
        (r.statement_start_offset / 2) + 1,
        (
            (
                CASE r.statement_end_offset
                    WHEN -1 THEN DATALENGTH(st.text)
                    ELSE r.statement_end_offset
                END
                - r.statement_start_offset
            ) / 2
        ) + 1
    ) AS RunningStatement
FROM sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS st
WHERE r.session_id <> @@SPID;

Deadlock investigation

SQL Server provides the system_health Extended Events session, which normally captures deadlock graph events. The deadlock graph identifies participating sessions, statements, resources, and the selected victim. 

SELECT
    XEvent.value
    (
        '(event/@timestamp)[1]',
        'datetime2'
    ) AS DeadlockTime,
    XEvent.query('.') AS DeadlockEvent
FROM
(
    SELECT CAST(event_data AS XML) AS EventData
    FROM sys.fn_xe_file_target_read_file
    (
        'system_health*.xel',
        NULL,
        NULL,
        NULL
    )
    WHERE object_name = 'xml_deadlock_report'
) AS Deadlocks
CROSS APPLY EventData.nodes
(
    '/event'
) AS XEventData(XEvent);

The file path and permissions can vary by SQL Server installation. Use the actual system_health event-file location if the wildcard path does not resolve in your environment.

Typical deadlock prevention techniques

  • Access tables in a consistent order across transactions.
  • Keep transactions short.
  • Use appropriate indexes to reduce the number of locked rows or pages.
  • Avoid unnecessary user interaction inside open transactions.
  • Implement safe retry logic for deadlock victims.
  • Review isolation levels and lock hints carefully.

10. Diagnose Login and Permission Errors

Login failure (Error 18456)

Possible causes include:

  • Incorrect username or password.
  • SQL Server authentication is disabled.
  • The login is disabled or locked by policy.
  • The login's default database is unavailable.
  • The login lacks access to the requested database.

The client often receives a general login-failed message. The SQL Server error log may contain a more specific state value that helps narrow down the cause. Avoid assuming that one state maps to the same root cause in every environment.

Inspect login status

SELECT
    name,
    type_desc,
    is_disabled
FROM sys.server_principals
WHERE name = 'ApplicationLogin';

Database permission denied (Error 229)

SELECT
    USER_NAME() AS DatabaseUser,
    SUSER_SNAME() AS LoginName;

SELECT
    HAS_PERMS_BY_NAME
    (
        'dbo.Employees',
        'OBJECT',
        'SELECT'
    ) AS CanSelectEmployees;

Grant only the permission the application actually needs. 

GRANT SELECT
ON OBJECT::dbo.Employees
TO ApplicationUser;
Do not solve permission problems by automatically adding users to db_owner or sysadmin. Investigate the missing permission and grant the least privilege necessary.

11. Build Reliable Error Handling with TRY...CATCH

TRY...CATCH allows a stored procedure or batch to respond to many execution errors without immediately returning control to the caller. 

BEGIN TRY

    DECLARE @Result INT;

    SET @Result = 10 / 0;

    SELECT @Result AS Result;

END TRY
BEGIN CATCH

    SELECT
        ERROR_NUMBER() AS ErrorNumber,
        ERROR_MESSAGE() AS ErrorMessage,
        ERROR_LINE() AS ErrorLine;

END CATCH;

Rethrow an error using THROW

BEGIN TRY

    INSERT INTO Users
    VALUES (1, 'amit@example.com');

END TRY
BEGIN CATCH

    PRINT 'An error occurred while inserting the user.';

    THROW;

END CATCH;

THROW without arguments inside CATCH rethrows the original error, preserving its error number, message, state, and relevant context. Avoid replacing an unexpected database error with a generic successful-looking response.

RAISERROR versus THROW

Feature RAISERROR THROW
Introduced Legacy SQL Server error-raising mechanism SQL Server 2012
Rethrow original error Requires reconstructing error information THROW; inside CATCH
Custom message Supports formatted messages Supports a message string
Severity control Supports severity specification New errors use severity 16
Transaction behavior Does not honor SET XACT_ABORT in the same way Honors SET XACT_ABORT

For most new application error-handling code, THROW is the preferred mechanism. RAISERROR remains relevant in existing systems and for specific legacy behaviors.

12. Production-Ready Transaction Error Handling

A production transaction should consider rollback behavior, transaction state, error propagation, and logging. 

CREATE OR ALTER PROCEDURE dbo.TransferAmount
    @FromAccountID INT,
    @ToAccountID INT,
    @Amount DECIMAL(12,2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY

        IF @Amount <= 0
        BEGIN
            THROW 50001, 'Transfer amount must be positive.', 1;
        END;

        BEGIN TRANSACTION;

        UPDATE dbo.Accounts
        SET Balance = Balance - @Amount
        WHERE AccountID = @FromAccountID
          AND Balance >= @Amount;

        IF @@ROWCOUNT = 0
        BEGIN
            THROW 50002, 'Source account missing or insufficient balance.', 1;
        END;

        UPDATE dbo.Accounts
        SET Balance = Balance + @Amount
        WHERE AccountID = @ToAccountID;

        IF @@ROWCOUNT = 0
        BEGIN
            THROW 50003, 'Destination account not found.', 1;
        END;

        COMMIT TRANSACTION;

    END TRY
    BEGIN CATCH

        IF XACT_STATE() <> 0
        BEGIN
            ROLLBACK TRANSACTION;
        END;

        THROW;

    END CATCH;
END;

Understand XACT_STATE()

Value Meaning Action
1 Transaction is active and committable. Commit or roll back.
-1 Transaction is active but uncommittable. Only a full rollback is allowed.
0 No active user transaction. No rollback is required.
Production consideration: The procedure above assumes it owns the transaction. If it can be called inside an existing transaction, it should follow an explicit transaction ownership or savepoint strategy. A nested BEGIN TRANSACTION does not create an independently committable nested transaction.

13. Create an Application Error Log

Logging helps preserve error information after the application request has completed. A production logging design should consider retention, sensitive data, permissions, and whether logging itself can fail. 

CREATE TABLE dbo.ErrorLog
(
    ErrorLogID BIGINT IDENTITY(1,1) PRIMARY KEY,
    ErrorNumber INT,
    ErrorSeverity INT,
    ErrorState INT,
    ErrorProcedure NVARCHAR(128),
    ErrorLine INT,
    ErrorMessage NVARCHAR(4000),
    LoggedAt DATETIME2(3) NOT NULL
        DEFAULT SYSUTCDATETIME(),
    LoginName SYSNAME,
    DatabaseName SYSNAME
);

Log an error inside CATCH

BEGIN TRY

    SELECT 10 / 0;

END TRY
BEGIN CATCH

    INSERT INTO dbo.ErrorLog
    (
        ErrorNumber,
        ErrorSeverity,
        ErrorState,
        ErrorProcedure,
        ErrorLine,
        ErrorMessage,
        LoginName,
        DatabaseName
    )
    VALUES
    (
        ERROR_NUMBER(),
        ERROR_SEVERITY(),
        ERROR_STATE(),
        ERROR_PROCEDURE(),
        ERROR_LINE(),
        ERROR_MESSAGE(),
        ORIGINAL_LOGIN(),
        DB_NAME()
    );

    THROW;

END CATCH;

Be aware that if the transaction is uncommittable, the INSERT into the error log may fail because the transaction cannot perform writes. For high-reliability logging, consider logging through the application layer or a separate connection, and ensure the original error is preserved.

14. Investigate Errors Using SQL Server Diagnostic Tools

A. SQL Server Error Log

The SQL Server error log records important server-level events, including startup and shutdown messages, certain login failures, and system errors. 

EXEC sys.xp_readerrorlog
    0,
    1,
    N'Login failed';

The first argument selects the current error log, and the second selects the SQL Server error log rather than the SQL Server Agent log. Access to diagnostic logs may require elevated permissions.

B. Extended Events

Extended Events provides lightweight event collection for SQL Server troubleshooting. You can capture error events, deadlocks, long-running statements, and other diagnostic information. 

CREATE EVENT SESSION CaptureErrors
ON SERVER
ADD EVENT sqlserver.error_reported
(
    ACTION
    (
        sqlserver.sql_text,
        sqlserver.session_id,
        sqlserver.username,
        sqlserver.database_name
    )
    WHERE ([severity] >= 11)
)
ADD TARGET package0.event_file
(
    SET filename = N'C:\SQLLogs\CaptureErrors.xel'
);

ALTER EVENT SESSION CaptureErrors
ON SERVER
STATE = START;

Ensure the SQL Server service account can write to the target directory. Choose an appropriate retention and rollover policy for production systems.

C. Query Store

Query Store helps investigate query performance changes by retaining query text, execution plans, and runtime statistics. It is especially useful when an application starts timing out after a deployment, statistics update, or plan change. 

SELECT
    q.query_id,
    qt.query_sql_text,
    p.plan_id,
    rs.avg_duration,
    rs.max_duration,
    rs.count_executions
FROM sys.query_store_query AS q
JOIN sys.query_store_query_text AS qt
    ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan AS p
    ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats AS rs
    ON p.plan_id = rs.plan_id
ORDER BY rs.max_duration DESC;

Query Store is a performance investigation tool, not a complete application error log. Use it alongside Extended Events, application logs, and SQL Server error logs.

15. A Systematic Troubleshooting Method

Step 1: Capture the failure

Record the error number, message, time, application, and affected request.

Step 2: Classify the error

Determine whether it is syntax, data, permission, concurrency, or resource related.

Step 3: Reproduce safely

Reproduce using the same parameters, schema, permissions, and relevant data.

Step 4: Inspect context

Check execution plan, transaction state, locks, object definitions, and server logs.

Step 5: Identify root cause

Find the underlying condition instead of treating only the error message.

Step 6: Apply a controlled fix

Correct code, schema, permissions, indexes, or transaction behavior.

Step 7: Verify and monitor

Retest edge cases and monitor for recurrence.

Root cause versus symptom

Symptom Possible root cause Evidence to collect
Application timeout Blocking, poor query plan, network delay, or application timeout setting Wait type, elapsed time, blocking chain, execution plan
Insert failure Constraint violation, conversion, truncation, or permission issue Error number, input values, schema, permissions
Intermittent deadlock Concurrent transactions accessing resources in conflicting orders Deadlock graph, transaction statements, indexes
Login failure Authentication, login status, default database, or access configuration Server error log, login state, database availability
Sudden performance regression Plan change, statistics change, parameter sensitivity, or data growth Query Store, actual plan, runtime statistics

16. Advanced Considerations

Severity levels

SQL Server severity levels describe the general seriousness of errors. User-correctable errors often have severity 11 through 16. Higher severity levels can indicate serious system conditions. Severity alone should not be used as the only measure of operational impact.

Connection-terminating errors

Some errors terminate a connection or prevent normal CATCH processing. The application should be able to detect a broken connection, discard it, and establish a new connection when appropriate.

Parameter-sensitive query performance

A query may perform well for one parameter value and poorly for another because the optimizer compiles and reuses plans based on parameter values and available statistics. Investigate actual execution plans and Query Store before applying hints or recompilation.

Client-side timeouts

A command timeout configured in an application is not the same as SQL Server's lock timeout. A client may stop waiting while SQL Server is still processing or cancelling the request. Correlate application logs with SQL Server session and request information.

Permissions and execution context

A stored procedure may execute under different security rules depending on ownership chaining, EXECUTE AS, module signing, and the caller's permissions. Test using the same security context as the application.

17. Common Troubleshooting Mistakes

  • Fixing the error message without identifying the root cause.
  • Using SELECT checks instead of unique constraints to prevent duplicates.
  • Suppressing exceptions without recording useful diagnostic details.
  • Using broad permissions such as db_owner to bypass access errors.
  • Assuming every error is caught by TRY...CATCH.
  • Retrying every error, including permanent data validation failures.
  • Ignoring the transaction state after an error.
  • Changing indexes without examining execution plans and workload patterns.
  • Logging sensitive values such as passwords, tokens, or personal data.
  • Terminating blocking sessions without understanding the business impact.

18. Practical Exercises

Exercise 1: Invalid column

Create a table with EmployeeID and EmployeeName. Write a query referencing a nonexistent column. Identify the error number and correct the query.

Exercise 2: Conversion failure

Create a table with VARCHAR salary values containing valid numbers and invalid text. Use TRY_CONVERT to find invalid records.

Exercise 3: Duplicate key

Create a table with a unique email constraint. Insert a duplicate email and handle the resulting error using TRY...CATCH.

Exercise 4: Foreign key violation

Create parent and child tables. Attempt to insert a child row referencing a nonexistent parent. Diagnose the constraint failure.

Exercise 5: Transaction rollback

Create a transaction that updates two account balances. Deliberately cause the second update to fail. Ensure the first update is rolled back.

Exercise 6: Blocking investigation

Open two SQL Server sessions. In the first session, update a row inside an uncommitted transaction. In the second session, attempt to update the same row. Inspect sys.dm_exec_requests to identify the blocking session.

19. Knowledge Check

  1. Which SQL Server error commonly indicates an invalid column name?

    Answer: Error 207.

  2. Which error commonly indicates a foreign key or CHECK constraint conflict?

    Answer: Error 547.

  3. What does TRY_CONVERT return when a value cannot be converted?

    Answer: NULL, unless another error condition occurs.

  4. Which error indicates that a session was selected as a deadlock victim?

    Answer: Error 1205.

  5. What does XACT_STATE() = -1 mean?

    Answer: The transaction is uncommittable and must be rolled back.

  6. Which statement rethrows the original error from a CATCH block?

    Answer: THROW;

  7. Which SQL Server feature captures deadlock graphs and other diagnostic events?

    Answer: Extended Events.

  8. Does a client command timeout necessarily mean SQL Server has stopped executing the request?

    Answer: No. The client may stop waiting while the server is still processing or cancelling the request.

20. Final Learning Outcome

You should now be able to interpret SQL Server error information, classify common failures, investigate their causes, implement reliable error handling, and use SQL Server diagnostic tools to troubleshoot production issues.

The key principle is to diagnose the underlying condition rather than simply suppressing the error. Reliable SQL Server systems preserve data integrity, capture useful diagnostics, recover safely, and make recurring problems observable.
