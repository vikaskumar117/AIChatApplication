APPLY THE IDEA

Worked example

A new service owns its schema and uses reviewed migrations; a legacy shared database is scaffolded read-only and deployed through the DBA pipeline.

  1. Identify the authoritative schema owner and deployment pipeline.
  2. Select migrations or scaffolding to match that ownership.
  3. Review SQL/data impact and environment differences.
  4. Test upgrade from a production-like prior schema and plan compatibility/rollback.

CODE OR QUERY

Try it

// Code First: create a migration from reviewed model changes.
dotnet ef migrations add AddOrderStatus
dotnet ef migrations script --idempotent

// Database First: scaffold selected schema from the existing database.
dotnet ef dbcontext scaffold "<connection-string-from-secret-store>" \
  Microsoft.EntityFrameworkCore.SqlServer \
  --context AppDbContext --schema sales --table Order --no-onconfiguring

TRADE-OFFS

Benefits and limitations

Benefits

  • Code First keeps model evolution and migration history close to application code.
  • Database First can integrate with an established schema and DBA governance.

Limitations

  • Migrations need careful review for data loss, locks, and deployment sequencing.
  • Scaffolding can be overwritten and database drift complicates model ownership.

DECISION GUIDE

When to use it

Use: Use Code First when the application team owns schema evolution; scaffold when the database is authoritative or externally governed.

Avoid: Avoid applying unreviewed migrations automatically at production startup or editing generated scaffolding in place without a regeneration strategy.

COMMON MISTAKES

Watch out

  • Assuming Code First means the database is created only at runtime.
  • Applying migrations automatically in production without deployment controls.
  • Editing scaffolded files directly and losing changes on regeneration.

BEST PRACTICES

In practice

  • Document schema ownership and drift policy.
  • Generate and review SQL scripts before production deployment.
  • Use partial classes/configuration for custom scaffold behavior.
  • Test migration compatibility across deployment order.

INTERVIEW PRACTICE

Common questions

  1. Who owns the schema in each workflow?
  2. How should a production migration be deployed?
  3. How do you preserve custom behavior across re-scaffolding?

SENIOR-LEVEL SCENARIO

Production thinking

A new API shares a legacy database with several consumers. Treat the database as authoritative, scaffold only the owned schema surface, place custom mapping separately, and coordinate additive changes through the database deployment process.

SUMMARY

In one minute

Code First treats the EF model and migrations as the schema-evolution source of truth. Database First starts from an existing database and scaffolds entity types and DbContext from its schema; the generated code can be refreshed as the database changes. The approach must fit ownership and deployment governance. A database may be shared across applications or controlled by DBAs, while a product team may own migrations alongside application code.
