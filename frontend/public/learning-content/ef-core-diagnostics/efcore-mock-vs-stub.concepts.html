THE IDEA

What is it?

A stub supplies predefined answers; a mock records or verifies expected interactions; a fake is a working simplified implementation (for example, an in-memory repository) that preserves a useful contract.

WHY IT MATTERS

What problem does it solve?

Choosing the least complex test double keeps tests readable and avoids mistaking a mock’s configured behavior for production correctness.

UNDER THE HOOD

How does it work?

Use a stub to control collaborator output, a mock when an interaction itself is part of the contract, and a fake when a lightweight working implementation improves confidence. Prefer real pure components; use real database integration tests when provider semantics matter.

KEY TAKEAWAYS

Remember

  • Stub supplies answers; mock verifies interaction; fake provides simplified working behavior.
  • Prefer the simplest test double that tests behavior.
  • Test doubles do not prove production database semantics.
  • Do not mock internal EF Core implementation details.
