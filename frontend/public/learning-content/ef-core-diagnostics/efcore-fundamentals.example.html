APPLY THE IDEA

Worked example

A request loads a customer projection and updates an order within one scoped DbContext.

  1. Configure provider, entity keys, relationships, and constraints.
  2. Compose IQueryable before materialization.
  3. Inspect generated SQL for important query paths.
  4. Use a scoped DbContext and explicitly save a bounded unit of work.

CODE OR QUERY

Try it

var order = await db.Orders
    .Where(o => o.Id == orderId)
    .Select(o => new { o.Id, o.Status })
    .SingleOrDefaultAsync(ct);

var entity = await db.Orders.SingleAsync(o => o.Id == orderId, ct);
entity.Status = OrderStatus.Confirmed;
await db.SaveChangesAsync(ct);

TRADE-OFFS

Benefits and limitations

Benefits

  • LINQ and change tracking simplify common relational CRUD and mapping.
  • Provider abstraction and migrations support repeatable development workflows.

Limitations

  • Generated SQL and provider translation can differ from developer expectations.
  • Change tracking, relationship loading, and abstractions can add allocations or hide round trips.

DECISION GUIDE

When to use it

Use: Use EF Core for domain-oriented data access when generated SQL and provider behavior are understood and measured.

Avoid: Avoid treating EF Core as a substitute for relational modeling, SQL knowledge, or reviewing critical generated SQL.

COMMON MISTAKES

Watch out

  • Treating IQueryable operations as already executed in memory.
  • Keeping one DbContext for an application lifetime.
  • Assuming EF InMemory behavior proves relational-provider correctness.

BEST PRACTICES

In practice

  • Scope DbContext to a request or explicit unit of work.
  • Use async database APIs with cancellation tokens in server paths.
  • Configure keys, relationships, and constraints intentionally.
  • Inspect SQL and use a relational provider for integration tests.

SENIOR-LEVEL SCENARIO

Production thinking

A team ships a query that works in the in-memory provider but fails on SQL Server translation. Reproduce using the production relational provider, inspect generated SQL, and keep provider-specific behavior inside integration coverage.

SUMMARY

In one minute

Entity Framework Core (EF Core) is a .NET object-relational mapper (ORM): it maps .NET entity types and LINQ queries to relational schema and SQL through a database provider. DbContext is a unit-of-work and identity map that coordinates querying, change tracking, and saving. EF Core reduces repetitive data-access code while preserving access to relational capabilities, but the abstraction does not remove SQL, transaction, schema, or provider behavior.
