APPLY THE IDEA

Worked example

A transient failover error on an idempotent read can retry within a short deadline; a unique-key conflict should be interpreted as a domain outcome, not retried blindly.

  1. Classify provider exception and operation outcome.
  2. Check request cancellation, deadline, and idempotency.
  3. Use one bounded retry layer with provider-aware transient classification.
  4. Keep external effects outside replay or use outbox/idempotency and monitor attempts.

TRADE-OFFS

Benefits and limitations

Benefits

  • Bounded transient retries can ride through brief failover or network blips.
  • Classification and idempotency protect data from duplicate effects.

Limitations

  • Retries increase latency and load; stacked retry layers multiply attempts.
  • Execution-strategy replay can repeat transaction work and requires idempotent boundaries.

DECISION GUIDE

When to use it

Use: Use provider-aware bounded retry for classified transient failures within request deadlines.

Avoid: Avoid retrying validation, foreign-key/unique conflicts, cancellation, or all exceptions indiscriminately.

COMMON MISTAKES

Watch out

  • Retrying all exceptions, including cancellation and constraint violations.
  • Retrying a transaction that has already sent an email or charged a card.
  • Combining several independent retry layers without an attempt budget.

BEST PRACTICES

In practice

  • Use provider execution strategy and a bounded total deadline.
  • Use idempotency keys for externally retried commands.
  • Test failover and uncertain commit outcomes.
  • Monitor retry counts, pool waits, and dependency health.

SENIOR-LEVEL SCENARIO

Production thinking

Database failover creates timeouts and retry storms. Cap retries and total deadline, remove duplicate retry layers, apply circuit/load shedding, verify writes are idempotent, and monitor recovery and duplicate request outcomes.

SUMMARY

In one minute

Database failure handling distinguishes transient connectivity/failover conditions, command timeouts, deadlocks, constraint conflicts, cancellation, and permanent configuration or schema errors. Retrying every failure can amplify outages, duplicate non-idempotent writes, and delay recovery. Some failures need a bounded retry; others require a caller correction or operator action.
