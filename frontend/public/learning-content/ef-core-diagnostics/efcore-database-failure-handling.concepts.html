THE IDEA

What is it?

Database failure handling distinguishes transient connectivity/failover conditions, command timeouts, deadlocks, constraint conflicts, cancellation, and permanent configuration or schema errors.

WHY IT MATTERS

What problem does it solve?

Retrying every failure can amplify outages, duplicate non-idempotent writes, and delay recovery. Some failures need a bounded retry; others require a caller correction or operator action.

UNDER THE HOOD

How does it work?

Use provider-supported execution strategies for classified transient faults, bounded retries with jitter and deadlines, idempotency keys for commands, and short transactions. Keep external side effects outside retryable database units or use an outbox; surface permanent errors appropriately.

KEY TAKEAWAYS

Remember

  • Not all database failures are transient.
  • Retries need limits, deadlines, and replay-safe operations.
  • Unique/FK conflicts are business/schema outcomes, not generic retry signals.
  • Stacked retries can multiply load during an outage.
