APPLY THE IDEA

Worked example

Unit-test a discount calculation without mocking the calculator itself or involving EF Core.

  1. Choose one behavior and its boundary.
  2. Create ordinary inputs and minimal fake collaborators.
  3. Call the public unit behavior once.
  4. Assert result, state transition, and only meaningful interactions.

CODE OR QUERY

Try it

[Fact]
public void Discount_is_applied_to_eligible_total()
{
    var total = PriceCalculator.Total(100m, 10m);

    Assert.Equal(90m, total);
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Fast, deterministic feedback for business rules.
  • Failures identify a narrow behavior and are inexpensive to run.

Limitations

  • Mocks can become coupled to implementation and do not validate infrastructure behavior.
  • Excessive isolation can miss wiring and database translation defects.

DECISION GUIDE

When to use it

Use: Use unit tests for pure logic, validation, state transitions, and orchestration decisions.

Avoid: Avoid testing EF query translation or relational behavior solely with mocked DbSet or EF InMemory.

COMMON MISTAKES

Watch out

  • Mocking every value object and pure function.
  • Asserting internal call order without a behavioral reason.
  • Using EF InMemory as evidence of relational correctness.

BEST PRACTICES

In practice

  • Keep tests small, deterministic, and independently runnable.
  • Use parameterized tests for rule boundaries.
  • Name tests around behavior and expected outcome.
  • Run relational integration tests for SQL-dependent behavior.

SENIOR-LEVEL SCENARIO

Production thinking

A pricing change has many boundary rules. Extract deterministic calculation logic, test thresholds and rounding, then add a small set of integration tests for persistence and API behavior.

SUMMARY

In one minute

A unit test verifies a focused unit of behavior with controlled inputs and collaborators, typically without booting the web host or connecting to a production-like database. Fast isolated tests support frequent feedback and precise business-rule coverage, but they do not prove EF translation, SQL constraints, provider behavior, or deployment wiring.
