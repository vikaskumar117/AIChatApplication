APPLY THE IDEA

Worked example

An API list returns a DTO projection; an edit command loads one tracked entity and changes allowed fields.

  1. Identify whether the request reads, updates, or both.
  2. Project to a DTO when only selected fields are required.
  3. Choose tracking behavior explicitly for entity results.
  4. Measure allocations and ensure detached updates are attached/validated deliberately if needed.

CODE OR QUERY

Try it

var rows = await db.Orders
    .AsNoTracking()
    .Where(o => o.CreatedAt >= start)
    .Select(o => new OrderSummary(o.Id, o.Status, o.Total))
    .ToListAsync(ct);

var order = await db.Orders.SingleAsync(o => o.Id == command.Id, ct);
order.Status = command.Status;
await db.SaveChangesAsync(ct);

TRADE-OFFS

Benefits and limitations

Benefits

  • No-tracking/projection reduces tracker state on read-heavy paths.
  • Tracking supports identity resolution and convenient change persistence.

Limitations

  • No-tracking entities do not automatically persist edits.
  • Tracking a large graph increases memory and can return existing context instances with locally modified values.

DECISION GUIDE

When to use it

Use: Use projection/no-tracking for read models and tracking for bounded update units.

Avoid: Avoid enabling tracking globally for large read-only reports or using no-tracking when you expect SaveChanges to persist detached edits.

COMMON MISTAKES

Watch out

  • Changing a no-tracking entity and expecting SaveChanges to detect it.
  • Returning full entity graphs where a DTO projection suffices.
  • Reusing a long-lived context and observing stale/locally changed instances.

BEST PRACTICES

In practice

  • Use short-lived DbContext instances.
  • Choose tracking mode per query based on behavior.
  • Prefer DTO projections for read APIs.
  • Test update flows for concurrency and field-level authorization.

SENIOR-LEVEL SCENARIO

Production thinking

A report retains thousands of tracked entities per request. Project only required fields, compare allocations and SQL result size, and retain tracked reads only in write workflows.

SUMMARY

In one minute

A tracking query registers materialized entities in DbContext’s change tracker, which records state and original values for SaveChanges. A no-tracking query materializes results without registering them for normal updates; identity resolution controls whether repeated keys share an instance. Tracking supports convenient updates and identity consistency but consumes CPU and memory. Read-only endpoints often benefit from projection or no-tracking materialization.
