APPLY THE IDEA

Worked example

A rising heap after each request but stable traffic suggests retained objects; compare GC heap size and inspect roots in a secured dump.

  1. Establish resource trends and relate them to traffic, version, and container limits.
  2. Use counters to distinguish allocation rate, GC, and retained heap.
  3. Capture a bounded trace; take a dump only when authorized and protected.
  4. Identify hot path or retaining root and reproduce under representative load.

CODE OR QUERY

Try it

dotnet-counters monitor --process-id <pid>
dotnet-trace collect --process-id <pid>
dotnet-dump collect --process-id <pid>
// Collect only with authorization, bounded duration, secure storage, and a data-handling plan.

TRADE-OFFS

Benefits and limitations

Benefits

  • Runtime tools distinguish live allocation, CPU hot paths, GC activity, and object retention.
  • Repeated measurements validate remediation rather than relying on one snapshot.

Limitations

  • Tracing and dumps add overhead and require runtime/OS access.
  • Heap dumps can contain secrets, tokens, personal data, and application payloads.

DECISION GUIDE

When to use it

Use: Use least-invasive metrics first, then approved traces or dumps when evidence needs deeper stacks or object roots.

Avoid: Avoid collecting or sharing production dumps without authorization, access controls, retention limits, and data review.

COMMON MISTAKES

Watch out

  • Calling all memory growth a leak without checking allocation and GC.
  • Collecting full dumps casually or storing them in unsecured locations.
  • Optimizing code from one CPU sample without representative load.

BEST PRACTICES

In practice

  • Start with metrics and least-invasive collection.
  • Bound duration and overhead of traces.
  • Secure, restrict, and expire diagnostic artifacts.
  • Compare before/after by build and representative request mix.

SENIOR-LEVEL SCENARIO

Production thinking

Memory climbs after deployment while request volume is flat. Compare per-build allocation and heap trends, trace hot allocations, inspect retained roots in an approved secured dump, and verify stable memory after the fix.

SUMMARY

In one minute

High CPU can result from application hot loops, excessive serialization, query translation/materialization, contention, or garbage collection. High memory can be allocation pressure, large caches, unbounded buffers, or retained object graphs. CPU and memory symptoms require different evidence: a high allocation rate can cause GC/CPU without a leak, while retained memory can grow with stable allocation rate.
