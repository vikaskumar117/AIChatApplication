APPLY THE IDEA

Worked example

Post an order through the test server, verify status code, and query the database to ensure the transaction persisted the expected order.

  1. Select a provider that matches the behavior under test.
  2. Create a unique database/schema per test run or collection.
  3. Arrange data through known setup and call the public HTTP/application boundary.
  4. Assert response and database outcome, then clean up regardless of test result.

CODE OR QUERY

Try it

public sealed class OrdersApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;
    public OrdersApiTests(WebApplicationFactory<Program> factory) =>
        _client = factory.CreateClient();

    [Fact]
    public async Task Post_order_returns_created()
    {
        var response = await _client.PostAsJsonAsync(
            "/api/orders", new CreateOrderRequest("SKU-1", 2));
        Assert.Equal(HttpStatusCode.Created, response.StatusCode);
    }
}

TRADE-OFFS

Benefits and limitations

Benefits

  • Validates real dependency injection, HTTP pipeline, serialization, and relational semantics.
  • Provides confidence in behavior across component boundaries.

Limitations

  • Slower and more operationally complex than unit tests.
  • Shared databases, nondeterministic state, and parallel runs can cause flaky tests.

DECISION GUIDE

When to use it

Use: Use for critical API flows, EF translation, constraints, transactions, authentication wiring, and provider-specific behavior.

Avoid: Avoid running destructive tests against shared or production databases or using a provider that cannot represent the behavior being tested.

COMMON MISTAKES

Watch out

  • Using one shared database and relying on test execution order.
  • Testing provider-specific SQL only with EF InMemory.
  • Ignoring cleanup after test failure.

BEST PRACTICES

In practice

  • Use disposable, isolated databases or containers.
  • Keep fixtures deterministic and parallel-safe.
  • Apply migrations/schema through an explicit test setup.
  • Test a focused set of critical end-to-end flows.

SENIOR-LEVEL SCENARIO

Production thinking

A migration introduces a SQL Server-specific filtered index and a query translation regression. Run integration tests against the same engine/provider version in an isolated database and verify both schema and endpoint behavior.

SUMMARY

In one minute

An integration test exercises multiple real components across a boundary, such as HTTP routing, dependency injection, serialization, EF Core translation, and a relational database. Integration tests catch configuration, mapping, provider, constraint, and middleware failures that isolated unit tests cannot observe.
