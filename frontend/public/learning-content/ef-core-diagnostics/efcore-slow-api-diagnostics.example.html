APPLY THE IDEA

Worked example

A route’s p99 rises while SQL duration is stable but command count rises with page size, pointing to N+1 or serialization-triggered loading.

  1. Confirm affected route, percentile, scope, and recent changes.
  2. Open representative slow traces and attribute time by span.
  3. Correlate EF command metrics, SQL plan history, pool waits, CPU/GC, and payload size.
  4. Mitigate safely, then verify p95/p99, errors, and resource trend.

TRADE-OFFS

Benefits and limitations

Benefits

  • Correlated traces distinguish application, database, and dependency latency.
  • Tail percentiles show user impact hidden by averages.

Limitations

  • High-cardinality or verbose telemetry can be expensive and expose sensitive data.
  • Sampling can omit rare slow traces and correlation requires consistent IDs.

DECISION GUIDE

When to use it

Use: Use end-to-end tracing and resource/dependency correlation for production latency incidents.

Avoid: Avoid logging full request bodies/SQL parameter values or optimizing from aggregate average duration alone.

COMMON MISTAKES

Watch out

  • Blaming SQL before examining trace spans or dependency time.
  • Using average latency as the sole SLO signal.
  • Enabling unrestricted EF sensitive-data logging in production.

BEST PRACTICES

In practice

  • Propagate trace/correlation IDs across services.
  • Track route percentiles, command count, dependency latency, errors, and saturation.
  • Use sampling and redaction policies.
  • Maintain rollback and incident runbooks.

INTERVIEW PRACTICE

Common questions

  1. Why are p95/p99 more useful than averages during incidents?
  2. How do traces distinguish SQL time from application time?
  3. Which EF metrics help identify N+1 or pool pressure?

SENIOR-LEVEL SCENARIO

Production thinking

A checkout API p99 doubles after a release. Compare old/new route traces, inspect database command count and dependency spans, check thread/connection pools and response size, then roll back or deploy a measured fix with dashboard verification.

SUMMARY

In one minute

Slow API diagnosis separates time spent in application code, database execution, network/dependency waits, queueing, serialization, and client transfer, then correlates a slow request with trace and resource evidence. Endpoint duration alone cannot reveal whether the cause is an N+1 query, blocking, pool exhaustion, downstream latency, CPU saturation, or oversized response.
