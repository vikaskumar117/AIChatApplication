APPLY THE IDEA

Worked example

Stub a payment gateway response to test orchestration; use a mock only when verifying that an authorization call is required is itself the behavior.

  1. Ask whether the dependency behavior or the interaction is the contract.
  2. Use a real deterministic object when practical.
  3. Stub nondeterministic answers; mock only meaningful interactions; use fakes for useful lightweight behavior.
  4. Test provider-specific behavior against a relational database separately.

CODE OR QUERY

Try it

// Stub: deterministic response, no interaction assertion.
var gateway = new StubPaymentGateway(PaymentResult.Approved);
var service = new CheckoutService(gateway);

var result = await service.CheckoutAsync(order, ct);

Assert.Equal(CheckoutStatus.Confirmed, result.Status);

TRADE-OFFS

Benefits and limitations

Benefits

  • Doubles isolate external nondeterminism and make failure paths testable.
  • A fake can exercise more realistic behavior than a long list of mock setups.

Limitations

  • Mocks can couple tests to call choreography.
  • Fakes may diverge from production implementation; stubs validate only configured cases.

DECISION GUIDE

When to use it

Use: Use the simplest double that exposes the behavior under test; reserve interaction mocks for meaningful contracts.

Avoid: Avoid mocking EF Core internals or using a fake repository as proof of SQL translation and constraints.

COMMON MISTAKES

Watch out

  • Calling every test double a mock and obscuring its purpose.
  • Verifying incidental call order rather than observable contract.
  • Treating an in-memory fake repository as equivalent to SQL Server.

BEST PRACTICES

In practice

  • Keep doubles at application-owned interfaces.
  • Use strict interaction expectations only when the interaction is contractual.
  • Make fakes explicit about behaviors they do not emulate.
  • Pair unit tests with provider-realistic integration tests.

INTERVIEW PRACTICE

Common questions

  1. How does a stub differ from a mock?
  2. When is a fake preferable?
  3. What can a test double not prove about a database provider?

SENIOR-LEVEL SCENARIO

Production thinking

A service test verifies six repository calls in exact order and breaks during a harmless refactor. Replace interaction-heavy assertions with a stubbed collaborator and assert the resulting business outcome; retain integration coverage for persistence.

SUMMARY

In one minute

A stub supplies predefined answers; a mock records or verifies expected interactions; a fake is a working simplified implementation (for example, an in-memory repository) that preserves a useful contract. Choosing the least complex test double keeps tests readable and avoids mistaking a mock’s configured behavior for production correctness.
